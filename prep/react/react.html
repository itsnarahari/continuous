📌 1. Overview

React architecture is based on a **component-driven, declarative design** that uses a **virtual DOM** for efficient UI rendering. It focuses on building reusable UI blocks (components) that react to state or data changes.

📌 2. Core Architectural Layers
  • ⚛️ React Components – Building blocks of UI; can be functional or class-based.
  • 📦 Virtual DOM – A lightweight in-memory copy of the real DOM to minimize costly updates.
  • 🔄 Reconciliation Engine (Fiber) – The brain that compares virtual DOM trees and updates the real DOM efficiently.
  • 🎛️ State & Props – Mechanisms for data flow and inter-component communication.
  • 🧩 React Hooks – Functions like useState, useEffect, and useContext manage state and side effects elegantly.

      │              UI Layer                │

      └──────────────────────────────────────┘

                     ▼

                     │
                     ▼
      ┌──────────────────────────────────────┐

📌 4. One-Way Data Flow

React follows **unidirectional (top-down)** data flow:

  • Parent passes data → via props → Child.
  • Child communicates back → via callbacks → Parent.
  • This ensures predictable and debuggable UI updates.
📌 5. Lifecycle & Rendering
  • 🟢 Mounting – Component created and inserted into DOM.
  • 🟡 Updating – Component re-renders on state/prop change.
  • 🔴 Unmounting – Component removed from DOM.

📌 1. Overview

The React Component Lifecycle defines the **sequence of events** that occur from a component’s creation to its removal from the DOM. It applies differently to **class components** and **functional components (via Hooks)**.

📌 2. Lifecycle Phases
  • 🟢 Mounting – Component is created and inserted into the DOM.
  • 🟡 Updating – Component re-renders when props or state change.
  • 🔴 Unmounting – Component is removed from the DOM.
📊 3. Class Component Lifecycle Methods
class Example extends React.Component {
  constructor() {
    super();
    console.log("🟢 constructor() - Initialization");
  }

  componentDidMount() {
    console.log("✅ componentDidMount() - Component mounted");
  }

  shouldComponentUpdate(nextProps, nextState) {
    console.log("🔄 shouldComponentUpdate() - Control re-render");
    return true;
  }

  componentDidUpdate(prevProps, prevState) {
    console.log("♻️ componentDidUpdate() - After re-render");
  }

  componentWillUnmount() {
    console.log("❌ componentWillUnmount() - Cleanup before removal");
  }

  render() {
    console.log("🧩 render() - Returns JSX");
    return <h3>Hello Lifecycle!</h3>;
  }
}
  • 🧠 constructor() – Initialize state and bind methods.
  • 🎨 render() – Returns JSX to display on UI.
  • ✅ componentDidMount() – Called once after first render; good for API calls.
  • 🔄 componentDidUpdate() – Called after every re-render due to state/prop changes.
  • 🧹 componentWillUnmount() – Used to clean up (timers, subscriptions, listeners).
📘 4. Functional Components Lifecycle (with Hooks)

Functional components don’t have lifecycle methods — instead, they use Hooks like useEffect() to replicate them. 

import { useState, useEffect } from "react";

function Example() {
  const [count, setCount] = useState(0);

  // 🟢 componentDidMount
  useEffect(() => {
    console.log("✅ Mounted");
  }, []);

  // 🟡 componentDidUpdate
  useEffect(() => {
    console.log("🔄 Updated:", count);
  }, [count]);

  // 🔴 componentWillUnmount
  useEffect(() => {
    return () => console.log("❌ Cleanup before unmount");
  }, []);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  );
}

📌 1. Overview

One-way data binding in React means that the data flows in a single direction — from parent components → to child components through props. The child cannot directly modify the parent’s data; it can only send data back via callback functions.

📊 2. Data Flow Diagram
Parent (holds state)
   ↓  props
Child (receives data)
   ↑  callback (event)
Parent (updates state again)
📘 3. Example of One-Way Data Binding
import React, { useState } from "react";

function Parent() {
  const [message, setMessage] = useState("Hello from Parent!");

  // Callback passed to child
  const updateMessage = (newMsg) => {
    setMessage(newMsg);
  };

  return (
    <div className="p-3 border border-info rounded">
      <h4>Parent Component</h4>
      <p>Message: {message}</p>
      <Child msg={message} onUpdate={updateMessage} />
    </div>
  );
}

function Child({ msg, onUpdate }) {
  return (
    <div className="mt-3 border border-secondary rounded p-2">
      <h5>Child Component</h5>
      <p>Received: {msg}</p>
      <button className="btn btn-warning" onClick={() => onUpdate("Updated from Child!")}>
        Send Update to Parent
      </button>
    </div>
  );
}

export default Parent;
📘 4. Explanation
  • 💡 Parent → Child: Data sent through props.
  • 🧭 Child → Parent: Sends data back using callback (function passed as prop).
  • 🧠 Unidirectional: Prevents accidental changes and keeps UI predictable.
📊 5. One-Way vs Two-Way Data Binding
Feature One-Way (React) Two-Way (Angular / Vue)
Data Flow Parent ➜ Child (Single Direction) Parent ⇄ Child (Both Directions)
Control Parent fully controls state View and Model sync automatically
Complexity Predictable and easier to debug Can become hard to track changes
📌 6. Summary
  • React enforces **one-way data flow** for better control and predictability.
  • Data goes **from parent → child** via props.
  • To modify data, child must **invoke a callback** from the parent.
  • This approach keeps the UI consistent and easier to debug.

📌 1. Overview

Property Drilling (also called Prop Drilling) occurs when you pass data from a parent component to deeply nested child components, **through multiple layers of intermediate components** that do not need the data themselves.

📊 2. Visual Representation
Parent
 └── Child A
      └── Child B
           └── Child C  ← Needs the data

Data must travel from Parent ➜ Child A ➜ Child B ➜ Child C
(even if A and B don’t use it)
📘 3. Example of Property Drilling
function Parent() {
  const user = { name: "Narahari", role: "Developer" };
  return <ChildA user={user} />;
}

function ChildA({ user }) {
  return <ChildB user={user} />;
}

function ChildB({ user }) {
  return <ChildC user={user} />;
}

function ChildC({ user }) {
  return <p>👤 Name: {user.name}, Role: {user.role}</p>;
}

➡️ Here, user is passed through ChildA and ChildB even though only ChildC actually needs it.

⚠️ 4. Disadvantages of Property Drilling
  • 🚧 Increases code complexity.
  • 🧱 Tight coupling between components.
  • 🌀 Hard to refactor or maintain as the app grows.
  • 🧩 Reusability of intermediate components is reduced.
💡 5. Solutions to Property Drilling
  • 🧠 React Context API – Provides a way to share data globally without passing props manually at every level.
  • 🪣 State Management Libraries – Like Redux, Recoil, or Zustand for centralized data storage.
📘 6. Example using Context API (Fix)
import React, { createContext, useContext } from "react";

const UserContext = createContext();

function Parent() {
  const user = { name: "Narahari", role: "Developer" };
  return (
    <UserContext.Provider value={user}>
      <ChildA />
    </UserContext.Provider>
  );
}

function ChildA() {
  return <ChildB />;
}

function ChildB() {
  return <ChildC />;
}

function ChildC() {
  const user = useContext(UserContext);
  return <p>👤 Name: {user.name}, Role: {user.role}</p>;
}

✅ With Context, ChildC directly accesses user without unnecessary prop passing.

📊 7. Comparison Table
Aspect With Property Drilling With Context API
Data Passing Manually through every level Globally available to children
Complexity High in deeply nested components Low and cleaner
Reusability Reduced Improved
📌 8. Summary
  • Property drilling = Passing props through components unnecessarily.
  • It can make your React tree hard to maintain and scale.
  • Use Context API or Redux to avoid it.
  • Ideal for sharing data like theme, user, language, or global state.

📌 1. Overview

React and modern web frameworks use different approaches to manage and update the DOM efficiently. Understanding the difference between the Real DOM, Virtual DOM, and Shallow DOM helps you grasp how rendering and performance optimization work in UI frameworks.

📊 2. What is DOM (Document Object Model)?
  • 📄 The DOM represents the **entire HTML structure** of a web page as a tree of objects.
  • 🧠 It allows JavaScript to manipulate structure, style, and content dynamically.
  • ⚠️ However, updating the real DOM is **slow**, because the browser needs to reflow and repaint the page every time a change occurs.
HTML ➜ Browser parses it ➜ Creates DOM Tree ➜ Used for rendering UI
📘 Example (Real DOM)
<div id="app">
  <h2>Hello React</h2>
</div>

document.getElementById("app").innerHTML = "<h2>Updated!</h2>";
➡️ Entire element is re-rendered and browser recalculates layout.
⚛️ 3. Virtual DOM (Used in React)
  • 🧩 The Virtual DOM (VDOM) is an **in-memory representation** of the real DOM.
  • 🌀 When state changes, React creates a new virtual DOM tree and compares it with the previous one using the Reconciliation (Diffing) Algorithm.
  • ⚡ Only the changed parts are updated in the real DOM, improving performance.
Render ➜ Create Virtual DOM copy ➜ Diff with previous ➜ Update only changed nodes
📘 Example (Virtual DOM in React)
function App() {
  const [text, setText] = useState("Hello");

  return (
    <div>
      <h2>{text}</h2>
      <button onClick={() => setText("Updated!")}>Change</button>
    </div>
  );
}
➡️ React updates only the <h2> node — not the entire DOM.
🧱 4. Shallow DOM (Used in Web Components)
  • 🧩 Shallow DOM is a term often used with **Shadow DOM** (part of Web Components).
  • 🔒 It provides encapsulation — HTML, CSS, and JS inside a component are **isolated** from the rest of the document.
  • 🎯 Useful for building custom HTML elements that don't affect global styles or scripts.
📘 Example (Shadow DOM)
// Define a custom element
class MyElement extends HTMLElement {
  constructor() {
    super();
    const shadow = this.attachShadow({ mode: "open" });
    shadow.innerHTML = "<h3>Inside Shadow DOM</h3>";
  }
}
customElements.define("my-element", MyElement);

➡️ The content inside <my-element> is isolated — outer CSS cannot affect it directly.

Used By All browsers (native) React, Preact Web Components

📌 1. Overview

In React, **form inputs** can be handled in two ways — Controlled or Uncontrolled components. The key difference lies in **who controls the form data** — React state or the DOM itself.

🎮 2. Controlled Components
  • React controls the value of the input field via state.
  • The input value is stored in the React component’s state and updated using onChange.
  • This makes form data predictable and easy to validate or manipulate.
function ControlledInput() {
  const [name, setName] = React.useState("");

  const handleChange = (e) => {
    setName(e.target.value);
  };

  return (
    <div>
      <label>Name:</label>
      <input type="text" value={name} onChange={handleChange} />
      <p>You typed: {name}</p>
    </div>
  );
}

✅ The value of the input always reflects the component’s state.

⚙️ 3. Uncontrolled Components
  • The input value is handled by the **DOM itself**, not by React state.
  • To access the value, we use a **ref** (useRef() or createRef()).
  • Used when you don’t need real-time validation or state updates.
function UncontrolledInput() {
  const inputRef = React.useRef();

  const handleSubmit = () => {
    alert("Entered name: " + inputRef.current.value);
  };

  return (
    <div>
      <label>Name:</label>
      <input type="text" ref={inputRef} />
      <button onClick={handleSubmit}>Submit</button>
    </div>
  );
}

⚡ The value lives in the DOM and is read only when needed.

📊 4. Comparison Table
Feature Controlled Component Uncontrolled Component
Data Source React State DOM (via ref)
Access Method Through state variable Through ref.current.value
Real-Time Updates Yes ✅ No ❌
Ease of Validation Easy (since state is known) Harder (manual DOM access)
Performance Slightly slower (re-renders on change) Faster (no re-renders)
Best For Form validation, dynamic UIs Simple forms, quick data capture

      <input type="email" value={email} onChange={(e) => setEmail(e.target.value)} />

📌 1. Overview

React uses a **Reconciliation Algorithm** (Fiber) to efficiently update the **Real DOM** by comparing it with the **Virtual DOM**. Keys play a crucial role in helping React **match old and new elements** during this process.

⚙️ 2. How Reconciliation Works
  • 🧩 React creates a **Virtual DOM** — an in-memory representation of UI.
  • 🔄 When state or props change, React creates a **new Virtual DOM** tree.
  • ⚡ React compares old vs. new Virtual DOM using the **Diffing Algorithm**.
  • ✅ Only updates elements that actually changed — minimizing costly DOM operations.
📘 3. Role of Keys in Reconciliation
  • Keys help React identify which items **correspond to which element**.
  • Without keys, React assumes elements are in order — may reuse DOM incorrectly.
  • With unique keys, React can **move, add, or delete** nodes efficiently.
🎨 4. Example Without Keys

📊 6. Diffing Algorithm Rules
  1. Elements of different types → React **replaces** the old node completely.
  2. Elements of the same type → React **updates** the attributes and recursively reconciles children.
  3. Lists with keys → React uses **keys to match old vs new children**.
  4. Lists without keys → React matches **by index**, may cause wrong updates.

  • Keys are essential for **stable identity** in dynamic lists.

  • Proper keys prevent **state loss** in child components (like input values).
  • React’s reconciliation + keys = highly efficient UI rendering.

React provides **Memoization techniques** to optimize performance by preventing **unnecessary re-renders** and **expensive computations**.

🧩 2. React.memo
  • Higher-order component that **memoizes a functional component**.
  • Prevents re-render if **props have not changed**.
  • Best for **pure functional components** that render the same output for same props.
import React from "react";

const Child = React.memo(({ name }) => {
  console.log("Child rendered");
  return <div>Hello {name}</div>;
});

function Parent() {
  const [count, setCount] = React.useState(0);

  return (
    <div>

      <Child name="Narahari" />
    </div>
  );
}

✅ `Child` will not re-render when `count` changes, only when `name` changes.

🧠 3. useMemo
  • Memoizes the **result of a function** between renders.
  • Useful for **expensive computations**.
  • Syntax: const memoizedValue = useMemo(() => compute(), [dependencies]);
import React, { useMemo } from "react";

function App({ number }) {
  const factorial = useMemo(() => {
    console.log("Computing factorial...");
    let result = 1;
    for(let i = 1; i <= number; i++) result *= i;
    return result;
  }, [number]);

  return <div>Factorial: {factorial}</div>;
}

✅ Computation runs only when `number` changes.

🧠 4. useCallback
  • Memoizes a **function** between renders.
  • Useful when passing callbacks to child components to avoid unnecessary re-renders.
  • Syntax: const memoizedFn = useCallback(() => { ... }, [dependencies]);
import React, { useState, useCallback } from "react";

const Child = React.memo(({ onClick }) => {
  console.log("Child rendered");
  return <button onClick={onClick}>Click</button>;
});

  const handleClick = useCallback(() => {
    console.log("Button clicked");
  }, []);

      <button onClick={() => setCount(count + 1)}>Increment</button>
      <Child onClick={handleClick} />
    </div>
  );
}

✅ `Child` will not re-render when `count` changes because `handleClick` reference is stable.

  • 🔹 **React.memo**: Memoize components to prevent unnecessary re-renders.
  • 🔹 **useMemo**: Memoize **expensive calculations**.
  • 🔹 **useCallback**: Memoize **functions** passed to children.
  • ⚠️ Overusing these hooks may increase memory usage; use only when performance issues exist.
📌 6. Summary
  • Memoization helps React apps **avoid unnecessary computations and re-renders**.

📌 1. Overview

Error Boundaries in React are components that **catch JavaScript errors** in their child component tree, log those errors, and display a **fallback UI** instead of breaking the entire app.

⚡ 2. Key Features
  • Catch errors in **render, lifecycle methods, and constructors** of child components.
  • Provide **fallback UI** to avoid app crash.
  • Can be used to **log errors** for analytics or debugging.
  • Only works for **class components** (React 18+ supports hooks-based approaches via libraries).
🧩 3. Creating an Error Boundary
import React from "react";

class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(error) {
    // Update state to show fallback UI
    return { hasError: true };
  }

  componentDidCatch(error, info) {
    // Log error to an external service
    console.error("Error caught:", error, info);
  }

  render() {
    if (this.state.hasError) {
      return <h2>Something went wrong.</h2>;
    }

    return this.props.children;
  }
}

⚡ 2. Call Stack

  • Continuously checks the **call stack** and **task queues**.

📌 1. Overview

**Hoisting** in JavaScript is the behavior where **variable and function declarations are moved to the top of their scope** during compilation. This allows functions to be called **before they are defined** in the code.

⚡ 2. Variable Hoisting
  • var declarations are hoisted and initialized with undefined.
  • let and const are hoisted but not initialized → accessing them before declaration throws **ReferenceError**.
🧩 Example: var Hoisting
console.log(a); // undefined
var a = 10;
console.log(a); // 10
🧩 Example: let/const Hoisting
console.log(b); // ReferenceError
let b = 20;

console.log(c); // ReferenceError
const c = 30;
⚡ 3. Function Hoisting
  • Function **declarations** are fully hoisted — can be called before definition.
  • Function **expressions** (var/let/const assigned) are hoisted like variables — not initialized.
🧩 Example: Function Declaration Hoisting
greet(); // "Hello World"

function greet() {
  console.log("Hello World");
}
🧩 Example: Function Expression Hoisting
sayHi(); // TypeError: sayHi is not a function

var sayHi = function() {
  console.log("Hi!");
};
⚡ 4. Class Hoisting
  • Class declarations are **not hoisted** — accessing them before declaration throws **ReferenceError**.
🧩 Example: Class Hoisting
const obj = new Person(); // ReferenceError

class Person {
  constructor(name) {
    this.name = name;
  }
}
📊 5. Key Points
  • ✅ Hoisting **only moves declarations**, not initializations.
  • ✅ `var` variables: hoisted and initialized with `undefined`.
  • ✅ `let` & `const`: hoisted but uninitialized (Temporal Dead Zone).
  • ✅ Function declarations are fully hoisted; function expressions are treated as variables.
  • ✅ Classes are hoisted but **cannot be accessed before declaration**.
📌 6. Summary
  • Hoisting affects **variables, functions, and classes** differently.
  • Understanding hoisting is essential for **predictable code execution**.
  • Best practice: **declare variables and functions before use** to avoid confusion.

  };

  return x => x * factor;

**React Fiber** is the **reconciliation engine** introduced in React 16 that improves rendering performance by breaking rendering work into **incremental units**. It allows React to **pause, resume, and prioritize updates**, making UI rendering smooth even in large, complex applications.

⚡ 2. Why Fiber Was Introduced
  • Before Fiber, React used a **stack-based recursive algorithm**, which blocked the main thread for long renders.
  • Large applications could suffer **laggy UIs** during updates.
  • Fiber allows **time-slicing**, enabling React to **split work** and handle **high-priority updates** first.
🧩 3. Key Features of React Fiber
  • 🔹 **Incremental Rendering** – Breaks rendering into small units for smooth updates.
  • 🔹 **Prioritization** – User interactions and animations can be prioritized over low-priority updates.
  • 🔹 **Backwards Compatible** – Works with existing React code without changes.
  • 🔹 **Error Handling** – Supports error boundaries better for more resilient UIs.
  • 🔹 **Concurrency & Suspense** – Enables features like React Suspense and concurrent rendering.
⚡ 4. How Fiber Works Conceptually
Component Tree
   │
   ▼
Fiber Nodes (Each component has a Fiber node)
   │
   ├─ Work Loop: Incrementally process units of work
   │   ├─ Check for changes
   │   ├─ Update virtual DOM
   │   ├─ Pause/resume if high-priority work arrives
   │
   ▼
Commit Phase
   ├─ Apply changes to Real DOM
   └─ Call lifecycle methods (componentDidMount, etc.)

Aspect Old Stack Reconciliation Fiber
Algorithm Recursive, synchronous Incremental, interruptible
Performance Blocks main thread Time-slicing for smooth updates
Prioritization None Supports high/low priority tasks
Error Handling Limited Improved with error boundaries
Concurrency No Supports concurrent rendering
⚡ 6. Practical Implications
  • Long lists, heavy animations, or complex UI updates no longer block the browser.
  • React can **pause low-priority rendering** for user interactions.
  • Enables **Concurrent Mode** (experimental) for smoother apps.
  • Works seamlessly with **Hooks, Suspense, and lazy loading**.
📌 7. Summary
  • React Fiber is the **heart of React's reconciliation**, enabling **incremental, prioritized, and interruptible rendering**.
  • It allows React to **handle large, dynamic UIs efficiently** without blocking the main thread.
  • Understanding Fiber helps in optimizing performance and using **Suspense, lazy loading, and concurrent features** effectively.

  • Useful when **component re-renders are costly** (e.g., large lists, heavy computations).
⚡ 3. Shallow Comparison Explained

PureComponent performs a **shallow equality check**:

  • Primitive values (numbers, strings) are compared by value.
  • Objects/arrays are compared by reference (not deep equality).
🧩 4. Example Usage

class Counter extends PureComponent {
  render() {
    console.log("Counter rendered");
    return <h2>Count: {this.props.count}</h2>;
  }
}

class App extends React.Component {
  state = { count: 0 };

  increment = () => {
    this.setState({ count: 0 }); // same value
  };

  render() {
    return (
      <div>
        <Counter count={this.state.count} />
        <button onClick={this.increment}>Increment</button>
      </div>
    );
  }
}

export default App;

  • Components with **frequent re-renders** but props/state often remain the same.
  • Large **lists or tables** where re-rendering each row is expensive.
  • Components where **performance optimizations** matter, but **deep comparisons are not required**.
⚡ 6. When Not to Use
  • Props/state contain **deeply nested objects**, as shallow comparison won't detect inner changes.
  • Simple, lightweight components where performance gain is negligible.
📌 7. Summary
  • PureComponent helps **optimize class components** by avoiding unnecessary re-renders via shallow comparison.
  • It is ideal for **performance-critical components**, especially in large applications.
  • For functional components, the equivalent is **React.memo()**.

📌 1. Overview

**Error Boundaries** in React are **components that catch JavaScript errors** anywhere in their child component tree, log those errors, and display a **fallback UI** instead of crashing the entire app.

⚡ 2. Key Points
  • Only **class components** can be Error Boundaries.
  • Catch errors in **lifecycle methods**, render phase, and constructors of child components.
  • Cannot catch errors inside **event handlers**, **async code**, or **server-side rendering**.
⚡ 3. Lifecycle Methods Used
  • static getDerivedStateFromError(error) – Updates state to show fallback UI.
  • componentDidCatch(error, info) – Logs error info (e.g., to a server).
🧩 4. Example Usage
import React from "react";

class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(error) {
    // Update state to render fallback UI
    return { hasError: true };
  }

  componentDidCatch(error, errorInfo) {
    // Log error to an error reporting service
    console.error("Error:", error, "Info:", errorInfo);
  }

  render() {
    if (this.state.hasError) {
      return <h2>Something went wrong.</h2>;
    }
    return this.props.children;
  }
}

// Usage
function BuggyComponent() {
  throw new Error("I crashed!");
  return <div>Hello</div>;
}

function App() {
  return (
    <ErrorBoundary>
      <BuggyComponent />
    </ErrorBoundary>
  );
}

export default App;
⚡ 5. Key Advantages
  • Prevents **entire app from crashing** due to a single component error.
  • Provides **graceful fallback UI** for better user experience.
  • Enables **error logging** for debugging and monitoring production apps.
⚡ 6. When to Use
  • Wrap **top-level components** to catch unexpected crashes.
  • Wrap **feature modules** individually for isolated error handling.
  • Combine with **React.lazy** and **Suspense** to handle async component errors.
📌 7. Summary
  • Error Boundaries are **class components** that catch rendering errors in child components.
  • Use them to **display fallback UI** and log errors without breaking the app.
  • Do **not replace try/catch in event handlers** or async code; they handle only render/lifecycle errors.

📌 1. Overview

**React Fiber** is React’s **reconciliation engine** introduced in React 16. It enables **incremental rendering**, **scheduling of updates**, and **prioritization of tasks**, making UIs more responsive and smooth.

⚡ 2. Why Fiber Was Introduced
  • Before Fiber, React used **stack reconciliation**, which blocked the main thread for large updates.
  • Fiber enables **interruptible rendering**, allowing React to pause, resume, and prioritize work.
  • Helps handle **high-priority updates** like animations or user input over **low-priority updates** like background rendering.
⚡ 3. Key Concepts
  • Fiber Node: Each React element is represented as a Fiber node with metadata (state, props, effect tags).
  • Reconciliation: Fiber traverses the tree to **compare old and new virtual DOM**, scheduling updates efficiently.
  • Incremental Rendering: Large updates are broken into units of work that can be paused/resumed.
  • Priority Levels: Updates have priority (sync, user interactions, low priority) to improve perceived performance.
🧩 4. Rendering Flow with Fiber
1. User triggers an update (state/props change)
2. React creates Fiber nodes for updated elements
3. Scheduler assigns priority to updates
4. Reconciliation: compares new Fiber tree with old Fiber tree
5. Commits high-priority updates first (e.g., user input)
6. Pauses low-priority updates if necessary
7. Once finished, updates DOM efficiently
⚡ 5. Advantages of Fiber
  • ✅ **Smooth UI updates** by splitting work into chunks.
  • ✅ **Interruptible rendering** for better responsiveness.
  • ✅ **Prioritization of updates** ensures important interactions are handled first.
  • ✅ Enables **Concurrent Mode** features for async rendering.
  • ✅ Handles **Suspense and lazy-loaded components** more efficiently.
⚡ 6. How It Works with Suspense
  • Suspense components can **pause rendering of child components** until data or code is ready.
  • Fiber scheduler ensures **other parts of the UI remain interactive** while waiting.
  • Lazy-loaded components benefit from Fiber’s incremental rendering.
📌 7. Summary
  • React Fiber is the **core engine behind React’s rendering** after version 16.
  • It **schedules, prioritizes, and interrupts** updates for better performance and responsiveness.
  • Supports advanced features like **Suspense, lazy loading, and concurrent mode**.
  • Understanding Fiber is useful for optimizing **performance-critical React applications**.

      {isPending && <span>Loading...</span>}

  );
}
