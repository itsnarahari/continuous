📌 1. Overview

React architecture is based on a **component-driven, declarative design** that uses a **virtual DOM** for efficient UI rendering. It focuses on building reusable UI blocks (components) that react to state or data changes.

📌 2. Core Architectural Layers
  • ⚛️ React Components – Building blocks of UI; can be functional or class-based.
  • 📦 Virtual DOM – A lightweight in-memory copy of the real DOM to minimize costly updates.
  • 🔄 Reconciliation Engine (Fiber) – The brain that compares virtual DOM trees and updates the real DOM efficiently.
  • 🎛️ State & Props – Mechanisms for data flow and inter-component communication.
  • 🧩 React Hooks – Functions like useState, useEffect, and useContext manage state and side effects elegantly.
📊 3. React Architecture Diagram (Conceptual)

      │              UI Layer                │
      │ ┌───────────────┐ ┌───────────────┐ │
      │ │ React Component│ │ React Component│ │
      │ └───────────────┘ └───────────────┘ │
      └──────────────────────────────────────┘
                     │
                     ▼
      ┌──────────────────────────────────────┐
      │           Virtual DOM Layer           │
      │   (In-memory representation of UI)    │
      └──────────────────────────────────────┘
                     │
                     ▼
      ┌──────────────────────────────────────┐
      │      Reconciliation (Fiber) Engine    │
      │ - Diffs old and new Virtual DOM       │
      │ - Updates only changed nodes          │
      └──────────────────────────────────────┘
                     │
                     ▼
      ┌──────────────────────────────────────┐
      │            Real DOM Layer             │
      │ (Browser renders the updated UI)      │
      └──────────────────────────────────────┘
📌 4. One-Way Data Flow

React follows **unidirectional (top-down)** data flow:

  • Parent passes data → via props → Child.
  • Child communicates back → via callbacks → Parent.
  • This ensures predictable and debuggable UI updates.
📌 5. Lifecycle & Rendering
  • 🟢 Mounting – Component created and inserted into DOM.
  • 🟡 Updating – Component re-renders on state/prop change.
  • 🔴 Unmounting – Component removed from DOM.
📌 6. Integration with Other Tools
  • 🌐 React Router – For navigation and routing.
  • 🧠 Redux / Context API – For global state management.
  • ⚡ Next.js – For server-side rendering and SEO optimization.
  • 🛠️ Vite / Webpack – For module bundling and fast development builds.

📌 8. Summary

React’s architecture emphasizes efficiency, modularity, and simplicity. Its Virtual DOM and Fiber reconciliation mechanism make it faster than traditional DOM manipulation frameworks. Combined with one-way data flow, it provides stability and predictability in complex UIs.

📌 1. Overview

The React Component Lifecycle defines the **sequence of events** that occur from a component’s creation to its removal from the DOM. It applies differently to **class components** and **functional components (via Hooks)**.

📌 2. Lifecycle Phases
  • 🟢 Mounting – Component is created and inserted into the DOM.
  • 🟡 Updating – Component re-renders when props or state change.
  • 🔴 Unmounting – Component is removed from the DOM.
📊 3. Class Component Lifecycle Methods
class Example extends React.Component {
  constructor() {
    super();
    console.log("🟢 constructor() - Initialization");
  }

  componentDidMount() {
    console.log("✅ componentDidMount() - Component mounted");
  }

  shouldComponentUpdate(nextProps, nextState) {
    console.log("🔄 shouldComponentUpdate() - Control re-render");
    return true;
  }

  componentDidUpdate(prevProps, prevState) {
    console.log("♻️ componentDidUpdate() - After re-render");
  }

  componentWillUnmount() {
    console.log("❌ componentWillUnmount() - Cleanup before removal");
  }

  render() {
    console.log("🧩 render() - Returns JSX");
    return <h3>Hello Lifecycle!</h3>;
  }
}
  • 🧠 constructor() – Initialize state and bind methods.
  • 🎨 render() – Returns JSX to display on UI.
  • ✅ componentDidMount() – Called once after first render; good for API calls.
  • 🔄 componentDidUpdate() – Called after every re-render due to state/prop changes.
  • 🧹 componentWillUnmount() – Used to clean up (timers, subscriptions, listeners).
📘 4. Functional Components Lifecycle (with Hooks)

Functional components don’t have lifecycle methods — instead, they use Hooks like useEffect() to replicate them.

import { useState, useEffect } from "react";

function Example() {
  const [count, setCount] = useState(0);

  // 🟢 componentDidMount
  useEffect(() => {
    console.log("✅ Mounted");
  }, []);

  // 🟡 componentDidUpdate
  useEffect(() => {
    console.log("🔄 Updated:", count);
  }, [count]);

  // 🔴 componentWillUnmount
  useEffect(() => {
    return () => console.log("❌ Cleanup before unmount");
  }, []);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  );
}

📌 1. Overview

One-way data binding in React means that the data flows in a single direction — from parent components → to child components through props. The child cannot directly modify the parent’s data; it can only send data back via callback functions.

📊 2. Data Flow Diagram
Parent (holds state)
   ↓  props
Child (receives data)
   ↑  callback (event)
Parent (updates state again)
📘 3. Example of One-Way Data Binding
import React, { useState } from "react";

function Parent() {
  const [message, setMessage] = useState("Hello from Parent!");

  // Callback passed to child
  const updateMessage = (newMsg) => {
    setMessage(newMsg);
  };

  return (
    <div className="p-3 border border-info rounded">
      <h4>Parent Component</h4>
      <p>Message: {message}</p>
      <Child msg={message} onUpdate={updateMessage} />
    </div>
  );
}

function Child({ msg, onUpdate }) {
  return (
    <div className="mt-3 border border-secondary rounded p-2">
      <h5>Child Component</h5>
      <p>Received: {msg}</p>
      <button className="btn btn-warning" onClick={() => onUpdate("Updated from Child!")}>
        Send Update to Parent
      </button>
    </div>
  );
}

export default Parent;
📘 4. Explanation
  • 💡 Parent → Child: Data sent through props.
  • 🧭 Child → Parent: Sends data back using callback (function passed as prop).
  • 🧠 Unidirectional: Prevents accidental changes and keeps UI predictable.
📊 5. One-Way vs Two-Way Data Binding
Feature One-Way (React) Two-Way (Angular / Vue)
Data Flow Parent ➜ Child (Single Direction) Parent ⇄ Child (Both Directions)
Control Parent fully controls state View and Model sync automatically
Complexity Predictable and easier to debug Can become hard to track changes
📌 6. Summary
  • React enforces **one-way data flow** for better control and predictability.
  • Data goes **from parent → child** via props.
  • To modify data, child must **invoke a callback** from the parent.
  • This approach keeps the UI consistent and easier to debug.

📌 1. Overview

Property Drilling (also called Prop Drilling) occurs when you pass data from a parent component to deeply nested child components, **through multiple layers of intermediate components** that do not need the data themselves.

📊 2. Visual Representation
Parent
 └── Child A
      └── Child B
           └── Child C  ← Needs the data

Data must travel from Parent ➜ Child A ➜ Child B ➜ Child C
(even if A and B don’t use it)
📘 3. Example of Property Drilling
function Parent() {
  const user = { name: "Narahari", role: "Developer" };
  return <ChildA user={user} />;
}

function ChildA({ user }) {
  return <ChildB user={user} />;
}

function ChildB({ user }) {
  return <ChildC user={user} />;
}

function ChildC({ user }) {
  return <p>👤 Name: {user.name}, Role: {user.role}</p>;
}

➡️ Here, user is passed through ChildA and ChildB even though only ChildC actually needs it.

⚠️ 4. Disadvantages of Property Drilling
  • 🚧 Increases code complexity.
  • 🧱 Tight coupling between components.
  • 🌀 Hard to refactor or maintain as the app grows.
  • 🧩 Reusability of intermediate components is reduced.
💡 5. Solutions to Property Drilling
  • 🧠 React Context API – Provides a way to share data globally without passing props manually at every level.
  • 🪣 State Management Libraries – Like Redux, Recoil, or Zustand for centralized data storage.
📘 6. Example using Context API (Fix)
import React, { createContext, useContext } from "react";

const UserContext = createContext();

function Parent() {
  const user = { name: "Narahari", role: "Developer" };
  return (
    <UserContext.Provider value={user}>
      <ChildA />
    </UserContext.Provider>
  );
}

function ChildA() {
  return <ChildB />;
}

function ChildB() {
  return <ChildC />;
}

function ChildC() {
  const user = useContext(UserContext);
  return <p>👤 Name: {user.name}, Role: {user.role}</p>;
}

✅ With Context, ChildC directly accesses user without unnecessary prop passing.

📊 7. Comparison Table
Aspect With Property Drilling With Context API
Data Passing Manually through every level Globally available to children
Complexity High in deeply nested components Low and cleaner
Reusability Reduced Improved
📌 8. Summary
  • Property drilling = Passing props through components unnecessarily.
  • It can make your React tree hard to maintain and scale.
  • Use Context API or Redux to avoid it.
  • Ideal for sharing data like theme, user, language, or global state.

📌 1. Overview

React and modern web frameworks use different approaches to manage and update the DOM efficiently. Understanding the difference between the Real DOM, Virtual DOM, and Shallow DOM helps you grasp how rendering and performance optimization work in UI frameworks.

📊 2. What is DOM (Document Object Model)?
  • 📄 The DOM represents the **entire HTML structure** of a web page as a tree of objects.
  • 🧠 It allows JavaScript to manipulate structure, style, and content dynamically.
  • ⚠️ However, updating the real DOM is **slow**, because the browser needs to reflow and repaint the page every time a change occurs.
HTML ➜ Browser parses it ➜ Creates DOM Tree ➜ Used for rendering UI
📘 Example (Real DOM)
<div id="app">
  <h2>Hello React</h2>
</div>

document.getElementById("app").innerHTML = "<h2>Updated!</h2>";
➡️ Entire element is re-rendered and browser recalculates layout.
⚛️ 3. Virtual DOM (Used in React)
  • 🧩 The Virtual DOM (VDOM) is an **in-memory representation** of the real DOM.
  • 🌀 When state changes, React creates a new virtual DOM tree and compares it with the previous one using the Reconciliation (Diffing) Algorithm.
  • ⚡ Only the changed parts are updated in the real DOM, improving performance.
Render ➜ Create Virtual DOM copy ➜ Diff with previous ➜ Update only changed nodes
📘 Example (Virtual DOM in React)
function App() {
  const [text, setText] = useState("Hello");

  return (
    <div>
      <h2>{text}</h2>
      <button onClick={() => setText("Updated!")}>Change</button>
    </div>
  );
}
➡️ React updates only the <h2> node — not the entire DOM.
🧱 4. Shallow DOM (Used in Web Components)
  • 🧩 Shallow DOM is a term often used with **Shadow DOM** (part of Web Components).
  • 🔒 It provides encapsulation — HTML, CSS, and JS inside a component are **isolated** from the rest of the document.
  • 🎯 Useful for building custom HTML elements that don't affect global styles or scripts.
📘 Example (Shadow DOM)
// Define a custom element
class MyElement extends HTMLElement {
  constructor() {
    super();
    const shadow = this.attachShadow({ mode: "open" });
    shadow.innerHTML = "<h3>Inside Shadow DOM</h3>";
  }
}
customElements.define("my-element", MyElement);

➡️ The content inside <my-element> is isolated — outer CSS cannot affect it directly.

📊 5. Comparison Table
Feature Real DOM Virtual DOM Shadow DOM
Definition Browser’s representation of HTML structure In-memory virtual copy used by React Encapsulated mini-DOM inside web components
Performance Slower on updates Faster due to diffing and minimal updates Fast, as it affects only local DOM
Isolation No isolation (global scope) No isolation (shared via React tree) Yes — CSS/JS scoped to component
Used By All browsers (native) React, Preact Web Components

        │        Real DOM          │

                   │
                   ▼
        ┌──────────────────────────┐
        │       Virtual DOM         │

        │        Shadow DOM         │

📌 7. Summary
  • 🌳 Real DOM: Browser’s actual structure — slow to update.
  • ⚛️ Virtual DOM: React’s efficient in-memory copy — fast updates via diffing.
  • 🧩 Shadow DOM: Encapsulated DOM inside custom web components — isolates styles and scripts.
  • 💡 Together, these form the foundation of modern, performant web UI rendering.

📌 1. Overview

Conditional Rendering in React means displaying UI elements or components **based on certain conditions or states**. It works just like JavaScript’s conditional statements (if, ternary, switch, etc.), but inside JSX.

📊 2. Why Use Conditional Rendering?
  • 🎯 To render different components for different states (e.g., logged in vs. logged out).
  • ⚡ To control visibility of UI parts dynamically.
  • 🧩 To improve reusability and readability in React apps.
📘 3. Using if / else Statement
function Greeting({ isLoggedIn }) {
  if (isLoggedIn) {
    return <h3>Welcome Back, Narahari!</h3>;
  } else {
    return <h3>Please Login to Continue</h3>;
  }
}

✅ Simple and clear, best for small conditions.

📘 4. Using Ternary Operator (Inline Condition)
function Greeting({ isLoggedIn }) {
  return (
    <div>
      {isLoggedIn ? (
        <h3 className="text-success">Welcome, User!</h3>
      ) : (
        <h3 className="text-warning">Please Log In</h3>
      )}
    </div>
  );
}

⚡ Commonly used inside JSX for cleaner inline rendering.

📘 5. Using Logical AND (&&) Operator
function Dashboard({ hasAccess }) {
  return (
    <div>
      <h4>Dashboard</h4>
      {hasAccess && <p className="text-info">Access Granted!</p>}
    </div>
  );
}

✅ The right-hand JSX runs only if the left-hand condition is true.

📘 6. Using Switch-Case or Function Return

🔁 Best suited when you have multiple possible conditions to handle.

        return <p>Hello, {user.name}!</p>;
      })()}

}

🧠 Useful for multiple condition branches inside JSX blocks.

📌 1. Overview

In React, **form inputs** can be handled in two ways — Controlled or Uncontrolled components. The key difference lies in **who controls the form data** — React state or the DOM itself.

🎮 2. Controlled Components
  • React controls the value of the input field via state.
  • The input value is stored in the React component’s state and updated using onChange.
  • This makes form data predictable and easy to validate or manipulate.
function ControlledInput() {
  const [name, setName] = React.useState("");

  const handleChange = (e) => {
    setName(e.target.value);
  };

  return (
    <div>
      <label>Name:</label>
      <input type="text" value={name} onChange={handleChange} />
      <p>You typed: {name}</p>
    </div>
  );
}

✅ The value of the input always reflects the component’s state.

⚙️ 3. Uncontrolled Components
  • The input value is handled by the **DOM itself**, not by React state.
  • To access the value, we use a **ref** (useRef() or createRef()).
  • Used when you don’t need real-time validation or state updates.
function UncontrolledInput() {
  const inputRef = React.useRef();

  const handleSubmit = () => {
    alert("Entered name: " + inputRef.current.value);
  };

  return (
    <div>
      <label>Name:</label>
      <input type="text" ref={inputRef} />
      <button onClick={handleSubmit}>Submit</button>
    </div>
  );
}

⚡ The value lives in the DOM and is read only when needed.

📊 4. Comparison Table
Feature Controlled Component Uncontrolled Component
Data Source React State DOM (via ref)
Access Method Through state variable Through ref.current.value
Real-Time Updates Yes ✅ No ❌
Ease of Validation Easy (since state is known) Harder (manual DOM access)
Performance Slightly slower (re-renders on change) Faster (no re-renders)
Best For Form validation, dynamic UIs Simple forms, quick data capture
💡 5. Hybrid Example

Sometimes you can use both — controlled for main fields, uncontrolled for less important ones.

function MixedForm() {
  const [email, setEmail] = React.useState("");
  const ageRef = React.useRef();

  const handleSubmit = () => {
    console.log("Email:", email);
    console.log("Age:", ageRef.current.value);
  };

  return (
    <form>
      <input type="email" value={email} onChange={(e) => setEmail(e.target.value)} />
      <input type="number" ref={ageRef} placeholder="Age" />
      <button type="button" onClick={handleSubmit}>Submit</button>
    </form>
  );
}
📌 6. Summary
  • Controlled → React controls the input (state).
  • Uncontrolled → DOM controls the input (ref).
  • Controlled = predictable + validation friendly.
  • Uncontrolled = simpler + less re-renders.

📌 1. Overview

Refs (References) in React provide a way to directly access or modify a DOM element or a child component without triggering a re-render. They are commonly used for handling focus, text selection, animations, or integrating third-party libraries.

⚙️ 2. Creating a Ref using useRef()
import React, { useRef } from "react";

function InputFocusExample() {
  const inputRef = useRef(null);

  const handleFocus = () => {
    inputRef.current.focus();
  };

  return (
    <div>
      <input ref={inputRef} type="text" placeholder="Click button to focus" />
      <button onClick={handleFocus} className="btn btn-warning mt-2">
        Focus Input
      </button>
    </div>
  );
}
  • ✅ useRef() creates a reference object.
  • 📦 The actual DOM node is available via ref.current.
  • 💡 Updating a ref does not cause re-rendering.
🎯 3. When to Use Refs
  • Focusing input fields.
  • Triggering animations manually.
  • Accessing DOM elements directly (scroll, video controls, etc.).
  • Storing mutable values that persist without re-rendering.
🧩 4. Forwarding Refs (Parent → Child Access)

By default, refs cannot be passed directly to child components. Forwarding Refs allows parent components to send a ref to access the child’s DOM node.

import React, { useRef, forwardRef } from "react";

// Child component
const CustomInput = forwardRef((props, ref) => {
  return <input ref={ref} type="text" placeholder="Type here..." />;
});

// Parent component
function ParentComponent() {
  const inputRef = useRef();

  const handleClick = () => {
    inputRef.current.focus();
  };

  return (
    <div>
      <CustomInput ref={inputRef} />
      <button onClick={handleClick} className="btn btn-success mt-2">
        Focus from Parent
      </button>
    </div>
  );
}

🧠 Here, forwardRef passes the ref from parent to child so that parent can directly access child’s DOM node.

⚡ 5. Combining Refs with useImperativeHandle()

Used with forwardRef() to expose specific methods from a child component to its parent.

import React, { useRef, useImperativeHandle, forwardRef } from "react";

const InputBox = forwardRef((props, ref) => {
  const inputRef = useRef();

  useImperativeHandle(ref, () => ({
    focusInput: () => inputRef.current.focus(),
    clearInput: () => (inputRef.current.value = "")
  }));

  return <input ref={inputRef} placeholder="Controlled via parent" />;
});

function Parent() {
  const inputRef = useRef();

  return (
    <div>
      <InputBox ref={inputRef} />
      <button onClick={() => inputRef.current.focusInput()}>Focus</button>
      <button onClick={() => inputRef.current.clearInput()}>Clear</button>
    </div>
  );
}
  • ⚙️ useImperativeHandle() customizes what the parent can access.
  • 🚀 Enables creating reusable, encapsulated component APIs.
📊 6. Comparison Table
Feature Ref Forward Ref
Purpose Access DOM element within same component Allow parent to access child’s DOM node
Syntax useRef() forwardRef()
Data Flow Internal (self-use) Parent → Child
Usage Focus input, store values Expose DOM or methods to parent
📌 7. Summary
  • Refs let you directly interact with DOM elements or store mutable data.
  • forwardRef allows parent access to child DOM nodes.
  • useImperativeHandle defines what actions are exposed to parent.
  • Use Refs sparingly — React prefers declarative UI updates via state.

📌 1. Overview

In React, list rendering means dynamically displaying multiple elements (like users, products, or todos) using the JavaScript map() function. React efficiently renders lists by giving each element a unique key prop to track changes.

⚙️ 2. Basic Example
function NameList() {
  const names = ["Alice", "Bob", "Charlie"];

  return (
    <ul>
      {names.map((name, index) => (
        <li key={index}>{name}</li>
      ))}
    </ul>
  );
}
  • ✅ map() is used to transform each array item into a React element.
  • 🧩 The key helps React efficiently update or remove elements.
💡 3. Rendering List of Objects
function UserList() {
  const users = [
    { id: 1, name: "John", age: 25 },
    { id: 2, name: "Emma", age: 28 },
    { id: 3, name: "Raj", age: 30 },
  ];

  return (
    <div>
      <h4>User Details</h4>
      <ul>
        {users.map((user) => (
          <li key={user.id}>
            {user.name} — {user.age} years old
          </li>
        ))}
      </ul>
    </div>
  );
}

✅ Always use a **unique key (like id)** instead of index when rendering lists of objects to prevent rendering bugs.

⚡ 5. Why “key” is Important
  • Helps React identify which items changed, added, or removed.
  • Improves performance in re-rendering lists.
  • Keys must be unique and stable — never use random values.
🚫 6. Common Mistakes
  • ❌ Using array index as key when items can change order (may cause UI mismatch).
  • ❌ Forgetting to add key — React shows a warning in the console.
📘 7. Conditional Rendering with Lists
function FilteredList({ items }) {
  return (
    <ul>
      {items.length > 0 ? (
        items.map((item) => <li key={item.id}>{item.name}</li>)
      ) : (
        <p>No items available</p>
      )}
    </ul>
  );
}
📌 8. Summary
  • Use map() to render arrays dynamically.
  • Always include a unique key prop.
  • Can render strings, JSX elements, or components.
  • Combine with conditions or filters for dynamic UIs.

📌 1. Overview

⚙️ 2. Why Keys Are Important

  • ⚡ Enables **faster re-rendering** by reusing existing DOM nodes.
  • 🧠 Prevents UI bugs during **add/remove/reorder** operations.
  • 📦 Keeps **component state stable** across renders.

📌 1. Overview

React uses a **Reconciliation Algorithm** (Fiber) to efficiently update the **Real DOM** by comparing it with the **Virtual DOM**. Keys play a crucial role in helping React **match old and new elements** during this process.

⚙️ 2. How Reconciliation Works
  • 🧩 React creates a **Virtual DOM** — an in-memory representation of UI.
  • 🔄 When state or props change, React creates a **new Virtual DOM** tree.
  • ⚡ React compares old vs. new Virtual DOM using the **Diffing Algorithm**.
  • ✅ Only updates elements that actually changed — minimizing costly DOM operations.
📘 3. Role of Keys in Reconciliation
  • Keys help React identify which items **correspond to which element**.
  • Without keys, React assumes elements are in order — may reuse DOM incorrectly.
  • With unique keys, React can **move, add, or delete** nodes efficiently.
🎨 4. Example Without Keys

        ))}

  );
}

❌ React may reuse DOM nodes incorrectly → UI glitches when tasks are added or removed.

    { id: 1, text: "Task1" },
    { id: 2, text: "Task2" },
    { id: 3, text: "Task3" }

📊 6. Diffing Algorithm Rules
  1. Elements of different types → React **replaces** the old node completely.
  2. Elements of the same type → React **updates** the attributes and recursively reconciles children.
  3. Lists with keys → React uses **keys to match old vs new children**.
  4. Lists without keys → React matches **by index**, may cause wrong updates.
⚡ 7. Key Takeaways
  • Keys are essential for **stable identity** in dynamic lists.
  • Unique and stable keys reduce **unnecessary DOM updates**.
  • Proper keys prevent **state loss** in child components (like input values).
  • React’s reconciliation + keys = highly efficient UI rendering.
📘 8. Summary
  • React uses **Virtual DOM** and **Fiber** to update the real DOM efficiently.
  • Keys in lists allow React to **match elements between renders** correctly.
  • Always use **unique, stable keys** for dynamic lists to prevent glitches and improve performance.

React provides **Memoization techniques** to optimize performance by preventing **unnecessary re-renders** and **expensive computations**.

🧩 2. React.memo
  • Higher-order component that **memoizes a functional component**.
  • Prevents re-render if **props have not changed**.
  • Best for **pure functional components** that render the same output for same props.
import React from "react";

const Child = React.memo(({ name }) => {
  console.log("Child rendered");
  return <div>Hello {name}</div>;
});

function Parent() {
  const [count, setCount] = React.useState(0);

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Increment</button>
      <Child name="Narahari" />
    </div>
  );
}

✅ `Child` will not re-render when `count` changes, only when `name` changes.

🧠 3. useMemo
  • Memoizes the **result of a function** between renders.
  • Useful for **expensive computations**.
  • Syntax: const memoizedValue = useMemo(() => compute(), [dependencies]);
import React, { useMemo } from "react";

function App({ number }) {
  const factorial = useMemo(() => {
    console.log("Computing factorial...");
    let result = 1;
    for(let i = 1; i <= number; i++) result *= i;
    return result;
  }, [number]);

  return <div>Factorial: {factorial}</div>;
}

✅ Computation runs only when `number` changes.

🧠 4. useCallback
  • Memoizes a **function** between renders.
  • Useful when passing callbacks to child components to avoid unnecessary re-renders.
  • Syntax: const memoizedFn = useCallback(() => { ... }, [dependencies]);
import React, { useState, useCallback } from "react";

const Child = React.memo(({ onClick }) => {
  console.log("Child rendered");
  return <button onClick={onClick}>Click</button>;
});

  const handleClick = useCallback(() => {
    console.log("Button clicked");
  }, []);

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Increment</button>
      <Child onClick={handleClick} />
    </div>
  );
}

✅ `Child` will not re-render when `count` changes because `handleClick` reference is stable.

  • 🔹 **React.memo**: Memoize components to prevent unnecessary re-renders.
  • 🔹 **useMemo**: Memoize **expensive calculations**.
  • 🔹 **useCallback**: Memoize **functions** passed to children.
  • ⚠️ Overusing these hooks may increase memory usage; use only when performance issues exist.
📌 6. Summary

📌 1. Overview

Error Boundaries in React are components that **catch JavaScript errors** in their child component tree, log those errors, and display a **fallback UI** instead of breaking the entire app.

⚡ 2. Key Features
  • Catch errors in **render, lifecycle methods, and constructors** of child components.
  • Provide **fallback UI** to avoid app crash.
  • Can be used to **log errors** for analytics or debugging.
  • Only works for **class components** (React 18+ supports hooks-based approaches via libraries).
🧩 3. Creating an Error Boundary
import React from "react";

class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(error) {
    // Update state to show fallback UI
    return { hasError: true };
  }

  componentDidCatch(error, info) {
    // Log error to an external service
    console.error("Error caught:", error, info);
  }

  render() {
    if (this.state.hasError) {
      return <h2>Something went wrong.</h2>;
    }

    return this.props.children;
  }
}

export default ErrorBoundary;
⚡ 4. Using an Error Boundary
import ErrorBoundary from "./ErrorBoundary";
import BuggyComponent from "./BuggyComponent";

function App() {
  return (
    <ErrorBoundary>
      <BuggyComponent />
    </ErrorBoundary>
  );
}

✅ If BuggyComponent throws an error, the fallback UI “Something went wrong.” is displayed instead of breaking the whole app.

📊 5. Best Practices
  • Wrap **top-level routes or sections** of the app, not every small component.
  • Log errors to external services like **Sentry, LogRocket, or custom analytics**.
  • Provide a **user-friendly fallback UI**, possibly with a **retry button**.
  • Combine with **React.lazy** and Suspense for dynamic component error handling.
  • Remember: Error boundaries **do not catch errors** in event handlers, async code, or server-side rendering.
💡 6. Limitations
  • Does not catch errors in **event handlers** – use try/catch in those functions.
  • Does not catch errors in **server-side rendering**.
  • Does not catch errors in **setTimeout or async code** – handle manually.
📌 7. Summary
  • Error Boundaries improve **app stability** by preventing crashes from runtime errors.
  • Use **class components** for creating Error Boundaries.
  • Always provide **fallback UI** and optionally log errors externally.
  • Best used at **top-level sections** or **routes**, not on every small component.

📌 1. Overview

JavaScript is **single-threaded**, meaning it executes code in a single call stack. The **event loop** allows asynchronous operations (like setTimeout, Promises, DOM events) to be handled efficiently without blocking the main thread.

⚡ 2. Call Stack
  • Stack structure where **functions are pushed** when called and **popped** when execution completes.
  • Maintains the execution context of synchronous code.
  • If the stack is full or blocked, the UI becomes unresponsive.
🧩 3. Event Loop
  • Continuously checks the **call stack** and **task queues**.
  • If call stack is empty, it pushes tasks from the **microtask queue** (Promises, MutationObserver) first, then **macrotask queue** (setTimeout, setInterval, I/O events).
  • Ensures asynchronous callbacks are executed in a non-blocking manner.
⚡ 4. Microtasks vs Macrotasks
Aspect Microtasks Macrotasks
Examples Promises (.then, .catch, .finally), MutationObserver setTimeout, setInterval, setImmediate, I/O events, UI rendering
Execution Timing Executed **immediately after current call stack** is empty Executed **after microtasks and current stack**, in the next tick of the event loop
Priority Higher (executed before macrotasks) Lower

setTimeout(() => console.log("Macrotask - setTimeout"), 0);

Promise.resolve()
  .then(() => console.log("Microtask - Promise"));

console.log("End");

// End

📌 1. Overview

**Hoisting** in JavaScript is the behavior where **variable and function declarations are moved to the top of their scope** during compilation. This allows functions to be called **before they are defined** in the code.

⚡ 2. Variable Hoisting
  • var declarations are hoisted and initialized with undefined.
  • let and const are hoisted but not initialized → accessing them before declaration throws **ReferenceError**.
🧩 Example: var Hoisting
console.log(a); // undefined
var a = 10;
console.log(a); // 10
🧩 Example: let/const Hoisting
console.log(b); // ReferenceError
let b = 20;

console.log(c); // ReferenceError
const c = 30;
⚡ 3. Function Hoisting
  • Function **declarations** are fully hoisted — can be called before definition.
  • Function **expressions** (var/let/const assigned) are hoisted like variables — not initialized.
🧩 Example: Function Declaration Hoisting
greet(); // "Hello World"

function greet() {
  console.log("Hello World");
}
🧩 Example: Function Expression Hoisting
sayHi(); // TypeError: sayHi is not a function

var sayHi = function() {
  console.log("Hi!");
};
⚡ 4. Class Hoisting
  • Class declarations are **not hoisted** — accessing them before declaration throws **ReferenceError**.
🧩 Example: Class Hoisting
const obj = new Person(); // ReferenceError

class Person {
  constructor(name) {
    this.name = name;
  }
}
📊 5. Key Points
  • ✅ Hoisting **only moves declarations**, not initializations.
  • ✅ `var` variables: hoisted and initialized with `undefined`.
  • ✅ `let` & `const`: hoisted but uninitialized (Temporal Dead Zone).
  • ✅ Function declarations are fully hoisted; function expressions are treated as variables.
  • ✅ Classes are hoisted but **cannot be accessed before declaration**.
📌 6. Summary
  • Hoisting affects **variables, functions, and classes** differently.
  • Understanding hoisting is essential for **predictable code execution**.
  • Best practice: **declare variables and functions before use** to avoid confusion.

📌 1. Overview

A **closure** is a function that **remembers and has access to its outer function’s variables** even after the outer function has finished execution. Closures are possible due to JavaScript's **lexical scoping** and **function scopes**.

⚡ 2. How Closures Work
  • Functions in JS form **lexical environments** at creation.
  • A closure retains access to **variables from its outer function scope**, even after the outer function has returned.
  • Closures are heavily used in **data encapsulation, callbacks, and functional programming**.
🧩 3. Basic Example
function outer() {
  let count = 0;

  return function inner() {
    count++;
    console.log(count);
  };
}

const counter = outer();
counter(); // 1
counter(); // 2
counter(); // 3

✅ `inner` remembers `count` from `outer` even after `outer` has finished execution.

⚡ 4. Practical Use Cases
  • 🔹 **Data Privacy / Encapsulation** – variables hidden from global scope. 
    function createUser(name) {
  let score = 0; // private
  return {
    increment: () => { score++; },
    getScore: () => score
  };
}
  • 🔹 **Function Factories** – dynamically create specialized functions. 
    function multiplier(factor) {
  return x => x * factor;
}
const double = multiplier(2);
console.log(double(5)); // 10
  • 🔹 **Callbacks and Event Handlers** – remember outer variables in async code.
⚡ 5. Key Points
  • Closures **capture variables by reference**, not by value.
  • Memory is kept alive as long as closure exists – careful with **memory leaks**.
  • Closures enable **private state**, function factories, and modular code.
  • Closures are created **every time a function is created**, not just when executed.
📌 6. Summary
  • Closures allow functions to **remember the scope** in which they were created.
  • Key concept for **modular, encapsulated, and reusable JS code**.
  • Closures are widely used in **callbacks, event handlers, functional programming, and state management**.

📌 1. Overview

**React Fiber** is the **reconciliation engine** introduced in React 16 that improves rendering performance by breaking rendering work into **incremental units**. It allows React to **pause, resume, and prioritize updates**, making UI rendering smooth even in large, complex applications.

⚡ 2. Why Fiber Was Introduced
  • Before Fiber, React used a **stack-based recursive algorithm**, which blocked the main thread for long renders.
  • Large applications could suffer **laggy UIs** during updates.
  • Fiber allows **time-slicing**, enabling React to **split work** and handle **high-priority updates** first.
🧩 3. Key Features of React Fiber
  • 🔹 **Incremental Rendering** – Breaks rendering into small units for smooth updates.
  • 🔹 **Prioritization** – User interactions and animations can be prioritized over low-priority updates.
  • 🔹 **Backwards Compatible** – Works with existing React code without changes.
  • 🔹 **Error Handling** – Supports error boundaries better for more resilient UIs.
  • 🔹 **Concurrency & Suspense** – Enables features like React Suspense and concurrent rendering.
⚡ 4. How Fiber Works Conceptually
Component Tree
   │
   ▼
Fiber Nodes (Each component has a Fiber node)
   │
   ├─ Work Loop: Incrementally process units of work
   │   ├─ Check for changes
   │   ├─ Update virtual DOM
   │   ├─ Pause/resume if high-priority work arrives
   │
   ▼
Commit Phase
   ├─ Apply changes to Real DOM
   └─ Call lifecycle methods (componentDidMount, etc.)
📊 5. Fiber vs Old Reconciliation
Aspect Old Stack Reconciliation Fiber
Algorithm Recursive, synchronous Incremental, interruptible
Performance Blocks main thread Time-slicing for smooth updates
Prioritization None Supports high/low priority tasks
Error Handling Limited Improved with error boundaries
Concurrency No Supports concurrent rendering
⚡ 6. Practical Implications
  • Long lists, heavy animations, or complex UI updates no longer block the browser.
  • React can **pause low-priority rendering** for user interactions.
  • Enables **Concurrent Mode** (experimental) for smoother apps.
  • Works seamlessly with **Hooks, Suspense, and lazy loading**.
📌 7. Summary
  • React Fiber is the **heart of React's reconciliation**, enabling **incremental, prioritized, and interruptible rendering**.
  • It allows React to **handle large, dynamic UIs efficiently** without blocking the main thread.
  • Understanding Fiber helps in optimizing performance and using **Suspense, lazy loading, and concurrent features** effectively.

📌 1. Overview

A PureComponent in React is a class component that **implements a shallow comparison of props and state** to determine if a re-render is necessary. It helps in **avoiding unnecessary re-renders** and improves performance for components that receive the same props frequently.

⚡ 2. Key Features
  • Extends React.PureComponent instead of React.Component.
  • Automatically implements shouldComponentUpdate() with **shallow prop/state comparison**.
  • Useful when **component re-renders are costly** (e.g., large lists, heavy computations).
⚡ 3. Shallow Comparison Explained

PureComponent performs a **shallow equality check**:

  • Primitive values (numbers, strings) are compared by value.
  • Objects/arrays are compared by reference (not deep equality).
🧩 4. Example Usage
import React, { PureComponent } from "react";

class Counter extends PureComponent {
  render() {
    console.log("Counter rendered");
    return <h2>Count: {this.props.count}</h2>;
  }
}

class App extends React.Component {
  state = { count: 0 };

  increment = () => {
    this.setState({ count: 0 }); // same value
  };

  render() {
    return (
      <div>
        <Counter count={this.state.count} />
        <button onClick={this.increment}>Increment</button>
      </div>
    );
  }
}

export default App;

✅ Notice that Counter will **not re-render** when the same prop value is passed, saving unnecessary DOM updates.

⚡ 5. When to Use PureComponent
  • Components with **frequent re-renders** but props/state often remain the same.
  • Large **lists or tables** where re-rendering each row is expensive.
  • Components where **performance optimizations** matter, but **deep comparisons are not required**.
⚡ 6. When Not to Use
  • Props/state contain **deeply nested objects**, as shallow comparison won't detect inner changes.
  • Simple, lightweight components where performance gain is negligible.
📌 7. Summary
  • PureComponent helps **optimize class components** by avoiding unnecessary re-renders via shallow comparison.
  • It is ideal for **performance-critical components**, especially in large applications.
  • For functional components, the equivalent is **React.memo()**.

📌 1. Overview

**Error Boundaries** in React are **components that catch JavaScript errors** anywhere in their child component tree, log those errors, and display a **fallback UI** instead of crashing the entire app.

⚡ 2. Key Points
  • Only **class components** can be Error Boundaries.
  • Catch errors in **lifecycle methods**, render phase, and constructors of child components.
  • Cannot catch errors inside **event handlers**, **async code**, or **server-side rendering**.
⚡ 3. Lifecycle Methods Used
  • static getDerivedStateFromError(error) – Updates state to show fallback UI.
  • componentDidCatch(error, info) – Logs error info (e.g., to a server).
🧩 4. Example Usage
import React from "react";

class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(error) {
    // Update state to render fallback UI
    return { hasError: true };
  }

  componentDidCatch(error, errorInfo) {
    // Log error to an error reporting service
    console.error("Error:", error, "Info:", errorInfo);
  }

  render() {
    if (this.state.hasError) {
      return <h2>Something went wrong.</h2>;
    }
    return this.props.children;
  }
}

// Usage
function BuggyComponent() {
  throw new Error("I crashed!");
  return <div>Hello</div>;
}

function App() {
  return (
    <ErrorBoundary>
      <BuggyComponent />
    </ErrorBoundary>
  );
}

export default App;
⚡ 5. Key Advantages
  • Prevents **entire app from crashing** due to a single component error.
  • Provides **graceful fallback UI** for better user experience.
  • Enables **error logging** for debugging and monitoring production apps.
⚡ 6. When to Use
  • Wrap **top-level components** to catch unexpected crashes.
  • Wrap **feature modules** individually for isolated error handling.
  • Combine with **React.lazy** and **Suspense** to handle async component errors.
📌 7. Summary
  • Error Boundaries are **class components** that catch rendering errors in child components.
  • Use them to **display fallback UI** and log errors without breaking the app.
  • Do **not replace try/catch in event handlers** or async code; they handle only render/lifecycle errors.

📌 1. Overview

**React Fiber** is React’s **reconciliation engine** introduced in React 16. It enables **incremental rendering**, **scheduling of updates**, and **prioritization of tasks**, making UIs more responsive and smooth.

⚡ 2. Why Fiber Was Introduced
  • Before Fiber, React used **stack reconciliation**, which blocked the main thread for large updates.
  • Fiber enables **interruptible rendering**, allowing React to pause, resume, and prioritize work.
  • Helps handle **high-priority updates** like animations or user input over **low-priority updates** like background rendering.
⚡ 3. Key Concepts
  • Fiber Node: Each React element is represented as a Fiber node with metadata (state, props, effect tags).
  • Reconciliation: Fiber traverses the tree to **compare old and new virtual DOM**, scheduling updates efficiently.
  • Incremental Rendering: Large updates are broken into units of work that can be paused/resumed.
  • Priority Levels: Updates have priority (sync, user interactions, low priority) to improve perceived performance.
🧩 4. Rendering Flow with Fiber
1. User triggers an update (state/props change)
2. React creates Fiber nodes for updated elements
3. Scheduler assigns priority to updates
4. Reconciliation: compares new Fiber tree with old Fiber tree
5. Commits high-priority updates first (e.g., user input)
6. Pauses low-priority updates if necessary
7. Once finished, updates DOM efficiently
⚡ 5. Advantages of Fiber
  • ✅ **Smooth UI updates** by splitting work into chunks.
  • ✅ **Interruptible rendering** for better responsiveness.
  • ✅ **Prioritization of updates** ensures important interactions are handled first.
  • ✅ Enables **Concurrent Mode** features for async rendering.
  • ✅ Handles **Suspense and lazy-loaded components** more efficiently.
⚡ 6. How It Works with Suspense
  • Suspense components can **pause rendering of child components** until data or code is ready.
  • Fiber scheduler ensures **other parts of the UI remain interactive** while waiting.
  • Lazy-loaded components benefit from Fiber’s incremental rendering.
📌 7. Summary
  • React Fiber is the **core engine behind React’s rendering** after version 16.
  • It **schedules, prioritizes, and interrupts** updates for better performance and responsiveness.
  • Supports advanced features like **Suspense, lazy loading, and concurrent mode**.
  • Understanding Fiber is useful for optimizing **performance-critical React applications**.

⚡ 2. Key Features
  • Incremental rendering for **non-blocking updates**.
  • Prioritizes **high-priority updates** like typing, clicking, or animations.
  • Allows low-priority updates (e.g., fetching data) to **yield to urgent updates**.
  • Integrates with **Suspense** for async component rendering.
⚡ 3. React Transition API
  • startTransition marks updates as **non-urgent** (low-priority).
  • Helps maintain **UI responsiveness** during expensive renders.

import React, { useState, useTransition } from "react";

function App() {
  const [count, setCount] = useState(0);
  const [isPending, startTransition] = useTransition();

  const handleClick = () => {
    startTransition(() => {
      // low-priority update
      setCount(c => c + 1);
    });
  };

  return (
    <div>
      <button onClick={handleClick}>Increment</button>
      {isPending && <span>Loading...</span>}
      <p>Count: {count}</p>
    </div>
  );
}

  • Use **Concurrent Mode features** selectively to optimize critical components.

// src/features/auth/authSlice.js
import { createSlice } from '@reduxjs/toolkit';
import { loginUser, logoutUser, refreshToken, fetchMe, updateRolesOnServer, updateUserOnServer } from './authThunks';

/**
 * State:
 *  - token: JWT access token (string | null)
 *  - roles: string[]
 *  - user: { id, name, email, ... } | null
 *  - expiresAt: epoch millis (number | null)
 *  - status: 'idle' | 'loading' | 'succeeded' | 'failed'
 *  - error: string | null
 */
const initialState = {
  token: null,
  roles: [],
  user: null,
  expiresAt: null,
  status: 'idle',
  error: null,
};

const authSlice = createSlice({
  name: 'auth',
  initialState,
  reducers: {
    /** Add a role locally (idempotent) */
    addRole(state, action) {
      const role = action.payload;
      if (!state.roles.includes(role)) state.roles.push(role);
    },
    /** Remove a role locally */
    removeRole(state, action) {
      const role = action.payload;
      state.roles = state.roles.filter(r => r !== role);
    },
    /** Clear all roles */
    clearRoles(state) { state.roles = []; },
    /** Shallow-merge user fields (local) */
    updateUser(state, action) {
      state.user = { ...(state.user || {}), ...(action.payload || {}) };
    },
    /** Set all credentials in one shot (e.g., SSO callback) */
    setCredentials(state, action) {
      const { token, roles = [], user = null, expiresAt = null } = action.payload || {};
      state.token = token; state.roles = roles; state.user = user; state.expiresAt = expiresAt;
      state.error = null; state.status = 'succeeded';
    },
    /** Local-only logout (no API call). */
    localLogout(state) { Object.assign(state, initialState); },
  },
  extraReducers: (builder) => {
    builder
      // LOGIN
      .addCase(loginUser.pending, (s) => { s.status = 'loading'; s.error = null; })
      .addCase(loginUser.fulfilled, (s, a) => {
        const { token, roles, user, expiresAt } = a.payload;
        s.status = 'succeeded'; s.token = token; s.roles = roles || []; s.user = user || null; s.expiresAt = expiresAt || null;
      })
      .addCase(loginUser.rejected, (s, a) => { s.status = 'failed'; s.error = a.payload || a.error?.message || 'Login failed'; })

      // REFRESH
      .addCase(refreshToken.fulfilled, (s, a) => {
        const { token, expiresAt } = a.payload; s.token = token; s.expiresAt = expiresAt || null;
      })

      // /me
      .addCase(fetchMe.fulfilled, (s, a) => {
        const { user, roles } = a.payload; if (user) s.user = user; if (roles) s.roles = roles;
      })

      // server roles update
      .addCase(updateRolesOnServer.fulfilled, (s, a) => { s.roles = a.payload.roles; })

      // server user update
      .addCase(updateUserOnServer.fulfilled, (s, a) => { s.user = a.payload.user; })

      // LOGOUT (server)
      .addCase(logoutUser.fulfilled, (s) => { Object.assign(s, initialState); });
  }
});

export const { addRole, removeRole, clearRoles, updateUser, setCredentials, localLogout } = authSlice.actions;
export default authSlice.reducer;

// src/lib/apiClient.js
/**
 * Minimal fetch wrapper: adds Authorization header if token provided.
 * You can replace with axios; this keeps example simple & dependency-free.
 */
export async function apiFetch(path, { method = 'GET', token, body, headers = {}, ...rest } = {}) {
  const h = { 'Content-Type': 'application/json', ...headers };
  if (token) h.Authorization = `Bearer ${token}`;
  const res = await fetch(path, {
    method,
    headers: h,
    body: body ? JSON.stringify(body) : undefined,
    ...rest,
  });
  // Normalize errors
  if (!res.ok) {
    const text = await res.text().catch(() => '');
    throw new Error(text || `HTTP ${res.status}`);
  }
  // Allow empty bodies
  const ct = res.headers.get('content-type') || '';
  return ct.includes('application/json') ? res.json() : null;
}

import { createAsyncThunk } from '@reduxjs/toolkit';
import { apiFetch } from '../../lib/apiClient';
import { selectToken } from './authSelectors';

/** Helper to compute expiry from JWT "exp" claim if server doesn't send */
function expiresFromJwt(token) {
  try {
    const [, payloadB64] = token.split('.');
    const payload = JSON.parse(atob(payloadB64.replace(/-/g,'+').replace(/_/g,'/')));
    return payload.exp ? payload.exp * 1000 : null;
  } catch { return null; }
}

/** Login: POST /auth/login {email, password} -> {token, roles, user, expiresAt?} */
export const loginUser = createAsyncThunk(
  'auth/login',
  async (creds, { rejectWithValue }) => {
    try {
      const data = await apiFetch('/auth/login', { method: 'POST', body: creds });
      // normalize
      const token = data.token;
      const expiresAt = data.expiresAt ?? (token ? expiresFromJwt(token) : null);
      return { token, roles: data.roles || [], user: data.user || null, expiresAt };
    } catch (e) { return rejectWithValue(e.message); }
  }
);

/** Logout: POST /auth/logout (optional). Always clear locally on success. */
export const logoutUser = createAsyncThunk(
  'auth/logout',
  async (_, { getState }) => {
    const token = selectToken(getState());
    try { await apiFetch('/auth/logout', { method: 'POST', token }); } catch { /* ignore */ }
    return true;
  }
);

/** Refresh: POST /auth/refresh -> {token, expiresAt?} */
export const refreshToken = createAsyncThunk(
  'auth/refresh',
  async (_, { getState, rejectWithValue }) => {
    const token = selectToken(getState());
    try {
      const data = await apiFetch('/auth/refresh', { method: 'POST', token });
      const next = data.token;
      const expiresAt = data.expiresAt ?? (next ? expiresFromJwt(next) : null);
      return { token: next, expiresAt };
    } catch (e) { return rejectWithValue(e.message); }
  }
);

/** /me: GET current user & roles */
export const fetchMe = createAsyncThunk(
  'auth/me',
  async (_, { getState, rejectWithValue }) => {
    const token = selectToken(getState());
    try { return await apiFetch('/auth/me', { token }); }
    catch (e) { return rejectWithValue(e.message); }
  }
);

/** Update roles on server (PUT /users/:id/roles) */
export const updateRolesOnServer = createAsyncThunk(
  'auth/updateRoles',
  async ({ userId, roles }, { getState, rejectWithValue }) => {
    const token = selectToken(getState());
    try { 
      const data = await apiFetch(`/users/${userId}/roles`, { method: 'PUT', token, body: { roles } });
      return { roles: data.roles ?? roles };
    } catch (e) { return rejectWithValue(e.message); }
  }
);

/** Update user details on server (PATCH /users/:id) */
export const updateUserOnServer = createAsyncThunk(
  'auth/updateUser',
  async ({ userId, patch }, { getState, rejectWithValue }) => {
    const token = selectToken(getState());
    try { 
      const data = await apiFetch(`/users/${userId}`, { method: 'PATCH', token, body: patch });
      return { user: data.user ?? { id: userId, ...patch } };
    } catch (e) { return rejectWithValue(e.message); }
  }

📌 Why use useCallback?

Every render in React creates a new function reference. If this callback is passed to a child, it can cause unnecessary re-renders. Using useCallback, we memoize the function so it only changes when dependencies change.

📌 1. What is the Virtual DOM?

The Virtual DOM (VDOM) is a lightweight, in-memory representation of the real DOM. React uses it to improve performance by reducing direct DOM manipulation.

It's like a blueprint of the actual UI elements.

📌 2. Why is Virtual DOM Needed?
  • ⚡ Updating the real DOM is slow (it's an expensive operation)
  • 🧠 Virtual DOM allows React to batch updates efficiently
  • 🎯 It minimizes the number of changes made to the real DOM
📌 3. How It Works (Step-by-Step)
  1. React renders components to the Virtual DOM
  2. It compares the new Virtual DOM with the previous one (using diffing algorithm)
  3. It calculates the minimum set of changes needed
  4. It efficiently updates the real DOM in one go (called reconciliation)
📌 4. Code Example

Consider this simple React component:


function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Count is: {count}</p>
      <button onClick={() => setCount(count + 1)}>Increment</button>
    </div>
  );
}

When you click the button, only the count text (`<p>`) is updated in the real DOM — not the whole UI.

📌 5. Real DOM vs Virtual DOM
Real DOM Virtual DOM
Updates are slow Updates are fast
Directly manipulates UI Calculates diff and updates efficiently
More re-rendering Minimal re-rendering
📌 6. Visualization

Let's say you have this DOM:

  <li>Banana</li>
  <li>Mango</li>
</ul>

If Mango is removed, Virtual DOM compares old vs new trees and tells React: only remove the Mango item, not the entire <ul>.

Short answer: Both React and Vue can be very fast when used correctly. In many real apps the difference is negligible compared to how you code (state placement, memoization, virtualization, bundling).

How their performance models differ
  • Vue 3: fine-grained reactivity (Proxies) tracks exact dependencies → fewer components re-render by default. Templates are compiled to optimized render functions.
  • React 18: re-renders a component when its parent renders/props change; you opt in to skipping work using React.memo, useMemo, useCallback. Concurrent rendering improves responsiveness under load but doesn’t make pure CPU work “faster”.

Rule of thumb: out-of-the-box, Vue may do less work for small reactive updates; with good memoization, React matches it.

What actually makes apps “feel fast”
  • Critical path: bundle size, network waterfalls, SSR/SSG, hydration.
  • Work avoided: limiting renders, virtualizing large lists, splitting routes/components.
  • Scheduling: breaking long tasks, deferring non-critical work, using transitions.
  • Data strategy: colocate state; minimize global/state explosions and prop drilling.

Short answer: Yes. Vue 2 and Vue 3 both use a Virtual DOM (VDOM). Vue 3 still diffs VDOM trees, but combines that with fine-grained reactivity so only components whose reactive data changed re-render, and the compiler adds hints to minimize the amount of diffing work.

How it works in Vue
  • Template → render function → VNodes: Vue compiles your SFC template into a render function that produces a tree of virtual nodes (VNodes).
  • Diff & patch: On state changes, Vue diffs the new VNode tree against the previous one and patches only the necessary parts of the real DOM.
  • Reactivity gates work: Vue tracks which reactive properties each component uses; when one changes, only those components re-render (others are skipped).
  • Compiler hints (Vue 3): the compiler hoists static nodes and adds patch flags so the runtime can skip whole subtrees or focus diffs (e.g., “only text changed”).

Why a Virtual DOM?
  • Performance: batch and minimize DOM mutations; skip static subtrees.
  • Portability: same render logic works for SSR, Native (via render targets), etc.
  • Predictability: declarative view updated from state; no manual DOM diffing.
Vue vs React (VDOM behavior)
  • Both use VDOM diff/patch.
  • Vue 3 also uses dependency tracking: a component won’t re-render if none of the reactive values it used changed. The compiler further narrows diffs with patch flags and static hoisting.
  • React re-renders from parents downward; you opt-out of work via React.memo/useMemo/useCallback.
Keys & list updates
  • Always provide a stable :key in v-for to preserve element identity and avoid DOM churn.
<li v-for="u in users" :key="u.id">{{ u.name }}</li>
When Vue “skips” work
  • v-once for static subtrees (render once, never update).
  • Compiler hoists static nodes out of the render function.
  • Patch flags let Vue update just text/props instead of re-diffing entire branches.
Common pitfalls
  • Missing/unstable :key in lists → unnecessary re-mounts.
  • Overly global state causing avoidable updates; keep state close to where it’s used.
  • Huge lists: VDOM still does work—use virtualization (e.g., vue-virtual-scroller).

import axios from "axios";

  const [errors, setErrors] = useState({});
  const [success, setSuccess] = useState("");

  const handleChange = (e) => {
    const { name, value } = e.target;
    setEmployee({ ...employee, [name]: value });
    setErrors({ ...errors, [name]: "" });
    setSuccess("");
  };

  const validate = () => {
    const newErrors = {};
    if (!employee.name.trim()) newErrors.name = "Name is required";
    if (!employee.email.trim()) newErrors.email = "Email is required";
    else if (!/\S+@\S+\.\S+/.test(employee.email)) newErrors.email = "Invalid email format";
    if (!employee.age.trim()) newErrors.age = "Age is required";
    else if (isNaN(employee.age)) newErrors.age = "Age must be a number";
    setErrors(newErrors);
    return Object.keys(newErrors).length === 0;
  };

  const handleSubmit = async (e) => {
    e.preventDefault();
    if (!validate()) return;

    try {
      await axios.post("https://your-api.com/employees", employee);
      setSuccess("✅ Employee saved successfully!");
      setEmployee({ name: "", email: "", age: "" });
    } catch (err) {
      setSuccess("❌ Failed to save employee. Please try again.");
    }
  };

  return (
    <div className="container mt-4">
      <h4>Add New Employee</h4>
      {success && <div className={`alert ${success.includes("✅") ? "alert-success" : "alert-danger"}`}>{success}</div>}
      <form onSubmit={handleSubmit}>
        <div className="mb-3">
          <label className="form-label">Name</label>
          <input type="text" name="name" className={`form-control ${errors.name ? "is-invalid" : ""}`}
            value={employee.name} onChange={handleChange} />
          <div className="invalid-feedback">{errors.name}</div>
        </div>

        <div className="mb-3">
          <label className="form-label">Email</label>
          <input type="email" name="email" className={`form-control ${errors.email ? "is-invalid" : ""}`}
            value={employee.email} onChange={handleChange} />
          <div className="invalid-feedback">{errors.email}</div>
        </div>

        <div className="mb-3">
          <label className="form-label">Age</label>
          <input type="text" name="age" className={`form-control ${errors.age ? "is-invalid" : ""}`}

📌 5. How to Create a Custom Hook

Custom hooks are just JavaScript functions that start with use and can use other hooks inside.


// useWindowWidth.js
import { useState, useEffect } from 'react';

function useWindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    const handleResize = () => setWidth(window.innerWidth);
    window.addEventListener('resize', handleResize);

    return () => window.removeEventListener('resize', handleResize);
  }, []);

  return width;
}

export default useWindowWidth;

📌 1. What is useMemo?

useMemo is a React Hook that caches a computed value so it doesn't have to be recalculated on every render.


const expensiveValue = useMemo(() => {
  return computeHeavyOperation(data);
}, [data]);

✅ Useful for performance optimization when computations are heavy or complex.

📌 2. What is useCallback?

useCallback returns a memoized version of a callback function that only changes if one of the dependencies changes.


const handleClick = useCallback(() => {
  console.log('Clicked!');
}, []);

✅ Useful when passing callbacks to child components to avoid unnecessary re-renders.

📌 3. Key Difference
  • useMemo – Caches the result of a function
  • useCallback – Caches the function reference itself
📌 4. Side-by-Side Example

const memoizedCallback = useCallback(() => {
  doSomething(a, b);
}, [a, b]);

📌 1. What is React Fiber?

React Fiber is the **complete rewrite of React's core algorithm**, introduced in React 16. It enables **incremental rendering**, **better performance**, and **prioritization** of UI updates. Unlike the older stack-based algorithm, Fiber uses a **linked list structure** for better control over work units.

📌 2. Goals of React Fiber
  • 🔁 Incremental rendering (split rendering work into chunks)
  • 🎯 Prioritize updates based on urgency (like animations vs. data fetch)
  • ⏸️ Pause, resume, and restart work as needed
  • 🔄 Concurrency and smooth rendering under load
📌 3. How Fiber Works Internally

Fiber breaks down rendering into a tree of units of work. It uses a **work loop** to perform updates incrementally, allowing the browser to do other work in between (like user input or animations).


function workLoop(deadline) {
  while (nextUnitOfWork && deadline.timeRemaining() > 1) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }
  if (!nextUnitOfWork && workInProgressRoot) {
    commitRoot();
  }
}

This allows React to split work across multiple frames for smooth rendering.

📌 4. Fiber Node Structure

Each Fiber node represents a component and contains information like:

  • type – Component type
  • stateNode – DOM node or class instance
  • child, sibling, return – For traversing the tree
  • pendingProps, memoizedProps – For props comparison
📌 5. Phases of Fiber

React Fiber has two main phases:

  1. Render Phase: Work is done on a copy of the Fiber tree (non-blocking)
  2. Commit Phase: Final DOM updates are committed (blocking)
📌 6. Reconciliation with Fiber

During reconciliation, React compares new elements with old ones and determines what to update, remove, or add. Fiber allows this to be done **asynchronously**, improving performance for large trees.

📌 7. Scheduling and Priority

React Fiber uses an internal priority system based on **"lanes"**, where:

  • High-priority tasks like input get processed first
  • Low-priority tasks (like logging) can be deferred
This makes React highly responsive under load.

📌 8. Concurrency with Fiber

Fiber is the foundation for **Concurrent Mode** in React. It enables:

  • Suspense for data fetching
  • Time-slicing (pausing work mid-way)
  • Better responsiveness for high-priority updates

📌 9. Real-World Benefits

With Fiber, React apps:

  • Feel smoother with animations
  • Don't block user interactions while rendering
  • Handle complex UIs better

📌 What is Concurrent Mode?

📌 What is Reconciliation?

Reconciliation is the process by which React updates the **DOM** when the **state or props** of a component change. It compares the new Virtual DOM tree with the previous one and applies the minimal number of changes to the real DOM.

📌 How It Works
  • 🧠 React maintains a Virtual DOM
  • 📤 When state/props change, a new Virtual DOM is created
  • 🕵️‍♂️ React compares the new Virtual DOM with the old one
  • 🔧 Only the changed elements are updated in the real DOM
📌 Key Algorithm: Diffing

React uses a **diffing algorithm** with these assumptions:

  • 📦 Elements of different types produce different trees
  • 🔁 You can hint React with a key prop to optimize reconciliation for lists
📌 Example

// Initial render
<ul>
  <li key="1">A</li>
  <li key="2">B</li>
</ul>

// After update
<ul>
  <li key="2">B</li>
  <li key="3">C</li>
</ul>

🔑 Using key helps React move/update elements correctly without re-rendering the whole list.

📌 Optimizations React Uses
  • 🧬 Component-level re-rendering only if props/state change
  • 🔁 Skips subtrees if component returns same result
  • 🚀 React.memo and PureComponent help skip unnecessary renders
📌 Real-World Tip

Always use key for list items. Avoid using index as key unless list never changes.

📌 Conclusion

Reconciliation makes React efficient by updating only the parts of the DOM that changed. This allows for fast and scalable UI updates even with complex components.

📌 Conceptual Differences
  • Syntax & mental model: Classes use this, lifecycle methods, and setState. Functions use plain JS functions and Hooks.

  • Performance: use React.memo, useMemo, useCallback to avoid unnecessary renders on hot paths.

  • Error boundaries that catch descendant render errors (wrap your functional tree with a class boundary).

React builds a lightweight virtual tree of UI (elements) and compares it to the previous one. It computes the minimal set of changes and applies them to the real DOM efficiently. Since React 16+, this is implemented by the Fiber architecture.

🧠 Mental Model
  • Your component returns elements (plain objects describing UI).
  • React creates a Fiber tree (one Fiber per element) to track work, props, state, lanes/priority.
  • On state/prop change, React renders a new tree and diffs it with the previous tree → produces mutations.
  • Mutations are applied in the commit phase (DOM updates, refs, lifecycle/effects).
🧵 Two Phases (Fiber)
  • Render phase (reconciliation): can be interrupted/paused; computes a new Fiber tree and a list of DOM ops.
  • Commit phase: synchronous; applies DOM updates, runs useLayoutEffect/componentDidMount/Update, then schedules useEffect.
🔍 Diffing Rules (Reconciliation)
  • Same type element (e.g., <button> → <button>): update props; keep DOM node; update children.
  • Different type (<button> → <div>): replace DOM node; unmount old subtree; mount new.
  • Lists use keys: keys identify item identity across renders. React matches by key first, then by index if missing.
// Good keys: stable IDs from data
items.map(item => <Row key={item.id} data={item} />)

// Bad: index as key (causes wrong reuse on insert/remove)

// Context + useReducer pattern (split state & dispatch to reduce re-renders)
import React from "react";

const CartStateCtx = React.createContext(null);
const CartDispatchCtx = React.createContext(null);

function cartReducer(state, action) {
  switch (action.type) {
    case "add": {
      const { id } = action.item;
      const qty = (state.items[id]?.qty || 0) + 1;
      return { ...state, items: { ...state.items, [id]: { ...action.item, qty } } };
    }
    case "remove": {
      const s = { ...state.items }; delete s[action.id];
      return { ...state, items: s };
    }
    default: return state;
  }
}

export function CartProvider({ children }) {
  const [state, dispatch] = React.useReducer(cartReducer, { items: {} });
  // Memoizing only the state object reference won't block re-render of all consumers; split contexts does.
  return (
    <CartDispatchCtx.Provider value={dispatch}>
      <CartStateCtx.Provider value={state}>{children}</CartStateCtx.Provider>
    </CartDispatchCtx.Provider>
  );
}

export function useCart() {
  const ctx = React.useContext(CartStateCtx);
  if (!ctx) throw new Error("useCart must be inside CartProvider");
  return ctx;
}
export function useCartDispatch() {
  const ctx = React.useContext(CartDispatchCtx);
  if (!ctx) throw new Error("useCartDispatch must be inside CartProvider");
  return ctx;
}

// Usage
function AddToCartButton({ item }) {
  const dispatch = useCartDispatch();

}

🗂️ Don’t put server state into Redux/Context unnecessarily
  • Server state changes often, has caching, background refresh, and stale-while-revalidate needs.
  • Use TanStack Query (React Query) or RTK Query to manage it; keep Redux/Context for client-only state (UI prefs, wizard step, cart before checkout).
🧰 Lightweight alternatives
  • Zustand: small, selector-based store using useSyncExternalStore; great perf & DX.
  • Jotai / Recoil: atom-based state; fine-grained updates, good for complex trees.
⚠️ Common pitfalls
  • Using Context as a single “god provider” → every change re-renders the app.
  • Storing server responses in Redux/Context without cache policies → stale data & manual invalidation pain.
  • Overusing hooks like useMemo/useCallback globally; memo only on hot paths.
✅ Decision guide
  • Tiny/medium app, few globals → Context + useReducer, split by domain.
  • Large app, many writers, need devtools/middleware → Redux Toolkit (+ RTK Query for server state).

  • Remote data (CRUD, caching, sync) → TanStack Query or RTK Query; keep client state separate.

function useRequest(url, opts = {}) {
  const [data, setData] = React.useState(null);
  const [error, setError] = React.useState(null);
  const [loading, setLoading] = React.useState(false);
  const [version, bump] = React.useState(0); // to force refetch

      try {

async function fetchWithRetry(input, init, { retries = 3, base = 300 } = {}) {
  let last;
  for (let i = 0; i <= retries; i++) {
    try {
      const res = await fetch(input, init);
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      return res;
    } catch (e) {
      last = e;
      if (i === retries) break;
      await new Promise(r => setTimeout(r, base * 2 ** i + Math.random() * 100));
    }
  }
  throw last;
}
