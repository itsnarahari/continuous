    private NameHolder name;

  • Now, obj is static, meaning it’s shared across all threads of the class.

  2. Thread-2 must wait until Thread-1 releases that lock.
  3. Once Thread-1 finishes and releases the lock, Thread-2 can proceed.

📌 Overview
  • In Java, every object and class has a **lock (monitor)** associated with it.
  • The type of lock you acquire depends on whether you synchronize on:
    • an **object instance** → instance-level lock
    • a **class object** → class-level lock
📌 1️⃣ Instance-Level Lock

class Printer {
    public synchronized void printData() {
        System.out.println(Thread.currentThread().getName() + " printing...");
    }
}
  • Lock is acquired on the **current instance (this)**.
  • Each object has its **own monitor lock**.
  • Multiple threads can execute the synchronized method on different objects at the same time.
Example:

Printer p1 = new Printer();
Printer p2 = new Printer();

new Thread(() -> p1.printData()).start();
new Thread(() -> p2.printData()).start();

✅ Both threads can run in parallel since they lock on different instances.

📌 2️⃣ Class-Level Lock

class Printer {
    public static synchronized void printData() {
        System.out.println(Thread.currentThread().getName() + " printing...");
    }
}
  • Lock is acquired on the Class object (Printer.class).
  • Only one thread across all instances can execute a class-level synchronized method at a time.
  • This ensures **global synchronization** for all instances of the class.
Example:

Printer p1 = new Printer();
Printer p2 = new Printer();

new Thread(() -> p1.printData()).start();
new Thread(() -> p2.printData()).start();

🚫 Only one thread executes at a time, even though there are two instances.

📌 Overview

Locking is used to ensure **thread safety** — preventing multiple threads from corrupting shared data. But not all locks are equal — the "best" approach depends on what kind of resource you’re protecting and your performance goals.

📌 Common Locking Approaches
Approach Description Pros Cons Best Use Case
synchronized(this) Locks on the current object instance. Simple, built-in, safe. Blocks entire method for that object. When you need to protect instance variables.
synchronized(ClassName.class) Locks on the class — shared by all instances. Ensures only one thread across the class. Reduces parallelism; global bottleneck. When protecting static/shared resources.
synchronized(obj) Locks on a specific object reference. Fine-grained control; flexible. Need to ensure same object is shared across threads. When different resources need independent locks.
ReentrantLock Explicit lock from java.util.concurrent.locks. More control (tryLock, interruptible, fairness policy). Requires manual unlock; more code. High-performance or timeout-based locking.
ReadWriteLock Allows multiple readers but only one writer. Better concurrency when reads are frequent. Complex to manage correctly. Read-heavy shared data (e.g., caches).
📌 Best Practices
  • ✅ Use fine-grained locks — lock only what’s necessary.
  • ✅ Prefer synchronized blocks over synchronized methods — gives better control of the critical section.
  • ✅ If using advanced concurrency (timeouts, fairness), prefer ReentrantLock.
  • ✅ Avoid locking on public objects or strings (risk of external interference).
  • ✅ Keep synchronized sections as small as possible for performance.
  • ✅ Avoid nested locks — can lead to deadlocks.
📌 Recommended Approach (Industry Standard)

class SafeCounter {
    private final Object lock = new Object(); // private lock object
    private int count = 0;

    public void increment() {
        synchronized (lock) {
            count++;
        }
    }

    public int getCount() {
        synchronized (lock) {
            return count;
        }
    }
}
  • Uses a private final lock object — prevents external access.
  • Synchronizes only the small part of code that needs safety.
  • This is considered the best practice for thread-safe locking.
📌 Summary
  • Use synchronized blocks with private final lock objects for simplicity and safety.
  • Use ReentrantLock if you need timeouts, fairness, or non-blocking attempts.
  • Do not rely solely on static or class-level locks — they limit concurrency.
  • Always design locking strategy to balance safety vs performance.

📌 Definition
  • Concurrency means executing multiple tasks seemingly at the same time by interleaving their execution on a single processor or across multiple processors.
  • It helps improve responsiveness and resource utilization.
  • It’s about dealing with multiple tasks at once, not necessarily doing them simultaneously (that’s parallelism).
📘 Real-World Example
  • Imagine a restaurant kitchen with one chef preparing multiple dishes.
  • The chef chops vegetables 🥕, boils rice 🍚, and grills paneer 🍢 — switching between tasks.
  • He’s not doing them all at once, but handling them concurrently — like a CPU switching between threads.

class KitchenTask implements Runnable {

    System.out.println(Thread.currentThread().getName() + " is doing: " + task);

📌 Definition
  • Context Switching is the process of saving the state of a currently running thread or process and restoring the state of another thread or process so the CPU can execute it.
  • It allows multiple tasks (threads/processes) to share the same CPU apparently concurrently.
⚙️ Why Context Switching Happens
  • Multitasking: CPU switches between multiple processes or threads to give each a share of CPU time.
  • Thread Scheduling: When one thread is waiting (e.g., I/O or lock), CPU switches to another ready thread.
  • Preemption: The operating system scheduler interrupts a running thread to let another (higher priority or fair share) thread run.
  • Concurrency: Enables multiple logical threads to progress seemingly in parallel on fewer CPU cores.
🧠 Where It Happens
  • 1. CPU Level (Hardware + OS)
    • The Operating System (OS) scheduler handles switching between processes and kernel threads mapped to CPU cores.
    • Each core can run one thread at a time (or two with Hyper-Threading).
    • When the CPU switches, it saves registers, program counter, and stack pointer of the current thread, then loads those of the next one.
  • 2. Java Level (JVM Thread Pool)
    • Java threads are mapped to OS threads (1:1 model).
    • The JVM’s Thread Scheduler (delegating to OS) decides which Java thread to run next.
    • In a Thread Pool, context switching occurs when one thread finishes a task and another is picked up from the queue.
    • However, the actual CPU-level switch still happens in the OS, not inside the JVM.
💡 Example

ExecutorService pool = Executors.newFixedThreadPool(2);

pool.submit(() -> {
  for (int i = 0; i < 5; i++) {
    System.out.println("Task 1 - Step " + i);
  }
});

pool.submit(() -> {
  for (int i = 0; i < 5; i++) {
    System.out.println("Task 2 - Step " + i);
  }
});

👉 The CPU will switch context between Task 1 and Task 2 threads — sometimes after each print statement — depending on the OS scheduler.

📊 Performance Note
  • Context switching is not free — it consumes CPU time to save and restore states.
  • Too many switches = CPU overhead and performance degradation (context-switch storm).
  • For CPU-intensive workloads, fewer threads (equal to CPU cores) are optimal.
  • For I/O-intensive workloads, more threads can help hide I/O latency.

📌 Definition
  • Context switching is triggered by the OS scheduler based on thread priorities, time-slicing, and resource availability.
  • It allows multiple threads or processes to share CPU cores efficiently without starvation.
⚙️ When Context Switching Happens
  • 1. Preemption by Scheduler:
    • Each thread is assigned a time slice (quantum).
    • When a thread uses its full quantum, the OS scheduler preempts it and runs the next ready thread.
  • 2. Higher-Priority Thread Becomes Ready:
    • If a higher-priority thread becomes ready (e.g., I/O completes), the OS may switch to it immediately.
  • 3. Thread Waits or Blocks:
    • When a thread is waiting for I/O, lock, or resource, it voluntarily yields the CPU.
    • CPU switches to a runnable thread instead of idling.
  • 4. Voluntary Yield:
    • A thread can call Thread.yield() to suggest giving up CPU voluntarily.
⚡ When Context Switching Does NOT Happen
  • Thread is still within its time quantum and no higher-priority thread is ready.
  • Thread is performing uninterrupted CPU-bound computation without blocking.
  • CPU cores are idle or dedicated to a real-time process that must run without interruption.
  • Threads of the same priority continue running until preempted or blocked.
🧠 JVM / Thread Pool Perspective
  • Java threads are mapped 1:1 to OS threads, so context switching decisions are mostly handled by the OS scheduler.
  • Thread pools manage runnable tasks — when one thread finishes a task, the pool assigns another task to the same thread, potentially avoiding extra context switching.
  • For CPU-bound tasks, having threads equal to CPU cores minimizes unnecessary context switches.

  • It is avoided when threads can continue uninterrupted without starving other threads.

  • Context switching is the process of storing the state of a thread or process so that it can resume later.
  • It allows CPU to switch between multiple threads or processes efficiently.
  • In Java, context switching happens at the thread level (managed by JVM + OS scheduler).

  • Java threads are managed by OS-level threads (for modern JVMs).
  • Each thread has its own stack and program counter.
  • When a thread is paused (e.g., waiting for I/O or time slice expires), JVM saves its context (PC, registers, stack).
  • OS scheduler decides which thread runs next and restores its context.
  • Java provides Thread.yield(), sleep(), wait()/notify() to influence thread scheduling.
📌 Where It Happens
  • Context switching primarily happens in CPU cores, controlled by the OS scheduler.
  • JVM manages Java thread states: NEW → RUNNABLE → RUNNING → WAITING → BLOCKED → TERMINATED.
  • The JVM interacts with the OS for actual CPU switching.

    • Program Counter (PC)
    • CPU registers

📌 Memory Areas Involved
  • Thread Stack: Stores local variables, method call frames, and return addresses for each thread.

📌 Thread States
  • NEW: Thread object is created but start() is not called yet.
  • RUNNABLE: After start(), thread is ready to run and waiting for CPU allocation.
  • RUNNING: Thread is executing its run() method.
  • WAITING: Thread is waiting indefinitely for another thread to signal it (wait() without timeout).
  • TIMED_WAITING: Thread is waiting for a specific time (sleep(), join(timeout), wait(timeout)).
  • BLOCKED: Thread is waiting to acquire a monitor lock to enter a synchronized block/method.
  • TERMINATED: Thread has completed execution and cannot be restarted.

📌 JVM & OS Role in Thread Life Cycle
  • Thread life cycle is **not fully controlled by Java code**; it's mostly managed by the JVM + OS scheduler.
  • Java provides the API (Thread class, Runnable, ExecutorService) to create and manage threads, but actual execution depends on the OS.
  • The OS handles **CPU allocation, scheduling, and context switching** between threads.
📌 External Factors Affecting Life Cycle
  • CPU Scheduling: Determines when a RUNNABLE thread moves to RUNNING.
  • Thread Priority: JVM can hint priority, but OS ultimately decides scheduling.
  • Synchronization & Locks: BLOCKED state occurs when a thread waits for a monitor lock.
  • I/O Operations: Waiting for I/O can move a thread to WAITING or TIMED_WAITING.
  • Interrupts: External threads can call interrupt() to wake a waiting thread.
📌 Life Cycle Transitions Externally Managed
  • NEW → RUNNABLE: Java code calls start().
  • RUNNABLE → RUNNING: OS scheduler picks a thread based on CPU availability.
  • RUNNING → BLOCKED/WAITING/TIMED_WAITING: OS manages waiting for locks or I/O.
  • Any → RUNNABLE: When conditions are met (lock released, I/O done, sleep timeout), OS moves thread back to RUNNABLE.
  • RUNNING → TERMINATED: Thread completes run() method.
📌 Key Points
  • Java provides **thread APIs** to influence life cycle, but **JVM + OS actually manage execution**.
  • Thread state changes like BLOCKED, WAITING, or TIMED_WAITING are **external events-driven**, not controlled directly by the thread itself.
  • Understanding the **external management** helps in designing thread-safe and efficient multithreaded applications.

📌 Problem with Runnable and Thread
  • Manual Thread Management: Creating a new Thread for each task is **resource-heavy** and inefficient.
  • Uncontrolled Threads: You cannot easily limit the number of concurrent threads.
  • No Reusability: Once a thread completes, it cannot be restarted.
  • Complex Error Handling: Managing exceptions and results from multiple threads manually is cumbersome.
📌 How ExecutorService Solves These Problems
  • Thread Pooling: Reuses a fixed number of threads for multiple tasks, reducing creation overhead.
  • Task Submission: You submit Runnable or Callable tasks; no need to manually create threads.
  • Concurrency Control: Limits the number of threads running concurrently.
  • Future & Callable: Allows returning results or handling exceptions asynchronously.
  • Graceful Shutdown: Provides APIs to shut down thread pools safely (shutdown(), shutdownNow()).

📌 What is ExecutorService?
  • An interface in java.util.concurrent that provides a high-level API for managing threads.
  • Abstracts thread creation, scheduling, and execution from the programmer.
  • Supports thread pools to efficiently reuse threads and manage multiple tasks.
📌 How ExecutorService Helps
  • Thread Pooling: Avoids creating a new thread for each task.
  • Task Submission: Submit Runnable or Callable tasks.
  • Concurrency Control: Limits number of threads running concurrently.
  • Result Handling: Using Future allows you to get results asynchronously.
  • Graceful Shutdown: Properly close threads using shutdown() or shutdownNow().
📌 Key Methods in ExecutorService
  • submit(Runnable/Callable task): Submits a task for execution. Returns a Future for result tracking.
  • invokeAll(Collection<Callable> tasks): Executes a collection of tasks and waits for all to complete.
  • invokeAny(Collection<Callable> tasks): Executes tasks and returns result of the first successful task.
  • shutdown(): Initiates orderly shutdown; no new tasks accepted, but existing tasks complete.
  • shutdownNow(): Attempts to stop all actively executing tasks and returns a list of pending tasks.
📌 When to Use Which Method
  • submit(): When you want to run a single task or want a Future to track result.
  • invokeAll(): When you have multiple tasks and want to wait for all to finish.
  • invokeAny(): When you need the first result from multiple tasks.
  • shutdown(): Normal shutdown after submitting tasks.
  • shutdownNow(): Emergency shutdown; stops running tasks forcefully.

📌 What is Thread Interrupt?

📌 What Are wait(), notify() & notifyAll()?
  • wait(): Makes the current thread release the **monitor lock** and enter **WAITING** state until another thread calls notify() or notifyAll() on the same object.
  • notify(): Wakes up **one waiting thread** randomly that is waiting on the object’s monitor.
  • notifyAll(): Wakes up **all threads** waiting on the object’s monitor.
📌 Why These Methods Are in Object, Not Thread?
  • Every Java object has a **monitor (lock)** associated with it.
  • wait/notify/notifyAll are **monitor-based** operations, not thread operations.
  • They require the **current thread to hold the object's lock** (inside synchronized block/method).
  • Since locks are tied to **objects**, these methods belong to **Object class**, not Thread.
📌 Example: Producer-Consumer Using wait & notify

import java.util.LinkedList;
import java.util.Queue;

class ProducerConsumer {
    private final Queue queue = new LinkedList<>();
    private final int capacity = 5;

    public void produce() throws InterruptedException {
        int value = 0;
        while (true) {
            synchronized(queue) {
                while (queue.size() == capacity) {
                    queue.wait(); // wait if queue is full
                }
                queue.add(value);
                System.out.println("Produced: " + value++);
                queue.notify(); // wake up consumer
            }
            Thread.sleep(500);
        }
    }

    public void consume() throws InterruptedException {
        while (true) {
            synchronized(queue) {
                while (queue.isEmpty()) {
                    queue.wait(); // wait if queue is empty
                }
                int val = queue.poll();
                System.out.println("Consumed: " + val);
                queue.notify(); // wake up producer
            }
            Thread.sleep(500);
        }
    }
}

public class WaitNotifyDemo {
    public static void main(String[] args) {
        ProducerConsumer pc = new ProducerConsumer();
        new Thread(() -> {
            try { pc.produce(); } catch (InterruptedException e) {}
        }).start();
        new Thread(() -> {
            try { pc.consume(); } catch (InterruptedException e) {}
        }).start();
    }
}
📌 Key Points
  • Use wait() when a thread needs to pause until a condition changes.
  • Use notify() to wake **one waiting thread** or notifyAll() to wake **all waiting threads**.
  • These methods **must be called inside synchronized block/method**, otherwise IllegalMonitorStateException is thrown.
  • Helps in **thread coordination**, e.g., producer-consumer, task pipelines, or resource sharing.
📌 Why Not in Thread Class?
  • Thread class represents a **thread of execution**, not the **monitor or lock**.
  • wait/notify work on **object locks**, so placing them in Object class ensures **any object can serve as a monitor**.

📌 Key Concept
  • All threads in Java **share memory within the same process**, specifically the **heap memory**.
  • Threads have their own **stack memory** for local variables, but **object references** on the heap can be shared.
  • This enables multiple threads to **read and write to the same objects**, enabling communication or shared work.
  • Shared data can lead to **race conditions**, **visibility issues**, and **data inconsistency** if not managed properly.
📌 How Data Sharing Happens
  • Shared Objects: Threads access the same object references.
  • Static Variables: Shared across all threads of the class.
  • Collections: Shared collections can be accessed by multiple threads (need synchronization).
  • Concurrent Utilities: `ConcurrentHashMap`, `CopyOnWriteArrayList`, `BlockingQueue` provide thread-safe shared data access.

🔄 What is ForkJoinPool?

ForkJoinPool is a specialized thread pool designed for tasks that can be recursively split into smaller tasks and later joined back together. It is optimized for parallelism and allows tasks to be forked and later joined in a recursive manner.

🎯 Key Features of ForkJoinPool:
  • Uses the work-stealing algorithm where idle threads steal work from busy threads.
  • Best suited for divide-and-conquer tasks, like recursive algorithms.
  • It can dynamically adjust the number of threads based on available CPUs and workload.
📚 Example of ForkJoinPool:

import java.util.concurrent.RecursiveTask;
import java.util.concurrent.ForkJoinPool;

public class ForkJoinExample {

    // A task that calculates the sum of a range of numbers
    static class SumTask extends RecursiveTask {
        private final int[] arr;
        private final int start, end;

        public SumTask(int[] arr, int start, int end) {
            this.arr = arr;
            this.start = start;
            this.end = end;
        }

        @Override
        protected Integer compute() {
            if (end - start <= 10) { // If the task is small enough, process it sequentially
                int sum = 0;
                for (int i = start; i < end; i++) {
                    sum += arr[i];
                }
                return sum;
            } else {
                int mid = (start + end) / 2;
                SumTask task1 = new SumTask(arr, start, mid);
                SumTask task2 = new SumTask(arr, mid, end);
                
                task1.fork();  // Fork task1
                int task2Result = task2.fork().join();  // Fork and join task2
                int task1Result = task1.join();  // Join task1
                
                return task1Result + task2Result;
            }
        }
    }

    public static void main(String[] args) {
        int[] numbers = new int[100];
        for (int i = 0; i < 100; i++) {
            numbers[i] = i + 1;  // Filling array with numbers 1 to 100
        }
        
        ForkJoinPool pool = new ForkJoinPool(); // Create ForkJoinPool
        SumTask task = new SumTask(numbers, 0, numbers.length);
        int result = pool.invoke(task); // Invoke the task
        System.out.println("Sum of numbers: " + result);
    }
}
⚡ ForkJoinPool Features

The ForkJoinPool utilizes a work-stealing algorithm to balance the workload across threads. When a thread completes its task, it can "steal" tasks from other threads, ensuring efficient usage of all threads.

⚖️ When to Use ForkJoinPool
  • When you have tasks that can be split into smaller tasks (divide-and-conquer pattern).
  • When you need parallelism and want to utilize multiple processors efficiently.
  • When the task is computationally expensive and can benefit from parallel execution.
🚦 Key Considerations
  • ForkJoinPool is most effective when the tasks are recursive and independent, like in divide-and-conquer algorithms.
  • It's not ideal for IO-bound tasks, as the overhead of managing threads may negate any performance gains.
  • The pool is designed to scale efficiently with the number of available CPU cores.

🔄 What is Future in Java?

Future is an interface that represents the result of an asynchronous computation. It allows you to check if the computation is complete, wait for its completion, and retrieve the result.

🎯 Key Features of Future:
  • Provides methods like get() to wait for the result, and isDone() to check if the task is completed.
  • Does not allow you to modify the task after it's submitted.
  • Can be used with ExecutorService to execute asynchronous tasks.
📚 Example of Future:

import java.util.concurrent.*;

public class FutureExample {
    public static void main(String[] args) throws ExecutionException, InterruptedException {
        ExecutorService executor = Executors.newSingleThreadExecutor();

        Callable task = () -> {
            TimeUnit.SECONDS.sleep(2);
            return 123;
        };

        Future future = executor.submit(task); // Submitting a task for execution

        // Waiting for the task to complete and get the result
        Integer result = future.get();
        System.out.println("Task result: " + result); // Output after 2 seconds: 123

        executor.shutdown();
    }
}
⚡ What is CompletableFuture in Java?

CompletableFuture is an extension of the Future interface that allows you to manually complete the future. It provides a way to write asynchronous, non-blocking code using lambda expressions and offers more flexibility than Future.

🎯 Key Features of CompletableFuture:
  • Can be manually completed using complete() method.
  • Supports chaining of asynchronous tasks with methods like thenApply(), thenAccept(), and thenCompose().
  • Supports both synchronous and asynchronous computations, and you can combine multiple futures.
📚 Example of CompletableFuture:

import java.util.concurrent.*;

public class CompletableFutureExample {
    public static void main(String[] args) throws ExecutionException, InterruptedException {
        // Creating a CompletableFuture
        CompletableFuture future = CompletableFuture.supplyAsync(() -> {
            try {
                TimeUnit.SECONDS.sleep(2); // Simulate a task
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
            return 123;
        });

        // Applying a function after completion
        future.thenApply(result -> {
            System.out.println("Processed result: " + result * 2); // Output: 246
            return result * 2;
        });

        // Block and get the result
        Integer result = future.get(); 
        System.out.println("Final result: " + result); // Output: 123
    }
}

🎯 Key Concepts
  • Inter-thread Communication: Threads communicate using wait() and notify() methods.
  • Synchronization: Threads are synchronized using a common lock object to ensure only one thread executes at a time.
  • Alternating Execution: One thread waits for the other to finish before continuing, ensuring even and odd numbers are printed in the correct order.
📚 Example Code

class EvenOddPrinter {
    private int number = 1;
    private final int MAX = 10;
    private final Object lock = new Object();

    // Thread for printing even numbers
    public void printEven() {
        synchronized (lock) {
            while (number <= MAX) {
                if (number % 2 != 0) {
                    try {
                        lock.wait();
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }
                }
                if (number <= MAX) {
                    System.out.println("Even: " + number);
                    number++;
                }
                lock.notify();
            }
        }
    }

    // Thread for printing odd numbers
    public void printOdd() {
        synchronized (lock) {
            while (number <= MAX) {
                if (number % 2 == 0) {
                    try {
                        lock.wait();
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }
                }
                if (number <= MAX) {
                    System.out.println("Odd: " + number);
                    number++;
                }
                lock.notify();
            }
        }
    }
}

    public static void main(String[] args) {
        EvenOddPrinter printer = new EvenOddPrinter();

        // Create and start even and odd threads
        Thread evenThread = new Thread(() -> printer.printEven());
        Thread oddThread = new Thread(() -> printer.printOdd());

        evenThread.start();
        oddThread.start();
    }
}

When you use volatile or synchronized keywords in Java, they ensure that the changes made by one thread to a variable are immediately visible to all other threads. But you are right in thinking about CPU caches, which also play a crucial role in memory access and performance.

Key Points to Understand:
  • CPU Caches: Modern CPUs have cache memory (L1, L2, L3 caches) located on each CPU core. These caches store frequently accessed data to speed up operations, reducing the need to fetch data from the slower main RAM. Each core has its local cache to work with.
  • Thread and Cache: When threads run on different CPU cores, they may use their respective CPU caches for faster data access. However, this can create issues where one thread updates a variable in its local cache, and other threads are unaware of this change if they are using their cache.
  • RAM vs CPU Cache: Main memory (RAM) holds the global state of the variables that threads are working on, while the CPU caches hold copies of frequently accessed data for performance reasons. Without proper synchronization (using volatile or synchronized), the CPU caches can lead to inconsistent views of the data across different threads.
  • Effect of `volatile` and `synchronized`:
    • volatile: Guarantees that a thread reads the most recent value from RAM rather than from the cache. It also ensures that any updates made by one thread are immediately visible to all other threads.
    • synchronized: When a thread enters a synchronized block, it releases the lock and flushes changes from the CPU cache to main memory (RAM). This ensures that the updated data is visible to other threads accessing the same memory.
What Happens in Practice?
  • Without volatile or synchronized, the CPU caches might contain stale or outdated copies of variables, and different threads could be working with inconsistent data.
  • With volatile or synchronized, updates to variables are immediately flushed to main memory (RAM), ensuring that all threads see the most up-to-date values, even if they have cached copies.
Conclusion:

CPU caches optimize performance by reducing the need to access slower RAM. However, without synchronization mechanisms like volatile and synchronized, these caches can lead to inconsistent data between threads. By using these mechanisms, Java ensures that data updates are immediately reflected in RAM, making them visible to all threads regardless of their CPU cache contents.

📌 What is Main Memory?

In Java Memory Model (JMM), main memory refers to the RAM of your system — where all shared variables are stored. Every Java thread has:

  • Its own **working memory** (like a cache)
  • Shared access to the **main memory** (RAM)

📌 Thread Working Memory vs Main Memory

- Threads may read/write variables into their local working memory (cache) for faster access.
- But those changes are not immediately visible to other threads unless synchronized properly.
- Hence, Java provides tools like volatile and synchronized to ensure changes are written to and read from main memory (RAM).

📌 What Does `volatile` Do?

- Declaring a variable as volatile tells Java:
👉 "Always read/write this variable directly from/to main memory (RAM) and not from thread cache."
- It ensures **visibility** across threads but does not guarantee atomicity.

📌 What Does `synchronized` Do?

- It locks a method or block so that only one thread can access it at a time.
- Before entering a `synchronized` block:

  • Thread flushes its working memory
  • Reloads values from main memory
- After exiting the block, updates are written back to RAM so other threads see them.

📌 So What Is Being Updated in RAM?

🔁 When threads use `volatile` or `synchronized`, any updates they make to variables are:

  • Written directly to the system's RAM (main memory)
  • Visible to all other threads
This ensures **data consistency** across threads.

📌 Summary

✅ `volatile` ensures a variable is always read/written from RAM.
✅ `synchronized` ensures mutual exclusion + visibility through RAM.
✅ **Main memory = RAM**, used to coordinate shared data across threads.

Definition: Double-Checked Locking is used in the Singleton design pattern to **ensure lazy initialization** while maintaining **thread safety** and **performance efficiency**.

Why Use It?

  • Thread Safety: Ensures only one instance of the class is created in a multi-threaded environment.
  • Performance Optimization: Reduces unnecessary synchronization after the instance is created.
  • Lazy Initialization: The instance is created only when needed.

Implementation:

class Singleton {
    private static volatile Singleton instance;

    private Singleton() { } // Private constructor

    public static Singleton getInstance() {
        if (instance == null) {  // First check (no locking)
            synchronized (Singleton.class) {  // Synchronize block
                if (instance == null) {  // Second check (with locking)
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

How It Works:

  • First Check: If `instance` is **null**, only then acquire the lock.

  • Second Check: **Prevents multiple instantiations** when multiple threads are waiting.
  • volatile Keyword: Ensures visibility of changes across threads.

  • ✅ Ensures **only one instance** is created.
  • ✅ **Thread-safe** without performance bottlenecks.
  • ✅ **Lazy initialization** saves memory.

  • ❌ Requires `volatile`, which is only supported in Java 5+.

📌 Context Switching
  • Yes, **context switching happens** when multiple threads are active and CPU time is shared.
  • The OS scheduler switches between Tomcat threads when:
    • Thread is waiting (I/O, sleep, blocking)
    • CPU is executing multiple threads concurrently (multi-core helps parallelism)

  1. HTTP request arrives at Tomcat.
  2. Tomcat assigns the request to a **worker thread** from the pool.
  3. Worker thread executes the **Servlet or JSP code**.
  4. If the thread is blocked (I/O), OS may **context switch** to another thread.
  5. Once processing completes, the response is sent back and thread returns to pool.
📌 Key Points
  • Thread pool avoids creating/destroying threads for every request → better performance.
  • One thread can handle **one request at a time**. Multiple requests → multiple threads.
  • Blocking operations can trigger **context switching**, but thread pool size limits maximum concurrency.
  • Properly tuning **maxThreads** prevents thread exhaustion or server overload.

  • These defaults are used **if you do not override** them in `application.properties` or `application.yml`.
  • Default values are **sufficient for most small/medium applications**, but high-traffic applications may need tuning.
  • Setting these values properly helps **avoid request queuing, thread starvation, or server overload**.
📌 Example – Default Thread Usage
  • If 50 HTTP requests arrive at the same time:
    • Tomcat uses **50 threads from the pool** to process them.
    • Threads beyond `maxThreads` are queued in `acceptCount`.

📌 What is JMM?
  • Java Memory Model defines how **threads interact through memory** and how changes made by one thread become visible to others.
  • It is a **specification** in Java that ensures **visibility, atomicity, and ordering guarantees** in multithreaded programs.
  • JMM is **not a physical memory model**; it defines **rules for compilers, JVM, and hardware** to behave consistently.
📌 Why JMM Exists
  • To solve **memory consistency errors**, where threads may see stale or inconsistent data.
  • To provide a **happens-before relationship** ensuring correct execution order of threads.
  • To allow **safe synchronization** and visibility of shared variables across threads.
📌 Key Concepts of JMM
  • Main Memory: Shared memory accessible by all threads (heap).
  • Working Memory (Thread Cache): Each thread may keep copies of variables locally for performance.
  • Happens-Before: If one action **happens-before** another, the first is visible to the second.
  • Volatile: Ensures **visibility** of updates across threads and prevents instruction reordering for that variable.
  • Synchronized: Provides **mutual exclusion** and also **memory visibility** guarantees.
📌 How JMM Works
  • Each thread can **cache variables in its working memory**.
  • Without proper synchronization, changes made by one thread **may not be visible** to others.
  • Using **synchronized blocks, locks, or volatile**, threads **flush changes to main memory** and **read latest values**.
  • JMM ensures that **instructions are executed in a predictable order** according to Java semantics.
📌 Example – Visibility Issue

class Shared {
    int value = 0;
}

Shared shared = new Shared();

Thread t1 = new Thread(() -> { shared.value = 10; });
Thread t2 = new Thread(() -> {
    while(shared.value == 0) {
        // may loop forever if t1 update not visible due to caching
    }
});
**Fix with volatile:** 

class Shared {
    volatile int value = 0;
}
---
📌 Key Points
  • JMM ensures **thread safety and predictable behavior** across different platforms and CPUs.
  • All **synchronized blocks, locks, and volatile variables** follow JMM rules for visibility and ordering.
  • Without JMM understanding, multithreaded code may have **subtle bugs like stale reads or race conditions**.
📌 Analogy
  • Main Memory = Central office shared by all employees (threads).
  • Working Memory = Each employee’s personal notebook (thread cache).
  • Volatile / synchronized = Employee writes in central office so everyone sees the update.

📌 What is CompletableFuture?
  • `CompletableFuture` is an extension of `Future` introduced in Java 8 in the `java.util.concurrent` package.
  • It represents a **future result of an asynchronous computation** that can be **manually completed** or **composed with other futures**.
  • Supports **non-blocking, asynchronous programming**, unlike regular `Future`.
📌 Key Differences: Future vs CompletableFuture
  • Future: Blocks when calling `get()`, cannot chain tasks, cannot manually complete, no easy async composition.
  • CompletableFuture: Non-blocking, supports callbacks (`thenApply`, `thenAccept`), can combine multiple futures, can be manually completed.
📌 Uses of CompletableFuture
  • Perform **asynchronous computations** without blocking the main thread.
  • Chain multiple tasks **sequentially or in parallel**.
  • Handle **exceptionally** in asynchronous pipelines.
  • Combine results of **multiple asynchronous tasks**.
📌 Commonly Used Methods
  • runAsync(Runnable): Run async task without result.
  • supplyAsync(Supplier): Run async task with result.
  • thenApply(Function): Transform result asynchronously.
  • thenAccept(Consumer): Consume result asynchronously without returning a value.
  • thenRun(Runnable): Run action after previous stage completes (no input or output).
  • thenCombine(CompletableFuture, BiFunction): Combine two futures’ results.
  • thenCompose(Function): Chain dependent async tasks.
  • exceptionally(Function): Handle exceptions asynchronously.
  • allOf(CompletableFuture…): Wait for all futures to complete.
  • anyOf(CompletableFuture…): Wait for any future to complete.
  • complete(value): Manually complete a CompletableFuture.
  • join(): Like `get()`, but throws unchecked exceptions.
📌 Example

import java.util.concurrent.*;

public class CompletableFutureDemo {
    public static void main(String[] args) {
        CompletableFuture future = CompletableFuture.supplyAsync(() -> {
            System.out.println(Thread.currentThread().getName() + " running task");
            return 10;
        }).thenApply(result -> result * 2)
          .thenApply(result -> result + 5);

        System.out.println("Result: " + future.join()); // 25
    }
}
📌 Advantages
  • Non-blocking and asynchronous computation support.
  • Easy to **chain, compose, and combine multiple async tasks**.
  • Better exception handling with `exceptionally`.
  • Can manually complete a future using `complete()`.
  • Integrates well with **ExecutorService** for custom thread pools.
📌 Disadvantages
  • More complex API compared to simple `Future` or `Runnable`.
  • Debugging asynchronous pipelines can be harder.
  • Improper chaining may lead to **nested callbacks** (callback hell).
  • Not ideal for very simple one-off tasks where Future is sufficient.
📌 Analogy
  • Future = A ticket for your order → wait in line until it's ready (blocking).
  • CompletableFuture = A smart ticket → you can continue shopping and **get notifications** when your order is ready, chain more actions, or combine with friends’ orders.

📌 Java Multithreading & Concurrency
  • Thread creation: Extend Thread or implement Runnable / Callable.
  • Thread lifecycle: New → Runnable → Running → Waiting/Blocked → Terminated.
  • Thread management: Context switching happens via OS when threads compete for CPU.
  • Thread safety: Use synchronized, volatile, locks, Atomic classes to prevent race conditions.
  • Concurrency issues: Deadlock, Starvation, Livelock, Memory Consistency Errors.
  • wait vs sleep: wait releases lock, sleep does not; wait used in inter-thread communication.
  • ExecutorService: Provides thread pool management, submit() returns Future, execute() does not.
  • Future: Represents result of async computation; blocks on get().
  • CompletableFuture: Non-blocking, supports chaining, combining, and exception handling; can be completed manually.
  • Atomic classes: Provide lock-free thread-safe operations (AtomicInteger, AtomicReference, etc.).
  • JMM: Ensures memory visibility, ordering, and atomicity; synchronized and volatile enforce happens-before relationships.
📌 Spring Boot Threading (Tomcat)
  • Embedded Tomcat uses a thread pool to handle HTTP requests.
  • Each request = 1 thread from pool; maxThreads defaults to 200, minSpareThreads defaults to 10.
  • Thread pool can be configured via application.properties / application.yml or Java code (TomcatServletWebServerFactory).
  • Context switching occurs if threads are blocked (I/O, DB) or multiple threads compete for CPU.
  • Proper tuning avoids thread starvation or server overload.
📌 Spring @Transactional Internals
  • @Transactional uses **AOP proxy** (JDK dynamic or CGLIB) to wrap target method.
  • Proxy uses **PlatformTransactionManager** (DataSourceTransactionManager or JpaTransactionManager) to start, commit, or rollback transactions.
  • SQL queries are generated either by **JPA provider (Hibernate)**, repository methods, @Query annotations, or developer-written SQL.
  • Transaction boundaries ensure **ACID** properties; rollback on unchecked exceptions by default.
  • Calling @Transactional method internally in same class does not trigger proxy → transactions won’t work.
📌 Reflection in Spring
  • Reflection allows **runtime inspection and manipulation of classes, methods, fields, and constructors**.
  • Spring uses reflection for:
    • Dependency Injection (setter/constructor injection)
    • Annotation scanning (@Autowired, @Service, @Controller)
    • Proxying methods in AOP
    • Dynamic controller method invocation in Spring MVC
  • Reflection example: 
    
Class<?> clazz = UserService.class;
Object obj = clazz.getDeclaredConstructor().newInstance();
Field field = clazz.getDeclaredField("userRepository");
field.setAccessible(true);
field.set(obj, new UserRepository());
  • Pros: Dynamic object creation, annotation processing, automation.
  • Cons: Performance overhead, bypasses compile-time checks, harder to debug.
