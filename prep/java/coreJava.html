1️⃣ JVM Memory – Big Picture

JVM Memory is divided into:

  • Heap Memory        (Shared)
  • Stack Memory       (Per Thread)
  • Method Area        (Metaspace)
  • PC Register        (Per Thread)
  • Native Method Stack

Interview Line:
  ✔ Heap is shared, Stack is thread-specific

2️⃣ Heap Memory (Object Storage)

What is stored:
  • Objects
  • Instance variables
  • Arrays

Heap is divided into:
  Young Generation:
    • Eden
    • Survivor (S0, S1)

  Old Generation:
    • Long-lived objects

Flow:
  • Objects created in Eden
  • Minor GC moves objects to Survivor
  • Surviving objects promoted to Old Gen

Interview Line:
  ✔ Most objects die young (Weak Generational Hypothesis)

3️⃣ Stack Memory (Method Execution)

What Stack Stores:
  • Method calls
  • Local variables
  • Reference variables
  • Return addresses

Key Points:
  • Each thread has its own stack
  • Stack frame created per method call
  • Stack memory is fast

Error:
  • StackOverflowError → Deep recursion

Interview Line:
  ✔ Stack memory is automatically freed on method exit

4️⃣ Method Area (Metaspace)

What is stored:
  • Class metadata
  • Method bytecode
  • Static variables
  • Runtime constant pool

Java 8+:
  • PermGen removed
  • Metaspace introduced
  • Uses native memory

Error:
  • Metaspace OutOfMemoryError

Interview Line:
  ✔ Metaspace grows dynamically by default

5️⃣ PC Register

Purpose:
  • Stores address of current instruction

Key Points:
  • One PC Register per thread
  • Helps JVM resume execution after context switch

Interview Line:
  ✔ PC Register enables thread scheduling

6️⃣ Native Method Stack

Purpose:
  • Executes native (JNI) methods
  • Uses C/C++ stack

Example:

1️⃣ Object Lifecycle in JVM (Very Deep)

Step-by-Step Object Lifecycle:

1. Class Loading
   • ClassLoader loads .class into Metaspace

2. Object Creation
   • new keyword requests memory
   • Memory allocated in Eden (Young Gen)

3. Initialization
   • Constructor executes
   • Reference stored in Stack
   • Object lives in Heap

4. Object Usage
   • Referenced by stack / heap objects

5. Object Becomes Unreachable
   • Reference removed / goes out of scope
   • Object becomes eligible for GC (NOT immediately removed)

6. Garbage Collection
   • Minor GC → Young Gen cleanup
   • Major GC → Old Gen cleanup

7. Memory Reclamation
   • Heap space freed
   • Memory reused

Interview Line:
  ✔ Object is eligible for GC, not immediately deleted

2️⃣ Memory Leak vs Memory Overflow (Very Important)

Memory Leak:
  • Objects are NOT used
  • But still referenced
  • GC cannot clean them

Memory Overflow:
  • JVM cannot allocate more memory
  • Heap / Metaspace exhausted

📊 Comparison Table

Memory Leak                     | Memory Overflow
--------------------------------|-------------------------------
Objects unreachable logically   | Memory exhausted physically
GC cannot collect               | GC tries but fails
Slow performance                | Application crash
Long-term issue                 | Immediate failure

🔎 Real Causes

Memory Leak Causes:
  • Static collections
  • ThreadLocal not removed
  • Listeners not deregistered
  • Caches without eviction

Memory Overflow Causes:
  • Huge object allocation
  • Infinite loops adding objects
  • Small heap size

1️⃣ protected Access Modifier – Deep Dive (Interview Favorite)

✔ Other Package – Via Inheritance ONLY
