Mix Of

📌 Core Idea
  • Library: You call it. You stay in control. Pick and choose functions/classes when you need them.
  • Framework: It calls you. It owns the app flow and invokes your code at the right time (Inversion of Control).
🔁 Inversion of Control (IoC) — micro example
// Library style (YOU control flow)
import _ from "lodash";
const arr = [1,3,2];
const sorted = _.sortBy(arr); // you call the library when you want

// Framework style (FRAMEWORK controls flow)
import express from "express";
const app = express();
app.get("/hello", (req, res) => res.send("Hi")); // Express calls YOUR handler on a request
app.listen(3000); // framework runs the loop and invokes you

🧰 When to pick what?
  • Use a library when you need a specific capability (e.g., state mgmt, charts, date/time), and you want to keep architectural freedom.
  • Use a framework when you want conventions, batteries-included tooling, and a consistent structure for teams and scale.
📝 Quick heuristics
  • Ask: “Who calls whom?” → If the tool calls your code, it’s a framework.
  • Prototype/small feature → library; Large app/team/onboarding → framework.
  • Need to swap pieces easily → library; Need integrated ecosystem → framework.
🏁 TL;DR
  • Library = toolbox (you’re the architect).
  • Framework = house blueprint (follow the plan; it orchestrates).
  • Choose based on control vs convention, team size, and project complexity.

Watch Optimistic and Pessimistic Locking On Youtube

Problem: Prevent lost updates when many requests read→modify→write the same rows. JPA offers two families of locks:

  • Optimistic → detect conflicts at commit using a @Version column, then retry.
  • Pessimistic → prevent conflicts by acquiring database locks up front (e.g., SELECT ... FOR UPDATE).
🔒 Optimistic Locking — version check, fail fast & retry
  • How it works: add a @Version field. JPA includes the version in UPDATE’s WHERE clause. If 0 rows are updated → another tx changed it → OptimisticLockException.
  • When to use: read-mostly data, short transactions, low to moderate contention, horizontally scaled services.
  • Lock modes: OPTIMISTIC (check at commit), OPTIMISTIC_FORCE_INCREMENT (also bumps version to “claim” the row).
  • Pros: no DB blocking, best throughput.
  • Cons: retries under contention; long transactions increase conflict odds.

Entity with version & service retry (inventory decrement)

@Entity
class Product {
  @Id Long id;
  @Version Long version;       // int/long/short/Timestamp supported
  int stock;
  // getters/setters
}

public interface ProductRepo extends JpaRepository<Product, Long> { }

@Service
class OrderService {
  private final ProductRepo repo;
  OrderService(ProductRepo repo){ this.repo = repo; }

  @Transactional
  public void reserve(Long id, int qty) {
    int attempts = 0;
    while (true) {
      try {
        Product p = repo.findById(id).orElseThrow();
        if (p.getStock() < qty) throw new IllegalStateException("Insufficient stock");
        p.setStock(p.getStock() - qty);
        repo.saveAndFlush(p);              // may throw OptimisticLockException
        return;                            // success
      } catch (ObjectOptimisticLockingFailureException | OptimisticLockException e) {
        if (++attempts > 3) throw e;       // give up after a few tries
        try { Thread.sleep(10L * attempts); } catch (InterruptedException ie) { Thread.currentThread().interrupt(); }
      }
    }
  }
}

public interface ProductRepo extends JpaRepository<Product, Long> {

Gotchas: bulk JPQL/SQL updates bypass the 1st-level cache & default version checks; either include the version in the WHERE or re-read entities after bulk ops.

🧱 Pessimistic Locking — block others, serialize the hotspot
  • How it works: JPA translates lock modes to DB row/table locks: PESSIMISTIC_READ (shared), PESSIMISTIC_WRITE (exclusive), PESSIMISTIC_FORCE_INCREMENT (exclusive + version bump). Under the hood: SELECT ... FOR UPDATE[/NOWAIT/SKIP LOCKED] depending on DB.
  • When to use: hot rows with frequent conflicting updates (wallet balance, single inventory counter), business rule “never oversell”, or when retries are too expensive.
  • Pros: no lost updates, simpler logic (no retries).
  • Cons: lower concurrency & risk of deadlocks; requires careful timeouts.

Repository method that locks the row (and times out if busy)

public interface ProductRepo extends JpaRepository<Product, Long> {

  @Lock(LockModeType.PESSIMISTIC_WRITE)
  @Query("select p from Product p where p.id = :id")
  @QueryHints({
    @QueryHint(name = "jakarta.persistence.lock.timeout", value = "2000") // 2s (JPA standard)
    // Hibernate vendor hint: @QueryHint(name = "org.hibernate.lock.timeout", value = "2000")
  })
  Product lockForUpdate(@Param("id") Long id);
}

@Service
class OrderServicePess {
  @Transactional
  public void reserve(Long id, int qty) {
    Product p = repo.lockForUpdate(id);     // DB-level lock held until commit/rollback
    if (p.getStock() < qty) throw new IllegalStateException("Insufficient stock");
    p.setStock(p.getStock() - qty);
  }
}

Timeout semantics: value is milliseconds; 0 = NOWAIT (fail fast), positive waits up to N ms, negative/infinite depends on provider (often -1).

Deadlocks: always acquire locks in a consistent order; keep transactions short.

🧭 Choosing the right strategy
  • Default to Optimistic for most CRUD/business flows; add a small retry with backoff.
  • Use Pessimistic on hot, highly contended rows (e.g., decrementing a single inventory bucket, ledger rows) or when business rules forbid retries.
  • Hybrid: start optimistic; switch to pessimistic for a specific code path once contention crosses a threshold (observed via OptimisticLockException rate).
⚠️ Pitfalls & tips
  • Bulk updates (@Modifying JPQL/SQL) don’t respect the 1st-level cache & version by default — reload affected entities or include version checks.
  • Long transactions increase conflict probability (optimistic) and lock hold time (pessimistic) — keep them short.
  • Isolation level: locking is orthogonal; stick to default READ COMMITTED unless you have specific reasons.
  • Second-level cache: cache mostly read-only/immutable data; write-heavy entities with locks don’t cache well.
  • APIs: expose the version field in write DTOs if clients do read-modify-write; reject mismatched versions with 409 Conflict.
📝 Summary
  • Optimistic = detect & retry using @Version; best throughput for typical workloads.
  • Pessimistic = block others with DB locks; use on hotspots & strict invariants (set timeouts!).
  • For counters/inventory, consider a single atomic UPDATE pattern — often faster and simpler than either lock.

Problem: Given intervals, find the minimum number of meeting rooms required.

int minMeetingRooms(int[][] intervals) {
  Arrays.sort(intervals, Comparator.comparingInt(a -> a[0]));
  PriorityQueue pq = new PriorityQueue<>(); // stores end times
  for (int[] m : intervals) {
    if (!pq.isEmpty() && pq.peek() <= m[0]) pq.poll();
    pq.offer(m[1]);
  }
  return pq.size();
}
// Input: [[0,30],[5,10],[15,20]] → Output: 2

  int[] a; int lo, hi; static final int TH = 1_000;
  protected Long compute() {

    return r + left.join();
  }
}

boolean isBalanced(TreeNode root) { return height(root) != -1; }
int height(TreeNode n){
  if (n==null) return 0;
  int L = height(n.l); if (L==-1) return -1;
  int R = height(n.r); if (R==-1) return -1;
  if (Math.abs(L-R) > 1) return -1;
  return Math.max(L,R)+1;
}

String longestPalindrome(String s){
  int n=s.length(), start=0, len=0;
  for(int i=0;i<n;i++){
    int[] a = expand(s,i,i), b = expand(s,i,i+1);
    if (a[1]-a[0]+1 > len) { start=a[0]; len=a[1]-a[0]+1; }
    if (b[1]-b[0]+1 > len) { start=b[0]; len=b[1]-b[0]+1; }
  }
  return s.substring(start,start+len);
}
int[] expand(String s,int l,int r){
  while(l>=0 && r<s.length() && s.charAt(l)==s.charAt(r)){ l--; r++; }
  return new int[]{l+1,r-1};
}

  if (root==null) return res;
  Queue<TreeNode> q = new ArrayDeque<>();
  q.add(root);
  while(!q.isEmpty()){

      TreeNode n=q.poll(); level.add(n.val);

🔹 HashMap is a key-value data structure based on hashing. It provides O(1) average time complexity for insert, search, and delete operations.

📌 HashMap Data Structure:

  • Internally, it is an **array of Node** (buckets).
  • Each bucket stores **a linked list** (before Java 8) or **a balanced tree** (after Java 8, when collisions exceed a threshold).

🔹 Important Components:

  • Capacity: Initial size of the HashMap (default: 16).
  • Load Factor: Default 0.75 (resizing occurs when 75% of the map is full).
  • Threshold: `capacity * load factor`, determines when resizing happens.

🔹 Internal Working of `put(K, V)`:

  1. Computes hashCode() of the key.
  2. Uses (hashCode % capacity) to find the index.
  3. If bucket is empty, stores the new entry.
  4. If a collision occurs, it stores the entry as:
    • 🔹 **Linked List** (before Java 8).
    • 🔹 **Balanced Tree (Red-Black Tree)** (after Java 8, if the chain length > 8).
  5. Resizes the HashMap if the threshold is reached.

🔹 Example of HashMap Implementation:


        import java.util.HashMap;

        public class HashMapExample {
            public static void main(String[] args) {
                HashMap map = new HashMap<>();
                map.put("Alice", 25);
                map.put("Bob", 30);
                map.put("Charlie", 35);
                
                System.out.println("Age of Bob: " + map.get("Bob")); // 30
            }
        }

🔹 How `get(K)` Works?

  • Computes the **hashCode()** of the key.
  • Finds the bucket using `(hashCode % capacity)`.
  • Traverses the linked list or tree to find the key.
  • Returns the value if found, else returns `null`.

🔹 HashMap Performance Optimization:

  • Use a good hash function to minimize collisions.
  • Set an **optimal initial capacity** to reduce resizing overhead.
  • Keep **load factor at 0.75** for the best trade-off between performance and memory usage.

🔹 What is Circular Dependency?

🔄 A **circular dependency** occurs when two or more beans depend on each other, causing a loop.

📌 Example of Circular Dependency


      @Component
      public class A {
          private final B b;

          @Autowired
          public A(B b) {
              this.b = b;
          }
      }

      @Component
      public class B {
          private final A a;

          @Autowired
          public B(A a) {
              this.a = a;
          }
      }

🛑 **Problem:** When Spring tries to instantiate A, it needs B, which again needs A, causing a cycle.

🔹 How to Fix Circular Dependency?

📌 1️⃣ Use @Lazy Annotation

🔄 Spring will **delay bean initialization** until it's needed.


      @Component
      public class A {
          private final B b;

          @Autowired
          public A(@Lazy B b) {
              this.b = b;
          }
      }

📌 2️⃣ Use Setter Injection Instead of Constructor Injection

🔄 Spring will first instantiate the beans and then set dependencies.


      @Component
      public class A {
          private B b;

          @Autowired
          public void setB(B b) {
              this.b = b;
          }
      }

📌 3️⃣ Use ObjectFactory or Provider from javax.inject

🔄 **Lazily loads dependencies** only when required.


      @Component
      public class A {
          private final Provider bProvider;

          @Autowired
          public A(Provider bProvider) {
              this.bProvider = bProvider;
          }

          public void someMethod() {
              B b = bProvider.get(); // Gets B when needed
          }
      }

📌 4️⃣ Refactor Code to Break Circular Dependency

🔄 **Introduce a third class** to manage dependencies.


      @Component
      public class Mediator {
          private final A a;
          private final B b;

          @Autowired
          public Mediator(A a, B b) {
              this.a = a;
              this.b = b;
          }
      }

✅ Summary

  • ✔ Circular dependency happens when two beans depend on each other.
  • ✔ Solutions include **@Lazy, setter injection, Provider, and refactoring code**.
  • ✔ The best practice is to **avoid circular dependencies** by **designing components properly**.

**Inter-thread communication** in Java is a mechanism that allows synchronized threads to communicate with each other. It helps avoid busy waiting and improves performance.

1️⃣ **Methods for Inter-Thread Communication**

  • wait() - Causes the current thread to wait until another thread notifies it.
  • notify() - Wakes up a single thread waiting on the same object's monitor.
  • notifyAll() - Wakes up all threads waiting on the same object's monitor.

2️⃣ **Example of Inter-Thread Communication using wait() & notify()**


class SharedResource {
    private int data;
    private boolean available = false;

    public synchronized void produce(int value) {
        while (available) { 
            try { wait(); } catch (InterruptedException e) { e.printStackTrace(); }
        }
        data = value;
        System.out.println("Produced: " + data);
        available = true;
        notify();  // Notify consumer
    }

    public synchronized void consume() {
        while (!available) { 
            try { wait(); } catch (InterruptedException e) { e.printStackTrace(); }
        }
        System.out.println("Consumed: " + data);
        available = false;
        notify(); // Notify producer
    }
}

class Producer extends Thread {
    SharedResource resource;
    Producer(SharedResource resource) { this.resource = resource; }

    public void run() {
        for (int i = 1; i <= 5; i++) {
            resource.produce(i);
        }
    }
}

class Consumer extends Thread {
    SharedResource resource;
    Consumer(SharedResource resource) { this.resource = resource; }

    public void run() {
        for (int i = 1; i <= 5; i++) {
            resource.consume();
        }
    }
}

public class InterThreadCommunicationExample {
    public static void main(String[] args) {
        SharedResource resource = new SharedResource();
        new Producer(resource).start();
        new Consumer(resource).start();
    }
}

3️⃣ **How it Works?**

  • The **Producer** thread produces data and then calls `notify()` to wake up the **Consumer**.
  • The **Consumer** thread waits (`wait()`) until new data is available and then processes it.
  • After consuming, it calls `notify()` to wake up the **Producer** again.

✅ Best Practices: Always call `wait()`, `notify()`, and `notifyAll()` inside a synchronized block to avoid race conditions.

import org.hibernate.engine.spi.SharedSessionContractImplementor;
import org.hibernate.id.IdentifierGenerator;
import java.io.Serializable;
import java.time.Year;
import java.util.Random;

public class CustomIdGenerator implements IdentifierGenerator {
    @Override
    public Serializable generate(SharedSessionContractImplementor session, Object object) {
        String year = String.valueOf(Year.now().getValue());
        String randomLetters = generateRandomLetters(4);
        String randomNumbers = String.valueOf(1000 + new Random().nextInt(9000));
        String lastLetter = generateRandomLetters(1);

            result.append(alphabet.charAt(random.nextInt(alphabet.length())));

PermGen vs Metaspace in Java:

  • PermGen (Permanent Generation): - Used before Java 8 to store **class metadata**, method details, and interned strings. - Had a **fixed max size** (`-XX:MaxPermSize`), leading to OutOfMemoryError: PermGen Space.
  • Metaspace: - Introduced in Java 8 to **replace PermGen**. - Uses **native memory** instead of JVM heap, so it **grows dynamically**. - Controlled via -XX:MaxMetaspaceSize (optional limit).

Key Differences:

Feature PermGen (Java 7 & Before) Metaspace (Java 8+)
Storage JVM Heap (Fixed) Native Memory (Dynamic)
Size Limit Limited (-XX:MaxPermSize) Unlimited (unless restricted with -XX:MaxMetaspaceSize)
OutOfMemoryError Frequent if full Less common
Performance Slower due to heap constraints Faster due to native memory usage

Conclusion:

  • PermGen was removed in Java 8 because it caused memory limitations.
  • Metaspace **uses native memory**, making it more flexible and efficient.
  • To prevent excessive growth, you can **limit Metaspace manually**.

Metaspace is managed by both the JVM and the OS. Below are the key components responsible for its control:

  • JVM's Memory Manager: Requests memory from the OS and manages allocation/deallocation based on class loading/unloading.
  • OS Memory Management: Since Metaspace is outside the heap, the OS manages its actual allocation.
  • Class Loader & Garbage Collector: JVM removes unused class metadata when classes become unreferenced.

How to Control Metaspace Growth?


      # Set a max limit for Metaspace
      java -XX:MaxMetaspaceSize=256m -jar myapp.jar

      # Enable garbage collection for class unloading
      java -XX:+UseG1GC -XX:+ClassUnloadingWithConcurrentMarkSweep

Key Takeaways:

  • ✅ JVM requests and manages Metaspace.
  • ✅ OS provides the required native memory.
  • ✅ Application Code can impact Metaspace by controlling class loading/unloading.

No, Metaspace does not store all memory areas like the heap, stack, or method area. Here’s how it fits in the JVM memory model:

📌 What does Metaspace store?
  • Class Metadata: Information about loaded classes, including methods, fields, and bytecode.
  • Runtime Constant Pool: Stores constants from class files (e.g., string literals).
  • Class Method Data: Metadata about methods but not the actual method code.
  • Reflection Objects: Metadata for reflection-based operations.
❌ What Metaspace does NOT store?
  • Heap (Objects & Data): Stored in the Young & Old Generation of Heap.
  • Stack (Threads' Execution Context): Stored in the JVM Stack Memory.
  • Method Code Execution: Stored in Code Cache (for JIT-compiled code).
📝 JVM Memory Breakdown
  • Heap: Stores objects & data.
  • Stack: Stores method call frames & local variables.
  • Metaspace: Stores class metadata.
  • Code Cache: Stores compiled machine code from JIT.
  • Direct Memory: Used by NIO buffers.
🏆 Example: Configuring Metaspace in JVM

        java -XX:MaxMetaspaceSize=256m -jar myapp.jar

This limits the maximum size Metaspace can grow.

✅ Conclusion

Metaspace only handles class metadata, while the heap, stack, and method area are managed separately by the JVM.

  @Override protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
      throws IOException, ServletException {
