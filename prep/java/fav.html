Narahari's Favorites

Key truth: Java is 100% pass-by-value. Methods receive a copy of the caller’s argument.

  • Primitives: copies of the actual values.
  • Objects: copies of the reference values (pointers). Both variables point to the same object, but the parameter is a different reference variable.
Primitives: the value is copied
void bump(int x) { x++; }   // 'x' is a copy
int a = 10;
bump(a);
System.out.println(a);       // 10 (unchanged)
Objects: the reference is copied (mutations are visible)
class Dog { String name; Dog(String n){ this.name = n; } }

void rename(Dog d) { d.name = "Bruno"; } // mutate via copied reference

Dog dog = new Dog("Rocky");
rename(dog);
System.out.println(dog.name);             // Bruno (changed)
Reassigning the parameter doesn’t affect the caller
void reassign(Dog d) { d = new Dog("Max"); } // only local reference changes

Dog dog = new Dog("Rocky");
reassign(dog);
System.out.println(dog.name);             // Rocky (unchanged)

Because only the reference value was passed; re-pointing the local parameter doesn’t re-point the caller’s variable.

Classic gotcha: swap doesn’t work with plain references
void swap(Dog a, Dog b) { Dog t = a; a = b; b = t; }

Dog d1 = new Dog("A"), d2 = new Dog("B");
swap(d1, d2);
System.out.println(d1.name + ", " + d2.name); // A, B (unchanged)

Swap using a mutable holder

class Box<T> { T v; Box(T v){ this.v=v; } }
void swapBoxes(Box<Dog> a, Box<Dog> b){ Dog t=a.v; a.v=b.v; b.v=t; }

Box<Dog> b1 = new Box<>(new Dog("A"));
Box<Dog> b2 = new Box<>(new Dog("B"));
swapBoxes(b1, b2);
System.out.println(b1.v.name + ", " + b2.v.name); // B, A
Immutables vs mutables
  • Immutable: String, boxed primitives, BigDecimal.
  • Mutable: arrays and most POJOs — mutating through the parameter affects the same underlying object.

Immutable example

void addBang(String s) { s = s + "!"; } // new String; local reassign only
String msg = "hi";
addBang(msg);
System.out.println(msg);                 // "hi"

Array (mutable) example

void incFirst(int[] a) { a[0]++; }
int[] arr = {1,2,3};
incFirst(arr);
System.out.println(java.util.Arrays.toString(arr)); // [2, 2, 3]
Wrappers & autoboxing pitfall
void inc(Integer x) { x = x + 1; } // creates a new Integer; local reassign only
Integer n = 5;
inc(n);
System.out.println(n);              // 5

Key idea: static members belong to the class, not instances. They are shared across all threads within the same ClassLoader. Thread-safety is not automatic—it depends on how you access/modify shared state.

1) Class initialization & visibility
  • One-time init: Class initialization (<clinit>) is synchronized by the JVM—only one thread runs it; others block.
  • Final fields: Properly set static final fields are safely published to all threads after init.
  • ClassLoader scope: Each ClassLoader has its own copy of static fields (important in app servers, plugins).

Example: safely initialized constant

public class Conf {
  public static final int PORT = 8080;  // visible to all threads after class init
}
2) Static mutable state = shared state
  • Multiple threads reading/writing the same static field can race without synchronization.
  • Use volatile (visibility/order) or atomic types / locks for compound actions.
  • Prefer immutable objects published via static final when possible.

Wrong: non-atomic static counter

public class Metrics {
  public static int hits = 0;
  public static void inc() { hits++; }   // data race: read-modify-write
}

Right: atomic or synchronized

import java.util.concurrent.atomic.AtomicLong;
public class Metrics {
  private static final AtomicLong HITS = new AtomicLong();
  public static long inc() { return HITS.incrementAndGet(); }       // lock-free
  public static long get() { return HITS.get(); }
}
// or
public class Metrics2 {
  private static long hits;
  public static synchronized void inc() { hits++; }                 // serialized
  public static synchronized long get() { return hits; }
}
3) Static methods & thread-safety
  • Static method ≠ thread-safe by itself. It is safe iff it only uses local variables / thread-safe collaborators.
  • Accessing mutable static fields inside a static method requires proper synchronization/atomics.

Pure function (thread-safe) vs shared-state (needs care)

public class MathUtil {
  public static int sum(int a, int b) { return a + b; }    // thread-safe (no shared state)
}

public class Cache {
  private static final java.util.Map<String,String> M = new java.util.HashMap<>();
  public static String get(String k) { return M.get(k); }  // NOT thread-safe
}

Fix with concurrent collections

import java.util.concurrent.ConcurrentHashMap;
public class CacheSafe {
  private static final ConcurrentHashMap<String,String> M = new ConcurrentHashMap<>();
  public static String get(String k) { return M.get(k); }
  public static void put(String k, String v) { M.put(k, v); }
}
4) Safe publication & singletons
  • Publish shared objects via static final, or use Initialization-on-demand Holder.
  • For lazy init with double-checked locking, the reference must be volatile.

Holder idiom (lazy & thread-safe)

public class Service {
  private Service() {}
  private static class Holder { static final Service INSTANCE = new Service(); }
  public static Service getInstance() { return Holder.INSTANCE; }
}

Double-checked locking (correct form)

public class RepoProvider {
  private static volatile Repo instance;
  public static Repo get() {
    Repo r = instance;
    if (r == null) {
      synchronized (RepoProvider.class) {
        r = instance;
        if (r == null) instance = r = new Repo();
      }
    }
    return r;
  }
}
5) Thread-local vs static
  • ThreadLocal<T> gives each thread its own copy—useful for formatters, temp buffers.
  • Avoid static ThreadLocal leaks in containers; clear on thread end or use frameworks that manage lifecycle.
private static final ThreadLocal<java.text.SimpleDateFormat> FMT =
  ThreadLocal.withInitial(() -> new java.text.SimpleDateFormat(\"yyyy-MM-dd\"));
6) Pitfalls to watch
  • Memory leaks: long-lived statics holding big caches/listeners prevent GC.
  • Circular init: static initializers that depend on other classes’ statics can deadlock or see default values.
  • Testing: statics keep state between tests; reset hooks or design for injection.

Goal: confirm it’s a leak (retained memory trends upward and never returns), localize the retained objects & reference chains, mitigate fast, and produce a root cause.

1) Fast triage (is it really a leak?)
  • Symptoms: rising RSS/heap, increasing GC frequency + pause %, OOMKill in k8s, slower responses.
  • Differentiate:
    • Heap leak: Old Gen grows & doesn’t fall after full GC.
    • Native leak: RSS grows while heap looks normal (Direct buffers, threads, JNI, metaspace).
    • Cache growth / legit load: stabilizes at new plateau after traffic spike? then not a leak.

Always-on signals to have in prod

# OOM heap dump & exit code capture
- XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps/app-oom.hprof

# Container-aware sizing (k8s)

  • jcmd/jstat: quick health and histograms.

# Later: jfr print --events 'AllocationInNewTLAB,AllocationOutsideTLAB'

./profiler.sh -e alloc -d 60 -f /dumps/alloc.html <pid>
3) Heap dump (point-in-time evidence)
  • Prefer off-peak. If memory is tight, copy the dump path to a big volume first.
# Online heap dump (may STW briefly)
jcmd <pid> GC.heap_dump /dumps/live-$(date +%s).hprof

# If OOM happens, use the automatic dump from -XX:+HeapDumpOnOutOfMemoryError

Analyze dump

  • Eclipse MAT: Dominator Tree → find biggest retained objects, Paths to GC Roots, Leak Suspects Report.
  • JDK jhat / VisualVM (lighter), YourKit/JProfiler (commercial).
  • Look for classic offenders: unbounded Map/List, caches without eviction, ThreadLocal values, listeners not removed, HTTP session bloat.
4) If it’s native (off-heap) growth
  • NMT (Native Memory Tracking) to break down native categories.
# Enable at startup (some overhead)
- XX:NativeMemoryTracking=summary  # or detail

# Query at runtime
jcmd <pid> VM.native_memory summary
  • Direct buffers: track via jcmd VM.native_memory; ensure proper release patterns; consider -Dio.netty.leakDetection.level=paranoid for Netty.
  • Metaspace/classloader leak: persistent redeploys, dynamic class gen. Watch Metaspace in NMT; look for custom ClassLoaders retaining references.
  • Thread leak: jcmd <pid> Thread.print, count threads over time.
5) Mitigation playbook (keep site up)
  • Enable/raise eviction on caches (Caffeine/Guava) or cap sizes (size-based + time-based).
  • Temporarily reduce heap pressure: lower concurrency, disable heavy features, throttle producers.
  • Roll a known-good version or scale out to dilute leak rate while investigating.
  • Set a restart policy on OOM as last resort (kept warm pods minimize downtime).

    .expireAfterAccess(java.time.Duration.ofMinutes(10))
    .recordStats()
    .build();
6) Proving root cause
  • From heap dominators, identify the owning field/collection → trace to code → add logging/metrics.
  • Reproduce in staging with the same traffic pattern and enable allocation profiling (JFR/async-profiler). Verify that fixes cap the retained set.

  • Runtime: jcmd, jstat, jmap, JFR, async-profiler, VisualVM

  • Native: NMT (VM.native_memory), pmap/smaps, Netty leak detector
  • Observability: Prometheus/Grafana (heap, RSS, GC), log-based GC analyzers (e.g., GCeasy)

What Optional does: wraps a possibly-absent value in a container so callers must handle both cases explicitly. That removes many accidental NullPointerExceptions caused by unchecked dereferences.

Typical flow without Optional (NPE-prone)
// Might return null → caller forgets to check → NPE later
User findUser(String id) { return dao.find(id); }

String emailDomain(User u) { return u.getEmail().split("@")[1]; } // NPE risk
With Optional: force explicit handling
import java.util.Optional;

Optional<User> findUser(String id) {
  return Optional.ofNullable(dao.find(id)); // never return null Optional
}

String emailDomain(String id) {
  return findUser(id)
      .map(User::getEmail)          // skipped if empty
      .filter(e -> e.contains("@"))
      .map(e -> e.substring(e.indexOf('@') + 1))
      .orElse("unknown.example");   // explicit default
}

Because the type is Optional<User>, the compiler nudges you to use map/flatMap/orElse & friends instead of blindly dereferencing.

Useful Optional operations
  • of(value) / ofNullable(value) / empty()
  • map, flatMap, filter for fluent transformations
  • orElse(default) (eager) vs orElseGet(supplier) (lazy)
  • orElseThrow() to fail fast with a clear exception
  • ifPresent(consumer), ifPresentOrElse (Java 9+)

orElse vs orElseGet (gotcha)

String expensiveDefault() { /* heavy work */ return "computed"; }
Optional<String> opt = Optional.of("value");

opt.orElse(expensiveDefault());     // calls expensiveDefault() even when present!
opt.orElseGet(() -> expensiveDefault()); // calls only if empty

Fail fast with context

User user = repo.findById(id)
    .orElseThrow(() -> new IllegalArgumentException("Unknown user: " + id));
Best practices (do’s)
  • ✅ Return Optional<T> from methods to model “might be absent”.
  • ✅ Always create with Optional.ofNullable(x) if x can be null.
  • ✅ Keep chains readable; extract steps into named methods when complex.
  • ✅ Prefer orElseGet for expensive defaults; orElseThrow for required values.
Anti-patterns / drawbacks (don’ts)
  • ❌ Don’t put Optional in fields, DTOs, or collections in most codebases—adds indirection/overhead and complicates serialization/ORM.
  • ❌ Don’t use Optional as a parameter to methods; prefer overloading or two methods.
  • ❌ Don’t call get() blindly; it defeats the purpose. Use orElse/orElseThrow.
  • ❌ Never store null inside Optional (i.e., Optional.of(null) throws immediately).
  • ⚠️ Overhead: it’s an extra object; heavy use on hot paths can allocate more—measure before blanketing.
  • ⚠️ Frameworks: Some mappers/JPA serializers don’t like Optional fields—prefer plain types there.
Interoperability patterns
// Bridging legacy null-returning APIs
Optional<Customer> cust = Optional.ofNullable(legacyFind());

// From Optional back to null (if a framework requires)
Customer maybe = cust.orElse(null);

// Stream integration (Java 9+)
Stream<Order> s = findOrder(id).stream(); // empty or singleton stream
Summary
  • Why it helps: makes absence explicit, encourages safe handling, and reduces accidental NPEs.
  • Trade-offs: extra allocations and verbosity if overused; avoid in fields/params and at serialization boundaries.

Definition: Reflection lets Java code inspect and manipulate classes, interfaces, fields, methods, constructors, and annotations at runtime. It lives in java.lang.reflect and works via Class<?>, Field, Method, Constructor, Modifier, AnnotatedElement.

Common capabilities (examples)
  • Discover members/annotations: list fields/methods, read annotations/parameters.
  • Access & invoke: read/write fields (even private*), call methods/constructors dynamically.
  • Create proxies: intercept interface calls using Proxy for cross-cutting concerns.

Inspecting and invoking

class User {
  private String name;
  public User(String n) { this.name = n; }
  private String greet(String who) { return "Hi " + who + ", I'm " + name; }
}

Class<?> c = Class.forName("com.acme.User");
Object u = c.getConstructor(String.class).newInstance("Narahari");

java.lang.reflect.Field f = c.getDeclaredField("name");
f.setAccessible(true);                 // JPMS note below*
System.out.println("name=" + f.get(u));
f.set(u, "Hari");

// call private method
java.lang.reflect.Method m = c.getDeclaredMethod("greet", String.class);
m.setAccessible(true);
String msg = (String) m.invoke(u, "Team");
System.out.println(msg);               // Hi Team, I'm Hari

Dynamic proxy (logging)

interface Repo { String find(long id); }
class RepoImpl implements Repo { public String find(long id){ return "U" + id; } }

Repo target = new RepoImpl();
Repo logged = (Repo) java.lang.reflect.Proxy.newProxyInstance(
  Repo.class.getClassLoader(),
  new Class[]{Repo.class},
  (proxy, method, args) -> {
    long t0 = System.nanoTime();
    Object out = method.invoke(target, args);
    System.out.println(method.getName() + " took " + (System.nanoTime()-t0) + "ns");
    return out;
  });

logged.find(42);
Where reflection is used
  • Frameworks & DI: Spring injects beans, calls lifecycle methods, scans annotations.
  • ORMs: Hibernate maps fields to columns, constructs entities, reads annotations.
  • Serialization: Jackson/Gson create objects and bind JSON <-> POJOs.
  • AOP / Proxies: dynamic proxies for security, logging, transactions.
  • Testing: JUnit/Mockito discover tests, access internals for verification.
  • Plugins: load classes by name, SPI discovery, service loaders.
Downsides / risks
  • Performance: Reflective access is slower than direct calls; avoid on hot paths or cache lookups/method handles.
  • Type safety: Errors become runtime (NoSuchMethodException, ClassCastException).
  • Encapsulation breakage: setAccessible(true) bypasses access checks—can violate invariants.
  • Maintainability: Renames/refactors can silently break reflective code.
  • Security & modules (Java 9+): Strong encapsulation may block deep reflection across modules/packages. You may need JVM flags like --add-opens my.module/pkg=other.module. SecurityManager (legacy) may also restrict.
  • Memory/Leaks: Poor proxy/classloader use can leak (app servers, reloading).

*JPMS note: Since Java 9, setting setAccessible(true) on non-exported packages can fail without --add-opens. Prefer public APIs, constructors, or configuration to avoid deep reflection.

Best practices
  • Prefer normal typed access. Use reflection only at boundaries (framework glue, generic libraries).
  • Cache reflected lookups (Method, Field) if used repeatedly.
  • Consider MethodHandles for faster, typed invocation where possible.
  • Guard with clear errors: throw informative exceptions when reflective lookup fails.
  • Respect encapsulation: avoid poking private state in app code; keep it in infra layers.

MethodHandles (alternative)

import java.lang.invoke.*;
MethodHandles.Lookup L = MethodHandles.lookup();
MethodHandle mh = L.findVirtual(String.class, "toUpperCase",
                                MethodType.methodType(String.class));
String res = (String) mh.invokeExact("hari"); // often faster than reflection invoke

Big picture: Annotations are metadata attached to program elements. The compiler encodes them in the .class file (as attributes). Depending on @Retention, they are kept only in source, in bytecode, or available at runtime via reflection or annotation processing.

1) Anatomy of an annotation type
  • Declared as a special interface with @interface. Elements look like no-arg abstract methods with optional default values.
  • Values can be: primitives, String, Class<?>, enums, other annotations, or arrays of these. (No nulls, no generics.)
  • Meta-annotations: @Target, @Retention, @Documented, @Inherited, @Repeatable.
import java.lang.annotation.*;
@Target({ElementType.TYPE, ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface Audited {
  String value() default "default-category";
  boolean enabled() default true;
}
2) Retention & where the data lives
  • SOURCE: present only in source; discarded by compiler (e.g., @SuppressWarnings).
  • CLASS: written to .class in attributes, but not visible at runtime; usable by bytecode tools.
  • RUNTIME: stored in .class and accessible via reflection at runtime.

In the class file, annotations are stored in attributes such as RuntimeVisibleAnnotations, RuntimeInvisibleAnnotations, and for type-use (JSR 308): RuntimeVisibleTypeAnnotations.

3) Access at runtime (reflection)
  • Reflection APIs (Class, Method, Field, Parameter) expose annotations if retention is RUNTIME.
  • At runtime, the JVM creates a dynamic proxy implementing your annotation interface; calls are routed to an internal invocation handler that returns element values.
@Audited(value = "payments")
class PaymentService {
  @Audited("capture") public void capture() {}
}

Class<?> c = PaymentService.class;
Audited typeAnn = c.getAnnotation(Audited.class);
System.out.println(typeAnn.value());               // "payments"

Audited mAnn = c.getDeclaredMethod("capture").getAnnotation(Audited.class);
System.out.println(mAnn.value());                  // "capture"
4) Compile-time processing (APT)
  • Annotation Processors (javax.annotation.processing / jakarta.annotation.processing) run during compilation.
  • They read annotations on elements (Elements, Types), validate, and generate code/resources (e.g., mapstruct, dagger, lombok).
@SupportedAnnotationTypes("com.acme.Audited")
@SupportedSourceVersion(SourceVersion.RELEASE_21)
public class AuditProcessor extends AbstractProcessor {
  @Override public boolean process(Set<? extends TypeElement> anns, RoundEnvironment env) {
    for (Element e : env.getElementsAnnotatedWith(processingEnv.getElementUtils()
                                .getTypeElement("com.acme.Audited"))) {
      // validate/generate files via Filer
    }
    return false; // allow other processors to see it
  }
}
5) Type annotations (JSR 308)
  • Can annotate any use of a type (casts, generics, arrays) and leverage tools like Checker Framework.
List<@NonNull String> names = List.of("a");     // annotate type argument
String s = (@NonNull String) obj;               // annotate cast
6) Repeatable & inherited annotations
  • @Repeatable(Container.class) lets you apply an annotation multiple times. The compiler synthesizes a container annotation behind the scenes.
  • @Inherited only affects class-level annotations and only along class inheritance (not interfaces, not methods/fields).
@Repeatable(Roles.class)
public @interface Role { String value(); }
public @interface Roles { Role[] value(); }

@Role("USER") @Role("ADMIN")
class AdminService {}
7) How frameworks use them
  • Spring: classpath scanning, reflection to read annotations (e.g., @Component, @Transactional), create proxies and apply behaviors.
  • JPA/Jackson: read annotations to map entities or bind JSON; values drive runtime behavior.
  • Bytecode tools (ASM, ByteBuddy): read CLASS-retained annotations to weave/transform.
8) Limitations & pitfalls
  • No nulls / limited element types; element defaults must be compile-time constants.
  • Order not guaranteed when iterating getAnnotations() (don’t rely on it).
  • Performance: reflective lookup is slower than direct code—cache results on hot paths.
  • Modules (Java 9+): deep reflection may require --add-opens to access non-exported packages.
  • Equality semantics: two annotation instances are equal if type + all element values match (arrays compared by contents).

Big picture: Pick based on interaction pattern (request/response vs event-driven), latency/throughput, schema & contract, and operational guarantees (ordering, retries, backpressure).

When to choose what?
  • REST: external/public APIs; human-debuggable payloads; gateways/WAFs; broad tooling (OpenAPI, Postman). Great for CRUD & request/response without tight latency goals.
  • gRPC: low-latency internal RPCs; strongly-typed contracts; streaming (real-time quotes, telemetry); small payloads at high RPS.
  • Kafka (messaging): decouple producers/consumers; event-driven architectures; fan-out; buffering spikes; audit trails; exactly-once processing (with caveats) and replays.

Design considerations & trade-offs
  • Schema evolution:
    • REST/JSON: tolerant readers; version in URL/headers; document with OpenAPI.
    • gRPC/Protobuf: reserved field numbers; add-only changes; keep defaults.
    • Kafka: use Schema Registry (Avro/Protobuf); evolve schemas compatibly.
  • Reliability:
    • REST/gRPC: use timeouts + retries + circuit breakers; make mutating calls idempotent (idempotency keys, PUT, upserts).
    • Kafka: at-least-once by default; handle duplicates; use consumer groups, DLQs; exactly-once processing requires transactions + idempotent producers.
  • Ordering & concurrency:
    • Kafka: key by entity (e.g., userId) to preserve per-entity order within a partition.
    • REST/gRPC: ordering is the client’s responsibility; consider versioned writes with optimistic locking.
  • Backpressure:
    • gRPC: HTTP/2 flow control; streaming with client/server backpressure.
    • Kafka: consumers control rate; throttle producers or use quotas.
  • Observability: standardize correlation IDs across all three; emit metrics (latency, error rate, queue lag), and distributed tracing (trace/span ids in headers/record headers).
Hybrid patterns (common in real systems)
  • Command via gRPC/REST, events via Kafka (CQRS/event-carried state transfer).
  • REST/gRPC front door behind an API Gateway, with async processing behind the scenes for long-running tasks.
  • Request/Reply over Kafka (correlation IDs, reply topics) when crossing network zones/firewalls.
Quick choosing checklist
  • Is the caller a browser or third-party? → REST.
  • Is it internal microservice with strict latency or needs streaming? → gRPC.
  • Do you need decoupling, fan-out, buffering, or audit/replay? → Kafka.
  • Unclear? Start with REST; migrate hot internal paths to gRPC; introduce Kafka for async workflows.

Goal: Let service A call service B by a stable logical name (e.g., orders) while instances scale up/down, move across nodes/zones, or roll during deploys—without hardcoded IPs/ports.

1) Core patterns
  • Client-side discovery: clients query a registry for orders → pick an instance with a client load balancer (e.g., Spring Cloud LoadBalancer). Pros: fewer hops; Cons: smarter clients.
  • Server-side discovery: a gateway/LB (NGINX/Envoy) routes orders to healthy instances. Pros: thin clients; Cons: extra hop.
  • Service mesh (sidecars like Envoy/Istio/Linkerd): sidecar handles discovery, mTLS, retries, circuit breaking. Pros: policy outside app; Cons: added infra complexity.

  • Eureka / Consul / ZooKeeper: apps register (self or via sidecar). Clients resolve by name → instance list.

Design checklist
  • ✅ Choose a registry (Eureka/Consul/K8s DNS) and a pattern (client-side, server-side, or mesh).
  • ✅ Expose /health (liveness/readiness) and configure checks; ensure graceful deregistration.

Big picture: In a microservices world you cannot (and usually should not) span a single ACID transaction across services. Use local transactions inside each service and coordinate outcomes via messages (Sagas), outbox/CDC, idempotency, and compensations. Fall back to XA/2PC only for tightly coupled systems with a shared coordinator.

1) Options at a glance
ApproachHow it worksProsCons / When to avoid
XA / 2PC Global coordinator prepares & commits multiple resources in one transaction Strong consistency Latency, availability penalties, complex ops; limited cloud-native support
Saga (Choreography) Services emit/consume events; each local tx triggers next step or compensation Loosely coupled; scales well Complex flows; risk of event storms; hard to visualize
Saga (Orchestration) Central “orchestrator” commands steps and compensations Single place for flow logic/visibility Coordinator becomes dependency; careful scaling required
TCC (Try-Confirm/Cancel) Reserve (try), then confirm or cancel Low contention; explicit compensation APIs must expose try/confirm/cancel; longer-lived locks/reservations
Outbox + CDC Write domain change and an outbox row in one DB tx; CDC relays to broker Atomic message publish; resilient Extra infra (CDC), outbox table growth
2) Saga patterns (example: Order → Payment → Inventory → Ship)
  • Choreography: OrderCreated → Payment service charges → emits PaymentAuthorized → Inventory reserves → … On failure, each service emits a compensation event (e.g., PaymentRefunded, InventoryReleased).
  • Orchestration: An Orchestrator issues commands (AuthorizePayment, ReserveStock), observes replies, then decides next action or compensations.
// Orchestrator sketch (commands + replies)
record AuthorizePaymentCmd(String orderId, Money amount) {}
record PaymentAuthorizedEvt(String orderId) {}
record PaymentDeclinedEvt(String orderId, String reason) {}

@Service

  void on(PaymentAuthorizedEvt evt) { bus.send(new ReserveStockCmd(evt.orderId())); }
  void on(PaymentDeclinedEvt evt) { bus.send(new CancelOrderCmd(evt.orderId())); }
}

4) Idempotency & exactly-once effects
  • Producers: use stable keys (e.g., orderId) and include a unique eventId / idempotency key.
  • Consumers: at-least-once is normal—handle duplicates:
    • Upserts with unique constraints (e.g., event_id UNIQUE) to make operations idempotent.
    • Maintain a processed_events table or cache to dedupe.
    • Use Kafka transactions (consume-transform-produce) to avoid “gaps” when re-emitting.

5) TCC (Try-Confirm-Cancel) reservation
  • Try: reserve resources (hold funds/stock) with expiry.
  • Confirm: finalize; Cancel: release reservation.
// Payments API (TCC)

POST /payments/confirm   { reservationId }
POST /payments/cancel    { reservationId }
6) Dealing with read-model staleness
  • Eventual consistency: Reads may be stale for a short time.
  • Techniques: read-your-writes (sticky to writer for a window), versioning + ETags, command query separation (CQRS) with projections updated from events.
  • UI/UX: show “processing…” states; retry fetch after a short delay.
7) Ordering, retries, and timeouts
  • Partition by key (Kafka) to keep per-entity order; design compensations as commutative when possible.
  • Use timeouts + bounded retries with jitter; surface a dead-letter queue and a replay process.
  • Protect with circuit breakers, bulkheads, and per-destination connection pools.
8) When (if ever) to use XA/2PC
  • Small number of resources, strong consistency is a hard requirement, and infra supports XA with proven reliability.
  • Expect higher latency and failure coupling; monitor coordinator health carefully.
9) Operational checklist
  • ✅ Unique event IDs, idempotency keys, and dedupe storage.
  • ✅ Outbox for atomic write+publish; CDC to broker.
  • ✅ Saga design with compensations; document state transitions.
  • ✅ Observability: trace IDs in events/headers, metrics for lag, retries, compensation counts.
  • ✅ Reconciliation: periodic jobs to detect & fix drift (e.g., compare ledger vs. projections).

Goal: keep user-facing latency predictable and prevent cascading failures when dependencies degrade. Use timeouts first, then retry with backoff, guard with a circuit breaker, isolate via bulkheads, and provide fallbacks where acceptable.

Concepts & states
  • Retry: reattempt failed calls with exponential backoff + jitter (only for transient errors; make operations idempotent).
  • Circuit Breaker: monitors recent calls in a sliding window. States: CLOSED (normal), OPEN (fail fast), HALF_OPEN (probe limited calls).
  • Fallback: alternative response when primary path fails (cache, default, degraded path, queue for later).
  • Bulkhead: isolate resources (thread/connection pools) per dependency to avoid total exhaustion.

import io.github.resilience4j.bulkhead.annotation.Bulkhead;
import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import io.github.resilience4j.retry.annotation.Retry;
import io.github.resilience4j.timelimiter.annotation.TimeLimiter;

@Service
public class CatalogClient {

  private final org.springframework.web.reactive.function.client.WebClient webClient;

  public CatalogClient(WebClient.Builder builder) {
    this.webClient = builder.baseUrl("http://catalog").build();
  }

  @TimeLimiter(name = "catalog")
  @CircuitBreaker(name = "catalog", fallbackMethod = "fallbackProduct")
  @Retry(name = "catalog")
  @Bulkhead(name = "catalog")
  public java.util.concurrent.CompletableFuture<Product> getProduct(String id) {
    return webClient.get().uri("/api/products/{id}", id)
        .retrieve()
        .bodyToMono(Product.class)
        .toFuture();
  }

  // Fallback signature must match method + Throwable at end
  private java.util.concurrent.CompletableFuture<Product> fallbackProduct(String id, Throwable t) {
    // Degraded response (e.g., cached/default)
    Product cached = new Product(id, "Unavailable", java.math.BigDecimal.ZERO);
    return java.util.concurrent.CompletableFuture.completedFuture(cached);
  }
}

Retries: good vs bad
  • ✅ Retry on transient failures (5xx, timeouts, network blips). Use exponential backoff + jitter (e.g., 100ms, 200ms, 400ms ± random).
  • ❌ Don’t retry on client errors (4xx) or non-idempotent operations unless guarded by idempotency keys.
  • ✅ Cap total retry time; use budgets per request.

Fallback strategies
  • Cache last known good (with TTL) for read flows.
  • Degrade non-critical features (recommendations, avatars).
  • Queue write requests to process later (asynchronous handoff) when primary is down.
  • Alternate path (secondary region/provider) with feature flags.
Bulkheads & timeouts (must-have)
  • Per-dependency connection pools and thread pools (don’t share everything).
  • Set client timeouts: connect/read/write; server timeouts too.
  • Use rate limiters to shed load before saturation.
Observability & tuning
  • Expose metrics: breaker state, failure/slow-call rates, retry counts, fallback rate, p95 latency.
  • Log with correlation IDs; add tags for dependency name and outcome (success|fallback|short-circuit).
  • Start with lenient thresholds; tighten after measuring real failure modes.
Common pitfalls
  • Infinite/too aggressive retries → retry storms. Always backoff + jitter + cap.
  • Fallbacks returning stale/unsafe data; set TTLs and mark responses as degraded.
  • Global shared thread pool → head-of-line blocking; isolate per dependency.
  • Mismatched fallback signatures → method not found at runtime; include Throwable parameter.

3) JWT essentials
  • Self-contained: header.payload.signature (JWS). Validate signature, issuer (iss), audience (aud), expiry (exp), nbf.

When immediate revocation is required, prefer opaque tokens + introspection or keep a short TTL and use gateway deny-lists.

  • Terminate OAuth2/OIDC, validate tokens (iss/aud/exp), enforce rate limits, mTLS (east-west), inject identity headers to services.

Goal: make each service scale on its own bottlenecks (CPU, IO, queue lag, DB) with minimal coupling, so adding capacity or changing traffic for one service doesn’t degrade others.

3) Distributed tracing with OpenTelemetry
  • Instrument services with OTel SDK or auto-instrumentation; export to an OTel Collector (OTLP).
  • Propagate context across HTTP (traceparent), gRPC (binary metadata), and Kafka headers.

6) Best practices
  • Log events, not sentences; include identifiers. Avoid multi-line stack traces unless needed.
  • Set timeouts & error handling so traces capture failures (not infinite spans).
  • Scrub PII (names/emails/cards) and secrets (tokens/keys). Use allow-lists.
  • Control cost: sampling, index lifecycle management (ILM), cold storage/archives.

Short answer: Both React and Vue can be very fast when used correctly. In many real apps the difference is negligible compared to how you code (state placement, memoization, virtualization, bundling).

How their performance models differ
  • Vue 3: fine-grained reactivity (Proxies) tracks exact dependencies → fewer components re-render by default. Templates are compiled to optimized render functions.
  • React 18: re-renders a component when its parent renders/props change; you opt in to skipping work using React.memo, useMemo, useCallback. Concurrent rendering improves responsiveness under load but doesn’t make pure CPU work “faster”.

Rule of thumb: out-of-the-box, Vue may do less work for small reactive updates; with good memoization, React matches it.

What actually makes apps “feel fast”
  • Critical path: bundle size, network waterfalls, SSR/SSG, hydration.
  • Work avoided: limiting renders, virtualizing large lists, splitting routes/components.
  • Scheduling: breaking long tasks, deferring non-critical work, using transitions.
  • Data strategy: colocate state; minimize global/state explosions and prop drilling.
Practical optimizations

React quick hits

import React, { memo, useMemo, useCallback } from "react";

const Row = memo(function Row({ item, onClick }) {
  // re-renders only if props change (by ===)
  const label = useMemo(() => computeLabel(item), [item.id]); 
  const handle = useCallback(() => onClick(item.id), [item.id, onClick]);
  return <div onClick={handle}>{label}</div>;
});

// Virtualize big lists
// import { FixedSizeList as List } from 'react-window';
  • Use memo aggressively on stable subtrees.
  • Keep state local; avoid unnecessary Context re-renders.
  • Virtualize long lists (react-window/react-virtual).

Vue 3 quick hits

<template>
  <ItemRow :item="item" />
  <!-- One-off static subtrees -->
  <div v-once>Static</div>
</template>

<script setup>
import { computed } from 'vue';
const props = defineProps({ item: Object });
const label = computed(() => computeLabel(props.item.id)); // cached
</script>
  • Prefer computed for derived data; it caches.
  • Use v-once/keep-alive for static/expensive subtrees.
  • Virtualize lists (vue-virtual-scroller).
Measure, don’t guess
  • Browser: Performance panel (FPS, long tasks); Lighthouse for LCP/INP/CLS.
  • React: React Profiler (record commits, “why did this render”).
  • Vue: Vue Devtools perf tab (component render times, reactive events).
  • Production: web-vitals, Real User Monitoring (RUM), flamecharts.
When one may edge the other
  • Many tiny reactive updates: Vue often wins with less tuning.
  • Heavy custom memoization/large trees: React performs great if you use memo + stable refs.
  • SSR/streaming: Both offer excellent SSR; pipeline and caching usually dominate differences.
Bottom line
  • Pick based on team expertise, ecosystem, and DX. With best practices, both deliver 60fps UIs.
  • Focus on architecture (state design, fetching, code-splitting, virtualization) more than framework choice.
