SOLID principles are a set of design guidelines in object-oriented programming to make the software more maintainable and scalable.

📌 1. Single Responsibility Principle (SRP)

A class should have only one reason to change, meaning it should only have one job.


public class ReportGenerator {
    public String generateReport() {
        return "Report Data";
    }
}

public class ReportPrinter {
    public void printReport(String report) {
        System.out.println(report);
    }
}
📌 2. Open/Closed Principle (OCP)

Software entities should be open for extension but closed for modification.


interface Discount {
    double applyDiscount(double price);
}

class SeasonalDiscount implements Discount {
    public double applyDiscount(double price) {
        return price * 0.9; // 10% off
    }
}

class ClearanceDiscount implements Discount {
    public double applyDiscount(double price) {
        return price * 0.7; // 30% off
    }
}
📌 3. Liskov Substitution Principle (LSP)

Subclasses should be able to replace their base classes without altering the correctness of the program.


class Bird {
    void fly() {
        System.out.println("Flying");
    }
}

class Sparrow extends Bird {}

class Ostrich extends Bird {
    @Override
    void fly() {
        throw new UnsupportedOperationException("Ostriches can't fly");
    }
}
📌 4. Interface Segregation Principle (ISP)

Clients should not be forced to depend on interfaces they do not use.


interface Printer {
    void print();
}

interface Scanner {
    void scan();
}

class MultifunctionPrinter implements Printer, Scanner {
    public void print() {
        System.out.println("Printing...");
    }
    public void scan() {
        System.out.println("Scanning...");
    }
}
📌 5. Dependency Inversion Principle (DIP)

High-level modules should not depend on low-level modules. Both should depend on abstractions.


interface NotificationService {
    void sendNotification(String message);
}

class EmailService implements NotificationService {
    public void sendNotification(String message) {
        System.out.println("Email: " + message);
    }
}

class NotificationSender {
    private NotificationService service;

    public NotificationSender(NotificationService service) {
        this.service = service;
    }
    public void send(String message) {
        service.sendNotification(message);
    }
}
✅ Conclusion

SOLID principles help in building maintainable and scalable software applications. Adhering to these principles reduces code coupling and increases flexibility.

Factory, Builder, and Abstract Factory are creational design patterns that help create objects in a flexible and scalable manner.

📌 1. Factory Design Pattern

The Factory Pattern provides a way to create objects without specifying the exact class of the object that will be created.


interface Vehicle {
    void drive();
}

class Car implements Vehicle {
    public void drive() {
        System.out.println("Car is driving...");
    }
}

class Bike implements Vehicle {
    public void drive() {
        System.out.println("Bike is riding...");
    }
}

// Factory class
class VehicleFactory {
    public static Vehicle getVehicle(String type) {
        if ("Car".equalsIgnoreCase(type)) {
            return new Car();
        } else if ("Bike".equalsIgnoreCase(type)) {
            return new Bike();
        }
        return null;
    }
}

// Usage
public class FactoryPatternDemo {
    public static void main(String[] args) {
        Vehicle car = VehicleFactory.getVehicle("Car");
        car.drive();
    }
}
📌 2. Builder Design Pattern

The Builder Pattern is used to construct complex objects step by step.


class Car {
    private String engine;
    private int wheels;
    
    private Car(CarBuilder builder) {
        this.engine = builder.engine;
        this.wheels = builder.wheels;
    }

    public static class CarBuilder {
        private String engine;
        private int wheels;

        public CarBuilder setEngine(String engine) {
            this.engine = engine;
            return this;
        }

        public CarBuilder setWheels(int wheels) {
            this.wheels = wheels;
            return this;
        }

        public Car build() {
            return new Car(this);
        }
    }
}

// Usage
public class BuilderPatternDemo {
    public static void main(String[] args) {
        Car car = new Car.CarBuilder().setEngine("V8").setWheels(4).build();
        System.out.println("Car built with engine: " + car.engine);
    }
}
📌 3. Abstract Factory Design Pattern

The Abstract Factory Pattern provides an interface for creating families of related objects. 


interface Vehicle {
    void drive();
}

class Car implements Vehicle {
    public void drive() {
        System.out.println("Car is driving...");
    }
}

class Bike implements Vehicle {
    public void drive() {
        System.out.println("Bike is riding...");
    }
}

interface VehicleFactory {
    Vehicle createVehicle();
}

// Concrete Factories
class CarFactory implements VehicleFactory {
    public Vehicle createVehicle() {
        return new Car();
    }
}

class BikeFactory implements VehicleFactory {
    public Vehicle createVehicle() {
        return new Bike();
    }
}

// Usage
public class AbstractFactoryPatternDemo {
    public static void main(String[] args) {
        VehicleFactory factory = new CarFactory();
        Vehicle car = factory.createVehicle();
        car.drive();
    }
}
✅ Conclusion
  • Factory Pattern: Creates objects based on input type.
  • Builder Pattern: Builds complex objects step by step.
  • Abstract Factory Pattern: Creates families of related objects without specifying concrete classes.

Inheritance is a core feature of Java, but it comes with several tricky scenarios. Let's explore some interesting questions.

📌 1. Can a constructor be inherited?

No, constructors are not inherited in Java. However, a subclass can call a superclass constructor using super().


class Parent {
    Parent() {
        System.out.println("Parent Constructor");
    }
}

class Child extends Parent {
    Child() {
        super(); // Explicit call to parent constructor
        System.out.println("Child Constructor");
    }
}

public class Test {
    public static void main(String[] args) {
        new Child();
    }
}

Output:
Parent Constructor
Child Constructor

📌 2. Can we override a private method?

No, private methods are not inherited, so they cannot be overridden.


class Parent {
    private void show() {
        System.out.println("Parent show()");
    }
}

class Child extends Parent {
    private void show() { // This is not overriding
        System.out.println("Child show()");
    }
}

public class Test {
    public static void main(String[] args) {
        Parent p = new Child();
        // p.show(); // Compilation Error: show() is private
    }
}
📌 3. What happens when a method in a subclass has the same name as a static method in the superclass?

Static methods are not overridden; instead, they are hidden.


class Parent {
    static void display() {
        System.out.println("Static method in Parent");
    }
}

class Child extends Parent {
    static void display() {
        System.out.println("Static method in Child");
    }
}

public class Test {
    public static void main(String[] args) {
        Parent obj = new Child();
        obj.display(); // Calls Parent's static method
    }
}

Output: Static method in Parent

📌 4. Can we inherit multiple classes in Java?

No, Java does not support multiple inheritance with classes to avoid ambiguity.


class A {
    void show() {
        System.out.println("Class A");
    }
}

class B {
    void show() {
        System.out.println("Class B");
    }
}

// class C extends A, B { // Compilation Error: Java does not support multiple inheritance
// }

public class Test {
    public static void main(String[] args) {
        System.out.println("Multiple Inheritance is not supported in Java.");
    }
}
📌 5. What happens if the parent class has a method with a return type, and the child class overrides it with a different return type?

The return type in the child class must be the same or a subtype (covariant return type).


class Parent {
    Number show() {
        return 100;
    }
}

class Child extends Parent {
    @Override
    Integer show() { // Valid, Integer is a subclass of Number
        return 200;
    }
}

public class Test {
    public static void main(String[] args) {
        Parent p = new Child();
        System.out.println(p.show()); // Output: 200
    }
}
✅ Conclusion
  • Constructors are not inherited but can be called with super().
  • Private methods cannot be overridden.
  • Static methods are hidden, not overridden.
  • Java does not support multiple inheritance with classes.
  • Covariant return types allow overriding methods with a subclass return type.

Abstract classes and interfaces are powerful OOP tools in Java. Let’s look at some tricky questions that test their deeper behavior.

📌 1. Can an abstract class have a constructor?

Yes, abstract classes can have constructors. They are called when a subclass object is created.


abstract class Animal {
    Animal() {
        System.out.println("Animal constructor called");
    }
}

class Dog extends Animal {
    Dog() {
        System.out.println("Dog constructor called");
    }
}

public class Test {
    public static void main(String[] args) {
        new Dog();
    }
}

Output:
Animal constructor called
Dog constructor called

📌 2. Can interfaces have constructors?

No, interfaces cannot have constructors because they cannot be instantiated directly.

📌 3. What if an interface and abstract class have the same method name?

If both declare the same method, the class implementing or extending them must override the method.


interface InterfaceA {
    void display();
}

abstract class AbstractB {
    abstract void display();
}

class MyClass extends AbstractB implements InterfaceA {
    @Override
    public void display() {
        System.out.println("Display from MyClass");
    }
}
📌 4. Can we implement multiple interfaces with same method signatures?

Yes, and you only need to provide one implementation.


interface A {
    void print();
}

interface B {
    void print();
}

class C implements A, B {
    public void print() {
        System.out.println("Single implementation");
    }
}
📌 5. Can we have default and static methods in interface?

Yes, from Java 8 onward.


interface Vehicle {
    default void start() {
        System.out.println("Default start");
    }

    static void fuel() {
        System.out.println("Static fuel method");
    }
}

class Car implements Vehicle {}

public class Test {
    public static void main(String[] args) {
        new Car().start(); // OK
        Vehicle.fuel();    // OK
    }
}
📌 6. What if an abstract class doesn't implement all interface methods?

Then it must also be declared abstract.


interface Printer {
    void print();
    void scan();
}

abstract class AbstractPrinter implements Printer {
    public void print() {
        System.out.println("Printing...");
    }
    // scan() not implemented -> class must be abstract
}
✅ Conclusion
  • Abstract classes can have constructors and partial implementations.
  • Interfaces can have default and static methods (since Java 8).
  • Java allows implementing multiple interfaces with same method signatures.
  • Classes must provide implementations for all interface methods unless they are abstract.

Exception handling is critical in robust Java applications. Below are some tricky scenarios to test your understanding.

📌 1. What happens if an exception is thrown in finally block?

If the finally block throws an exception, it will override any exception thrown in the try or catch block.


public class Test {
    public static void main(String[] args) {
        try {
            throw new RuntimeException("Try Exception");
        } finally {
            throw new RuntimeException("Finally Exception");
        }
    }
}

Output:
Finally Exception — the original exception is lost.

📌 2. Can we catch multiple exceptions in a single catch?

Yes, using multi-catch (Java 7+).


try {
    // risky code
} catch (IOException | SQLException e) {
    e.printStackTrace();
}
📌 3. Can finally block prevent System.exit()?

No, finally won't execute if System.exit() is called.


try {
    System.exit(0);
} finally {
    System.out.println("Finally won't run");
}
📌 4. What if exception is thrown in catch?

If not handled inside catch, it propagates up the call stack.


try {
    int a = 10 / 0;
} catch (ArithmeticException e) {
    throw new NullPointerException("Chained Exception");
}
📌 5. Is finally guaranteed to run?

Almost always — except when JVM shuts down abnormally (e.g., System.exit, kill -9, fatal error).

📌 6. Can we rethrow an exception in catch?

Yes, it can be rethrown or wrapped.


try {
    someMethod();
} catch (IOException e) {
    throw new RuntimeException("Wrapped", e);
}
✅ Conclusion
  • Be cautious of overriding exceptions in finally.
  • Multi-catch simplifies code but avoids catching unrelated exceptions.
  • System.exit() halts all further execution — including finally.
  • Always log or handle exceptions responsibly — never swallow them silently!

Polymorphism allows objects to be treated as instances of their parent type. It enables the same method to behave differently based on the object that is invoking it.

📌 Types of Polymorphism
  • Compile-time Polymorphism (Method Overloading): Same method name with different parameters.
  • Runtime Polymorphism (Method Overriding): Method in subclass overrides superclass method.
🔥 Example: Compile-time Polymorphism

public class Calculator {
    public int add(int a, int b) {
        return a + b;
    }
    
    public double add(double a, double b) {
        return a + b;
    }
}
🔥 Example: Runtime Polymorphism

class Animal {
    public void sound() {
        System.out.println("Animal makes sound");
    }
}

class Dog extends Animal {
    public void sound() {
        System.out.println("Dog barks");
    }
}

public class TestPolymorphism {
    public static void main(String[] args) {
        Animal a = new Dog(); // Parent reference, child object
        a.sound(); // Output: Dog barks
    }
}
🧠 Tricky Questions
  • Q: Can static methods be overridden?
    A: No, they are hidden (not overridden) because they belong to class, not instance.
  • Q: Can we achieve runtime polymorphism with private or final methods?
    A: No. Private and final methods can't be overridden.
  • Q: Will the method call depend on reference type or object type?
    A: At runtime, method call is resolved based on the object type (not reference).
  • Q: Can constructors be overloaded?
    A: Yes, constructor overloading is valid and an example of compile-time polymorphism.
✅ Conclusion

Polymorphism enables flexibility and reusability in object-oriented programming. It is one of the core pillars of OOP and is widely used in frameworks like Spring and Hibernate.

📌 Why Optimize APIs?

Efficient APIs improve **performance, reduce latency, and scale better** under high traffic.

🔹 Key API Optimization Techniques

  • Pagination & Limit Offsets: Prevents fetching large datasets at once.
  • Asynchronous Processing: Use message queues (Kafka, RabbitMQ) for background tasks.
  • Caching: Store frequent API responses in Redis or CDN for faster retrieval.
  • Compression (GZIP/Brotli): Reduces payload size, improving network performance.
  • Database Query Optimization: Use indexes, denormalization, and optimized joins.
  • Rate Limiting: Protects APIs from abuse using tools like Redis Bucket4J.
  • GraphQL / Partial Responses: Allows clients to fetch only required data.
  • Connection Pooling: Reuse database connections for better resource management.

🔹 Example: Optimizing an API in Spring Boot


import org.springframework.cache.annotation.Cacheable;
import org.springframework.web.bind.annotation.*;
import java.util.List;

@RestController
@RequestMapping("/products")
public class ProductController {

    private final ProductService productService;

    public ProductController(ProductService productService) {
        this.productService = productService;

    @GetMapping

                                     @RequestParam(defaultValue = "10") int size) {
        return productService.getPaginatedProducts(page, size);
    }
}

🚀 Best Practices for Optimized APIs

  • Use **CDNs and Edge Caching** for static and frequently accessed resources.
  • Leverage **WebSockets** for real-time updates instead of polling.
  • Optimize **SQL queries** with proper indexing and query tuning.
  • Enable **lazy loading** for large responses to improve efficiency.
  • Implement **Circuit Breaker patterns** (e.g., Resilience4J) to handle failures gracefully.

🔹 Summary

API optimization improves **scalability, latency, and efficiency** by leveraging caching, pagination, compression, and better query handling.

📌 Why Microservices Need Resilience?

Microservices run in **distributed environments**, making them prone to **failures, network issues, and high latency**. Resilience patterns help ensure system stability.

🔹 Key Microservices Resilience Patterns

  • Retry Pattern: Automatically retries failed operations.
  • Circuit Breaker Pattern: Prevents repeated calls to failing services.
  • Bulkhead Pattern: Isolates service failures to prevent cascading issues.
  • Rate Limiting: Controls excessive requests to prevent overload.
  • Timeout Pattern: Avoids long waits for unresponsive services.
  • Failover & Redundancy: Uses backup instances in case of failures.
  • Event Sourcing: Maintains system state through immutable events.
  • Saga Pattern: Handles distributed transactions across multiple services.

🔹 Example: Circuit Breaker with Resilience4J


import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;
import java.util.Random;

@RestController
@RequestMapping("/orders")
public class OrderController {

    @GetMapping
    @CircuitBreaker(name = "orderService", fallbackMethod = "fallbackResponse")
    public String placeOrder() {
        if (new Random().nextBoolean()) { // Simulate random failure
            throw new RuntimeException("Service Unavailable");
        }
        return "Order placed successfully!";
    }

    public String fallbackResponse(Exception ex) {
        return "Fallback: Order service is currently unavailable.";
    }
}

🚀 Best Practices for Resilient Microservices

  • Use **timeouts** to prevent indefinite waiting.
  • Enable **retry logic** with exponential backoff.
  • Implement **circuit breakers** to avoid repeated failures.
  • Isolate failures with **bulkheads**.
  • Use **distributed tracing** (Jaeger, Zipkin) for observability.
  • Store critical data using **event-driven architectures**.

🔹 Summary

Microservices resilience patterns ensure system **stability, fault tolerance, and reliability** in distributed environments.

Both CrudRepository and JpaRepository are used in Spring Data JPA, but they have key differences.

🔹 CrudRepository (Basic CRUD Operations)

  • Provides basic save(), findById(), delete(), exists(), etc.
  • Suitable for simple CRUD operations.
  • Does NOT provide JPA-specific features like pagination or batch operations.

🔹 JpaRepository (Extended JPA Features)

  • Extends CrudRepository and PagingAndSortingRepository.
  • Provides additional methods like flush(), saveAndFlush(), findAll(Pageable pageable).
  • Supports batch operations and pagination.

💡 Example:


        import org.springframework.data.repository.CrudRepository;
        import org.springframework.data.jpa.repository.JpaRepository;
        import java.util.List;

        // Using CrudRepository
        public interface EmployeeCrudRepo extends CrudRepository<Employee, Long> {
            List<Employee> findByName(String name); // Custom query
        }

        // Using JpaRepository
        public interface EmployeeJpaRepo extends JpaRepository<Employee, Long> {
            List<Employee> findByName(String name);
        }

🔹 When to Use What?

  • Use CrudRepository when you need only basic CRUD operations.
  • Use JpaRepository when you need batch updates, pagination, or JPA-specific features.

SpringApplication.run() is the entry point of a Spring Boot application. It initializes the application context, loads beans, and starts the embedded server.

🔹 Steps Performed Internally:

  1. Creates a SpringApplication instance: Determines if it's a web application.
  2. Configures environment: Loads properties from `application.properties` or `application.yml`.
  3. Loads Initializers: Calls `ApplicationContextInitializer` beans.
  4. Loads Listeners: Registers event listeners (e.g., `ApplicationListener`).
  5. Creates ApplicationContext: Loads the appropriate context (`AnnotationConfigServletWebServerApplicationContext` for web apps).
  6. Refreshes the ApplicationContext: Initializes all beans and configurations.
  7. Calls CommandLineRunners and ApplicationRunners: Executes additional startup logic.
  8. Starts the embedded server: (Tomcat, Jetty, etc., for web applications).

💡 Example:


        import org.springframework.boot.SpringApplication;
        import org.springframework.boot.autoconfigure.SpringBootApplication;

        @SpringBootApplication
        public class MySpringBootApplication {
            public static void main(String[] args) {
                SpringApplication.run(MySpringBootApplication.class, args);
            }
        }

🔹 Equivalent Manual Steps (Without SpringApplication.run()):


        import org.springframework.context.annotation.AnnotationConfigApplicationContext;

        public class ManualSpringBoot {
            public static void main(String[] args) {
                AnnotationConfigApplicationContext context = new AnnotationConfigApplicationContext(MyConfig.class);
                context.refresh(); // Manually refreshing the context
                context.start();   // Starting the context
                context.close();   // Closing when done
            }
        }

💡 Why use SpringApplication.run()?

  • Encapsulates all **boilerplate startup logic**.
  • Handles **environment setup, listeners, and context refresh** automatically.
  • Manages **embedded server startup** for web applications.

🔹 HashMap is a key-value data structure based on hashing. It provides O(1) average time complexity for insert, search, and delete operations.

📌 HashMap Data Structure:

  • Internally, it is an **array of Node** (buckets).
  • Each bucket stores **a linked list** (before Java 8) or **a balanced tree** (after Java 8, when collisions exceed a threshold).

🔹 Important Components:

  • Capacity: Initial size of the HashMap (default: 16).
  • Load Factor: Default 0.75 (resizing occurs when 75% of the map is full).
  • Threshold: `capacity * load factor`, determines when resizing happens.

🔹 Internal Working of `put(K, V)`:

  1. Computes hashCode() of the key.
  2. Uses (hashCode % capacity) to find the index.
  3. If bucket is empty, stores the new entry.
  4. If a collision occurs, it stores the entry as:
    • 🔹 **Linked List** (before Java 8).
    • 🔹 **Balanced Tree (Red-Black Tree)** (after Java 8, if the chain length > 8).
  5. Resizes the HashMap if the threshold is reached.

🔹 Example of HashMap Implementation:


        import java.util.HashMap;

        public class HashMapExample {
            public static void main(String[] args) {
                HashMap map = new HashMap<>();
                map.put("Alice", 25);
                map.put("Bob", 30);
                map.put("Charlie", 35);
                
                System.out.println("Age of Bob: " + map.get("Bob")); // 30
            }
        }

🔹 How `get(K)` Works?

  • Computes the **hashCode()** of the key.
  • Finds the bucket using `(hashCode % capacity)`.
  • Traverses the linked list or tree to find the key.
  • Returns the value if found, else returns `null`.

🔹 HashMap Performance Optimization:

  • Use a good hash function to minimize collisions.
  • Set an **optimal initial capacity** to reduce resizing overhead.
  • Keep **load factor at 0.75** for the best trade-off between performance and memory usage.

🔹 `Map` is an interface in Java that provides a key-value store.

📌 Different Implementations of `Map`:

  • 🔹 HashMap → Uses **array + linked list + red-black tree**.
  • 🔹 TreeMap → Uses **Red-Black Tree** (sorted order).
  • 🔹 LinkedHashMap → Uses **Doubly Linked List** (preserves insertion order).
  • 🔹 ConcurrentHashMap → Uses **Segmented Locks for thread safety**.

🔹 How Does `HashMap` Work Underneath?

  • Stores data in an array of Node<K, V>.
  • Uses hashCode() and (hash % capacity) to find bucket.
  • Handles **collisions using Linked List (before Java 8)** and **Red-Black Tree (after Java 8, if needed).**

🔹 Example of `HashMap`:


        import java.util.HashMap;

        public class HashMapExample {
            public static void main(String[] args) {
                HashMap map = new HashMap<>();
                map.put("Alice", 25);
                map.put("Bob", 30);
                map.put("Charlie", 35);
                
                System.out.println("Age of Bob: " + map.get("Bob")); // 30
            }
        }

🔹 How Does `TreeMap` Work Underneath?

  • Stores data in a Red-Black Tree (Self-balancing Binary Search Tree).
  • Keeps **keys sorted in natural or custom order**.
  • O(log n) complexity for insert/search.

🔹 Example of `TreeMap`:


        import java.util.TreeMap;

        public class TreeMapExample {
            public static void main(String[] args) {
                TreeMap map = new TreeMap<>();
                map.put("Alice", 25);
                map.put("Bob", 30);
                map.put("Charlie", 35);
                
                System.out.println("First Entry: " + map.firstEntry()); // Alice=25
            }
        }

🔹 How Does `ConcurrentHashMap` Work?

  • Uses **segment-based locking** (before Java 8) and **CAS (Compare-And-Swap)** (after Java 8).
  • Provides **thread-safe** operations with **high performance**.

🔹 Example of `ConcurrentHashMap`:


        import java.util.concurrent.ConcurrentHashMap;

        public class ConcurrentHashMapExample {
            public static void main(String[] args) {
                ConcurrentHashMap map = new ConcurrentHashMap<>();
                map.put("Alice", 25);
                map.put("Bob", 30);

                System.out.println("Alice's Age: " + map.get("Alice"));
            }
        }

🔹 Summary of `Map` Implementations:

Type Data Structure Sorting Thread Safety
HashMap Array + Linked List + Red-Black Tree No No
TreeMap Red-Black Tree Yes No
LinkedHashMap Linked List + HashMap No No
ConcurrentHashMap Bucket-based HashMap No Yes

🔹 JVM divides memory into different areas:

  • 📌 Heap Memory → Stores objects during runtime.
  • 📌 Stack Memory → Stores method execution data.
  • 📌 Metaspace → Stores class metadata.

📌 Default JVM Memory Allocation:


        -Xms256m  # Initial heap memory
        -Xmx1g    # Max heap memory

📌 Customizing JVM Memory in Spring Boot:


        java -Xms512m -Xmx2g -jar myapp.jar

🔹 Memory Area Configurations:

Memory Area Purpose JVM Option
Heap Stores objects -Xms / -Xmx
Metaspace Stores class metadata -XX:MetaspaceSize

🔹 Example Java Code to Get Memory Info:


        public class MemoryInfo {
            public static void main(String[] args) {
                Runtime runtime = Runtime.getRuntime();
                System.out.println("Max Memory: " + runtime.maxMemory());
                System.out.println("Total Memory: " + runtime.totalMemory());
                System.out.println("Free Memory: " + runtime.freeMemory());
            }
        }

🔹 JVM Behavior When Memory is Exhausted:

  • 📌 Garbage Collection (GC) tries to free memory.
  • 📌 If GC fails, OutOfMemoryError occurs.
  • 📌 Application may crash or slow down.

📌 Example: Simulating `OutOfMemoryError`


        List memoryList = new ArrayList<>();
        while (true) {
            memoryList.add(new int[1_000_000]); // Allocates 1MB each loop
        }

🔹 How to Fix?

  • ✔ Increase Heap Size: `-Xmx2g`
  • ✔ Monitor JVM Memory: `jstat -gc `
  • ✔ Use Better Garbage Collector: `-XX:+UseG1GC`

📌 Configuring JVM Memory:


        java -Xms512m -Xmx2g -XX:+UseG1GC -jar myapp.jar

In Java, when using a custom object as a key in a HashMap, we must override equals() and hashCode() methods to ensure proper key comparisons.

📌 1. How HashMap Works?
  • 🔹 HashMap stores key-value pairs using a **hashing mechanism**.
  • 🔹 When adding an object as a key, **HashMap computes its hash code** to determine the storage bucket.
  • 🔹 If two objects have the **same hash code**, it checks the **equals() method** to differentiate keys.
📌 2. What Happens Without Overriding equals() and hashCode()?

If we don’t override equals() and hashCode(), Java will use **the default Object class implementations**, causing issues when retrieving values from the HashMap.

📌 3. Example Without Overriding equals() and hashCode()

import java.util.HashMap;

class Employee {
    int id;
    String name;

    public Employee(int id, String name) {
        this.id = id;
        this.name = name;
    }
}

public class HashMapExample {
    public static void main(String[] args) {
        HashMap<Employee, String> map = new HashMap<>();
        Employee e1 = new Employee(101, "John");
        Employee e2 = new Employee(101, "John");

        map.put(e1, "Developer");
        System.out.println("Value: " + map.get(e2)); // ❌ Returns null
    }
}

⚠️ Even though e1 and e2 have the same data, map.get(e2) returns null because Java uses default hashCode(), which is different for each object.

📌 4. Correct Approach: Override equals() and hashCode()

import java.util.HashMap;
import java.util.Objects;

class Employee {
    int id;
    String name;

    public Employee(int id, String name) {
        this.id = id;
        this.name = name;
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name);
    }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;
        if (obj == null || getClass() != obj.getClass()) return false;
        Employee employee = (Employee) obj;
        return id == employee.id && Objects.equals(name, employee.name);
    }
}

public class HashMapExample {
    public static void main(String[] args) {
        HashMap<Employee, String> map = new HashMap<>();
        Employee e1 = new Employee(101, "John");
        Employee e2 = new Employee(101, "John");

        map.put(e1, "Developer");
        System.out.println("Value: " + map.get(e2)); // ✅ Returns "Developer"
    }
}

✅ Now, map.get(e2) correctly retrieves "Developer" because hashCode() and equals() are overridden.

✅ Conclusion
  • ✔️ If we don’t override equals() and hashCode(), HashMap treats objects as different keys, even if they have the same data.
  • ✔️ Overriding these methods ensures correct key comparison and retrieval.
  • ✔️ Use Objects.hash() for a reliable hash code.

In Java, **fail-fast** and **fail-safe** are two different approaches to handling concurrent modifications while iterating over a collection.

📌 1. Fail-Fast Iterators
  • 🔹 Fail-Fast iterators immediately throw ConcurrentModificationException if a collection is modified while iterating.
  • 🔹 They operate directly on the collection and detect structural changes.
  • 🔹 Examples: ArrayList, HashSet, HashMap (iterator on keySet, entrySet).
📌 2. Example of Fail-Fast Iterator

import java.util.*;

public class FailFastExample {
    public static void main(String[] args) {
        List<String> list = new ArrayList<>();
        list.add("One");
        list.add("Two");
        list.add("Three");

        Iterator<String> iterator = list.iterator();
        while (iterator.hasNext()) {
            System.out.println(iterator.next());
            list.add("Four"); // ❌ Throws ConcurrentModificationException
        }
    }
}

⚠️ The above code will throw **ConcurrentModificationException** because the collection is modified while iterating.

📌 3. Fail-Safe Iterators
  • 🔹 Fail-Safe iterators **do not throw exceptions** if the collection is modified during iteration.
  • 🔹 They work on a **clone (copy) of the collection**, so modifications do not affect the iterator.
  • 🔹 Examples: CopyOnWriteArrayList, CopyOnWriteArraySet, ConcurrentHashMap.
📌 4. Example of Fail-Safe Iterator

import java.util.concurrent.*;

public class FailSafeExample {
    public static void main(String[] args) {
        CopyOnWriteArrayList<String> list = new CopyOnWriteArrayList<>();
        list.add("One");
        list.add("Two");
        list.add("Three");

        Iterator<String> iterator = list.iterator();
        while (iterator.hasNext()) {
            System.out.println(iterator.next());
            list.add("Four"); // ✅ No Exception
        }

        System.out.println("Final List: " + list);
    }
}

✅ In this example, **modifications are allowed** during iteration because CopyOnWriteArrayList works on a separate copy.

Feature Fail-Fast Fail-Safe
Exception Handling Throws ConcurrentModificationException No exception, continues execution
Working Mechanism Directly operates on collection Iterates over a copy
Modification Effect Modifications lead to failure Modifications are allowed
Performance Faster but unsafe Slower due to copy creation
Examples ArrayList, HashMap CopyOnWriteArrayList, ConcurrentHashMap
✅ Conclusion
  • ✔️ **Use Fail-Fast** when modifications should be avoided during iteration.
  • ✔️ **Use Fail-Safe** when concurrent modifications are expected.
  • ✔️ Fail-Fast is efficient but unsafe, while Fail-Safe ensures stability at the cost of performance.

In Java, **Class Loaders** are responsible for loading class files into memory at runtime. Java 8 introduced improvements, and Java 9 further refined the modular system.

📌 1. Types of Class Loaders

Java has three main class loaders:

  • ✔️ **Bootstrap ClassLoader** - Loads core Java classes (e.g., java.lang.*).
  • ✔️ **Extension (Platform) ClassLoader** - Loads classes from lib/ext or java.ext.dirs.
  • ✔️ **Application (System) ClassLoader** - Loads classes from the application’s classpath.
📌 2. Class Loader Hierarchy

public class ClassLoaderExample {
    public static void main(String[] args) {
        // Bootstrap ClassLoader (null in Java)
        System.out.println("Bootstrap ClassLoader: " + String.class.getClassLoader());

        // Extension (Platform) ClassLoader
        System.out.println("Platform ClassLoader: " + ClassLoaderExample.class.getClassLoader().getParent());

        // Application (System) ClassLoader
        System.out.println("System ClassLoader: " + ClassLoaderExample.class.getClassLoader());
    }
}

✅ Bootstrap ClassLoader returns null because it's implemented in native code.

📌 3. How Class Loaders Work?
  • ✔️ Java follows **Parent Delegation Model**, where a class loader first asks its parent to load a class before loading it itself.
  • ✔️ If the parent cannot find the class, the current loader loads it.
  • ✔️ Prevents loading duplicate or malicious classes.
📌 4. Custom Class Loader Example

You can create a **custom class loader** by extending ClassLoader:


import java.io.*;

public class CustomClassLoader extends ClassLoader {
    @Override
    public Class<?> loadClass(String name) throws ClassNotFoundException {
        if (!name.startsWith("com.example")) {
            return super.loadClass(name);
        }

        try {
            String fileName = name.replace('.', '/') + ".class";
            InputStream input = getClass().getClassLoader().getResourceAsStream(fileName);
            if (input == null) return super.loadClass(name);

            byte[] bytes = input.readAllBytes();
            return defineClass(name, bytes, 0, bytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name);
        }
    }
}

✅ This custom class loader loads classes starting with "com.example" manually.

📌 5. Changes in Java 9 and Later

        this.city = city;

        return new Address(this.city); // Deep copy

Cloning in Java is used to create a copy of an object. It can be done in two ways:

📌 1. Shallow Cloning

- In **shallow cloning**, a new object is created, but its fields **reference the same objects** as the original. - Changes in referenced objects affect both original and cloned objects. 


class Address implements Cloneable {
    String city;
    
    Address(String city) {
        this.city = city;
    }

    @Override
    protected Object clone() throws CloneNotSupportedException {
        return super.clone(); // Performs shallow copy
    }
}

class Person implements Cloneable {
    String name;
    Address address;

    Person(String name, Address address) {
        this.name = name;
        this.address = address;
    }

    @Override
    protected Object clone() throws CloneNotSupportedException {
        return super.clone(); // Performs shallow copy
    }
}

public class ShallowCloneExample {
    public static void main(String[] args) throws CloneNotSupportedException {
        Address address = new Address("New York");
        Person p1 = new Person("John", address);
        Person p2 = (Person) p1.clone(); // Shallow copy

        System.out.println("Before Modification: " + p2.address.city); // Output: New York

        p1.address.city = "Los Angeles"; // Changing original object reference

        System.out.println("After Modification: " + p2.address.city); // Output: Los Angeles (changes in both)
    }
}
⚠️ Issue with Shallow Copy

If the cloned object has references to other objects, both original and cloned objects **share** the same references. This can lead to unexpected modifications.

📌 2. Deep Cloning

- In **deep cloning**, a completely new object is created along with copies of all referenced objects. - The original and cloned objects are fully independent. 


class Address implements Cloneable {
    String city;
    
    Address(String city) {
        this.city = city;
    }

    @Override
    protected Object clone() throws CloneNotSupportedException {
        return new Address(this.city); // Creates new object
    }
}

class Person implements Cloneable {
    String name;
    Address address;

    Person(String name, Address address) {
        this.name = name;
        this.address = address;
    }

    @Override
    protected Object clone() throws CloneNotSupportedException {
        Person clonedPerson = (Person) super.clone();
        clonedPerson.address = (Address) address.clone(); // Deep Copy
        return clonedPerson;
    }
}

public class DeepCloneExample {
    public static void main(String[] args) throws CloneNotSupportedException {
        Address address = new Address("New York");
        Person p1 = new Person("John", address);
        Person p2 = (Person) p1.clone(); // Deep copy

        System.out.println("Before Modification: " + p2.address.city); // Output: New York

        p1.address.city = "Los Angeles"; // Changing original object reference

        System.out.println("After Modification: " + p2.address.city); // Output: New York (independent copy)
    }
}
✅ Key Differences
Feature Shallow Copy Deep Copy
Copies primitive fields ✅ Yes ✅ Yes
Copies reference fields ❌ No (Shares references) ✅ Yes (Creates new objects)
Objects are independent? ❌ No ✅ Yes
Changes in original reflect in cloned? ✅ Yes ❌ No
🔍 When to Use?
  • ✔ Use **shallow cloning** when references should be shared.
  • ✔ Use **deep cloning** when each object should be **fully independent**.
  • ✔ If cloning is required, consider **serialization-based deep copy** for complex objects.

In Spring Framework, there are multiple ways to manage transactions. The main methods are **Declarative Transaction Management** and **Programmatic Transaction Management**.

@Service

    @Autowired
    private UserRepository userRepository;

    @Transactional
    public void createUser(User user) {
        userRepository.save(user);
        // Any runtime exception here will cause rollback
    }
}

✔ Advantages: Simple and less boilerplate code.

❌ Disadvantages: Cannot handle fine-grained transaction control.

- Manages transactions manually using **TransactionTemplate** or **PlatformTransactionManager**. - Provides fine-grained transaction control.

🔹 Using TransactionTemplate

@Service
public class UserService {

    @Autowired
    private TransactionTemplate transactionTemplate;

    public void createUser(User user) {
        transactionTemplate.execute(status -> {
            userRepository.save(user);
            return null;
        });
    }
}

@Service
public class UserService {

    @Autowired
    private PlatformTransactionManager transactionManager;

    public void createUser(User user) {
        DefaultTransactionDefinition def = new DefaultTransactionDefinition();
        TransactionStatus status = transactionManager.getTransaction(def);
        try {
            userRepository.save(user);
            transactionManager.commit(status);
        } catch (Exception e) {
            transactionManager.rollback(status);
        }

❌ Disadvantages: More complex and requires manual handling.

❌ Disadvantages: XML configuration is verbose.

Atomic Variables in Java are part of the java.util.concurrent.atomic package. They provide **lock-free, thread-safe** operations for variables like integers, booleans, and references using **Compare-And-Swap (CAS)** mechanism.

📌 Why Use Atomic Variables?
  • Provides **thread-safe updates** without using synchronization.
  • **Better performance** than `synchronized` for simple operations.
  • Avoids issues like race conditions in multithreading.
📌 Types of Atomic Variables
  • AtomicInteger - For atomic integer operations.
  • AtomicLong - For atomic long operations.
  • AtomicBoolean - For atomic boolean values.
  • AtomicReference<T> - For atomic reference updates.
📌 Example: Using AtomicInteger

import java.util.concurrent.atomic.AtomicInteger;

public class AtomicExample {
    private static AtomicInteger count = new AtomicInteger(0);

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> count.incrementAndGet()); // Atomic increment
        Thread t2 = new Thread(() -> count.incrementAndGet());

        t1.start();
        t2.start();

        try {
            t1.join();
            t2.join();
        } catch (InterruptedException e) {
            e.printStackTrace();
        }

        System.out.println("Final Count: " + count.get()); // Output: 2
    }
}
📌 Compare-And-Swap (CAS) Mechanism

Atomic variables use **CAS (Compare-And-Swap)** instead of locks. This prevents thread contention: 


boolean updated = count.compareAndSet(0, 10); // If count == 0, set to 10
System.out.println(updated); // true if update successful
📌 When to Use Atomic Variables?
  • For **simple operations** like counters and flags.
  • When **high performance** is required.
  • If using **synchronized is too expensive** due to contention.

  • Resource Owner: The user who owns the data.
  • Client: The application requesting access.
  • Authorization Server: Issues access tokens after authentication.
  • Resource Server: Hosts protected resources (e.g., APIs).
📌 OAuth 2.0 Workflow

1. The client requests access from the resource owner.
2. The resource owner grants permission.
3. The client sends the request to the authorization server.
4. The authorization server issues an access token.
5. The client uses the token to access the resource server.
📌 Types of OAuth 2.0 Authentication Flows
🔹 1. Authorization Code Flow (Most Secure) 🔹

The **Authorization Code Flow** is the most secure method, as the access token is not exposed to the frontend. 


1. User logs in and authorizes the app.
2. App receives an **Authorization Code**.
3. The backend exchanges the code for an **Access Token**.
4. The token is used to access protected resources.
🔹 2. Implicit Flow (For Frontend Apps) 🔹

Used in **client-side apps** (Single Page Applications - SPA). It is less secure since tokens are exposed in the URL. 


1. User logs in and authorizes the app.
2. The browser directly receives an **Access Token**.
3. The token is used for API requests.
🔹 3. Client Credentials Flow (Machine-to-Machine) 🔹

Used for **server-to-server** authentication where no user is involved (e.g., Microservices communication). 


1. The client authenticates with the authorization server.
2. The server issues an **Access Token**.
3. The token is used to access resources.
🔹 4. Password Credentials Flow (Legacy Approach) 🔹

Used in **trusted applications** where the client directly collects the user's **username & password**. 


1. The user provides credentials to the app.
2. The app exchanges credentials for an **Access Token**.
3. The token is used to access resources.
🔹 5. Device Authorization Flow (For IoT Devices) 🔹

Used for **devices without browsers** (e.g., Smart TVs, IoT devices). The user logs in on a different device. 


1. The device requests authorization.
2. The user logs in on another device and enters a code.
3. The server issues an **Access Token**.
4. The device uses the token for API requests.
📌 Example: OAuth 2.0 with Spring Boot

@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http.oauth2Login();
        return http.build();
    }
}
✅ Summary Table
Flow Use Case Security Level
Authorization Code Web apps, secure login 🔒 High
Implicit SPA (Client-side apps) ⚠️ Low (Token in URL)
Client Credentials Machine-to-Machine 🔒 High
Password Credentials Trusted legacy apps ⚠️ Medium (Credentials shared)
Device Authorization IoT devices, TVs 🔒 High
✅ Key Takeaways
  • OAuth 2.0 enables **secure authorization** without sharing passwords.
  • **Authorization Code Flow** is the most secure and widely used.
  • Use **Client Credentials Flow** for microservices communication.
  • Implicit and Password Grant Types are **not recommended** for new applications.

✅ 2. Testing a Service Layer with Mockito

Let's assume we have a simple **UserService** that fetches user data from a repository.


@Service
public class UserService {
    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public User getUserById(Long id) {
        return userRepository.findById(id)
                .orElseThrow(() -> new UserNotFoundException("User not found"));
    }
}

Now, let's write a **unit test** for this service.


@ExtendWith(MockitoExtension.class)
public class UserServiceTest {

    @Mock
    private UserRepository userRepository;

    @InjectMocks
    private UserService userService;

    @Test
    void testGetUserById_Success() {
        User mockUser = new User(1L, "John Doe");
        when(userRepository.findById(1L)).thenReturn(Optional.of(mockUser));

        User user = userService.getUserById(1L);

        assertNotNull(user);
        assertEquals("John Doe", user.getName());
        verify(userRepository, times(1)).findById(1L);
    }

    @Test
    void testGetUserById_NotFound() {
        when(userRepository.findById(2L)).thenReturn(Optional.empty());

        assertThrows(UserNotFoundException.class, () -> userService.getUserById(2L));
    }
}

Code Coverage is a metric that measures the percentage of your source code executed by your test cases. It helps ensure that critical parts of your application are tested and reduces the risk of undetected bugs.

📌 How Code Coverage Works

During test execution, a code coverage tool tracks which lines, branches, and paths in the source code are executed. The result is then displayed as a report, showing coverage percentages.

✅ Key Code Coverage Metrics
  • Line Coverage: Percentage of code lines executed by tests.
  • Branch Coverage: Ensures both if and else branches are tested.
  • Method Coverage: Ensures each method is executed at least once.
  • Path Coverage: Ensures all possible execution paths in a method are tested.
✅ Popular Code Coverage Tools
  • JaCoCo (Java Code Coverage): A widely used tool for Java applications.
  • Cobertura: Another Java coverage tool, but less popular than JaCoCo.
  • SonarQube: Provides advanced analysis, including code quality and coverage.
  • Emma: A lightweight coverage tool for Java.
✅ 1. Using JaCoCo in Spring Boot

Add the following dependency in pom.xml:


<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.7</version>
    <executions>
        <execution>
            <goals>
                <goal>prepare-agent</goal>
            </goals>
        </execution>
        <execution>
            <id>report</id>
            <phase>verify</phase>
            <goals>
                <goal>report</goal>
            </goals>
        </execution>
    </executions>
</plugin>
✅ 2. Running JaCoCo

Execute the following command to generate the coverage report:


mvn clean test
mvn jacoco:report

The HTML report will be generated in target/site/jacoco/index.html.

✅ 3. Checking Code Coverage in IntelliJ IDEA
  1. Run tests with coverage: Ctrl + Shift + F10 → "Run with Coverage".
  2. View the coverage report in the **Coverage Tool Window**.
✅ 4. Enforcing Code Coverage in CI/CD

To fail the build if coverage is below a threshold, add this in pom.xml:


<configuration>
    <rules>
        <rule>
            <element>CLASS</element>
            <limits>
                <limit>
                    <counter>LINE</counter>
                    <value>COVEREDRATIO</value>
                    <minimum>0.80</minimum>
                </limit>
            </limits>
        </rule>
    </rules>
</configuration>
✅ Summary
  • Code coverage helps identify untested parts of the application.
  • JaCoCo is the most popular tool for Java applications.
  • Use coverage reports to improve test quality and prevent regressions.
  • Integrate coverage checks in CI/CD to maintain high test standards.

JPA (Java Persistence API) is a specification for ORM (Object-Relational Mapping) in Java. Hibernate is the most popular JPA implementation. In Spring Boot, Spring Data JPA simplifies JPA-based data access layers.

📌 What is Relational Mapping?

Relational mapping defines how Java objects (entities) are mapped to database tables. JPA annotations are used to declare entity relationships like OneToOne, OneToMany, ManyToOne, and ManyToMany.

✅ Types of JPA Relationships
  • @OneToOne: Maps a one-to-one relationship between two entities.
  • @OneToMany: Maps one entity to many (child) entities.
  • @ManyToOne: Many entities share a single parent entity.
  • @ManyToMany: Each entity can relate to many others and vice versa.
✅ Example Entity with All Mappings

@Entity
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    @OneToOne(cascade = CascadeType.ALL)
    @JoinColumn(name = "profile_id", referencedColumnName = "id")
    private Profile profile;

    @OneToMany(mappedBy = "user", cascade = CascadeType.ALL)
    private List<Order> orders;

    @ManyToOne
    @JoinColumn(name = "department_id")
    private Department department;

    @ManyToMany
    @JoinTable(
        name = "user_roles",
        joinColumns = @JoinColumn(name = "user_id"),
        inverseJoinColumns = @JoinColumn(name = "role_id"))
    private Set<Role> roles;
}
✅ Annotation Properties Explained
  • @JoinColumn: Specifies the foreign key column.
    • name: Column name in current entity.
    • referencedColumnName: Target column in the referenced entity.
  • @OneToOne / @OneToMany / @ManyToOne / @ManyToMany: Relationship type.
  • cascade: Operations to cascade (e.g., ALL, PERSIST, REMOVE).
  • mappedBy: Used in bidirectional mapping to indicate the owning side.
  • @JoinTable: Used in @ManyToMany for defining join table and columns.
✅ Supporting Entities

    @Id
    private Long id;
    private String bio;
}

@Entity
public class Order {
    @Id
    private Long id;

    @ManyToOne

✅ Summary
  • JPA + Hibernate handles object-relational mapping in Spring Boot.
  • Use annotations like @OneToOne, @ManyToOne, etc., to define relationships.
  • Use @JoinColumn and @JoinTable to control DB schema generation.
  • Cascading and bidirectional mappings improve data handling efficiency.

The best use case for @ManyToMany is when both entities can have a many-to-many relationship. A common example is User and Role — where a user can have multiple roles, and a role can be assigned to multiple users.

  • A user can have multiple roles like ADMIN, USER, MANAGER.
  • Each role can be assigned to multiple users.

Cascading in a @ManyToMany relationship determines how operations like persist, merge, remove, and refresh are propagated from one entity to its related entities.

📌 Why Cascading Is Important

Without cascading, you have to explicitly save or delete both sides of the relationship. Cascading helps propagate the operation automatically.

✅ Example with Cascade

@Entity
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    @ManyToMany(cascade = { CascadeType.PERSIST, CascadeType.MERGE })
    @JoinTable(
        name = "user_roles",
        joinColumns = @JoinColumn(name = "user_id"),
        inverseJoinColumns = @JoinColumn(name = "role_id"))
    private Set<Role> roles = new HashSet<>();
}

@Entity
public class Role {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String roleName;

    @ManyToMany(mappedBy = "roles")
    private Set<User> users = new HashSet<>();
}
✅ Cascade Types Explained
  • CascadeType.PERSIST: Saves the related entity when the owning entity is saved.
  • CascadeType.MERGE: Updates the related entity when the owning entity is updated.
  • CascadeType.REMOVE: Deletes the related entity — ⚠️ not recommended in @ManyToMany as it can lead to unintended deletions.
  • CascadeType.REFRESH: Refreshes the related entity when the owning entity is refreshed.
  • CascadeType.ALL: Includes all of the above.
⚠️ Important Notes
  • DO NOT use CascadeType.REMOVE in @ManyToMany unless you're absolutely sure — it can delete shared entities from the database.
  • It's safer to use only PERSIST and MERGE.
  • The owning side (entity with @JoinTable) should control cascade behavior.
✅ Summary
  • Use cascade = { PERSIST, MERGE } for safe propagation in @ManyToMany.
  • Avoid REMOVE unless managing deletion very carefully.
  • Cascading helps automate saving/updating related entities.

In a bidirectional @ManyToMany relationship, the inverse side is the entity that does not own the relationship. It just maps the relationship using the mappedBy attribute.

📌 Owning vs Inverse Side
  • Owning Side: The entity that defines the @JoinTable. It controls inserts/updates to the join table.
  • Inverse Side: The entity with mappedBy, which simply reflects the relationship defined by the owning side.
✅ Example: User ↔ Role

// Owning Side
@Entity
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    @ManyToMany
    @JoinTable(
        name = "user_roles",
        joinColumns = @JoinColumn(name = "user_id"),
        inverseJoinColumns = @JoinColumn(name = "role_id"))
    private Set<Role> roles = new HashSet<>();
}

// Inverse Side
@Entity
public class Role {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String roleName;

    @ManyToMany(mappedBy = "roles") // Inverse side: refers to 'roles' in User
    private Set<User> users = new HashSet<>();
}
✅ Summary
  • The owning side defines the @JoinTable and controls DB updates.
  • The inverse side uses mappedBy to mirror the relationship.
  • Only the owning side should be used to persist changes to the join table.
  • Inverse helps avoid duplicate join table definitions and keeps the mapping clean.
