The first step is to clarify the workload. “1 million requests per second” is not enough by itself: read/write ratio, payload size, latency target, consistency, availability, request distribution, and peak multiplier determine the design. Assume a globally available product lookup API with 1 million requests per second at peak, 95% reads, 5% writes, p99 latency below 150 ms, and a requirement to survive one availability-zone failure.

3. Keep the API tier stateless

Any request should be able to reach any healthy instance. Do not keep sessions, locks, or authoritative business state in an API server's heap. Store sessions in a shared store or use short-lived signed tokens. This allows Kubernetes or an instance group to add and remove API instances without losing user state.

4. Read path: cache first
public ProductResponse find(String id) {
    ProductResponse cached = localCache.getIfPresent(id);
    if (cached != null) {
        return cached;
    }

    ProductResponse value = redisTemplate.opsForValue()
        .get("product:" + id);
    if (value != null) {
        localCache.put(id, value);
        return value;
    }

    ProductResponse loaded = productRepository.findById(id)
        .orElseThrow(() -> new NotFoundException(id));
    redisTemplate.opsForValue().set(
        "product:" + id, loaded, Duration.ofMinutes(5));
    localCache.put(id, loaded);
    return loaded;
}
  • L1 cache: very low latency and no network hop, but local to one instance and bounded by memory.
  • L2 Redis Cluster: shared cache across instances with sharding and replication.
  • Negative caching: briefly cache not-found results to reduce cache penetration.
  • Stampede protection: use request coalescing, jittered TTLs, or a per-key distributed lock for hot keys.
  • Invalidation: publish product-change events or use versioned keys; never assume cache invalidation is free.
5. Write path and idempotency
@Transactional
public ProductResponse create(String idempotencyKey,
                              CreateProductRequest request) {
    Optional<IdempotencyRecord> previous =
        idempotencyRepository.findByKey(idempotencyKey);
    if (previous.isPresent()) {
        return previous.get().storedResponse();
    }

    Product product = productRepository.save(Product.create(request));
    outboxRepository.save(OutboxEvent.productCreated(product));
    ProductResponse response = ProductResponse.from(product);

    idempotencyRepository.save(
        IdempotencyRecord.completed(idempotencyKey, response));
    return response;
}

The unique constraint on idempotencyKey is essential. If a client retries after a timeout, the server returns the original result instead of creating a duplicate product or charging a customer twice. The transactional outbox commits the database change and event record together; a publisher sends the event to Kafka asynchronously.

6. Database and storage design
  • Use a database that can scale reads with replicas and writes with partitioning or sharding.
  • Choose a partition key that distributes traffic evenly, such as tenant ID plus a hash or entity ID; avoid a single hot tenant or sequential hotspot.
  • Keep database transactions short and index only query paths that are actually required.
  • Do not send every read to the primary; use replicas only where replica lag is acceptable.
  • For high-volume event or telemetry data, write to a partitioned log and consume into storage rather than synchronously updating many tables per request.
  • Separate operational queries from analytics using CDC, events, or a separate read model.

7. Messaging and asynchronous work

The synchronous API should do only the work required to return the contract. Search indexing, notifications, audit processing, recommendations, and analytics should usually be emitted as durable events and processed asynchronously. 

@KafkaListener(topics = "product-events", groupId = "search-indexer")
public void updateSearchIndex(ProductCreated event) {
    searchIndex.upsert(event.productId(), event.name());
    // Commit the offset only after successful processing.
}

Partition by a key that preserves ordering where needed, monitor consumer lag, make consumers idempotent, and use retry topics/dead-letter topics for poison messages. Do not create one Kafka partition per API request; size partitions for throughput and consumer parallelism.

8. Rate limiting and overload protection
  • Apply per-client, per-tenant, and global limits at the edge using a token-bucket or leaky-bucket algorithm.
  • Use bounded thread pools and queues; an unbounded queue only moves overload into memory.
  • Reject early with HTTP 429 when a client exceeds its budget.
  • Use circuit breakers and bulkheads for dependencies such as Redis, databases, and external APIs.
  • Return a fast degraded response when the business contract allows it, such as cached or stale data.

11. Security
  • Terminate TLS at the edge and use mTLS or service identity for sensitive internal calls.
  • Validate JWT issuer, audience, expiry, scopes, and tenant authorization.
  • Use WAF rules, payload limits, schema validation, and request timeouts.
  • Keep secrets in a secret manager; never log tokens, credentials, or sensitive payloads.
  • Use tenant-aware cache keys and authorization checks to prevent cross-tenant data leakage.

Trade-offs and final answer

A robust 1-million-RPS design is not one giant Spring Boot process. It is a horizontally scaled, stateless fleet behind regional load balancing, with edge rate limiting, L1/L2 caching, partitioned storage, asynchronous event processing, idempotent writes, strict timeouts, and complete observability. The final architecture depends on the workload: a read-heavy API can be mostly cache-backed, while a write-heavy system needs partitioned logs, sharded storage, and carefully bounded synchronous work. Prove the sizing with load tests and capacity experiments before production.

“The database is slow” is not enough information to choose a fix. First separate query time, lock wait, connection wait, network time, storage I/O, CPU, memory pressure, replication lag, and application-side serialization. Scaling a broken access pattern often multiplies the load. The first goal is to identify the dominant bottleneck with measurements.

1. Establish a baseline
For reads:
  p50/p95/p99 latency, rows examined, rows returned, cache hit ratio

For writes:
  commit latency, WAL/redo volume, lock wait, fsync latency, batch size

For the database:
  CPU, memory, buffer-cache hit ratio, disk IOPS, disk latency,
  active sessions, connection wait, lock graph, replication lag

For the application:
  pool active/idle/pending, transaction duration, retry count,
  query count per request, payload size, and trace spans

Correlate a slow API trace with the exact SQL, bind values, database plan, connection-pool wait, and lock wait. A request that spends 200 ms waiting for a connection has a different fix from a request whose SQL spends 200 ms scanning disk pages.

2. Find bad read queries
-- Problem: function on the indexed column can prevent an index seek
SELECT * FROM orders
WHERE DATE(created_at) = '2026-10-23';

-- Better: keep the column searchable by the index
SELECT id, customer_id, status, total
FROM orders
WHERE created_at >= '2026-10-23 00:00:00'
  AND created_at <  '2026-10-24 00:00:00';
  • Use EXPLAIN/EXPLAIN ANALYZE and confirm whether the plan uses an index seek, an efficient range scan, or an unintended full-table scan.
  • Return only required columns instead of SELECT *; smaller rows reduce memory, I/O, network, and serialization cost.
  • Fix N+1 queries by batching, joining intentionally, or using a read projection.
  • Paginate with a stable indexed key instead of large OFFSET values.
  • Remove redundant queries and fetch repeated reference data from a bounded cache.
-- Slow at a deep page: database scans/skips many rows
SELECT id, created_at, total
FROM orders
ORDER BY id
LIMIT 50 OFFSET 500000;

-- Keyset pagination: continue after the last ID received
SELECT id, created_at, total
FROM orders
WHERE id > :lastSeenId
ORDER BY id
LIMIT 50;
3. Design the right indexes
-- Query pattern:
SELECT id, status, created_at
FROM orders
WHERE tenant_id = :tenant
  AND status = :status
ORDER BY created_at DESC
LIMIT 50;

-- Composite index follows equality filters, then ordering/range
CREATE INDEX idx_orders_tenant_status_created
    ON orders (tenant_id, status, created_at DESC);

Indexes speed reads by reducing scanned data, but every index also increases write work, storage, cache pressure, and maintenance. Add indexes from measured query patterns, check their usage, remove redundant indexes, and verify plans after deployment. A low-cardinality column alone, such as a boolean status, may not be a useful index unless combined with a selective predicate.

4. Remove lock and transaction bottlenecks
-- Keep the transaction short. Do not call a remote service while holding DB locks.
BEGIN;
UPDATE inventory
SET available = available - 1,
    version = version + 1
WHERE product_id = :id
  AND available > 0
  AND version = :expectedVersion;
COMMIT;
  • Keep transactions short and avoid network calls, user interaction, or slow computation inside them.
  • Update rows in a consistent order to reduce deadlocks.
  • Use optimistic locking for low-conflict updates and retry only bounded transient conflicts.
  • Use row-level locking only where a business invariant requires it; do not lock an entire table by default.
  • Inspect blocking sessions and deadlock graphs rather than increasing transaction timeouts blindly.
5. Fix connection-pool and thread contention
spring:
  datasource:
    hikari:
      maximum-pool-size: 30
      connection-timeout: 1000
      validation-timeout: 500
      leak-detection-threshold: 2000

Do not increase the pool automatically. If the database can execute only 30 useful concurrent queries, a pool of 300 creates contention and context switching. Check active, idle, pending, and timeout metrics. Fix unclosed connections, long transactions, slow queries, and excessive retries before changing pool size.

6. Optimize writes
  • Batch inserts and updates instead of committing one row per transaction.
  • Use prepared statements and bulk operations; avoid ORM-generated one-row-at-a-time loops.
  • Update only changed columns and avoid unnecessary read-before-write operations.
  • Use an idempotency key for retried commands so the same write is not applied twice.
  • Move non-critical work such as search indexing, notifications, and analytics to an outbox/event stream.
  • Keep indexes limited on write-heavy tables; every insert/update must maintain affected indexes.
@Transactional
public void importOrders(List<Order> orders) {
    for (int i = 0; i < orders.size(); i++) {
        entityManager.persist(orders.get(i));
        if (i % 100 == 0) {
            entityManager.flush();
            entityManager.clear();
        }
    }
}
7. Separate hot and cold data

Large historical tables make indexes, backups, vacuum/compaction, and scans more expensive. Partition by a meaningful access key such as time or tenant when the database supports it. Keep hot operational data small, archive cold records, and ensure queries include the partition key so partition pruning can occur. 

-- Conceptual time partitioning
CREATE TABLE audit_event (
    event_id BIGINT NOT NULL,
    created_at TIMESTAMP NOT NULL,
    payload JSONB NOT NULL
) PARTITION BY RANGE (created_at);

-- Queries constrained by created_at can scan only relevant partitions.
8. Use caches and read models carefully
  • Cache stable, frequently read data with a bounded TTL and explicit invalidation/versioning.
  • Use request coalescing or stale-while-revalidate to avoid a cache stampede.
  • Cache negative results briefly to reduce repeated lookups for missing keys.
  • For complex read queries, maintain a denormalized read model updated from durable events.
  • Do not cache highly volatile or authorization-sensitive data without a clear consistency and isolation design.
9. Reduce ORM and serialization overhead
// Prefer a projection when the endpoint needs three columns.
@Query("select new com.example.api.OrderSummary(o.id, o.status, o.total) "
     + "from Order o where o.customerId = :customerId")
List<OrderSummary> findSummaries(Long customerId);

Avoid loading a large entity graph when the endpoint needs a small response. Use projections, fetch plans, batch fetching, and explicit DTO mapping. Confirm the generated SQL; an apparently simple ORM call can still create many queries or select thousands of columns.

10. Handle reads and writes differently

Writes are slowLock waits, transaction length, index count, batch size, trigger cost, WAL/redo and disk latency

Safe improvement sequence
  1. Capture traces, slow-query logs, plans, lock graphs, pool metrics, and database resource metrics.
  2. Fix the top query or lock contributor and measure again with production-like data.
  3. Remove N+1 calls, reduce payloads, add only proven indexes, and shorten transactions.
  4. Batch writes and move non-critical work to asynchronous processing.
  5. Add cache/read models where their consistency model is acceptable.
  6. Retest p95/p99 latency, throughput, error rate, and database resource usage before considering infrastructure scaling.

Interview summary: when a database handling 1 million reads and writes is slow, do not immediately add replicas or a larger machine. First identify whether the time is spent in query execution, scans, locks, connections, I/O, ORM behavior, or retries. Optimize plans and indexes, shorten transactions, batch writes, reduce data loaded, cache safe reads, partition hot data, and move non-critical work asynchronously. Scaling may be needed later, but it should be based on measured saturation after the access path is efficient.

Service A does not call the temporary IP address of a specific instance of B, C, or D. It calls a stable logical service name, such as http://payment-service. A service-discovery system or platform load balancer continuously maps that name to the current healthy instances. When instances scale up, scale down, restart, or move to another node, the mapping changes while the client-facing name remains stable.

Without service discovery
Service A -> 10.0.1.12:8080 (old B instance)

B is replaced by autoscaling:
Service B -> 10.0.4.27:8080

Service A still calls 10.0.1.12 -> connection failure
With platform service discovery
Service A -> payment-service:8080
                  |
                  +-> stable virtual IP / DNS name
                  +-> healthy B instance 10.0.4.27
                  +-> healthy B instance 10.0.5.31

New instance starts -> readiness passes -> added automatically
Old instance stops -> removed automatically

What happens during auto-scaling?
  1. The autoscaler increases the desired replica count based on CPU, request rate, latency, or queue lag.
  2. A new B instance starts and remains out of service while its readiness check is failing.
  3. After readiness succeeds, the platform adds the instance to the service endpoint set.
  4. Service A's load balancer or client-side discovery sends new requests to the healthy instance.
  5. During scale-down, the instance is marked terminating and removed from discovery before it exits.
  6. In-flight requests get a termination grace period; new requests are routed to remaining instances.

  • Timeouts: never wait indefinitely for an instance that is terminating or unhealthy.
  • Retries: retry only transient and idempotent operations, with exponential backoff and jitter.
  • Circuit breaker: stop sending traffic to a failing dependency for a period.
  • Load balancing: distribute requests across healthy endpoints, not merely registered endpoints.
  • Graceful shutdown: fail readiness first, drain traffic, finish safe in-flight work, then terminate.

Important caveats
  • Do not cache IP addresses forever; DNS and registry data must have a bounded refresh/TTL policy.
  • A readiness check means “safe to receive traffic,” while liveness means “restart me if I am stuck”; do not confuse them.
  • Use backward-compatible API and event contracts because autoscaling can run old and new versions simultaneously during deployment.
  • For stateful services, keep state in a database, cache, or durable store rather than local instance memory.
  • Do not use retries to hide overload; retry storms can make a failing dependency worse.
Interview summary

Auto-scaling changes instance IPs, but callers use a stable logical name. Kubernetes Services, DNS, cloud load balancers, or registries maintain the current healthy endpoint set. Readiness checks add new instances only after they can serve traffic and remove terminating instances before shutdown. Timeouts, safe retries, circuit breakers, graceful termination, and bounded endpoint caching ensure Service A continues working while B, C, and D scale or fail.

Consumers are independent and can be deployed or replayed separately.

Publish an event when something has happened, not when another service must synchronously return a result. Use a transactional outbox so the local business change and event record commit together. 5. Request/reply over messaging

A message broker can also implement asynchronous request/reply: include a correlation ID and a reply topic. This is useful when the caller wants a response but can tolerate asynchronous timing and broker-based delivery. Do not turn it into a hidden synchronous HTTP call with unbounded wait times. 

{
  "messageId": "msg-101",
  "correlationId": "corr-789",
  "replyTo": "inventory-replies",
  "type": "GetAvailability",
  "payload": {

}
How to decide
  1. Does the caller need the result now? Choose REST or gRPC for an immediate response; choose a command/event for later work.
  2. Can the caller tolerate eventual consistency? If yes, asynchronous events reduce coupling and improve resilience.
  3. Is this a command or a fact? Use a command such as ReserveStock for requested work; use an event such as StockReserved for a fact that already occurred.
  4. What is the throughput and payload shape? Choose gRPC for high-volume typed internal calls and a broker for buffering and fan-out.
  5. What happens when the dependency is down? If the business can queue/retry, async is safer; if not, define timeout, fallback, and failure response for sync.
  6. Is ordering required? Partition messages by aggregate ID or use a protocol that preserves the required order.
  7. Who owns the data? Avoid direct database reads across service boundaries; call the owning API or consume its events.
Reliability rules for every option
  • Timeouts: every outbound call needs a deadline smaller than the caller's own deadline.
  • Retries: use bounded retries with exponential backoff and jitter; never retry non-idempotent work without an idempotency key.
  • Idempotency: repeated requests or messages must not duplicate business effects.
  • Authentication: use service identity, mTLS, OAuth2 client credentials, or the platform's workload identity.

Option 2: Keyset/cursor pagination
-- First page
SELECT id, status, created_at, total
FROM orders
WHERE tenant_id = :tenantId
ORDER BY created_at DESC, id DESC
LIMIT :limit;

-- Next page uses the last row from the previous page

FROM orders
WHERE tenant_id = :tenantId
  AND (created_at, id) < (:lastCreatedAt, :lastId)
ORDER BY created_at DESC, id DESC
LIMIT :limit;

Keyset pagination asks for rows after the last item received. It remains efficient at deep pages when the ordering columns are indexed, because the database can seek directly to the next range. The cursor should contain the complete position, not only a non-unique timestamp. 

public record OrderCursor(Instant createdAt, long id) { }

public PageResponse<OrderResponse> nextPage(
        String tenantId, int requestedLimit, String encodedCursor) {
    int limit = Math.min(Math.max(requestedLimit, 1), 100);
    OrderCursor cursor = cursorCodec.decode(encodedCursor); // validate signature and expiry

    List<OrderResponse> items = repository.findAfter(
        tenantId, cursor.createdAt(), cursor.id(), limit + 1);

    boolean hasMore = items.size() > limit;
    if (hasMore) {
        items = items.subList(0, limit);
    }

    String next = hasMore
        ? cursorCodec.encode(lastCursor(items))
        : null;
    return new PageResponse<>(items, next, hasMore);
}
Always use a stable, unique order
-- Unsafe: created_at may contain ties
ORDER BY created_at DESC

-- Safe: id breaks ties deterministically
ORDER BY created_at DESC, id DESC

If the ordering column is not unique, rows can appear twice or disappear between pages. Add a unique tie-breaker such as the primary key. The cursor must include both values and the query must use the same direction and filter for every page.

Required index
CREATE INDEX idx_orders_tenant_created_id
    ON orders (tenant_id, created_at DESC, id DESC);

The index should match the tenant/filter predicates and the ordering columns. Verify it with the database execution plan. Without the matching index, cursor syntax alone does not guarantee fast pagination.

A monolith usually performs an in-process method call and may share one transaction, memory cache, connection pool, and database access path. After decomposition, the same business request can become a chain of network calls, serialization steps, independent pools, remote database queries, retries, and distributed consistency work. The traffic rate did not change, but the work per request, latency variance, and failure surface did.

The hidden change
Before:
API -> method call -> shared cache -> one DB transaction

After:
API -> Service A -> Service B -> Service C -> Service D
       |             |             |
       DB/pool       DB/pool       DB/pool
       network + serialization at every boundary

A request that was one local operation can become four network round trips and several database calls. At high concurrency, small delays multiply and queues form at every boundary.

Sharding by user_id guarantees that one user's rows are colocated, but a celebrity can create a much larger access rate than normal users. Even if the 500 million records are evenly distributed, the request distribution is not. The overloaded shard is a hot shard; the celebrity's key is a hot key.

Why changing the hash is not an immediate fix
Current routing:

Celebrity user_id = 42
Millions of requests -> shard-07

Changing the hash function globally would remap many users,
require moving data, and can cause downtime or inconsistent reads.

  • Use request coalescing so concurrent cache misses produce one database load instead of thousands.
  • Serve stale-but-acceptable data for public read endpoints during a short outage or refresh.
  • Apply per-user and per-client rate limits to protect the database from abusive traffic.
  • Move expensive fan-out work to asynchronous workers and precompute the celebrity's read model.

Long-term fix 3: virtual shards and rebalancing

Instead of mapping users directly to physical shards, map them to many virtual shards. Physical database nodes own ranges of virtual shards. When one node is hot, move selected virtual shards to a new node rather than remapping all 500 million records. 

user_id -> virtual shard 1842 -> physical shard A

Online rebalance:
1. Copy virtual shard 1842 to physical shard C.
2. Replicate changes while copying.
3. Switch the routing directory atomically to shard C.
4. Verify reads and writes.
5. Remove the old copy after a retention period.
No-downtime migration plan
  1. Measure: confirm the hot key, read/write ratio, p99 latency, lock waits, pool usage, and storage capacity.
  2. Prepare: create the routing directory, new bucket/shard schema, indexes, cache namespace, and monitoring.
  3. Dual-write: for the selected celebrity data, write the old authoritative location and the new bucket/replica using an idempotent outbox or CDC pipeline.
  4. Backfill: copy historical rows in bounded batches, throttled below the shard's safe capacity.
  5. Verify: compare counts, checksums, versions, and sampled reads between old and new locations.
  6. Shadow-read: read the new location in the background and compare results without serving them yet.
  7. Read switch: use a feature flag or atomic directory version to route a small percentage of reads to the new location.
  8. Ramp up: move traffic gradually while monitoring latency, errors, lag, and database load.
  9. Write switch: make the new placement authoritative after the replication lag is zero and verification succeeds.
  10. Retire: stop dual-writing after a safe period, keep the old copy for rollback, then delete it asynchronously.

Option 1: database sequence plus Base62
private static final char[] BASE62 =
    "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
        .toCharArray();

static String toBase62(long value) {
    if (value == 0) return "0";

    StringBuilder result = new StringBuilder();
    while (value > 0) {
        int remainder = (int) (value % 62);
        result.append(BASE62[remainder]);
        value /= 62;
    }
    return result.reverse().toString();
}

// Each call receives a unique sequence value.
long id = sequence.nextValue();
String code = toBase62(id);

A database sequence or atomic distributed counter gives every request a unique numeric ID. Base62 converts the ID into a shorter URL-safe string. The sequence value is unique even when many service instances request values concurrently. Gaps are acceptable because failed transactions can consume sequence values.

Option 2: atomic Redis counter

} catch (DuplicateKeyException ex) {

Redis INCR is atomic on one Redis primary. Protect the counter with persistence, replication, failover planning, and monitoring; a failover or accidental counter reset must not generate IDs that collide with already persisted codes. The database unique constraint remains necessary.

Option 3: distributed ID generator
Snowflake-style ID:
  timestamp bits | worker/instance bits | per-millisecond sequence bits

Each instance receives a unique worker ID.
The generated 64-bit ID is globally unique under the configured constraints.
Encode it with Base62 for the public short code.

  • Handle clock rollback; timestamp-based generators must not silently produce duplicates when time moves backward.
  • Reserve enough sequence bits for the expected per-instance rate.
  • Keep the database unique constraint as a final safety net.

Random codes can be acceptable when the alphabet and length provide enough space, but collisions are mathematically possible. Let the unique constraint decide the race; do not trust an existence check. Keep retries bounded so a problem in the generator cannot create an infinite request loop.

Duplicate codes and duplicate requests are different problems. If a client retries the same create request, an idempotency key should return the original short code instead of creating a second URL. Reject reuse of the same key with a different request payload.

Creation flow
1. Authenticate user and validate the long URL.
2. Check idempotency key for an existing completed response.
3. Allocate a unique numeric ID or random candidate code.
4. Convert ID to Base62 if using a counter.
5. Insert short_code with a database unique constraint.
6. On duplicate-key error, retry with a new candidate a bounded number of times.
7. Store the idempotency result and return the code.
8. Cache short_code -> original_url for redirect traffic.
Multi-region considerations
  • Use one globally coordinated ID generator, or allocate non-overlapping worker/region bits.
  • Do not use independent regional counters that can produce the same Base62 code.
  • Use globally unique database constraints or route code creation to an authoritative region.
  • Separate code generation from redirect reads; redirects can be served from replicated caches and read stores.
  • If code length must remain fixed, calculate the capacity of the alphabet: Base62 with 7 characters provides 627 possible combinations.
Recommended design

For a typical TinyURL service, generate a unique numeric ID using a database sequence or Snowflake-style service, encode it with Base62, insert it under a unique index, and use an idempotency key for client retries. Cache redirects aggressively. The generator improves collision avoidance, but the unique database constraint is what guarantees correctness under concurrency.

Failover changes the location of traffic, but it does not remove the work. If Server A is already overloaded or failing because a shared dependency is unhealthy, moving all of A's work to B can overload B. B then fails, the load balancer sends traffic to C, and the failure spreads. This is a cascading failure: a local failure becomes a system-wide failure because there is no capacity isolation or overload control.

Normal:

B fails -> C receives more traffic -> C fails -> system outage

Option 1: Shared Redis cache

This is the usual choice when many application instances need the same cached data. Redis owns the shared cache state, while each application server may keep a short-lived L1 cache for speed. Use Redis Cluster or a managed Redis service for partitioning and failover.

Option 2: Consistent-hash routing

Route the same key to the same cache server using consistent hashing. This improves locality and avoids copying every key everywhere, but it requires rebalancing when servers join or leave. Use virtual nodes and replication so one cache-server failure does not lose all keys for a range. 

hash("user-42") -> virtual node -> Cache Server B
hash("user-91") -> virtual node -> Cache Server A

Consistent hashing is useful for a cache-only cluster, but it is not a replacement for durable storage. A miss must still be safely rebuilt from the database or another authoritative source.

Option 3: Sticky sessions

The load balancer can keep a user on one server, making that server's LRU more useful. However, sticky sessions create uneven load, make failover more expensive, and do not solve sharing for batch jobs or service-to-service calls. Treat this as an optimization, not the primary cache design.

Read path:

Choose an ID scheme that matches the required guarantees: uniqueness, global scope, sortability, length, generation latency, and whether IDs must be unpredictable. Option 1: Snowflake-style 64-bit ID
| 1 unused sign bit | 41-bit timestamp | 10-bit worker ID | 12-bit sequence |

Timestamp: milliseconds since a custom epoch
Worker ID: assigned to one server/instance, 0-1023
Sequence: 0-4095 IDs per worker per millisecond

Capacity: 1024 workers x 4096 IDs/ms per worker
IDs are unique and roughly increasing without a database round trip.

The worker ID must be unique at the same time. Assign it through deployment configuration, a coordinator such as ZooKeeper/etcd, a Kubernetes StatefulSet ordinal, or a carefully managed machine identity. Do not let two live instances accidentally use the same worker ID. 

public final class SnowflakeIdGenerator {
    private static final long EPOCH = 1704067200000L; // 2024-01-01 UTC
    private static final int WORKER_BITS = 10;
    private static final int SEQUENCE_BITS = 12;
    private static final long MAX_WORKER = (1L << WORKER_BITS) - 1;
    private static final long MAX_SEQUENCE = (1L << SEQUENCE_BITS) - 1;

    private final long workerId;
    private long lastMillis = -1;
    private long sequence = 0;

    public SnowflakeIdGenerator(long workerId) {
        if (workerId < 0 || workerId > MAX_WORKER) {
            throw new IllegalArgumentException("worker ID out of range");
        }
        this.workerId = workerId;
    }

    public synchronized long nextId() {
        long now = System.currentTimeMillis();
        if (now < lastMillis) {
            throw new IllegalStateException("Clock moved backwards");
        }
        if (now == lastMillis) {
            sequence = (sequence + 1) & MAX_SEQUENCE;
            if (sequence == 0) {
                now = waitForNextMillis(lastMillis);
            }
        } else {
            sequence = 0;
        }
        lastMillis = now;
        return ((now - EPOCH) << (WORKER_BITS + SEQUENCE_BITS))
            | (workerId << SEQUENCE_BITS)
            | sequence;
    }

    private long waitForNextMillis(long previous) {
        long now;
        do {
            now = System.currentTimeMillis();
        } while (now <= previous);
        return now;
    }
}

This sample is thread-safe within one generator instance. Production code must also define what to do on clock rollback: fail closed, wait until the previous timestamp catches up, use a logical clock, or switch to another generator. Never silently generate duplicate IDs after a rollback.

Snowflake, UUIDv7, and ULID are approximately time ordered, not a perfect global ordering of events. Network delay, clock skew, retries, and concurrent transactions can make an ID's order differ from commit order. If business correctness requires ordering, store a per-aggregate version or use an ordered event partition in addition to the global ID.

  • Spread partitions with jitter instead of starting every tenant at exactly midnight.
  • Use calendar, timezone, daylight-saving, and missed-run policies explicitly.
  • Do not run duplicate singleton maintenance jobs unless they use a distributed lock or partition ownership.
10. Observe and protect the main system
Batch: queued/running/completed/failed/canceled jobs, duration, SLA misses
Queue: depth, oldest message age, throughput, retry/DLQ count
Workers: active count, CPU/memory, lease expiry, partition latency
Database: connections, pool wait, CPU, locks, replica lag, query p99
Providers: rate limit, 429/5xx, delivery outcome, external latency
Correctness: duplicate effects, skipped partitions, reconciliation difference
Main app: API p99, error rate, saturation, cache hit ratio during batch windows

Set an emergency kill switch that stops new batch work while preserving queued messages. Alert when batch activity changes interactive latency, when the oldest job misses its SLA, or when a partition is stuck. Trace job ID, partition ID, user/tenant scope, attempt number, and downstream request ID.

Interview summary: create asynchronous jobs, partition millions of users into resumable work units, process them with isolated bounded workers, and use durable queues for backpressure. Add fair scheduling, quotas, idempotency, retries, leases, progress, cancellation, secure outputs, and observability. Protect the main application with separate compute and data capacity, and reduce or pause batch traffic automatically when interactive SLOs are threatened.

Do not make reads and writes compete for exactly the same resources. Separate their paths, scale them independently, and define which data requires immediate consistency. A typical design uses a write-optimized source of truth, asynchronous events for derived read models, read replicas and caches for query traffic, and bounded queues to absorb unpredictable write spikes.

Reference architecture
Clients
  -> API gateway and rate limits
      -> command/write path -> primary/sharded OLTP store
                              -> outbox/event stream
                                  -> read-model builders and analytics
      -> query/read path -> L1/L2 cache -> read replica/materialized view/search index

Autoscaling signals:
  reads: request rate, cache misses, p99 latency
  writes: queue depth, commit latency, log/disk throughput

Critical writes are admitted by capacity; optional work is queued or shed.
1. Identify the workload shape
Read-heavy example: 100,000 reads/sec, 1,000 writes/sec
Write-heavy example: 50,000 writes/sec, 5,000 reads/sec
Spike example: normal 10,000 reads/sec -> 1,000,000 reads/sec for 30 seconds

Measure:
- read/write ratio and request size
- hot keys and tenant concentration
- consistency and freshness requirements
- burst duration and acceptable queue delay
- write amplification from indexes, events, and replicas

Averages hide the problem. Design for peak arrival rate, burst duration, recovery time, and the slowest dependency. A cache hit, a database point read, and a multi-table report have very different capacity costs even if they are all called “reads.”

2. Optimize the read path
Query request
  -> normalize authorization-aware cache key
  -> local L1 cache
  -> shared Redis/CDN cache
  -> read replica or materialized read model
  -> authoritative database only when necessary

Use TTL jitter, single-flight loading, bounded result sizes,
cursor pagination, and stale-while-revalidate where safe.
  • Cache immutable and frequently requested data at the edge or application layer.
  • Use short L1 caches plus a shared L2 cache when many application instances serve the same keys.
  • Use read replicas or a denormalized search/read model for query shapes that do not need primary reads.
  • Prevent cache stampedes, penetration, and hot-key overload with coalescing and per-key limits.
  • Return bounded pages and selected fields; never let a normal API scan or return millions of rows.
3. Optimize the write path
Command
  -> validate and authorize
  -> short transaction on the source of truth
  -> append outbox event
  -> acknowledge after durable commit

Optional downstream work:
  -> queue for indexing, notifications, analytics, projections

Batch independent writes where safe, use prepared statements,
avoid unnecessary indexes, and partition by a balanced key.

Keep the transaction short and avoid calling remote services inside it. Every extra index, synchronous event publish, trigger, and replica increases write cost. Use an outbox so a committed write is not lost from the event stream, and let non-critical consumers catch up asynchronously.

4. Use CQRS or purpose-built read models when needed
Write model: normalized orders/payments/inventory
  -> OrderCreated, OrderPaid, OrderUpdated events
      -> customer order timeline in Redis/Cassandra
      -> search index for text/filter queries
      -> analytics aggregates in warehouse

Read model is rebuilt from events and can be scaled independently.
The API documents that derived views may be eventually consistent.

CQRS is useful when read and write access patterns differ significantly. It adds event schemas, replay, lag, and consistency complexity, so do not introduce it for a simple CRUD application without a scaling or query-shape reason.

5. Absorb unpredictable spikes
Traffic spike
  -> gateway admission control and per-tenant quotas
  -> serve cache hits immediately
  -> queue work that can be delayed
  -> shed optional features and expensive queries
  -> autoscale stateless APIs and consumers
  -> protect database with connection and concurrency limits

When the queue is full: fail fast with 429/503 and Retry-After,
do not create unlimited threads or database connections.

Queueing is useful only when the business can tolerate delay. For a user-facing read, serve stale or degraded data where safe. For a payment or inventory command, preserve correctness and reject excess traffic rather than pretending it succeeded.

6. Scale storage correctly
PressureDesign response
Many repeated readsCDN, Redis/L1 cache, materialized views, request coalescing
Many independent readsRead replicas, search cluster, partitioned query store
High write ratePartition/shard, append log, batch, remove unnecessary indexes
One hot key or tenantReplicate hot data, shard/salt where semantics allow, rate-limit the source
Large analytical scansWarehouse/lake and asynchronous reports, never the OLTP primary

Replication improves read capacity and availability; it does not automatically increase write capacity. Sharding can increase write and storage capacity, but requires routing, rebalancing, and cross-shard query trade-offs.

7. Handle consistency explicitly
Strong: payment, inventory reservation, account balance
  -> authoritative write store and carefully chosen read source

Read-after-write: user just changed profile
  -> sticky/version-aware read or wait for projection version

Eventual: recommendations, counters, search, dashboards
  -> local read model with freshness/lag monitoring

Never serve stale data for a decision that can lose money or violate policy.
8. Isolate failures
  • Use separate connection pools, thread pools, queues, and database users for reads, writes, and batch work.
  • Apply circuit breakers and timeouts independently to cache, replicas, primary, search, and event consumers.
  • Prevent a slow replica from blocking the write path; route only healthy replicas.
  • Use bulkheads so a hot tenant or expensive report cannot exhaust all API capacity.
  • Use read-only degraded mode during write-store pressure only when the product can safely support it.
9. Autoscale using the right signals
API: request rate, concurrency, p95/p99 latency, rejected requests
Read path: cache miss rate, replica CPU, query latency, hot-key rate
Write path: commit latency, queue depth, log flush, disk IOPS, lock wait
Consumers: lag, oldest event age, projection rebuild rate
Database: connections pending, locks, replication lag, storage growth

Scale before CPU alone becomes the bottleneck; CPU may be low while
connections, disk, locks, or queue age are already saturated.
10. Example decision flow
A score endpoint receives a million reads during a live event:
1. CDN/Redis serves the same score snapshot for most requests.
2. Only one request refreshes a key through single-flight.
3. The write/event path updates the score store asynchronously.
4. If Redis fails, serve a recent bounded stale value or 503; do not fan out to the database.
5. A separate analytics consumer records the event stream without blocking the score update.

A payment write spike occurs at the same time:
1. Reserve database write capacity and queue non-critical work.
2. Use idempotency keys and bounded retries.
3. Reject excess requests safely instead of accepting work the system cannot commit.

Interview summary: separate read and write paths, cache and replicate reads, shard and batch writes, and use an outbox/event stream for asynchronous projections. Absorb spikes with bounded queues, admission control, quotas, and load shedding; isolate pools and dependencies; define consistency per operation; and autoscale from latency, queue, connection, lock, and lag signals. Reliability means protecting the write source of truth while serving safe degraded reads, not simply adding more application instances.

Reduce latency at every hop: serve static and cacheable content from a CDN, route users to a nearby healthy region, keep services and data close to the user, minimize cross-region calls, and measure the complete request path. Global low latency is a combination of network placement, storage design, payload size, caching, connection reuse, and consistent routing.

Reference architecture
User -> Anycast/global load balancer
     -> nearest healthy region
         -> regional API gateway
         -> stateless services
         -> local cache and regional read model
         -> home-region or globally consistent write store

Static assets, images, and public responses -> CDN edge
Async events and replicated read models move data between regions.
Design steps
  1. Set a target such as p95 API latency under 150 ms by geography, not only one global average.
  2. Use a CDN for immutable assets, compression, HTTP/2 or HTTP/3, and cacheable public responses.
  3. Use latency-based routing with health checks and gradual failover to another region.
  4. Keep read traffic local through regional caches, replicas, search indexes, or materialized views.
  5. Assign each user or tenant a home region for writes when strong ownership is required.
  6. Use asynchronous replication for data that can be eventually consistent.
  7. Reduce payloads with field selection, pagination, compact serialization, and connection pooling.
Data and consistency trade-offs
Product catalog -> replicated local read model and CDN
User profile    -> home-region writes, replicated reads
Payment/balance -> authoritative strongly consistent owner
Analytics       -> asynchronous event replication and warehouse

Do not add a synchronous cross-region database call to every request
and still expect consistently low latency.

A request can be fast in the API layer but slow because it waits for a remote database, cache miss, or third-party provider. Include replication lag and read-after-write behavior in the product contract. For critical state, prefer correctness over an unsafe stale response.

Example latency budget
Edge to region:          35 ms
Gateway and auth:        10 ms
Local cache/read model:  20 ms
Service processing:      25 ms
Serialization/network:   15 ms
Safety margin:           45 ms
                         ----
                         150 ms p95

Track the budget by region and endpoint. Warm caches and capacity before a planned event, use request deadlines, and return a bounded degraded response instead of allowing one remote dependency to hold the entire request open.

Operational requirements
  • Deploy the same immutable service version and compatible schemas in every region.
  • Monitor p50/p95/p99 latency, cache hit ratio, route selection, replication lag, and cross-region calls.
  • Use regional circuit breakers, bulkheads, capacity reservations, and health-aware routing.
  • Test region failure, DNS or Anycast failure, stale reads, cold caches, and provider latency regularly.
  • Respect data residency, encryption, privacy, and tenant-isolation requirements.

Interview summary: place users near a healthy regional serving stack, push cacheable content to the edge, keep reads local, choose a clear write ownership model, and replicate only what can be replicated safely. Optimize payloads and connection reuse, minimize synchronous cross-region calls, and verify the design with geography-specific latency and failover tests.

Separate the long-lived connection layer from message persistence and fan-out. WebSocket or another bidirectional protocol handles active connections, while a durable message log stores messages and allows delivery workers to recover after a connection or server failure. Presence, typing indicators, and read receipts should be treated as lower-durability signals than chat messages.

Reference architecture
Client -> edge/load balancer -> connection gateway
                                    -> connection registry: user -> gateway/shard
                                    -> message service -> durable log
                                                       -> conversation store
                                                       -> fan-out workers
                                    -> online recipients over WebSocket
                                    -> offline push notification service

Media files use object storage and signed URLs; chat messages contain metadata,
not large binary payloads.
Connection and message flow
1. Client authenticates and opens a WebSocket connection.
2. Gateway registers user/device and heartbeat with a TTL.
3. Sender submits message with client-generated idempotency key.
4. Message service authorizes the conversation and persists the message.
5. Durable event is published after persistence.
6. Fan-out delivers to connected recipients or records an unread state.
7. Client acknowledges with message ID and server sequence.

A gateway restart causes reconnect and replay from the last acknowledged sequence.

Never use the in-memory connection on one server as the only copy of a message. A connection server can disappear at any time; delivery must be recoverable from the durable store or event log.

Partitioning and scale
  • Shard conversations by conversation ID or a stable participant/tenant key.
  • Keep ordering guarantees scoped to one conversation, not the entire global system.
  • Scale connection gateways by active connections, memory, file descriptors, and message rate.
  • Scale message and fan-out workers by queue depth, oldest message age, and conversation hot spots.
  • Use backpressure and per-conversation limits for a celebrity group or broadcast room.
  • Use a connection registry with TTLs; do not rely on a permanently accurate presence record.
Delivery semantics and idempotency
Message key = conversationId + ":" + clientMessageId

Persist with a unique constraint before acknowledging the sender.
If the sender retries, return the existing server message ID.
Recipients may receive a duplicate after reconnect, so clients deduplicate
by server message ID and request messages after their last acknowledged cursor.

At-least-once delivery with client deduplication is usually more practical than pretending to provide exactly-once delivery over networks. Use sequence numbers per conversation for ordering and expose a resynchronization endpoint when a client detects a gap.

Presence, typing, and notifications
Presence: ephemeral key with TTL and heartbeat
Typing: coalesced events, short expiry, best effort
Read receipt: durable if the product needs it, otherwise compacted state
Push notification: asynchronous queue, provider rate limits, deduplication

Do not persist every typing event as a permanent chat message.

Presence is approximate by design. A mobile device may lose connectivity without sending a clean disconnect. Use heartbeats and expiration, and show “last seen” semantics rather than making unsafe real-time claims.

Reliability and security
  • Use TLS, short-lived access tokens, conversation authorization, and tenant isolation.
  • Apply message size, send rate, connection, and group-member limits to prevent abuse.
  • Use per-user and per-conversation circuit breakers and bounded fan-out queues.
  • Persist messages before delivery and retain enough history for reconnect replay.
  • Handle offline users through unread counters and push notifications, not unbounded gateway buffering.
  • Define retention, deletion, encryption, moderation, and legal hold requirements before choosing storage.
Monitor the system
Connections: active, reconnect rate, heartbeat failures, gateway memory/file descriptors
Messages: accepted, persisted, delivered, duplicate, rejected, end-to-end latency
Queues: depth, oldest message age, fan-out lag, DLQ count
Storage: write latency, replication lag, hot conversations, unread state size
Quality: delivery gap rate, push success, presence freshness, dropped best-effort events
Security: authentication failures, rate-limit hits, suspicious fan-out and abuse patterns

Interview summary: use stateless scalable connection gateways, a durable conversation store and event log, partitioned fan-out workers, and a connection registry with TTLs. Persist before acknowledging, use idempotency and cursors for reconnects, keep ordering per conversation, treat presence and typing as ephemeral, protect hot rooms with backpressure, and monitor end-to-end delivery rather than only WebSocket connection count.
