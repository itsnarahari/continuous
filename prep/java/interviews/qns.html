In Java, custom/global exceptions are often extended from RuntimeException, especially in Spring Boot REST APIs, because most application exceptions are not realistically recoverable by the immediate caller.

The core difference is: 

// Checked exception
public class UserNotFoundException extends Exception {
    public UserNotFoundException(String message) {
        super(message);
    }
}

// Unchecked exception
public class UserNotFoundException extends RuntimeException {
    public UserNotFoundException(String message) {
        super(message);
    }
}

If you extend Exception, Java forces the caller to handle or declare it: 

public User getUser(Long id) throws UserNotFoundException {
    if (id == null) {
        throw new UserNotFoundException("User not found");
    }
    return repository.findById(id).orElse(null);
}

Then this caller must also deal with it: 

public void processUser() {
    try {
        User user = getUser(10L);
    } catch (UserNotFoundException e) {
        // forced handling
    }
}

Or propagate it: 

public void processUser() throws UserNotFoundException {
    User user = getUser(10L);
}

That can spread through many layers: 

Controller
   -> throws UserNotFoundException
Service
   -> throws UserNotFoundException
Repository

But in a Spring Boot REST API, suppose the user does not exist: 

public User getUser(Long id) {
    return repository.findById(id)
        .orElseThrow(() ->
            new UserNotFoundException("User not found: " + id)
        );
}

Usually, the service caller cannot meaningfully fix that missing user. We want the exception to bubble up to centralized handling: 

public class UserNotFoundException extends RuntimeException {

    public UserNotFoundException(String message) {
        super(message);
    }
}

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<String> handleUserNotFound(
            UserNotFoundException ex) {

        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(ex.getMessage());
    }
}

The flow is: 

HTTP GET /users/100
        ->
Controller
        ->
Service
        ->
repository.findById(100)
        ->
Not found
        ->
throw UserNotFoundException
        ->
No try/catch needed in Service
        ->
No try/catch needed in Controller
        ->
@RestControllerAdvice catches it
        ->
HTTP 404 response

That is why RuntimeException fits very naturally.

Useful rule
Situation Prefer
User not found RuntimeException
Invalid business state RuntimeException
Duplicate email RuntimeException
Insufficient balance Usually RuntimeException
Validation failure RuntimeException
REST API domain error RuntimeException
Caller is expected to recover Checked Exception
Caller must consciously handle failure Checked Exception

For example, a checked exception can make sense when recovery is genuinely expected: 

public void importFile(Path path) throws InvalidImportFileException {
    // caller may ask user to upload another file
}

But even here, many modern Java/Spring applications still choose unchecked exceptions depending on architecture.

Spring transaction rollback behavior

One more important reason in Spring: by default, Spring rolls back transactions for unchecked exceptions such as RuntimeException, but not generally for checked exceptions. 

@Transactional
public void transferMoney() {
    debit();
    credit();

    throw new PaymentFailedException();
}

If: 

class PaymentFailedException extends RuntimeException

Rollback happens by default.

If: 

class PaymentFailedException extends Exception

You may need: 

@Transactional(rollbackFor = PaymentFailedException.class)

So the deeper answer is: we do not extend RuntimeException merely because it is convenient. We use it when the caller is not expected to recover locally and the exception should propagate to a centralized boundary such as @RestControllerAdvice.

Best interview sentence: I use checked exceptions when the caller is expected to explicitly recover from the failure; I use unchecked exceptions for programming errors, invalid state, and domain/API failures that should propagate to centralized exception handling.

Best interview answer

Jackson is the JSON processing and data-binding library commonly integrated with Spring Boot REST APIs. On an incoming request, @RequestBody tells Spring MVC to read the HTTP body. Spring selects an appropriate HttpMessageConverter; for JSON this is commonly MappingJackson2HttpMessageConverter, which delegates to a configured Jackson ObjectMapper to deserialize JSON into the controller parameter type. On the response side, @RestController or @ResponseBody causes the returned Java object to be written to the HTTP response body, and the Jackson message converter serializes it into JSON. The main ObjectMapper operations include readValue, writeValueAsString, readTree, treeToValue, valueToTree, and convertValue. For generic types such as List<User>, we use TypeReference or JavaType because of Java type erasure. In production, I prefer reusing Spring Boot's configured mapper, using DTOs instead of exposing JPA entities directly, registering modules for special types, and handling malformed JSON centrally through @RestControllerAdvice.

Best interview answer

When a client calls a Spring Boot MVC REST API, the request first reaches the server operating system and the embedded Servlet container, commonly Tomcat. Tomcat's Connector and NIO infrastructure manage socket activity, and request processing is assigned to a worker thread. The request enters the Servlet FilterChain, where custom filters and Spring Security filters can perform authentication and authorization. If allowed, it reaches Spring MVC's DispatcherServlet, which acts as the Front Controller. DispatcherServlet asks a HandlerMapping to locate the matching controller handler and receives a HandlerExecutionChain containing the handler and mapped interceptors. After interceptor preHandle methods succeed, a compatible HandlerAdapter invokes the controller method. Before invocation, HandlerMethodArgumentResolvers resolve values such as @PathVariable, @RequestParam, and @RequestHeader. For @RequestBody, Spring selects an HttpMessageConverter; for JSON, a Jackson-based converter commonly delegates to ObjectMapper for deserialization. Bean Validation then runs when @Valid is present. The controller calls the service, which may pass through Spring AOP proxies for concerns such as @Transactional. The repository is commonly a Spring Data-generated proxy that delegates through JPA EntityManager and Hibernate, obtains a connection from the pool, and executes SQL through JDBC. The result returns to the service, is mapped to a DTO, and returns to the controller. Spring MVC then processes the return value, performs content negotiation, selects an HttpMessageConverter, and Jackson serializes the Java response object into JSON. Interceptor completion callbacks run, the Servlet filter chain unwinds, Tomcat writes the HTTP response to the socket, and the worker thread normally returns to the pool for reuse. If an exception occurs, Spring MVC's HandlerExceptionResolver infrastructure can route it to matching @ExceptionHandler or @RestControllerAdvice methods and serialize the resulting error response.

Best interview answer

Tomcat can manage far more TCP connections than worker threads because a connection is not the same as an active request and is not permanently tied to one worker thread. With the NIO connector, incoming connections are accepted by Acceptor logic and represented through non-blocking socket infrastructure. Connections are monitored for I/O readiness by Poller logic using Java NIO Selector-style mechanisms backed by operating-system readiness facilities. Idle keep-alive connections therefore do not need one permanently blocked application worker thread each. When a socket becomes readable because HTTP request data arrives, Tomcat schedules socket-processing work to its executor. An available worker thread then performs request processing through the Servlet FilterChain, Spring Security, DispatcherServlet, Controller, Service, Repository, and downstream systems. After the response completes, the worker thread returns to the pool, while the TCP connection may remain open and return to readiness monitoring for a later request. This is why thousands of connections can coexist with only hundreds of request workers. However, NIO only solves efficient network connection management; it does not make blocking JDBC, database calls, or external HTTP calls non-blocking. If all worker threads are blocked on slow downstream systems, Tomcat can still suffer thread-pool exhaustion. Redis uses a related I/O multiplexing idea but is more event-loop-centered for command processing, which works extremely well because most Redis operations are short, in-memory operations. The core principle in both systems is that a large number of connected clients does not require the same number of dedicated threads.

Best interview answer

Platform Threads are expensive OS-backed threads, so traditional Spring MVC applications normally use a bounded worker pool such as a few hundred request-processing threads. The scalability problem appears when these expensive threads spend most of their time waiting for databases, remote APIs, files, or other I/O. Virtual Threads provide a lightweight Java Thread abstraction managed by the JVM. A Virtual Thread executes by mounting onto a carrier Platform Thread. When it reaches a supported blocking operation, it can often suspend and unmount, allowing the carrier to execute another runnable Virtual Thread. Later, when the operation completes, the Virtual Thread becomes runnable and may continue on the same or a different carrier. This allows very large numbers of concurrent waiting tasks without requiring the same number of OS threads. However, Virtual Threads do not make JDBC non-blocking, do not increase CPU cores, do not remove HikariCP limits, and do not make downstream systems infinitely scalable. Pinning and long blocking operations in problematic critical sections must still be understood, with behavior considered against the actual JDK version. ThreadLocal and Spring transaction context can work because the Virtual Thread remains the logical Thread even when carrier threads change, but arbitrary asynchronous task boundaries such as @Async still require separate context-propagation thinking. Compared with WebFlux, Virtual Threads preserve simple imperative programming and integrate naturally with existing blocking ecosystems such as Spring MVC, JPA, Hibernate, and JDBC, while WebFlux uses a small event-loop model with reactive pipelines and requires blocking work to stay away from event-loop threads. The most important production rule is that cheap threads do not mean unlimited capacity: database connections, external API concurrency, CPU, memory, sockets, and downstream services still require explicit limits, timeouts, bulkheads, and backpressure strategies.

@GeneratedValue tells JPA/Hibernate how the primary key value should be generated for an entity. It is commonly used with @Id. 

@Entity
class Employee {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
}

JPA provides four main strategies: AUTO, IDENTITY, SEQUENCE, and TABLE.

1. GenerationType.IDENTITY

The database generates the primary key using an auto-increment column. Hibernate inserts the row first and then reads the generated id from the database. 

@Entity
class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
}
CREATE TABLE product (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL
);

Use IDENTITY mostly with MySQL, SQL Server, and databases where auto-increment identity columns are common.

2. GenerationType.SEQUENCE

The database sequence generates the id before the insert. Hibernate can ask the sequence for the next value and then use that value while inserting the row. 

@Entity
class OrderEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq")
    @SequenceGenerator(
        name = "order_seq",
        sequenceName = "order_sequence",
        allocationSize = 1
    )
    private Long id;

    private String orderNumber;
}
CREATE SEQUENCE order_sequence
    START WITH 1
    INCREMENT BY 1;

CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    order_number VARCHAR(100) NOT NULL
);

Use SEQUENCE mostly with PostgreSQL, Oracle, and databases that support sequences. It is often better for batching than IDENTITY.

3. GenerationType.AUTO

Hibernate chooses the best strategy based on the database dialect. For example, it may choose SEQUENCE for PostgreSQL or a different strategy depending on the database. 

@Entity
class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.AUTO)
    private Long id;

    private String email;
}

Use AUTO when you want Hibernate to decide. For interview answers and production clarity, many teams prefer explicitly choosing IDENTITY or SEQUENCE.

4. GenerationType.TABLE

Hibernate uses a separate table to store and update id values. This works across databases, but it is usually slower because every id generation needs extra table access. 

@Entity
class Invoice {
    @Id
    @GeneratedValue(strategy = GenerationType.TABLE, generator = "invoice_gen")
    @TableGenerator(
        name = "invoice_gen",
        table = "id_generator",
        pkColumnName = "gen_name",
        valueColumnName = "gen_value",
        pkColumnValue = "invoice_id",
        allocationSize = 1
    )
    private Long id;

    private Double amount;
}
CREATE TABLE id_generator (
    gen_name VARCHAR(100) PRIMARY KEY,
    gen_value BIGINT NOT NULL
);

CREATE TABLE invoice (
    id BIGINT PRIMARY KEY,
    amount DOUBLE
);

Use TABLE rarely. It is mostly useful for legacy databases or databases without identity or sequence support.

Comparison table
Strategy How id is generated Common database When to use
AUTO Hibernate chooses automatically Depends on dialect Simple apps, database-independent code
IDENTITY Auto-increment column MySQL, SQL Server When the database table owns id generation
SEQUENCE Database sequence PostgreSQL, Oracle High-performance inserts and batching
TABLE Separate id generator table Any database Legacy or portable fallback, rarely preferred
Important interview points
  • IDENTITY gets the id from an auto-increment column after insert.
  • SEQUENCE gets the id from a database sequence before insert.
  • SEQUENCE usually works better with Hibernate batch inserts.
  • AUTO lets Hibernate choose, but explicit strategy is clearer.
  • TABLE is portable but slower and rarely used in modern applications.

Interview one-liner: use IDENTITY for MySQL-style auto-increment, use SEQUENCE for PostgreSQL/Oracle sequence-based ids, avoid TABLE unless needed, and use AUTO only when you are comfortable letting Hibernate decide.

We have a list of employees, and each employee has multiple hobbies. The requirement is to return a map where the key is the hobby and the value is the list of employee names who have that hobby. 

class Employee {
    private String name;
    private List<String> hobbies;

    public Employee(String name, List<String> hobbies) {
        this.name = name;
        this.hobbies = hobbies;
    }

    public String getName() {
        return name;
    }

    public List<String> getHobbies() {
        return hobbies;
    }
}
List<Employee> employees = Arrays.asList(
    new Employee("Ravi", Arrays.asList("Cricket", "Music")),
    new Employee("Anu", Arrays.asList("Music", "Reading")),
    new Employee("Kiran", Arrays.asList("Cricket", "Travel"))
);

Expected output: 

{
    Cricket=[Ravi, Kiran],
    Music=[Ravi, Anu],
    Reading=[Anu],
    Travel=[Kiran]
}
Way 1: Using flatMap + groupingBy + mapping
Map<String, List<String>> hobbyToEmployeeNames =
    employees.stream()
        .flatMap(employee ->
            employee.getHobbies().stream()
                .map(hobby ->
                    new AbstractMap.SimpleEntry<>(hobby, employee.getName())
                )
        )
        .collect(Collectors.groupingBy(
            Map.Entry::getKey,
            Collectors.mapping(Map.Entry::getValue, Collectors.toList())
        ));
Methods used
  • stream() converts the employee list into a stream.
  • flatMap() converts one employee into multiple hobby-name pairs.
  • map() creates one pair like Cricket -> Ravi.
  • groupingBy() groups all pairs by hobby.
  • mapping() collects only employee names, not the whole pair object.
  • toList() creates the final list of names for each hobby.

This is the most common interview solution because it shows proper Stream API usage.

Way 2: Using normal for loops
Map<String, List<String>> result = new HashMap<>();

for (Employee employee : employees) {
    for (String hobby : employee.getHobbies()) {
        result
            .computeIfAbsent(hobby, key -> new ArrayList<>())
            .add(employee.getName());
    }
}

computeIfAbsent() checks whether the hobby already exists in the map. If it does not exist, it creates a new ArrayList. Then we add the employee name to that list.

This approach is very readable and is often preferred in production when the stream version feels too dense.

Way 3: Using Map.merge()
Map<String, List<String>> result = new HashMap<>();

for (Employee employee : employees) {
    for (String hobby : employee.getHobbies()) {
        List<String> names = new ArrayList<>();
        names.add(employee.getName());

        result.merge(hobby, names, (oldList, newList) -> {
            oldList.addAll(newList);
            return oldList;
        });
    }
}

merge() says: if the hobby is not present, insert the new list. If the hobby is already present, merge the old list and the new list.

Way 4: If duplicate names should be avoided

If an employee has duplicate hobbies, or you want each name only once per hobby, collect into a Set instead of a List.

@Transactional tells Spring to run a method inside a database transaction. If the method completes successfully, Spring commits the transaction. If it fails with an unchecked exception, Spring rolls back the transaction by default. 

@Service
public class PaymentService {

    @Transactional
    public void transferMoney(Long fromAccountId, Long toAccountId, BigDecimal amount) {
        Account from = accountRepository.findById(fromAccountId).orElseThrow();
        Account to = accountRepository.findById(toAccountId).orElseThrow();

        from.debit(amount);
        to.credit(amount);

        accountRepository.save(from);
        accountRepository.save(to);
    }
}

In the above example, debit and credit should succeed together. If credit fails after debit, the whole transaction should roll back.

Important attributes
Attribute Meaning
propagation Defines how this method joins, creates, or avoids a transaction.
isolation Defines how visible changes from other transactions are.
rollbackFor Forces rollback for checked exceptions.
readOnly Optimizes transaction for read operations.
timeout Sets maximum transaction execution time.
Propagation

Propagation answers this question: if one transactional method calls another transactional method, should the second method use the existing transaction, create a new one, or run without a transaction?

Propagation Behavior Common use
REQUIRED Use existing transaction; create one if none exists. Default for most service methods.
REQUIRES_NEW Suspend existing transaction and start a new one. Audit/log record that must save independently.
NESTED Run inside nested transaction using savepoint. Partial rollback inside a larger transaction.
SUPPORTS Use transaction if present; otherwise run without one. Read methods that can work either way.
NOT_SUPPORTED Suspend transaction and run without transaction. Long external calls that should not hold DB locks.
MANDATORY Must have an existing transaction; otherwise error. Internal method that should never run alone.
NEVER Must not run inside a transaction; error if one exists. Rare cases where transaction is forbidden.
Example: REQUIRED
@Transactional(propagation = Propagation.REQUIRED)
public void placeOrder(OrderRequest request) {
    orderRepository.save(request.toOrder());
    inventoryService.reduceStock(request.productId(), request.quantity());
}

REQUIRED is the default. If placeOrder() is already called inside another transaction, it joins that transaction. Otherwise, Spring creates a new transaction.

Example: REQUIRES_NEW for audit logs
@Service
public class OrderService {

    private final AuditService auditService;

    public OrderService(AuditService auditService) {
        this.auditService = auditService;
    }

    @Transactional
    public void placeOrder(OrderRequest request) {
        orderRepository.save(request.toOrder());

        auditService.saveAudit("ORDER_CREATED");

        if (request.quantity() <= 0) {
            throw new IllegalArgumentException("Invalid quantity");
        }
    }
}

@Service
public class AuditService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveAudit(String message) {
        auditRepository.save(new AuditLog(message));
    }
}

If placeOrder() fails, the order transaction rolls back. But saveAudit() uses REQUIRES_NEW, so its audit record can commit independently.

Example: MANDATORY
@Transactional(propagation = Propagation.MANDATORY)
public void reduceStock(Long productId, int quantity) {
    Product product = productRepository.findById(productId).orElseThrow();
    product.reduceStock(quantity);
}

Use MANDATORY when the method must be called only from an existing transaction. If no transaction exists, Spring throws an exception.

Isolation

Isolation answers this question: how much should one transaction be protected from changes made by other concurrent transactions?

Isolation Allows / prevents When to use
READ_UNCOMMITTED Allows dirty reads. Almost never used in business apps.
READ_COMMITTED Prevents dirty reads. Common default in many databases.
REPEATABLE_READ Prevents dirty and non-repeatable reads. When same row must stay stable during transaction.
SERIALIZABLE Strongest isolation; transactions behave one by one. Critical consistency, but lower performance.
DEFAULT Uses database default isolation level. Most common choice.
Read problems
Problem Meaning
Dirty read Transaction reads uncommitted data from another transaction.
Non-repeatable read Same row gives different values when read twice in one transaction.
Phantom read Same query returns new rows because another transaction inserted matching data.
Example: isolation for balance check
@Transactional(isolation = Isolation.REPEATABLE_READ)
public void withdraw(Long accountId, BigDecimal amount) {
    Account account = accountRepository.findById(accountId).orElseThrow();

    if (account.getBalance().compareTo(amount) < 0) {
        throw new InsufficientBalanceException("Insufficient balance");
    }

    account.debit(amount);
}

REPEATABLE_READ helps when the same account row should not unexpectedly change while the transaction is running.

Example: read-only transaction
@Transactional(readOnly = true)
public List<AccountStatement> getStatements(Long accountId) {
    return statementRepository.findByAccountId(accountId);
}

readOnly = true is useful for query methods. It tells Spring/Hibernate that the method should not modify data and can be optimized for reads.

Rollback rules
  • Runtime exceptions trigger rollback by default.
  • Checked exceptions do not trigger rollback by default.
  • Use rollbackFor when a checked exception should roll back.
@Transactional(rollbackFor = PaymentFailedException.class)
public void makePayment() throws PaymentFailedException {
    debit();
    credit();
    throw new PaymentFailedException("Payment failed");
}
Common pitfalls
  • @Transactional usually works through Spring proxy, so self-invocation may not apply it.
  • Do not keep transactions open during slow external API calls.
  • Use REQUIRES_NEW carefully because it creates an independent transaction.
  • Higher isolation improves consistency but can reduce performance.
  • Put transaction boundaries mostly on service methods, not controller methods.

Interview one-liner: @Transactional controls commit and rollback; propagation controls how methods join or create transactions, and isolation controls how concurrent transactions see each other's data.

Audit fields are used to track who created or updated a row and when it happened. Common columns are created_by, updated_by, created_date, and updated_date.

There are two common ways to do this in Spring Boot:

  • Using Spring Data JPA auditing annotations like @CreatedBy and @LastModifiedBy.
  • Using a Hibernate interceptor/listener to set audit fields before insert and update.
Way 1: Spring Data JPA auditing annotations

This is the cleanest and most common approach when you are using Spring Data JPA repositories. 

@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class AuditEntity {

    @CreatedBy
    @Column(name = "created_by", updatable = false)
    private String createdBy;

    @LastModifiedBy
    @Column(name = "updated_by")
    private String updatedBy;

    @CreatedDate
    @Column(name = "created_date", updatable = false)
    private LocalDateTime createdDate;

    @LastModifiedDate
    @Column(name = "updated_date")
    private LocalDateTime updatedDate;
}

Any entity can extend this base class: 

@Entity
@Table(name = "orders")
public class Order extends AuditEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String orderNumber;
    private BigDecimal amount;
}
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_number VARCHAR(100),
    amount DECIMAL(10, 2),
    created_by VARCHAR(100),
    updated_by VARCHAR(100),
    created_date TIMESTAMP,
    updated_date TIMESTAMP
);

Enable JPA auditing in a configuration class: 

@Configuration
@EnableJpaAuditing(auditorAwareRef = "auditorProvider")

Get the username from the token stored in Spring Security context: 

public class SecurityAuditorAware implements AuditorAware<String> {

    @Override
    public Optional<String> getCurrentAuditor() {
        Authentication authentication =
                SecurityContextHolder.getContext().getAuthentication();

        if (authentication == null || !authentication.isAuthenticated()) {
            return Optional.of("SYSTEM");
        }

        if (authentication instanceof JwtAuthenticationToken jwtAuth) {
            String username = jwtAuth.getToken().getClaimAsString("preferred_username");

            if (username != null) {
                return Optional.of(username);
            }
        }

        return Optional.of(authentication.getName());
    }
}

JWT token
   -> Spring Security filter validates token
   -> Authentication stored in SecurityContextHolder
   -> AuditorAware reads current username
   -> @CreatedBy / @LastModifiedBy fields are filled automatically
   -> Entity is saved with audit columns
Way 2: Hibernate interceptor approach

A Hibernate interceptor can set audit fields before insert and update. This is useful when you want audit logic at the Hibernate layer, or when some saves do not go through normal repository auditing.

First create a common interface: 

public interface Auditable {
    void setCreatedBy(String createdBy);
    void setUpdatedBy(String updatedBy);
    void setCreatedDate(LocalDateTime createdDate);
    void setUpdatedDate(LocalDateTime updatedDate);
}

Then make your base entity implement it: 

@MappedSuperclass
public abstract class AuditEntity implements Auditable {

    @Column(name = "created_by", updatable = false)
    private String createdBy;

    @Column(name = "updated_by")
    private String updatedBy;

    @Column(name = "created_date", updatable = false)
    private LocalDateTime createdDate;

    @Column(name = "updated_date")
    private LocalDateTime updatedDate;

    public void setCreatedBy(String createdBy) {
        this.createdBy = createdBy;
    }

    public void setUpdatedBy(String updatedBy) {
        this.updatedBy = updatedBy;
    }

        this.createdDate = createdDate;
    }

    public void setUpdatedDate(LocalDateTime updatedDate) {
        this.updatedDate = updatedDate;
    }
}

Create a helper to read username from the current token: 

@Component
public class CurrentUserProvider {

    public String getUsername() {
        Authentication authentication =
                SecurityContextHolder.getContext().getAuthentication();

        if (authentication == null || !authentication.isAuthenticated()) {
            return "SYSTEM";
        }

        if (authentication instanceof JwtAuthenticationToken jwtAuth) {
            String username = jwtAuth.getToken().getClaimAsString("preferred_username");
            return username != null ? username : jwtAuth.getName();
        }

        return authentication.getName();
    }
}

Create the Hibernate interceptor: 

@Component
public class AuditHibernateInterceptor extends EmptyInterceptor {

    private final CurrentUserProvider currentUserProvider;

    public AuditHibernateInterceptor(CurrentUserProvider currentUserProvider) {
        this.currentUserProvider = currentUserProvider;
    }

    @Override
    public boolean onSave(Object entity, Serializable id, Object[] state,
                          String[] propertyNames, Type[] types) {

        if (entity instanceof Auditable auditable) {
            String username = currentUserProvider.getUsername();
            LocalDateTime now = LocalDateTime.now();

            auditable.setCreatedBy(username);
            auditable.setUpdatedBy(username);
            auditable.setCreatedDate(now);
            auditable.setUpdatedDate(now);

            setValue(state, propertyNames, "createdBy", username);
            setValue(state, propertyNames, "updatedBy", username);
            setValue(state, propertyNames, "createdDate", now);
            setValue(state, propertyNames, "updatedDate", now);

            return true;
        }

        return false;
    }

    @Override
    public boolean onFlushDirty(Object entity, Serializable id, Object[] currentState,
                                Object[] previousState, String[] propertyNames,
                                Type[] types) {

        if (entity instanceof Auditable auditable) {
            String username = currentUserProvider.getUsername();
            LocalDateTime now = LocalDateTime.now();

            auditable.setUpdatedBy(username);
            auditable.setUpdatedDate(now);

            setValue(currentState, propertyNames, "updatedBy", username);
            setValue(currentState, propertyNames, "updatedDate", now);

            return true;
        }

        return false;
    }

    private void setValue(Object[] state, String[] propertyNames,
                          String propertyName, Object value) {
        for (int index = 0; index < propertyNames.length; index++) {
            if (propertyNames[index].equals(propertyName)) {
                state[index] = value;
                return;
            }
        }
    }
}

Register the interceptor with Hibernate: 

@Configuration
public class HibernateAuditConfig {

    @Bean
    public HibernatePropertiesCustomizer hibernatePropertiesCustomizer(
            AuditHibernateInterceptor interceptor) {

        return properties ->
                properties.put("hibernate.session_factory.interceptor", interceptor);
    }
}

Approach Best use Notes

Important points
  • createdBy and createdDate should normally be set only during insert.
  • updatedBy and updatedDate should change on every update.
  • The token should be validated before the username is read from SecurityContextHolder.
  • Use SYSTEM for scheduler jobs, batch jobs, or unauthenticated internal operations.
  • For normal applications, prefer Spring Data auditing; use interceptor only when you need Hibernate-level control.

Interview one-liner: use Spring Data auditing annotations for standard audit columns; implement AuditorAware to read the username from the token, and use a Hibernate interceptor only when audit values must be handled centrally at the Hibernate persistence layer.

What is CQRS?

CQRS stands for: 

Command Query Responsibility Segregation

The main idea is to separate: 

WRITE operations
    from


READ operations

In a traditional application, the same model, service, repository, and database are often used for both reads and writes.

In CQRS, we separate them into: 

Command Side
-> Changes system state


Query Side
-> Reads system state

A Query asks the system for information.

The fundamental separation is:

-> changes state

-> returns data
-> should not change state

How can we handle read-after-write problems?

Possible strategies include:

  1. Return enough data from the command response for immediate UI display.
  2. Temporarily read from the write model for critical read-after-write flows.
  3. Use polling with retry and backoff.
  4. Use WebSocket or Server-Sent Events when the projection becomes available.
  5. Track projection versions or event offsets.
  6. Use synchronous projection updates when strict consistency is truly required.

There is no universal solution. The correct choice depends on business requirements.

CQRS stands for Command Query Responsibility Segregation. It separates operations that change system state from operations that read system state. The command side is optimized for business rules, transactional consistency, and domain invariants, while the query side is optimized for fast reads, search, filtering, dashboards, and denormalized views. In a distributed implementation, a command updates the write model and produces an event; a projection consumer processes that event and updates the read model. This allows independent scaling and different data models or databases, but introduces eventual consistency, duplicate delivery, ordering, replay, and operational complexity. In production, I would address reliable event publication using the Transactional Outbox Pattern and make consumers idempotent. CQRS does not require Kafka, separate databases, microservices, or Event Sourcing; those are optional architectural choices.

Given an integer array, separate all 0s to the end and keep all non-zero values at the beginning. The important condition is: do it in the same array, without creating another array. 

Input:  [0, 1, 0, 3, 12]
Output: [1, 3, 12, 0, 0]

If the array contains only 0s and 1s, the same idea becomes: 

Input:  [0, 1, 0, 1, 1, 0]
Output: [1, 1, 1, 0, 0, 0]
Way 1: Stable two-pointer approach

This keeps the relative order of non-zero elements the same. 

public static void moveZerosToEnd(int[] nums) {
    int insertPosition = 0;

    for (int index = 0; index < nums.length; index++) {
        if (nums[index] != 0) {
            nums[insertPosition] = nums[index];
            insertPosition++;
        }
    }

    while (insertPosition < nums.length) {
        nums[insertPosition] = 0;
        insertPosition++;
    }
}

Explanation:

  • insertPosition points to where the next non-zero number should be placed.
  • The first loop copies all non-zero values to the front of the same array.
  • The second loop fills the remaining positions with 0.
  • No extra array is used; only one variable is used.
Dry run
Array: [0, 1, 0, 3, 12]

index = 0, value = 0  -> skip
index = 1, value = 1  -> nums[0] = 1
index = 2, value = 0  -> skip
index = 3, value = 3  -> nums[1] = 3
index = 4, value = 12 -> nums[2] = 12

Now fill remaining positions with 0:
[1, 3, 12, 0, 0]

    }

Way 2: Swap-based two-pointer approach

This also works in-place. It swaps every non-zero element with the position where the next non-zero value should go. 

public static void moveZerosToEndUsingSwap(int[] nums) {
    int nonZeroPosition = 0;

    for (int index = 0; index < nums.length; index++) {
        if (nums[index] != 0) {
            int temp = nums[index];
            nums[index] = nums[nonZeroPosition];
            nums[nonZeroPosition] = temp;

            nonZeroPosition++;
        }
    }
}

This is useful when you want to perform fewer writes in some cases. It still uses the same array and does not create another array.

If array contains only 0s and 1s

If the question specifically means separate 1s first and 0s last, use this two-pointer version. It swaps values in the same array and does not use an extra array. 

public static void separateOnesAndZeros(int[] nums) {
    int left = 0;
    int right = nums.length - 1;

    while (left < right) {
        while (left < right && nums[left] == 1) {
            left++;
        }

        while (left < right && nums[right] == 0) {
            right--;
        }

        if (left < right) {
            int temp = nums[left];
            nums[left] = nums[right];
            nums[right] = temp;
            left++;
            right--;
        }
    }
}
Input:  [0, 1, 0, 1, 1, 0]
Output: [1, 1, 1, 0, 0, 0]
Complexity
  • Time complexity: O(n)
  • Space complexity: O(1)
  • Same array is modified in-place.

Interview one-liner: use a two-pointer approach; keep one pointer for the next non-zero position, move non-zero values to the front, and fill the remaining positions with zero.

If the child overridden method declares Exception, the compiler gives an error because Exception is a broader checked exception than the parent contract allows.

The rule is simple:

  • A child method cannot introduce a broader checked exception than the parent method declares.
  • A child method may throw the same exception or a narrower checked exception.
  • A child method may throw any unchecked exception, even if the parent throws none.
class Parent {
    void calculate() throws RuntimeException {
        System.out.println("Parent");
    }
}

class Child extends Parent {
    @Override
    void calculate() throws Exception {   // Compile-time error
        System.out.println("Child");
    }
}

This also fails: 

class Parent {
    void calculate() throws ArithmeticException {
    }
}

class Child extends Parent {
    @Override
    void calculate() throws Exception {  // Compile-time error
    }
}

But these are allowed: 

class Parent {
    void calculate() throws RuntimeException {
    }
}

class Child extends Parent {
    @Override
    void calculate() throws ArithmeticException {
    }
}
class Parent {
    void calculate() {
    }
}

class Child extends Parent {
    @Override
    void calculate() throws ArithmeticException {
    }
}

The vice versa cases follow the same inheritance rule:

Parent method Child method Result
throws Exception throws IOException Allowed
throws IOException throws Exception Compile-time error
throws RuntimeException throws Exception Compile-time error
throws RuntimeException throws ArithmeticException Allowed
No throws throws RuntimeException Allowed
No throws throws IOException Compile-time error

Interview one-liner: a child method can narrow checked exceptions, but it cannot widen them; unchecked exceptions are always allowed in overriding.

In Spring Boot, JPA/Hibernate handles this using annotations like @Entity, @Id, @OneToOne, @OneToMany, @ManyToOne, @ManyToMany, @JoinColumn, and @JoinTable.

Example: one department has many employees.

A Many-to-Many relation means many rows in one table can match many rows in another table. In relational databases, this is not stored directly in the two tables. Instead, Hibernate creates a join table.

Example: one student can join many courses, and one course can have many students. 

@Entity
class Student {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    @ManyToMany
    @JoinTable(
        name = "student_course",
        joinColumns = @JoinColumn(name = "student_id"),
        inverseJoinColumns = @JoinColumn(name = "course_id")
    )
    private Set<Course> courses;
}

@Entity
class Course {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;

    @ManyToMany(mappedBy = "courses")
    private Set<Student> students;
}
CREATE TABLE student (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL
);

CREATE TABLE course (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(150) NOT NULL
);

CREATE TABLE student_course (
    student_id BIGINT NOT NULL,
    course_id BIGINT NOT NULL,
    PRIMARY KEY (student_id, course_id),
    CONSTRAINT fk_sc_student
        FOREIGN KEY (student_id) REFERENCES student(id),
    CONSTRAINT fk_sc_course
        FOREIGN KEY (course_id) REFERENCES course(id)
);

Here, student_course is the join table. It stores only the relationship, not extra business data.

When to avoid direct Many-to-Many
  • If the join table needs extra columns like enrolled_at, status, or grade, use a separate entity instead of plain @ManyToMany.
  • In that case, model it as two @ManyToOne relationships through an intermediate entity such as Enrollment.
  • Be careful with cascade and fetch type because many-to-many graphs can grow quickly.

Interview one-liner: Many-to-Many in JPA is backed by a join table, and if the association has extra attributes, an intermediate entity is usually the better design.

@Aspect
@Component
public class RateLimitAspect {

    private final Map<String, AtomicInteger> counters = new ConcurrentHashMap<>();

    @Around("@annotation(rateLimited)")
    public Object enforce(ProceedingJoinPoint pjp, RateLimited rateLimited) throws Throwable {
        String key = rateLimited.key().isBlank()
                ? pjp.getSignature().toShortString()
                : rateLimited.key();

        AtomicInteger count = counters.computeIfAbsent(key, k -> new AtomicInteger(0));
        if (count.incrementAndGet() > rateLimited.requests()) {
            throw new TooManyRequestsException("Rate limit exceeded for " + key);
        }

        return pjp.proceed();
    }
}

A common real-time pattern: create a custom annotation for audit logging so every sensitive operation is tracked consistently without copy-pasting log statements.

1. Define annotation
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface AuditLog {
    String action();
    String module() default "GENERAL";
    boolean logArgs() default false;
}
2. Use on business methods
@Service
public class AccountService {

    @AuditLog(action = "TRANSFER_MONEY", module = "PAYMENTS", logArgs = true)
    @Transactional
    public void transfer(Long from, Long to, BigDecimal amount) {
        debit(from, amount);
        credit(to, amount);
    }

    @AuditLog(action = "BLOCK_ACCOUNT", module = "COMPLIANCE")
    public void blockAccount(Long accountId) {
        accountRepository.updateStatus(accountId, Status.BLOCKED);
    }
}
3. Aspect to process annotation
@Aspect
@Component
@Slf4j
public class AuditLogAspect {

    private final AuditRepository auditRepository;

    public AuditLogAspect(AuditRepository auditRepository) {
        this.auditRepository = auditRepository;
    }

    @Around("@annotation(auditLog)")
    public Object logAudit(ProceedingJoinPoint pjp, AuditLog auditLog) throws Throwable {
        String user = SecurityContextHolder.getContext()
                .getAuthentication().getName();

        long start = System.currentTimeMillis();
        try {
            Object result = pjp.proceed();
            saveAudit(user, auditLog, pjp, "SUCCESS", System.currentTimeMillis() - start);
            return result;
        } catch (Exception ex) {
            saveAudit(user, auditLog, pjp, "FAILED", System.currentTimeMillis() - start);
            throw ex;
        }
    }

    private void saveAudit(String user, AuditLog auditLog,
                           ProceedingJoinPoint pjp, String status, long durationMs) {
        auditRepository.save(new AuditEntry(
                user,
                auditLog.module(),
                auditLog.action(),
                pjp.getSignature().toShortString(),
                status,
                durationMs
        ));
    }
}

File handling can be done as simple multipart upload, streaming upload/download, chunk upload, or direct object-storage upload using pre-signed URLs.

What is multipart?

multipart/form-data is an HTTP request format where text fields and files are sent as separate parts in one request. In Spring Boot, a file part is commonly received as MultipartFile.

Default Spring Boot upload size

Spring Boot's default multipart limits are commonly 1MB per file and 10MB per request. Increase them in configuration when your use case needs larger files. 

spring.servlet.multipart.max-file-size=100MB
spring.servlet.multipart.max-request-size=100MB
spring.servlet.multipart.file-size-threshold=2MB
Approach 1 - Simple multipart upload
@RestController
@RequestMapping("/files")
public class FileController {

    private final Path root = Paths.get("uploads");

    @PostMapping("/upload")
    public ResponseEntity<String> upload(@RequestParam("file") MultipartFile file) throws IOException {
        if (file.isEmpty()) {
            return ResponseEntity.badRequest().body("File is empty");
        }

        Files.createDirectories(root);
        String safeName = Paths.get(file.getOriginalFilename()).getFileName().toString();
        Path target = root.resolve(UUID.randomUUID() + "-" + safeName);

        try (InputStream inputStream = file.getInputStream()) {
            Files.copy(inputStream, target, StandardCopyOption.REPLACE_EXISTING);
        }

        return ResponseEntity.ok("Uploaded: " + target.getFileName());
    }
}
Approach 2 - Stream download
@GetMapping("/download/{fileName}")
public ResponseEntity<StreamingResponseBody> download(@PathVariable String fileName) throws IOException {
    Path file = Paths.get("uploads").resolve(fileName).normalize();
    if (!Files.exists(file)) {
        return ResponseEntity.notFound().build();
    }

    StreamingResponseBody body = outputStream -> {
        try (InputStream inputStream = Files.newInputStream(file)) {
            inputStream.transferTo(outputStream);
        }
    };

    return ResponseEntity.ok()
            .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=\"" + file.getFileName() + "\"")
            .contentType(MediaType.APPLICATION_OCTET_STREAM)
            .body(body);
}
Approach 3 - Chunk upload business logic

Chunk upload means the client splits a large file into smaller parts and sends each part with metadata like upload id, chunk number, total chunks, and file name. The server stores chunks temporarily and merges them after all parts arrive. 

@PostMapping("/upload-chunk")
public ResponseEntity<String> uploadChunk(
        @RequestParam String uploadId,
        @RequestParam int chunkNumber,
        @RequestParam int totalChunks,
        @RequestParam String fileName,
        @RequestParam("chunk") MultipartFile chunk) throws IOException {

    Path tempDir = Paths.get("uploads", "tmp", uploadId);
    Files.createDirectories(tempDir);

    Path chunkPath = tempDir.resolve(String.valueOf(chunkNumber));
    try (InputStream in = chunk.getInputStream()) {
        Files.copy(in, chunkPath, StandardCopyOption.REPLACE_EXISTING);
    }

    long uploadedChunks = Files.list(tempDir).count();
    if (uploadedChunks == totalChunks) {
        Path finalFile = Paths.get("uploads").resolve(fileName).normalize();
        try (OutputStream out = Files.newOutputStream(finalFile, StandardOpenOption.CREATE,
                StandardOpenOption.TRUNCATE_EXISTING)) {
            for (int i = 1; i <= totalChunks; i++) {
                Files.copy(tempDir.resolve(String.valueOf(i)), out);
            }
        }
        return ResponseEntity.ok("Upload completed: " + finalFile.getFileName());
    }

    return ResponseEntity.ok("Chunk " + chunkNumber + " uploaded");
}
What is resumable upload?

Resumable upload allows retrying only missing chunks instead of uploading the full file again. Store metadata in DB/Redis: uploadId, file name, total chunks, uploaded chunk numbers, checksum, status, and expiry time. 

@GetMapping("/upload-status/{uploadId}")
public ResponseEntity<Set<Integer>> uploadedChunks(@PathVariable String uploadId) {
    Set<Integer> chunks = uploadSessionService.findUploadedChunkNumbers(uploadId);
    return ResponseEntity.ok(chunks);
}

Trap: If a key object's hash code changes after insertion, the entry becomes unreachable in the bucket — get() returns null even though the entry still exists in memory.

    private int id;

    MutableKey(int id) { this.id = id; }

    void setId(int id) { this.id = id; }   // mutating field used in hashCode

    @Override
    public int hashCode() { return id; }

    @Override
    public boolean equals(Object o) {
        return o instanceof MutableKey mk && mk.id == this.id;
    }
}

Map<MutableKey, String> map = new HashMap<>();

`ArrayList` and `Set` look simple from the outside, but internally they use very different storage and lookup strategies. That is why they behave differently for duplicates, ordering, memory usage, and search performance.

1. ArrayList internals
  • Backed by a resizable array called elementData.
  • Insertion at the end is usually fast because the array grows amortized.
  • When capacity is full, Java allocates a bigger array and copies the old elements.
  • Random access by index is fast because it reads directly from the array.
  • Middle insert/remove is expensive because elements must shift left or right.
Operation Typical cost
get(index) O(1)
add(value) at end Amortized O(1)
add(index, value) O(n)
remove(index) O(n)
contains(value) O(n) 
List<String> list = new ArrayList<>();
list.add("A");
list.add("B");
list.add("C");

System.out.println(list.get(1));   // B
list.add(1, "X");                  // shifts B, C to the right
System.out.println(list);          // [A, X, B, C]

In interviews, remember the growth behavior too: ArrayList starts with a small internal array and grows when needed, which reduces frequent reallocation but can still cause occasional copy overhead.

📌 Problem
Given int[][] intervals, merge all overlapping intervals and return result.
💡 Approach
  • Sort by start time
  • Iterate and merge when current.start ≤ lastMerged.end
⏱ Complexity

Time: O(n log n), Space: O(n)


public static int[][] merge(int[][] intervals) {
    if (intervals == null || intervals.length == 0) return new int[0][0];

    Arrays.sort(intervals, Comparator.comparingInt(a -> a[0]));
    List<int[]> result = new ArrayList<>();
    int[] current = intervals[0];

    for (int i = 1; i < intervals.length; i++) {
        if (intervals[i][0] <= current[1]) {
            current[1] = Math.max(current[1], intervals[i][1]);
        } else {
            result.add(current);
            current = intervals[i];
        }
    }
    result.add(current);
    return result.toArray(new int[result.size()][]);
}

        l++; r--;
    }

📌 Problem
Given 2D matrix, return elements in spiral order.
⏱ Complexity

Time: O(m×n), Space: O(1) extra (output excluded)


public static List<Integer> spiralOrder(int[][] matrix) {
    List<Integer> res = new ArrayList<>();
    if (matrix.length == 0) return res;
    int top = 0, bottom = matrix.length - 1;
    int left = 0, right = matrix[0].length - 1;

    while (top <= bottom && left <= right) {
        for (int i = left; i <= right; i++) res.add(matrix[top][i]);
        top++;
        for (int i = top; i <= bottom; i++) res.add(matrix[i][right]);
        right--;
        if (top <= bottom) {
            for (int i = right; i >= left; i--) res.add(matrix[bottom][i]);
            bottom--;
        }
        if (left <= right) {
            for (int i = bottom; i >= top; i--) res.add(matrix[i][left]);
            left++;
        }
    }
    return res;
}

public static int lengthOfLongestSubstring(String s) {

    int left = 0, max = 0;

    for (int right = 0; right < s.length(); right++) {
        char c = s.charAt(right);
        if (map.containsKey(c)) {

📌 Problem
Print nodes level by level (BFS).
💡 Approach
  • Use queue, process nodes level by level

static class TreeNode {
    int val;
    TreeNode left, right;
    TreeNode(int v) { val = v; }
}

public static List<List<Integer>> levelOrder(TreeNode root) {
    List<List<Integer>> res = new ArrayList<>();
    if (root == null) return res;
    Queue<TreeNode> q = new LinkedList<>();
    q.offer(root);

    while (!q.isEmpty()) {
        int size = q.size();
        List<Integer> level = new ArrayList<>();
        for (int i = 0; i < size; i++) {
            TreeNode node = q.poll();
            level.add(node.val);
            if (node.left != null) q.offer(node.left);
            if (node.right != null) q.offer(node.right);
        }
        res.add(level);
    }
    return res;
}

📌 Problem
Implement a simple in-memory rate limiter for N requests per second.
💡 Approach
  • Token bucket: refill tokens at fixed rate, consume per request

public class TokenBucket {

    private final int capacity;
    private final int refillPerSecond;
    private double tokens;
    private long lastRefillTimestamp;

    public TokenBucket(int capacity, int refillPerSecond) {
        this.capacity = capacity;
        this.refillPerSecond = refillPerSecond;
        this.tokens = capacity;
        this.lastRefillTimestamp = System.nanoTime();
    }

    public synchronized boolean allowRequest() {
        refill();
        if (tokens >= 1) {
            tokens -= 1;
            return true;
        }
        return false;
    }

    private void refill() {
        long now = System.nanoTime();
        double seconds = (now - lastRefillTimestamp) / 1_000_000_000.0;
        double add = seconds * refillPerSecond;
        if (add > 0) {
            tokens = Math.min(capacity, tokens + add);
            lastRefillTimestamp = now;
        }
    }
}

Problem statement

Given an integer array containing both 0 and non-zero values, solve the following two variations:

  1. Move all 0s to the end of the array.
  2. Move all 0s to the beginning of the array.

The important constraints are:

  • Do not create another array.
  • Modify the same input array in place.
  • Preserve the relative order of non-zero elements.
  • Target O(n) time complexity.
  • Target O(1) extra space complexity.
Example input
int[] arr = {0, 1, 0, 3, 12, 0, 5};

Expected result when moving all zeros to the end: 

{1, 3, 12, 5, 0, 0, 0}

Expected result when moving all zeros to the beginning: 

{0, 0, 0, 1, 3, 12, 5}

Notice that the relative order of non-zero elements remains unchanged: 

1, 3, 12, 5
Approach 1: Move all zeros to the end

We maintain a variable called writeIndex.

Its job is to point to the next position where a non-zero element should be written. 

public static void moveZerosToEnd(int[] arr) {

int writeIndex = 0;

// Step 1: Move all non-zero elements forward
for (int value : arr) {
    if (value != 0) {
        arr[writeIndex++] = value;
    }
}

// Step 2: Fill remaining positions with zeros
while (writeIndex < arr.length) {
    arr[writeIndex++] = 0;
}


}
How it works

Consider: 

arr = {0, 1, 0, 3, 12, 0, 5}

Initially: 

writeIndex = 0

We scan every value.

Current value Action writeIndex Important array portion
0 Skip 0 -
1 Write at index 0 1 {1}
0 Skip 1 {1}
3 Write at index 1 2 {1, 3}
12 Write at index 2 3 {1, 3, 12}
0 Skip 3 {1, 3, 12}
5 Write at index 3 4 {1, 3, 12, 5}

After the first loop, all non-zero elements are compacted at the beginning: 

{1, 3, 12, 5, ?, ?, ?}

Now: 

writeIndex = 4

Fill all remaining positions with zero: 

{1, 3, 12, 5, 0, 0, 0}
Approach 2: Move all zeros to the beginning

For moving zeros to the beginning while preserving non-zero order, we should process the array from right to left.

We maintain writeIndex starting from the last array position. 

public static void moveZerosToBeginning(int[] arr) {

int writeIndex = arr.length - 1;

// Step 1: Move non-zero elements toward the end
// Traverse from right to left to preserve their order
for (int i = arr.length - 1; i >= 0; i--) {
    if (arr[i] != 0) {
        arr[writeIndex--] = arr[i];
    }
}

// Step 2: Fill remaining beginning positions with zeros
while (writeIndex >= 0) {
    arr[writeIndex--] = 0;
}


}
Why do we traverse from right to left?

Suppose the input is: 

{0, 1, 0, 3, 12, 0, 5}

The non-zero order is: 

1, 3, 12, 5

Since we are compacting non-zero values toward the right side, traversing from right to left allows us to preserve that order.

Current value Action writeIndex after action
5 Write at index 6 5
0 Skip 5

            "Zeros at End         : " + Arrays.toString(arr)

    moveZerosToBeginning(arr);

    System.out.println(

public static void moveZerosToEnd(int[] arr) {

    int writeIndex = 0;

    for (int value : arr) {
        if (value != 0) {
            arr[writeIndex++] = value;
        }
    }

    while (writeIndex < arr.length) {
        arr[writeIndex++] = 0;
    }
}

public static void moveZerosToBeginning(int[] arr) {

    int writeIndex = arr.length - 1;

    for (int i = arr.length - 1; i >= 0; i--) {
        if (arr[i] != 0) {
            arr[writeIndex--] = arr[i];
        }
    }

    while (writeIndex >= 0) {
        arr[writeIndex--] = 0;
    }
}


}

Recommended approach: HashMap with two passes

The cleanest general Java solution uses a HashMap.

We perform two passes:

  2. Scan the original string again and return the first character whose frequency is 1.
Java solution
import java.util.HashMap;


import java.util.Map;
import java.util.Optional;

public class FirstNonRepeatedCharacter {


public static Optional<Character> findFirstNonRepeated(String str) {

    if (str == null || str.isEmpty()) {
        return Optional.empty();
    }

    Map<Character, Integer> frequencyMap = new HashMap<>();

    // First pass: Count character frequencies
    for (char ch : str.toCharArray()) {
        frequencyMap.merge(ch, 1, Integer::sum);
    }

    // Second pass: Preserve original string order
    for (char ch : str.toCharArray()) {
        if (frequencyMap.get(ch) == 1) {
            return Optional.of(ch);
        }
    }

    return Optional.empty();
}

public static void main(String[] args) {

    String input = "aabbcdde";

    Optional<Character> result =
            findFirstNonRepeated(input);

    System.out.println(
            result
                .map(String::valueOf)
                .orElse("No non-repeated character found")
    );
}


}

    frequencyMap.merge(ch, 1, Integer::sum);
}

for (char ch : str.toCharArray()) {
    if (frequencyMap.get(ch) == 1) {
        return ch;
    }
}

return null;


}
Best interview explanation

I use two passes over the string. In the first pass, I store the frequency of each character in a HashMap. In the second pass, I scan the original string again and return the first character whose frequency is exactly 1. The second scan is important because a normal HashMap does not guarantee the original character order. The solution runs in O(n) average time and uses O(u) extra space, where u is the number of distinct characters.

4. Request logging filter

Use OncePerRequestFilter so each HTTP request gets exactly one start log and one end log. MDC adds searchable fields to all logs printed during the same request thread. 

package com.example.demo.logging;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;
import java.time.Instant;
import java.util.Optional;
import java.util.UUID;

@Component
public class RequestLoggingFilter extends OncePerRequestFilter {

    private static final Logger log = LoggerFactory.getLogger(RequestLoggingFilter.class);

    @Value("${spring.application.name}")
    private String applicationName;

    @Value("${app.instance-id:${spring.application.name}-local}")
    private String instanceId;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain)
            throws ServletException, IOException {

        long startNanos = System.nanoTime();
        Instant startTime = Instant.now();

        String requestId = Optional.ofNullable(request.getHeader("X-Request-Id"))
                .filter(id -> !id.isBlank())
                .orElse(UUID.randomUUID().toString());

        response.setHeader("X-Request-Id", requestId);

        MDC.put("applicationName", applicationName);
        MDC.put("instanceId", instanceId);
        MDC.put("requestId", requestId);
        MDC.put("method", request.getMethod());
        MDC.put("path", request.getRequestURI());
        MDC.put("query", Optional.ofNullable(request.getQueryString()).orElse(""));
        MDC.put("clientIp", getClientIp(request));
        MDC.put("startTime", startTime.toString());

        log.info("request_start");

        try {
            filterChain.doFilter(request, response);
        } catch (Exception ex) {
            MDC.put("exception", ex.getClass().getSimpleName());
            log.error("request_failed", ex);
            throw ex;
        } finally {
            long durationMs = (System.nanoTime() - startNanos) / 1_000_000;

            MDC.put("endTime", Instant.now().toString());
            MDC.put("durationMs", String.valueOf(durationMs));
            MDC.put("status", String.valueOf(response.getStatus()));

            log.info("request_end");
            MDC.clear();
        }
    }

    private String getClientIp(HttpServletRequest request) {
        String forwardedFor = request.getHeader("X-Forwarded-For");
        if (forwardedFor != null && !forwardedFor.isBlank()) {
            return forwardedFor.split(",")[0].trim();
        }
        return request.getRemoteAddr();
    }
}

        this.orderService = orderService;
    }

    @PostMapping
    public ResponseEntity<OrderResponse> createOrder(@RequestBody OrderRequest request) {
        log.info("creating_order");

        OrderResponse response = orderService.create(request);

        log.info("order_created");
        return ResponseEntity.status(HttpStatus.CREATED).body(response);
    }

Production best practices
  • Always log in JSON in container/Kubernetes environments.
  • Use a correlation id such as X-Request-Id or trace id from OpenTelemetry/Sleuth/Micrometer tracing.
  • Do not log passwords, tokens, OTPs, card numbers, or full request bodies with PII.
  • Log request metadata, status, duration, and business identifiers like order id or user id only when safe.
  • Use INFO for start/end/business events, WARN for recoverable problems, and ERROR for failures.
  • Set log retention and masking rules in ELK/Splunk/CloudWatch.
  • For async execution, copy MDC context to async threads using a TaskDecorator.

Interview one-liner: In production Spring Boot apps, I use JSON logs with MDC fields and a OncePerRequestFilter to log request start, request end, method, path, status, duration, request id, application name, and instance id so every request can be traced end to end.
