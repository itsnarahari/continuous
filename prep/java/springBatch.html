Spring Boot Q&A

Spring Batch is a lightweight, comprehensive framework designed for batch processing — executing large volumes of data in a reliable, transactionally safe, and reusable way. Before it existed, developers had to build custom scripts or schedulers that were hard to scale and maintain.

1️⃣ Before Spring Batch – Traditional Approach
  • Developers wrote manual scripts or cron jobs to process files, database updates, and reports.
  • No standard framework for handling retries, transaction management, or failure recovery.
  • Jobs were often long-running, hard to monitor, and not restartable after failure.

public void processFile() {
    List<String> lines = Files.readAllLines(Paths.get("users.csv"));
    for (String line : lines) {
        String[] parts = line.split(",");
        userRepository.save(new User(parts[0], parts[1]));
    }
}

🧱 This approach worked for small data sets, but for large jobs:

  • Errors would stop the entire job midway.
  • There was no checkpoint or resume mechanism.
  • No visibility into which records failed or succeeded.

2️⃣ What is Spring Batch?
  • A framework from the Spring ecosystem for robust, transactional batch processing.
  • Handles reading, processing, and writing large data sets in chunks.
  • Provides built-in support for retries, skips, parallelism, monitoring, and job metadata persistence.

@Bean
public Step importUsersStep() {
    return stepBuilderFactory.get("importUsers")
        .<UserInput, User>chunk(100)
        .reader(csvReader())
        .processor(userProcessor())
        .writer(databaseWriter())
        .build();
}

⚡ Here, Spring Batch reads 100 records at a time, processes them, and commits them to the database — ensuring consistent performance and recoverability.

3️⃣ Core Concepts
  • Job: A batch process definition consisting of one or more steps.
  • Step: A unit of work — typically read, process, write.
  • ItemReader / ItemProcessor / ItemWriter: Interfaces for reading, transforming, and writing data.
  • JobRepository: Stores metadata (job status, start time, end time, parameters, etc.).
  • JobLauncher: Triggers jobs programmatically or via schedulers.
4️⃣ How Spring Batch Solves Existing Problems
  • ✅ Restartability: Jobs can resume from the last committed checkpoint after failure.
  • ✅ Transaction Management: Each chunk executes in its own transaction.
  • ✅ Scalability: Supports parallel execution, partitioning, and remote chunking.
  • ✅ Monitoring: Job and Step metadata stored in DB (with restart/failure tracking).
  • ✅ Abstraction: Built-in readers/writers for CSV, XML, JSON, JDBC, JMS, etc.

  A[ItemReader] --> B[ItemProcessor]
  B --> C[ItemWriter]
  C --> D[(Database)]
5️⃣ When to Use Spring Batch
  • ⏱️ Large-volume data import/export (e.g., daily ETL jobs, financial reconciliations).
  • 📦 Periodic cleanup or archival tasks.
  • 📊 Report generation or transformation pipelines.
  • ⚙️ Integration with event-based triggers (Kafka, REST, Scheduler, etc.).
6️⃣ Advantages
  • 🧩 Highly configurable and modular architecture.
  • 🧱 Built-in transaction management, job persistence, and restartability.
  • ⚡ Handles massive datasets efficiently with chunking.
  • 🧭 Integrates easily with Spring Boot, Spring Data, and Spring Cloud.
  • 🧠 Supports advanced patterns like partitioning, scaling, and async execution.
7️⃣ Disadvantages / Limitations
  • ⚠️ Not ideal for real-time, low-latency processing (Kafka Streams or reactive systems are better).
  • ⚙️ Complex configuration for small/simple jobs.
  • 📊 Requires persistent JobRepository for tracking and recovery.
  • 🪣 Heavy for small, one-off scripts (overhead of setup and metadata tables).
  • 🧵 Limited parallelization within a single JVM (but can scale via partitioning or multi-instance setup).
📌 Summary
  • Spring Batch provides a standard, reliable way to perform large-scale batch data processing.
  • It eliminates the pain of manual error handling, retries, and restart logic.
  • Highly suitable for ETL, bulk imports, migrations, and scheduled jobs.
  • When combined with @Async, @Scheduled, and Kafka, it becomes a powerful backbone for enterprise data pipelines.

Understanding how Spring Batch orchestrates jobs internally is key to mastering its behavior. This section explains the main components, how they interact, and how data flows through the system — from JobLauncher → Job → Step → Reader → Processor → Writer.

1️⃣ High-Level Architecture Overview
  • Spring Batch uses a layered architecture for **data reading, processing, and writing**.
  • Each job consists of multiple steps — each step can be configured independently.
  • All job metadata and execution details are stored in a **JobRepository** (database). 

flowchart LR
    A[JobLauncher] --> B[Job]
    B --> C[Step 1]
    B --> D[Step 2]
    C --> E[ItemReader]
    E --> F[ItemProcessor]
    F --> G[ItemWriter]
    G --> H[(JobRepository)]
2️⃣ Key Components Explained
  • JobLauncher: Entry point that triggers job execution (manually or via scheduler).
  • Job: A batch workflow definition made up of one or more steps.
  • Step: Defines a unit of work — usually “read → process → write”.
  • JobRepository: Stores metadata about job executions, statuses, and parameters.
  • JobExplorer: Provides read-only access to job metadata for dashboards or monitoring.
  • JobInstance & JobExecution:
    • JobInstance: Unique combination of job name + parameters.
    • JobExecution: A single run attempt of a job instance (can be retried).
  • StepExecution: Execution metadata for each step in a job run.
3️⃣ Chunk-Oriented Processing

Instead of processing one record at a time, Spring Batch processes items in **chunks** — a fixed-size group of records per transaction. This ensures **efficient commits** and **recoverable progress**. 


@Bean
public Step userImportStep() {
    return stepBuilderFactory.get("userImportStep")
        .<UserInput, User>chunk(100)
        .reader(csvReader())
        .processor(userProcessor())
        .writer(databaseWriter())
        .build();
}
  • ☑️ Chunk Size: Defines how many records are read before a transaction commit.
  • ☑️ Checkpoint: After every chunk commit, progress is recorded in JobRepository.
  • ☑️ Restartability: On failure, job resumes from last successful chunk. 

flowchart LR
  R[ItemReader] -->|Read 100 records| P[ItemProcessor]
  P -->|Transform| W[ItemWriter]
  W -->|Commit + Save Checkpoint| J[(JobRepository)]
4️⃣ Transaction & Retry Management
  • Each chunk runs inside a single **transaction**.
  • If an exception occurs during read/process/write:
    • The transaction rolls back for that chunk only.
    • Job can be configured to **retry** or **skip** faulty records.

.step("orderStep")
  .<Order, Order>chunk(50)
  .reader(orderReader())
  .processor(orderProcessor())
  .writer(orderWriter())
  .faultTolerant()
  .retryLimit(3)
  .skipLimit(10)
  .build();

⚡ faultTolerant() enables built-in mechanisms to handle transient failures gracefully.

5️⃣ Execution Metadata – How Spring Tracks Jobs
  • Spring Batch stores metadata in DB tables prefixed with BATCH_ (e.g., BATCH_JOB_INSTANCE, BATCH_JOB_EXECUTION).
  • Each execution includes:
    • Job Name
    • Execution ID
    • Start/End Time
    • Status (STARTED, COMPLETED, FAILED)
    • Parameters & Exit Codes

SELECT JOB_NAME, STATUS, START_TIME, END_TIME, EXIT_CODE 
FROM BATCH_JOB_EXECUTION ORDER BY START_TIME DESC;

🧭 This metadata makes Spring Batch jobs **traceable**, **restartable**, and easy to monitor.

6️⃣ Execution Flow Summary

  participant J as Job
  participant S as Step
  participant R as Reader
  participant P as Processor
  participant W as Writer

📌 Summary
  • Spring Batch divides work into **Jobs → Steps → Chunks** for control and recovery.
  • Each chunk executes transactionally and persists progress for restarts.
  • JobRepository ensures visibility and traceability of job executions.
  • Supports **retries, skips, and checkpoints** for resilient data processing.
  • This architecture allows safe scaling and orchestration in distributed systems.

Scaling Spring Batch is essential for processing **large datasets efficiently** or distributing work across multiple nodes. This section explains **parallel steps, partitioning, and remote chunking** — key strategies to improve throughput while maintaining job integrity.

1️⃣ Parallel Steps
  • Allows multiple independent steps to run **concurrently** in the same job.
  • Configured using a TaskExecutor with multiple threads.
  • Best suited for steps that do not depend on each other.

@Bean
public Job parallelJob() {
    return jobBuilderFactory.get("parallelJob")
        .start(step1())
        .split(new SimpleAsyncTaskExecutor())
        .add(step2(), step3())
        .end()
        .build();
}
2️⃣ Partitioning (Multi-threaded / Multi-node)
  • Used to **divide a step into smaller partitions**, each processing a subset of data.
  • Each partition runs independently — can be in the same JVM or across multiple servers.
  • Spring Batch orchestrates partition execution and merges results.

@Bean
public Step managerStep(Step workerStep) {
    return stepBuilderFactory.get("managerStep")
        .partitioner(workerStep.getName(), new RangePartitioner())
        .step(workerStep)
        .gridSize(4)
        .taskExecutor(new SimpleAsyncTaskExecutor())
        .build();
}
3️⃣ Remote Chunking (Distributed Workers)
  • Master step reads data and sends **chunks to remote worker nodes** via messaging systems (Kafka, RabbitMQ, etc.).
  • Workers process and write data independently, reporting completion back to the master.
  • Ideal for **horizontal scaling across microservices or cloud instances**.

@Bean
public Step masterStep(JmsTemplate jmsTemplate) {
    return stepBuilderFactory.get("masterStep")
        .chunk(100)
        .reader(itemReader())
        .writer(messagingItemWriter(jmsTemplate))
        .build();
}
      

@Bean
public IntegrationFlow workerFlow() {
    return IntegrationFlows
        .from(Jms.messageDrivenChannelAdapter(connectionFactory())
            .destination("chunkQueue"))
        .handle(chunkProcessorHandler())
        .get();
}
4️⃣ Choosing the Right Strategy
  • Parallel Steps: Simple, within a single JVM, steps are independent.
  • Partitioning: Splits a single step into multiple threads or instances, ideal for large datasets.
  • Remote Chunking: Distributes work across servers, suitable for massive datasets and microservices.
📌 Summary
  • ⚡ Scaling Spring Batch improves throughput and resource utilization.
  • 🧩 Parallel steps handle independent work concurrently.
  • 🪣 Partitioning splits steps for multi-threaded or multi-instance execution.
  • ☁️ Remote chunking allows fully distributed, event-driven batch processing.
  • ✅ All strategies rely on JobRepository for checkpointing, metadata, and restartability.

Spring Batch is built around a set of core components that define how **jobs are executed, monitored, and managed**. Understanding these components is essential for designing robust batch jobs.

1️⃣ Job
  • The **top-level container** representing a batch job.
  • Defines the **workflow**, composed of one or more steps.
  • Job metadata and execution state are stored in the JobRepository.
2️⃣ Step
  • Represents a **single unit of work** in a job.
  • Two main types of steps:
    • Tasklet Step: Executes a single task (simple or custom logic).
    • Chunk-Oriented Step: Processes data in chunks (read → process → write).
  • Each step maintains its own **StepExecution metadata**.
3️⃣ ItemReader
  • Reads data from a source (file, database, queue, etc.) one item at a time.
  • Supports multiple formats: FlatFileItemReader, JdbcCursorItemReader, JpaPagingItemReader, etc.
  • Handles state management for restartability.
4️⃣ ItemProcessor
  • Optional component used to **transform or validate** data read by the ItemReader.
  • Accepts an input item, performs processing, and returns the output item to be written.
  • Can also filter items by returning null.
5️⃣ ItemWriter
  • Writes processed items to a destination (database, file, queue, etc.).
  • Supports batch writes for efficiency.
  • Ensures commit within the transaction defined by the chunk size.
6️⃣ JobRepository
  • Stores **job execution metadata**, checkpoints, and parameters.
  • Essential for **restartability** and tracking job progress.
  • Typically backed by a relational database.
7️⃣ JobLauncher
  • Triggers job execution.
  • Can launch jobs **synchronously or asynchronously**.
  • Accepts **JobParameters** to create a unique JobInstance.
8️⃣ JobParameters & JobInstance
  • JobParameters: Input parameters for a job (date, file name, etc.) to distinguish instances.
  • JobInstance: Unique run of a job with specific parameters. Prevents re-running the same parameter combination unless explicitly restarted.
9️⃣ StepExecution & JobExecution
  • StepExecution: Tracks the state of a single step within a job run.
  • JobExecution: Tracks the overall job run, combining all StepExecutions.
  • Both store status, start/end times, exit codes, and allow restart/retry.
🔟 Additional Components
  • Tasklet: A functional interface for single-task steps.
  • SkipPolicy / RetryPolicy: Configurable policies for handling errors.
  • Listeners: JobExecutionListener, StepExecutionListener for hooks before/after execution.
  • Partitioner: Splits a step into multiple partitions for parallel processing.
  • JobExplorer: Read-only access to job metadata for monitoring or dashboards.
📌 Summary
  • Spring Batch is modular — Jobs → Steps → Readers/Processors/Writers.
  • JobRepository ensures **restartability and traceability**.
  • JobLauncher triggers jobs with **JobParameters**, creating unique JobInstances.
  • StepExecutions track progress at step level; listeners and policies allow **error handling and monitoring**.

Control-M is an enterprise job scheduler that can trigger Spring Batch jobs based on schedules, dependencies, or manual execution requests.

1️⃣ Automatic Scheduling
  • Control-M can trigger a job **at a defined schedule**, such as daily, hourly, or based on a calendar.
  • For Spring Batch jobs, Control-M typically calls a **shell script or REST API endpoint** that invokes the job.
  • Example: Trigger a Spring Batch job via JobLauncherCommandLineRunner from the command line.

# Shell script to run Spring Batch job
#!/bin/bash
java -jar my-batch-app.jar \
    --spring.batch.job.names=myBatchJob \
    --job.param.date=$(date +%Y-%m-%d)
  • Control-M schedule: run the above script daily at 2:00 AM.
  • Job parameters (like date) can be passed dynamically from Control-M variables.
2️⃣ Manual Triggering
  • Control-M allows users to **manually trigger a job** from the Control-M GUI or command line.
  • Useful for **ad-hoc processing**, testing, or re-running failed jobs.
  • Example using REST API (Spring Boot exposed endpoint for JobLauncher):

# Trigger job manually via REST
curl -X POST http://localhost:8080/batch/startJob \
    -H "Content-Type: application/json" \
    -d '{"jobName":"myBatchJob","jobParams":{"date":"2025-10-13"}}'
  • Control-M can be configured to call this endpoint **manually or via a workflow dependency**.
  • Job parameters can be customized dynamically by the user at trigger time.
3️⃣ Benefits of Using Control-M
  • Centralized scheduling and monitoring for **all batch jobs**.
  • Supports **dependency-based execution**, e.g., run this job only after another job succeeds.
  • Audit and logging of job execution history for compliance.
  • Supports both **automatic (calendar/time-based) and manual/ad-hoc triggers**.
4️⃣ Example Workflow
  • Job sequence in Control-M:
    1. Step 1: Trigger “Load Data” Spring Batch job at 2:00 AM.
    2. Step 2: Trigger “Process Data” job after Step 1 succeeds.
    3. Step 3: Notify via email/SMS after completion.
  • Control-M ensures jobs are executed **in the correct order**, with retries if failures occur.
📌 Summary
  • Control-M triggers Spring Batch jobs **automatically or manually**.
  • Automatic: use **cron-like schedules** or dependency workflows calling scripts or REST endpoints.
  • Manual: triggered via **GUI, command line, or REST API**, with dynamic parameters.
  • Centralizes **monitoring, audit, and dependencies** across multiple jobs and environments.

ShedLock ensures that in a distributed environment, only one instance of a scheduled task runs at a time.

Mechanism
  • Uses a database table as lock registry.
  • Instance acquires lock → executes task → releases lock on completion or expiration.

myScheduledJob 2025-10-13 12:05:00 instance-1 2025-10-13 12:15:00

@SchedulerLock(name = "myScheduledJob", lockAtMostFor = "10m", lockAtLeastFor = "1m")
public void runScheduledTask() { log.info("Executing task"); }

Spring Boot Example

    return new RedisLockProvider(redisConnectionFactory);
}

@Scheduled(cron = "0 0 * * * *")
@SchedulerLock(name = "myRedisJob", lockAtMostFor = "10m", lockAtLeastFor = "1m")

Notes

  • TTL ensures lock expires if job crashes.
  • Dynamic, high-performance locking for variable execution jobs.

lockAtLeastFor ensures the lock exists for a minimum duration but the job **finishes immediately** after its logic completes.

  • Execution does not wait for the minimum time.
  • Other instances cannot acquire the lock until the minimum duration expires.

  • Distributed Queues (Kafka/RabbitMQ/SQS) → jobs triggered per message.
  • Database Row-Based Locking → dynamic lock per job row (SELECT … FOR UPDATE).
  • Distributed Lock with Heartbeat / Lease Renewal (Redis, Zookeeper, Consul).
  • Event-Driven Orchestration / Saga Pattern → trigger only when downstream completes.

By default, Spring Batch runs jobs synchronously — meaning the thread that starts the job also executes all steps **in sequence**. However, Spring Batch provides several mechanisms to enable **asynchronous and parallel execution** when needed.

1️⃣ Default Behavior – Synchronous Execution
  • When a job is launched using JobLauncher.run(), it executes in the same thread.
  • Each step (and chunk within it) runs **sequentially** in the same thread.
  • Good for predictable, ordered execution and transactional integrity.

jobLauncher.run(myJob, new JobParameters());

👉 The above runs synchronously — the caller waits until the entire job finishes.

2️⃣ Asynchronous Execution – AsyncJobLauncher
  • Spring provides SimpleAsyncTaskExecutor or TaskExecutorJobLauncher to run jobs asynchronously.
  • In this case, the job runs in a separate thread, and the caller gets control back immediately.

@Bean
public JobLauncher asyncJobLauncher(JobRepository jobRepository) {
    TaskExecutorJobLauncher launcher = new TaskExecutorJobLauncher();
    launcher.setJobRepository(jobRepository);
    launcher.setTaskExecutor(new SimpleAsyncTaskExecutor());
    return launcher;
}

🚀 Now when you call jobLauncher.run(), the job starts in a new thread asynchronously.

3️⃣ Parallelism Within Steps
  • Spring Batch allows **multi-threaded steps** using TaskExecutor at the Step level.
  • Each chunk (read-process-write unit) executes in a separate thread.
  • Useful when you have large data to process faster.

@Bean
public Step multiThreadedStep() {
    return stepBuilderFactory.get("multiThreadedStep")
        .chunk(100)
        .reader(reader())
        .processor(processor())
        .writer(writer())
        .taskExecutor(new SimpleAsyncTaskExecutor())  // creates multiple threads
        .throttleLimit(5)                             // max 5 concurrent threads
        .build();
}

💡 Each chunk runs concurrently, but Spring Batch still maintains transaction boundaries and checkpoints per chunk.

4️⃣ Parallel Steps & Partitioning
  • Split or Partition steps can execute multiple sub-steps or partitions in parallel threads.
  • Ideal for processing multiple data partitions (e.g., different files or DB ranges).

@Bean
public Job parallelJob() {
    return jobBuilderFactory.get("parallelJob")
        .start(flow1())
        .split(new SimpleAsyncTaskExecutor())
        .add(flow2())
        .end()
        .build();
}

🧩 Here flow1 and flow2 run in parallel threads.

5️⃣ Key Takeaways
  • ✅ By default — Spring Batch runs synchronously (single-threaded).
  • ⚙️ Asynchronous job launch — via TaskExecutorJobLauncher.
  • 🚀 Parallel chunks — via TaskExecutor on steps.
  • 🧩 Parallel steps — via split() or partitioning.
  • 🧠 Spring Batch manages its own threads safely with transactions & checkpoints.
📌 Summary
  • Default: Synchronous, single-threaded execution.
  • Async options: Asynchronous job launchers, multi-threaded steps, parallel flows, or partitions.
  • Thread safety: Spring Batch handles transactions & commits safely across threads.

Spring Batch jobs can be triggered not only by cron schedules but also by **external events** — like Kafka messages, REST API calls, or other schedulers.

1️⃣ Kafka Trigger – Event-Driven Batch Start
  • Listen to a Kafka topic using @KafkaListener.
  • When a message arrives, trigger the batch job using JobLauncher.

@Component
@RequiredArgsConstructor
public class KafkaJobTrigger {

    private final JobLauncher jobLauncher;
    private final Job processDataJob;

    @KafkaListener(topics = "trigger-batch-job", groupId = "batch-group")
    public void onMessage(String message) throws Exception {
        JobParameters params = new JobParametersBuilder()
                .addString("messageId", message)
                .addLong("time", System.currentTimeMillis())
                .toJobParameters();

        jobLauncher.run(processDataJob, params);
        log.info("Spring Batch Job triggered by Kafka message: {}", message);
    }
}
  • Kafka acts as an **event source** to start processing dynamically.
  • Useful for near-real-time or streaming-triggered batch loads.
2️⃣ REST API Trigger – Manual / On-Demand Execution
  • Expose a REST endpoint that starts a Spring Batch job manually.
  • Useful for ad-hoc runs, re-processing, or integration with external systems.

@RestController
@RequiredArgsConstructor
@RequestMapping("/batch")
public class JobController {

    private final JobLauncher jobLauncher;
    private final Job loadDataJob;

    @PostMapping("/start")
    public ResponseEntity<String> startJob(@RequestParam String fileName) {
        try {
            JobParameters jobParameters = new JobParametersBuilder()
                    .addString("fileName", fileName)
                    .addLong("time", System.currentTimeMillis())
                    .toJobParameters();

            jobLauncher.run(loadDataJob, jobParameters);
            return ResponseEntity.ok("Job started successfully for " + fileName);
        } catch (Exception e) {
            return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                    .body("Job failed: " + e.getMessage());
        }
    }
}
  • Triggered via POST /batch/start?fileName=data.csv.
  • Can be called by Control-M, Jenkins, or external APIs.
3️⃣ Scheduler Trigger – Time-Based / Recurring Jobs
  • Use Spring’s @Scheduled annotation to run jobs automatically on a fixed schedule.
  • Ideal for daily, hourly, or weekly recurring tasks.

@Component
@RequiredArgsConstructor
public class SchedulerJobTrigger {

    private final JobLauncher jobLauncher;
    private final Job aggregateJob;

    @Scheduled(cron = "0 0 2 * * *")  // every day at 2 AM
    public void runJob() throws Exception {
        JobParameters params = new JobParametersBuilder()
                .addLong("time", System.currentTimeMillis())
                .toJobParameters();

        jobLauncher.run(aggregateJob, params);
        log.info("Spring Batch job triggered by scheduler at 2 AM");
    }
}
  • Spring Scheduler, Quartz, or Control-M can handle timing.
  • Combined with ShedLock for distributed locking (to avoid duplicate execution).
📌 Summary
  • Kafka Trigger: Real-time event → Batch job starts on message arrival.
  • REST Trigger: On-demand → Trigger via API call (manual/automated).
  • Scheduler Trigger: Time-based → Cron or Control-M triggers the job automatically.
  • All triggers internally use JobLauncher.run() with JobParameters.

Mutual Fund broker platforms rely heavily on **batch processing** to handle NAV updates, daily calculations, transaction settlements, and compliance reports. Spring Batch is ideal for these nightly or event-driven data workflows.

1️⃣ Problem – Before Batch Processing
  • Each broker or fintech app manually fetched NAV, holdings, and transactions from the **fund house** APIs or files.
  • Processing was **slow, error-prone**, and often overlapped between instances (duplicate calculations).
  • No proper checkpointing or resume ability — if failed midway, the entire run restarted.

Example: A broker app manually downloads NAV files and computes portfolio values for thousands of users.

2️⃣ How Spring Batch Solves It
  • Spring Batch defines a structured Job → Step → Reader / Processor / Writer pipeline.
  • Jobs can be triggered:
    • ⏰ Nightly (via Control-M or @Scheduled)
    • 📥 Event-based (via Kafka when NAV file arrives)
    • 🖐️ On-demand (via REST API)
  • Supports fault tolerance, restartability, and transactional consistency.
  • Integrates with ShedLock to ensure only one instance runs the NAV update job at a time.
3️⃣ Example Use Case – NAV Calculation Job
  • Every night, the fund maintainer publishes new NAV values in a file or Kafka event.
  • Spring Batch job runs to read that NAV data, calculate user portfolio values, and persist results.

@Component
@RequiredArgsConstructor
public class NavUpdateJobTrigger {

    private final JobLauncher jobLauncher;
    private final Job navCalculationJob;

    // Trigger automatically every night at 2 AM
    @Scheduled(cron = "0 0 2 * * *")
    @SchedulerLock(name = "navCalculationJob", lockAtMostFor = "1h", lockAtLeastFor = "10m")
    public void triggerNavJob() throws Exception {
        JobParameters params = new JobParametersBuilder()
                .addLong("time", System.currentTimeMillis())
                .toJobParameters();
        jobLauncher.run(navCalculationJob, params);
        log.info("Triggered NAV Calculation Job for all funds.");
    }
}
4️⃣ Event-Driven Alternative (Kafka)

If the MF maintainer publishes NAV data into a Kafka topic:


@KafkaListener(topics = "nav-updates")
public void onNavUpdate(String navJson) throws Exception {
    JobParameters params = new JobParametersBuilder()
            .addString("navJson", navJson)
            .addLong("time", System.currentTimeMillis())
            .toJobParameters();

    jobLauncher.run(navCalculationJob, params);
}
  • Automatically processes NAV updates as soon as they arrive.
  • No waiting for nightly schedule — near-real-time processing possible.

  • Reader: Read NAV data from CSV, database, or Kafka payload.

  • Writer: Update holdings, valuations, and reports in DB.
