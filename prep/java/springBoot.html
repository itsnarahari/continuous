📌 Problem Statement
  • You have multiple implementations of the same interface (e.g., EncryptionX and EncryptionY).
  • You want Spring Boot to **dynamically pick one implementation** based on configuration or runtime condition.
  • Example use case: different encryption algorithms for different environments (DEV, QA, PROD).
📌 Interface and Implementations

public interface Encryption {
    void encrypt();
}

@Service("encryptionX")
class EncryptionX implements Encryption {
    public void encrypt() {
        // Encryption logic X
    }
}

@Service("encryptionY")
class EncryptionY implements Encryption {
    public void encrypt() {
        // Encryption logic Y
    }
}
📌 1️⃣ Approach 1 – Map Injection (Best for Dynamic Runtime Switching)
  • Inject all available beans as a Map<String, Encryption>.
  • Spring automatically populates the map with bean name → bean instance pairs.
  • Choose which one to use based on the property value.

@Component
@RequiredArgsConstructor
public class EncryptionService {

    @Value("${encryption.type:encryptionX}")
    private String encryptionType;

    private final Map<String, Encryption> encryptions;

    public void encrypt() {
        Encryption encryption = encryptions.get(encryptionType);
        if (encryption == null) {
            throw new IllegalArgumentException("Invalid encryption type: " + encryptionType);
        }
        encryption.encrypt();
    }
}
📘 application.yml

encryption:
  type: encryptionY
  • Set the property to switch between implementations.
  • No restart needed if property value changes dynamically (can also expose via API).
📌 2️⃣ Approach 2 – Factory Pattern
  • Encapsulate selection logic in a separate factory class.
  • Cleaner design when you want to keep logic isolated.

@Component
@RequiredArgsConstructor
public class EncryptionFactory {

    private final EncryptionX encryptionX;
    private final EncryptionY encryptionY;

    @Value("${encryption.type:encryptionX}")
    private String encryptionType;

    public Encryption getEncryption() {
        return switch (encryptionType) {
            case "encryptionY" -> encryptionY;
            default -> encryptionX;
        };
    }
}

@Service
@RequiredArgsConstructor
public class EncryptionService {
    private final EncryptionFactory encryptionFactory;

    public void encrypt() {
        encryptionFactory.getEncryption().encrypt();
    }
}
📌 3️⃣ Approach 3 – @ConditionalOnProperty (Best for Environment-Based Configuration)
  • Spring will create only the bean that matches the property value.
  • Useful when you want one active implementation per environment (e.g., QA uses X, PROD uses Y).

@Service
@ConditionalOnProperty(name = "encryption.type", havingValue = "encryptionX", matchIfMissing = true)
class EncryptionX implements Encryption {
    public void encrypt() { ... }
}

@Service
@ConditionalOnProperty(name = "encryption.type", havingValue = "encryptionY")
class EncryptionY implements Encryption {
    public void encrypt() { ... }
}
📌 Key Points
  • Map Injection: Inject all beans → select dynamically → good for runtime switching.
  • Factory Pattern: Centralize logic → good for cleaner architecture.
  • @ConditionalOnProperty: Only one bean is created → best for environment-based configs.
  • Avoid manually creating beans with new EncryptionX() inside Spring components – breaks DI and AOP.
📌 Analogy
  • Think of each Encryption as a different encryption machine.
  • Spring is the factory manager deciding which machine to use based on config.
  • You just pass the type (“X” or “Y”), and Spring routes to the correct one automatically.

📌 1️⃣ Increased Complexity
  • Microservices are distributed systems made up of multiple smaller deployable units — this adds **operational and architectural complexity**.
  • Developers must handle **service discovery, communication, fault tolerance, monitoring**, and **distributed logging**.
  • Teams need to be skilled in **DevOps, CI/CD, containerization (Docker, Kubernetes)** to manage them effectively.
📌 2️⃣ Distributed System Challenges
  • Services communicate via network calls (REST, gRPC, Kafka), which introduces **latency and potential failures**.
  • Need additional mechanisms like:
    • ✅ Circuit breakers (e.g., Resilience4j, Hystrix)
    • ✅ Retries and timeouts
    • ✅ Service discovery and load balancing
  • Debugging distributed issues across multiple nodes is harder than in a monolithic app.
📌 3️⃣ Data Management Complexity
  • Each microservice usually manages its **own database** to ensure loose coupling.
  • This makes **cross-service transactions** difficult to maintain (no simple ACID guarantees).
  • Requires handling **eventual consistency** and implementing patterns like **Saga** or **CQRS** for data coordination.
📌 4️⃣ Deployment & Versioning Overhead
  • With multiple services, **build, deploy, and manage pipelines** multiply.
  • Keeping APIs **backward compatible** across versions adds overhead.
  • Requires sophisticated **CI/CD automation** and orchestration (Kubernetes, Jenkins, etc.).
📌 5️⃣ Higher Resource Usage
  • Each service might run in its own container or JVM — leading to **higher memory and CPU usage**.
  • For small-scale applications, this can become **less efficient** than a monolith.
📌 6️⃣ Complex Testing & Debugging
  • End-to-end testing involves spinning up **multiple dependent services**, making it slower and complex.
  • Tracing a request across services requires **distributed tracing tools** (Zipkin, Jaeger, Sleuth).
  • Simple bugs can be hard to reproduce locally.
📌 7️⃣ Operational and Monitoring Challenges
  • Need centralized solutions for:
    • 📊 Metrics (Prometheus, Grafana)
    • 📜 Logs (ELK Stack, Loki)
    • 📡 Traces (Zipkin, Jaeger)
  • Without good observability tools, diagnosing production issues becomes difficult.
📌 8️⃣ Communication Overhead
  • In a monolith, methods communicate in-process; in microservices, it’s **inter-process communication (IPC)** via network.
  • This adds **serialization/deserialization**, network cost, and higher response time.
📌 9️⃣ Skill and Team Requirements
  • Microservices demand broader skills — **DevOps, CI/CD, container orchestration, observability, distributed tracing, etc.**
  • Harder to maintain for small teams or organizations without dedicated DevOps support.
📌 10️⃣ When Not to Use Microservices
  • ❌ Small-scale or early-stage projects — simpler monolithic design is better.
  • ❌ Teams without distributed system experience.
  • ❌ When latency, simplicity, or tight consistency are higher priorities than scalability.
📌 Summary
  • Microservices offer scalability and modularity but come at the cost of **operational, architectural, and data complexity**.
  • Best suited for **large-scale systems** with multiple independent teams and mature DevOps culture.
  • Otherwise, a **modular monolith** might be a more practical and efficient starting point.
📌 Analogy
  • Monolith = One big ship with all facilities in one place (easy to steer but harder to scale).
  • Microservices = A fleet of smaller boats (flexible, scalable, but needs coordination, communication, and strong navigation control).

📌 What is @Transactional?
  • `@Transactional` is a **declarative transaction management annotation** provided by Spring.
  • It ensures **atomicity, consistency, isolation, and durability (ACID)** of database operations.
  • Can be applied at **class or method level** to manage transaction boundaries automatically.
📌 How it Works Internally
  • Spring creates a **proxy object** for the bean containing `@Transactional` methods (JDK dynamic proxy or CGLIB proxy).
  • When a method annotated with `@Transactional` is called, the **call goes through the proxy** first.
  • The proxy uses a **PlatformTransactionManager** (e.g., `DataSourceTransactionManager` for JDBC or `JpaTransactionManager` for JPA) to manage transactions.
  • Steps inside the proxy:
    1. Check if a **transaction is already active** (propagation rules).
    2. If not active, **start a new transaction** using TransactionManager.
    3. Call the actual target method.
    4. If method succeeds → **commit transaction**.
    5. If method throws exception → **rollback transaction** (based on rollback rules).
📌 Who Creates the Query?
  • If using **JDBC template**, the developer writes SQL, Spring executes it within the transaction.
  • If using **Spring Data JPA**, query creation can happen in three ways:
    • **Method names** – Spring derives queries from repository method names (`findByName`, etc.).
    • **@Query annotation** – Custom JPQL or native SQL query.
    • **Criteria API / QueryDSL** – Programmatically build queries.
  • Spring doesn’t generate SQL for every method—it either delegates to **JPA provider (Hibernate/EclipseLink)** or uses developer-defined SQL.
📌 Query Execution Flow
  1. Transaction proxy starts transaction.
  2. JPA repository method invoked.
  3. Spring Data JPA delegates call to **EntityManager**.
  4. EntityManager uses **Hibernate/JPA provider** to create SQL query.
  5. SQL sent to **database via JDBC**.
  6. Database executes query, returns results to EntityManager.
  7. Transaction proxy commits or rolls back based on success or exception.
📌 Example – @Transactional

@Service
public class UserService {

    @Autowired
    private UserRepository userRepository;

    @Transactional
    public void createUsers() {
        userRepository.save(new User("Alice"));
        userRepository.save(new User("Bob"));
        // If exception occurs here, both saves are rolled back
    }
}
📌 Key Points
  • Spring uses **AOP proxy** to manage transaction boundaries.
  • Actual SQL execution is delegated to **JPA provider or JDBC**.
  • `@Transactional` supports:
    • Propagation (REQUIRED, REQUIRES_NEW, etc.)
    • Isolation levels (READ_COMMITTED, SERIALIZABLE, etc.)
    • Rollback rules (by default rollback on unchecked exceptions)
  • Without a proxy (e.g., calling method internally in same class), `@Transactional` **won’t work**.
📌 Analogy
  • Transaction proxy = Bank teller ensuring atomicity for multiple operations.
  • Repository method = Person requesting multiple operations (insert, update).
  • Database = Vault executing commands.
  • If anything fails → proxy rolls back all operations.

📌 What is Reflection?
  • Reflection is a **Java feature** that allows inspecting and manipulating **classes, methods, fields, and constructors at runtime**.
  • It allows Spring (or any framework) to **instantiate classes, call methods, and inject dependencies dynamically** without knowing the class at compile-time.
📌 Why Spring Uses Reflection
  • Spring IoC / DI (Inversion of Control / Dependency Injection) uses reflection to **create beans dynamically**.
  • Enables **setter / constructor injection** without explicit class instantiation.
  • Spring AOP uses reflection to **wrap methods in proxies**.
  • Spring MVC uses reflection to **call controller methods dynamically** based on HTTP requests.
  • Allows **reading annotations at runtime** (`@Autowired`, `@Transactional`, `@RequestMapping`).
📌 How Spring Uses Reflection – Example

// Example: Manual Reflection
Class<?> clazz = Class.forName("com.example.UserService");
Object obj = clazz.getDeclaredConstructor().newInstance();

// Accessing fields
Field field = clazz.getDeclaredField("userRepository");
field.setAccessible(true); // bypass private
field.set(obj, new UserRepository());

// Invoking methods
Method method = clazz.getDeclaredMethod("createUser", String.class);
method.invoke(obj, "Alice");

@Service

    @Autowired
    private UserRepository userRepository;

        userRepository.save(new User(name));

📌 Key Points
  • Reflection allows **dynamic object creation and method invocation**.
  • Enables Spring to **inject dependencies** at runtime, not compile-time.
  • Helps **scan classes for annotations** like `@Controller`, `@Service`, `@Repository`.
  • Used heavily in **Spring AOP, Spring MVC, and Spring Data**.
📌 Advantages
  • Dynamic instantiation of classes and objects.
  • Annotation processing at runtime.
  • Frameworks like Spring can **automate wiring and method calls**.
📌 Disadvantages
  • Performance overhead compared to normal method calls.
  • May bypass **compile-time checks**, leading to runtime errors.
  • Code readability can suffer if overused manually.
📌 Analogy
  • Reflection = Remote control that can **operate any appliance** without knowing its type in advance.
  • Spring uses reflection like a universal remote to **create beans, inject dependencies, and call methods dynamically**.

ShedLock ensures that in a distributed Spring Boot environment, **only one instance of a scheduled task runs at a time**, even if multiple app instances are running.

1️⃣ Purpose
  • Prevent duplicate executions of @Scheduled tasks across multiple instances.
  • Works in **clustered or cloud deployments** where multiple app instances share the same job.
2️⃣ Mechanism
  • Uses a **shared storage** (database, Redis, MongoDB) as a lock registry.
  • Steps:
    1. An instance tries to acquire the lock in the shared storage.
    2. If the lock is free or expired, the instance writes a lock record and executes the job.
    3. Other instances attempting to acquire the lock **fail and skip execution**.
    4. Lock is released after job completion or when lockAtMostFor expires.
3️⃣ Database Lock Example

Simplified ShedLock table:

name locked_at locked_by lock_until
myScheduledJob 2025-10-13 12:05:00 instance-1 2025-10-13 12:15:00
  • name: unique job identifier.
  • locked_at: timestamp when lock was acquired.
  • locked_by: the instance holding the lock.
  • lock_until: time until which this lock is valid.
4️⃣ Spring Boot + ShedLock Example

@Scheduled(cron = "0 0 * * * *")
@SchedulerLock(
    name = "myScheduledJob",
    lockAtMostFor = "10m",
    lockAtLeastFor = "1m"
)
public void runScheduledTask() {
    log.info("Executing scheduled task at " + LocalDateTime.now());
}
  • lockAtMostFor: Maximum time the lock is held (prevents stuck tasks).
  • lockAtLeastFor: Minimum lock duration (prevents too frequent execution).
5️⃣ Summary
  • ShedLock prevents duplicate execution across **multiple instances** by locking on the shared storage.
  • Works seamlessly with @Scheduled tasks in clustered environments.
  • It ensures **single-instance execution**, but does not replace transaction management or concurrency control within batch jobs.

Using **Redis (or sharded Redis)** as the lock registry allows ShedLock to coordinate scheduled tasks **without relying on a relational database**, suitable for cloud-native or microservice environments.

1️⃣ How it Works
  • ShedLock creates a **lock key** in Redis for each scheduled task.
  • When a task is triggered:
    1. The instance attempts to **set the lock key atomically** using Redis commands (like SET key value NX PX timeout).
    2. If the key is **successfully set**, the instance executes the scheduled job.
    3. If the key already exists, **other instances skip execution**.
    4. When the job finishes, the lock expires automatically after the configured TTL (lockAtMostFor).
  • Sharded Redis is fully supported: ShedLock uses the **Redis client** (Lettuce or Jedis) to interact with the cluster, ensuring atomic key operations per shard.
2️⃣ Spring Boot + Redis Example

@Configuration
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "10m")
public class SchedulerConfig {

    @Bean
    public LockProvider lockProvider(RedisConnectionFactory redisConnectionFactory) {
        return new RedisLockProvider(redisConnectionFactory);
    }
}

@Component
public class ScheduledTasks {

    @Scheduled(cron = "0 0 * * * *")
    @SchedulerLock(
        name = "myRedisScheduledJob",
        lockAtMostFor = "10m",
        lockAtLeastFor = "1m"
    )
    public void runTask() {
        log.info("Executing scheduled task at " + LocalDateTime.now());
    }
}
3️⃣ Advantages of Redis-based Lock
  • ⚡ **High performance** – Redis is in-memory and very fast.
  • ☁️ **Cloud-friendly** – works well in Kubernetes, Docker, and microservices.
  • 🔀 **Sharded Redis support** – can coordinate locks across distributed clusters.
  • 🔒 Atomic operations ensure **only one instance executes the job**.
  • 🕒 TTL ensures **stale locks are automatically released**.
4️⃣ Notes & Best Practices
  • Use **RedisLockProvider** with Lettuce or Jedis clients.
  • Set **lockAtMostFor** slightly longer than the maximum job execution time to avoid duplicate runs.
  • For **highly critical jobs**, monitor lock acquisition failures to detect skipped executions.
  • Sharded Redis handles **automatic failover**, but make sure all nodes can see the lock key consistently.
📌 Summary
  • ShedLock with Redis provides **distributed, high-performance locks** for scheduled jobs.
  • Sharded Redis ensures **scalable, fault-tolerant coordination** across multiple instances.
  • TTL-based locks prevent **stuck executions** and maintain single-instance guarantees.

In ShedLock, lockAtLeastFor guarantees that the lock **will not be released before a minimum duration**, but it does **not force the job to wait**.

1️⃣ How lockAtLeastFor Works
  • lockAtLeastFor ensures that **the lock itself is held at least for the given duration**.
  • However, the **scheduled method execution completes immediately** once the task logic finishes.
  • This prevents **another instance from acquiring the lock too soon**, even if the current job finished very quickly.
2️⃣ Example

@Scheduled(cron = "0 * * * * *")
@SchedulerLock(
    name = "myTask",
    lockAtMostFor = "10m",
    lockAtLeastFor = "2m"
)
public void myTask() {
    log.info("Task started");
    // Simulate short task
    Thread.sleep(30_000); // 30 seconds
    log.info("Task finished");
}
  • Task duration: 30 seconds
  • lockAtLeastFor: 2 minutes
  • Behavior:
    • Task finishes in 30 seconds → execution completes immediately
    • Lock is still held for remaining 1.5 minutes
    • Other instances attempting to acquire the lock during this period **will skip execution**
3️⃣ Key Takeaways
  • ✅ Job execution is never artificially delayed — it completes as soon as its logic finishes.
  • ✅ Lock duration is enforced so no other instance can run the job before the minimum time.
  • ✅ Prevents **too frequent execution** in a clustered environment.
📌 Summary
  • lockAtMostFor → ensures a max lock duration to avoid stuck jobs.
  • lockAtLeastFor → ensures a min lock duration so another instance won’t start too soon.
  • Execution finishes as fast as possible; the lock may continue to exist until lockAtLeastFor expires.

When a job depends on downstream services with **unpredictable response times**, fixed-time locks may fail. Here are **more robust alternatives**:

1️⃣ Distributed Queues (Message-Driven Scheduling)
  • Use **RabbitMQ, Kafka, or SQS** to trigger jobs instead of fixed schedules.
  • Each job is **represented as a message** in a queue.
  • Consumers (instances) **process messages one by one**, or with controlled concurrency.
  • Guarantees **exactly-once or at-least-once processing** depending on your queue setup.

// Kafka consumer example
@KafkaListener(topics = "job-queue")

    log.info("Processing job: " + payload.getId());
    downstreamService.call(payload);
}
2️⃣ Database Row-Based Locking
  • Instead of fixed-duration locks, acquire a **row lock in the database** at the time of processing:
    • Use `SELECT ... FOR UPDATE` in a transaction.
    • Only one instance can acquire the lock for a particular job row.
    • When the job completes (even if it’s slow), the transaction releases the lock.
  • Advantages:
    • Dynamic — lock duration **matches actual job execution time**.
    • Works well for jobs stored as **database entries** (like batch jobs or tasks table).
3️⃣ Distributed Lock with Heartbeat / Lease Renewal
  • Use distributed lock systems that support **dynamic lease renewal**:
    • Redis (Redisson), Zookeeper, Consul, etc.
    • Acquire a lock with a **short TTL**, then periodically **renew the lock** while the job is running.
    • If the job crashes, lock expires automatically.
  • Advantages:
    • Handles **variable execution time** automatically.
    • Prevents another instance from starting until the job truly finishes.
4️⃣ Event-Driven Orchestration / Saga Pattern
  • Instead of a fixed schedule, trigger jobs based on **events** from downstream services.
  • Each event signals that **upstream work is done** and processing can start safely.
  • Can be combined with **message queues or distributed locks** to ensure **single execution**.
📌 Summary
  • Fixed-duration locks (ShedLock) are **not ideal** when job time is unpredictable.
  • Better alternatives:
    • Distributed queues (Kafka, RabbitMQ) → jobs triggered per message
    • Database row-level locks → dynamic lock duration
    • Distributed lock with heartbeat/lease renewal → variable execution support
    • Event-driven orchestration → start only when downstream work is complete
  • All approaches ensure **single-instance execution** while adapting to unpredictable job durations.

In Spring, the @Transactional annotation controls transaction boundaries. When you have **nested transactional methods**, the behavior depends on the **propagation type**.

1️⃣ Default Behavior (Propagation.REQUIRED)
  • If a method with @Transactional calls another @Transactional method, by default Spring uses Propagation.REQUIRED.
  • This means **both methods participate in the same transaction**.
  • Rollback in inner or outer method will affect the **entire transaction**.
2️⃣ Propagation Options
  • REQUIRED: Join existing transaction or create new if none exists (default).
  • REQUIRES_NEW: Suspend existing transaction and start a **new independent transaction**.
  • NESTED: Execute in a **nested transaction** using JDBC savepoints. Can rollback independently from outer transaction.
  • SUPPORTS: Execute within existing transaction if available, otherwise run non-transactionally.
3️⃣ Example Code

@Service
public class OrderService {

    @Transactional
    public void placeOrder() {
        // outer transaction starts
        insertOrder();
        updateInventory();
    }

    @Transactional(propagation = Propagation.REQUIRED)
    public void insertOrder() {
        // joins outer transaction
        // exception here will rollback the entire placeOrder()
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void updateInventory() {
        // independent transaction
        // exception here will rollback only updateInventory, outer transaction continues
    }
}
4️⃣ Key Points / Best Practices
  • Default REQUIRED means **nested calls share the same transaction**.
  • Use REQUIRES_NEW if you want **isolated transactions** inside another transactional method.
  • Use NESTED (with JDBC support) for **savepoint-based rollback**, useful in batch processing.
  • Self-invocation of methods (this.innerMethod()) **does NOT trigger transactional behavior** — use **proxying or AOP**.
  • Be careful with checked vs unchecked exceptions for rollback — by default, Spring rolls back only for **RuntimeException**.
📌 Summary
  • Nested @Transactional methods usually **share the same transaction** (REQUIRED) unless propagation changes it.
  • REQUIRES_NEW creates a **new independent transaction**.
  • NESTED uses **savepoints**, allowing partial rollbacks without affecting the outer transaction.
  • Transactional behavior depends on **propagation, exceptions, and proxy mechanism**.

In a distributed Spring Boot setup (multiple app instances running the same Spring Batch job), concurrency and duplicate execution can occur if not configured properly. Spring Batch provides built-in mechanisms to ensure that only one instance processes a job at a time.

1️⃣ Default Behavior
  • Spring Batch uses a shared JobRepository (usually database-backed) to coordinate job executions.
  • When one instance starts a job, it creates an entry in tables like BATCH_JOB_INSTANCE and BATCH_JOB_EXECUTION.
  • If another instance tries to start the same job with identical parameters, Spring Batch throws:
    • JobExecutionAlreadyRunningException
    • JobInstanceAlreadyCompleteException
    ensuring only one instance runs it.
2️⃣ Required Setup — Shared JobRepository
  • All service instances must share the same database for job metadata.
  • Each instance reads and writes to the same tables:
    • BATCH_JOB_INSTANCE
    • BATCH_JOB_EXECUTION
    • BATCH_STEP_EXECUTION
  • This database acts as a distributed lock between instances.

@Configuration

public class BatchConfig {

        factory.afterPropertiesSet();
        return factory.getObject();

    @Bean

        SimpleJobLauncher launcher = new SimpleJobLauncher();
        launcher.setJobRepository(jobRepository);

public class RangePartitioner implements Partitioner {
    @Override
    public Map<String, ExecutionContext> partition(int gridSize) {
        Map<String, ExecutionContext> result = new HashMap<>();
        int range = 1000;
        for (int i = 0; i < gridSize; i++) {
            ExecutionContext context = new ExecutionContext();
            context.putInt("minId", i * range + 1);
            context.putInt("maxId", (i + 1) * range);
            result.put("partition" + i, context);
        }
        return result;
    }
}

Q: In microservices world, how can services communicate privately? Which grant type is generally used?

Answer: Services communicate over secured channels using OAuth2 Client Credentials Grant. Each service has its own client id/secret to authenticate with the authorization server and obtain a token.

Q: List all OAuth2 grant types with examples and pros/cons.

Answer:

  • Authorization Code: Used by web apps; pros: secure, supports refresh token; cons: requires redirect flow.
  • Implicit: Used by single-page apps; pros: simpler; cons: less secure, no refresh token.
  • Client Credentials: Used by microservices; pros: server-to-server secure communication; cons: not for user delegation.
  • Resource Owner Password Credentials: User provides credentials directly; pros: simple; cons: unsafe, rarely recommended.
  • Refresh Token: Used to obtain new access tokens; pros: extends session without re-login; cons: requires secure storage.

When a Spring Boot REST API request that usually completes in 200ms suddenly takes 20 seconds under heavy load, it indicates performance bottlenecks such as thread starvation, slow database queries, connection pool exhaustion, or poor resource configuration.

📊 Step-by-Step Performance Investigation Strategy
1️⃣ Confirm the Scope of the Problem
  • Check if the slowdown is global or endpoint-specific.
  • Compare latency across environments (staging vs production).
  • Is it happening only under concurrent load (stress or spike)?
2️⃣ Analyze Application Metrics
  • Enable Spring Boot Actuator and observe: /actuator/metrics/http.server.requests for latency patterns.
  • Use Micrometer + Prometheus + Grafana dashboards for real-time monitoring.
  • Track CPU, memory, GC, thread count, and DB connection pool usage.
3️⃣ Profile the Application
  • Use profilers like VisualVM, JProfiler, YourKit, or Java Flight Recorder (JFR).
  • Capture CPU and heap snapshots under load.
  • Identify hotspots — methods consuming most CPU or memory.
4️⃣ Check Thread and Connection Pooling

spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      connection-timeout: 30000
server:
  tomcat:
    threads:
      max: 200
      min-spare: 20
      accept-count: 100
      connection-timeout: 30s
  • Monitor HikariCP metrics — check if connections are exhausted or waiting too long.
  • Increase Tomcat max threads if requests are queuing.
  • Tune connection timeout and thread pool parameters.
5️⃣ Investigate Database Layer
  • Enable spring.jpa.show-sql=true or use a query profiler.
  • Check for N+1 queries, missing indexes, or long-running joins.
  • Use EXPLAIN ANALYZE on SQL queries.
  • Implement caching (Caffeine, Redis) for frequently accessed data.
6️⃣ Analyze Garbage Collection & Memory Pressure

# Enable GC logging
java -Xlog:gc*,gc+heap=debug:file=gc.log:time,uptime,level,tags
  • Frequent GC cycles or full GCs can stall threads for seconds.
  • Use G1GC or ZGC for large heaps.
  • Inspect allocation rate and object churn under load.
7️⃣ Identify Synchronization or Blocking Code
  • Look for synchronized blocks or blocking I/O in the request path.
  • Use async or reactive APIs if waiting for I/O responses (e.g., WebClient).
  • Replace heavy computation with background tasks or queues.
8️⃣ Check External Dependencies
  • Upstream services (REST APIs, message queues, file storage) may respond slowly under load.
  • Apply timeouts and circuit breakers using Resilience4j.

@Bean
public WebClient webClient() {
    return WebClient.builder()
        .clientConnector(new ReactorClientHttpConnector(
            HttpClient.create()
                .responseTimeout(Duration.ofSeconds(5))
        ))
        .build();
}
9️⃣ Conduct Load Testing & Benchmarking
  • Use tools like JMeter, k6, or Gatling to simulate load.
  • Gradually increase concurrent users to identify the saturation point.
  • Analyze throughput (RPS), latency percentiles (P95, P99), and error rates.
🔟 Apply Fixes and Re-Test
  • Reduce blocking calls and optimize DB queries.
  • Increase resource pools (threads, connections) within safe limits.
  • Introduce caching layers for repeated expensive operations.
  • Deploy with autoscaling if hosted on Kubernetes or AWS ECS.
🏁 Key Takeaway

Performance tuning is an iterative process — measure ➜ identify ➜ fix ➜ re-measure. Focus first on metrics (CPU, threads, DB latency), then optimize the slowest component rather than guessing. Always validate improvements through consistent load testing and profiling.

In a microservices architecture, services often need to communicate with each other privately and securely. OAuth2 with client credentials grant type is commonly used for service-to-service authentication.

🧩 How Service-to-Service Communication Works
  • Each service registers itself as a client in the OAuth2 authorization server.
  • The service uses client_id and client_secret to request an access token.
  • Other microservices validate this token before processing the request.
⚡ Client Credentials Grant Flow
  1. Service A requests a token from the authorization server: 
    
POST /oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id=service-a
&client_secret=SECRET
  2. Authorization server responds with an access_token.
  3. Service A calls Service B and includes the token in the Authorization: Bearer <token> header.
  4. Service B validates the token before processing the request.
✅ Key Points
  • No user involvement — ideal for server-to-server communication.
  • Access tokens are short-lived; services can refresh tokens if needed.
  • Works well with Spring Boot + Spring Security OAuth2 or any OAuth2-compliant framework.
  • Alternative: Mutual TLS (mTLS) can also secure service-to-service calls.
📌 Summary

For private communication between microservices, OAuth2 client credentials grant is the standard choice. It allows services to authenticate themselves securely without user context, ensuring trusted, private communication within the system.

OAuth2 defines several grant types to obtain access tokens, each suited for a specific use case.

1️⃣ Authorization Code Grant
  • Flow: User logs in via browser → app receives authorization code → exchanges for access token.
  • Example: Web apps with front-end + back-end separation.
  • Real World: Google Login, GitHub OAuth login on third-party apps.
  • Advantages:
    • Secure: access token never exposed to browser directly.
    • Supports refresh tokens.
  • Disadvantages:
    • More complex flow than implicit grant.
    • Requires server-side code to handle code exchange.
2️⃣ Implicit Grant
  • Flow: User authenticates → access token returned directly via browser URL fragment.
  • Example: Single Page Applications (SPAs) without a backend.
  • Real World: Old JavaScript SPAs using Facebook Login.
  • Advantages:
    • Simpler: no server-side token exchange required.
  • Disadvantages:
    • Less secure: access token exposed in URL and browser.
    • No refresh token.
3️⃣ Client Credentials Grant
  • Flow: Service authenticates itself using client_id & client_secret → gets access token.
  • Example: Microservices communication, machine-to-machine APIs.
  • Real World: Internal microservices in AWS, Kubernetes-based services.
  • Advantages:
    • No user context needed.
    • Secure for server-to-server communication.
  • Disadvantages:
    • Cannot be used for user-specific actions.
4️⃣ Resource Owner Password Credentials Grant (Password Grant)
  • Flow: User provides username/password → client exchanges them directly for token.
  • Example: First-party trusted apps.
  • Real World: Legacy mobile apps directly sending credentials to auth server.
  • Advantages:
    • Simple, fast token acquisition.
  • Disadvantages:
    • Highly insecure for third-party apps (credentials exposed).
    • Not recommended in modern applications.
5️⃣ Refresh Token Grant
  • Flow: Client uses refresh token to obtain a new access token without user login.
  • Example: Long-lived sessions in mobile apps or web apps.
  • Real World: Gmail mobile app refreshing tokens silently in background.
  • Advantages:
    • Improves UX by avoiding repeated logins.
    • Reduces exposure of user credentials.
  • Disadvantages:
    • Refresh token compromise can lead to unauthorized access.

✅ Summary: Other microservices never talk directly to WebSocket clients. They publish events to a broker, and the WebSocket gateway pushes those events to all connected browsers or apps in real time.

🔹 Event-Based Communication
  • Pattern: Publish/Subscribe through a message broker (Kafka, RabbitMQ, Redis Streams, etc.).
  • Flow: One service publishes an event (e.g. “OrderCreated”) and any number of other services subscribe and react to it.
  • Direction: Always server-to-server. Clients (browsers/mobile) usually aren’t direct consumers.
  • Nature: Asynchronous and fire-and-forget; the publisher doesn’t know or wait for who will handle the event.
  • Usage: Decoupling internal services, audit/event sourcing, background processing.
  • Reliability: Brokers provide delivery guarantees (at-least-once, exactly-once) and message persistence.
🔹 WebSocket Communication
  • Pattern: Persistent full-duplex TCP connection between a client (browser/app) and a gateway/service.
  • Flow: After the handshake, either side can push messages instantly over the same connection.
  • Direction: Client <—> Server, typically to deliver real-time data to users.
  • Nature: Bidirectional and stateful; remains open until closed.
  • Usage: Live dashboards, chat apps, collaborative editing, real-time notifications.
  • Reliability: No built-in persistence or replay; if a client is offline, messages are lost unless you add a broker/queue behind it.
🔑 Key Differences at a Glance
Aspect Event-Based WebSocket
Communication Server ↔ Server (via broker) Client ↔ Server (direct)
Connection Short-lived; per message Long-lived; persistent
Direction One-way publish/subscribe Full-duplex
Reliability Guaranteed by broker No built-in guarantee
Use Case Internal microservice decoupling Real-time UI updates

✅ Summary: Event-based messaging is about loose coupling between backend services using a broker and reliable delivery. WebSocket is about real-time, interactive communication between a client and server over a single long-lived connection. In practice, large systems often combine both: services talk to each other through events, and a WebSocket gateway subscribes to those events to instantly update connected clients.

🔹 1. Initial HTTP/REST-Like Handshake
  • The WebSocket connection starts as a normal HTTP request (GET) to a specific URL such as ws://yourserver:8080/ws/notify or wss:// (secure).
  • The client sends an HTTP header Upgrade: websocket and Connection: Upgrade asking the server to switch from HTTP to WebSocket protocol.
  • The server responds with 101 Switching Protocols if it accepts. After this, the connection is no longer HTTP.
🔹 2. Persistent TCP Socket
  • Once the upgrade succeeds, the underlying connection becomes a raw TCP socket.
  • This socket remains open on the same port (commonly 80 for ws:// or 443 for wss://, but you can use any custom port).
  • Both client and server can send frames (binary or text) anytime without re-establishing connections.
🔹 3. No REST Calls After Upgrade
  • After the handshake there are no REST requests, no request/response cycle.
  • Data travels as WebSocket frames over the open TCP connection—completely independent of HTTP verbs like GET/POST.
  • Because it’s full-duplex, the server can push data instantly without the client polling.
🔹 4. Ports and Security
  • By default, ws:// uses port 80 and wss:// (TLS/SSL encrypted) uses port 443.
  • You can run a WebSocket server on any custom port (e.g., 8080, 3001), provided firewalls and load balancers allow it.
  • When running behind HTTPS (common in production), wss:// is required to encrypt data just like HTTPS.
✅ Quick Recap

1️⃣ **Start:** HTTP(S) request with an Upgrade header.
2️⃣ **Switch:** Server returns 101 Switching Protocols.
3️⃣ **Persist:** Connection becomes a bidirectional TCP socket over a single port.
4️⃣ **Communicate:** Client & Server exchange lightweight frames—no REST, no repeated handshakes.

👉 So WebSocket is neither “just REST” nor “another random port protocol.” It’s a TCP-based protocol that *piggybacks* on HTTP only for the initial upgrade, then lives as a continuous socket connection.

🔹 Short Answer: No, it does not use REST.

The call s.sendMessage(new TextMessage(message)) writes the data directly to the already-established WebSocket TCP connection. After the initial handshake, there is **no HTTP request/response** involved.

🔹 What Actually Happens
  • Step 1 – Handshake: Your WebSocket session s was created earlier when the client upgraded from HTTP to WebSocket. That opened a persistent TCP socket (on port 80/443 or a custom port).
  • Step 2 – Frame Encoding: When you call sendMessage, Spring converts your string to a WebSocket “frame” (a small binary/text packet defined by the WebSocket protocol).
  • Step 3 – TCP Write: That frame is pushed through the low-level OutputStream of the socket. It’s literally a write() on the TCP socket, not an HTTP POST/GET.
  • Step 4 – Client Receive: The browser or app listening on socket.onmessage gets the data instantly.
🔑 Key Takeaways
  • ✅ No REST calls, no HTTP overhead.
  • ✅ Pure bidirectional socket I/O after the upgrade.
  • ✅ Faster and lighter than making a new HTTP request for every message.

👉 So sendMessage() is basically “write bytes on the existing WebSocket channel,” not “call a REST API to publish data.”

📌 1. What is ShedLock?

In a distributed Spring Boot application, scheduled jobs using @Scheduled may run on all instances of the service, leading to duplicate execution.

ShedLock solves this problem by ensuring that a scheduled task runs on only one instance at a time, while other instances skip execution.

📌 2. How ShedLock Works

ShedLock uses a shared store (like DB, Redis, Mongo, etc.) to keep lock information. Before executing a task, it tries to acquire a lock in the store. If successful → task runs. If not → task is skipped on that instance.

📌 3. Setup in Spring Boot 3

Add dependency in pom.xml:


<dependency>
    <groupId>net.javacrumbs.shedlock</groupId>
    <artifactId>shedlock-spring</artifactId>
    <version>5.13.0</version>
</dependency>
<dependency>
    <groupId>net.javacrumbs.shedlock</groupId>
    <artifactId>shedlock-provider-jdbc-template</artifactId>
    <version>5.13.0</version>
</dependency>

Enable ShedLock in a config class:


@Configuration
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "PT30S")
public class SchedulerConfig {

    @Bean
    public LockProvider lockProvider(DataSource dataSource) {
        return new JdbcTemplateLockProvider(
            JdbcTemplateLockProvider.Configuration.builder()
                .withJdbcTemplate(new JdbcTemplate(dataSource))
                .usingDbTime() // Works in distributed systems
                .build()
        );
    }
}
📌 4. Using ShedLock with @Scheduled

Now annotate scheduled methods with @SchedulerLock:


@Component
public class MyJob {

    @Scheduled(cron = "0 */1 * * * ?")
    @SchedulerLock(name = "myTask", 
                   lockAtMostFor = "PT30S", 
                   lockAtLeastFor = "PT10S")
    public void runTask() {
        System.out.println("Running job at " + LocalDateTime.now());
    }
}

✅ lockAtMostFor: maximum lock duration (safety in case job crashes).
✅ lockAtLeastFor: ensures task does not re-run too quickly.

  • Batch processing (send email/SMS, generate reports)
  • Integration jobs (sync with 3rd party APIs)
📌 Conclusion

ShedLock is essential when using @Scheduled in a cluster. It guarantees that only one instance executes a job at a time, preventing duplication and ensuring consistency.

📌 1. What is Hibernate Dialect?

Dialect in Hibernate is a class that tells Hibernate how to generate SQL queries for a specific database. Each database (MySQL, PostgreSQL, Oracle, SQL Server, etc.) has its own SQL syntax and special features.

Example: LIMIT in MySQL vs TOP in SQL Server vs ROWNUM in Oracle.

📌 2. Why is it Necessary?
  • ✅ Ensures Hibernate generates database-specific SQL.
  • ✅ Handles differences in data types (e.g., VARCHAR vs NVARCHAR).
  • ✅ Maps Hibernate functions to DB-specific functions (e.g., current_timestamp, concat).
  • ✅ Optimizes DDL generation (table creation, sequences, auto-increment, etc.).
📌 3. How to Configure in Spring Boot?

In application.properties:


spring.jpa.database-platform=org.hibernate.dialect.MySQL8Dialect

Or for PostgreSQL:


spring.jpa.database-platform=org.hibernate.dialect.PostgreSQLDialect

🔹 If not set, Hibernate tries to auto-detect the dialect based on JDBC driver, but it may not always be optimal → better to configure explicitly.

📌 4. Example

Consider a query with pagination:

  • MySQL Dialect → SELECT * FROM users LIMIT 10 OFFSET 20
  • Oracle Dialect → SELECT * FROM (SELECT u.*, ROWNUM r FROM users u) WHERE r BETWEEN 21 AND 30
  • SQL Server Dialect → SELECT TOP 10 * FROM users ORDER BY id OFFSET 20 ROWS

👉 Without the correct Dialect, Hibernate would generate invalid SQL for your DB.

📌 5. Common Dialects
  • org.hibernate.dialect.MySQL8Dialect
  • org.hibernate.dialect.PostgreSQLDialect
  • org.hibernate.dialect.Oracle12cDialect
  • org.hibernate.dialect.SQLServerDialect
  • org.hibernate.dialect.H2Dialect (for testing)
📌 Conclusion

Hibernate Dialect is the bridge between Hibernate and your database. It ensures Hibernate generates the correct SQL syntax, handles pagination, data types, and DDL operations. Without it, you risk portability issues or runtime SQL errors.

📌 1. Future – Basic Asynchronous Computation

Future<T> was introduced in Java 5 to represent the result of an asynchronous computation. You submit a task to an ExecutorService and get back a Future. But it has limitations:

  • ❌ Cannot manually complete a task.
  • ❌ No chaining (can’t combine multiple futures).
  • ❌ get() is blocking.

ExecutorService executor = Executors.newFixedThreadPool(2);

Future<String> future = executor.submit(() -> {
    Thread.sleep(2000);
    return "Hello from Future!";
});

System.out.println("Doing other work...");

// Blocks until result is available
String result = future.get();  
System.out.println(result);

executor.shutdown();

👉 Here, future.get() blocks until the task finishes.

📌 2. CompletableFuture – Enhanced Async API

CompletableFuture<T> (Java 8) extends Future and provides powerful features:

  • ✅ Non-blocking callbacks (thenApply, thenAccept, thenRun).
  • ✅ Can be manually completed.
  • ✅ Combine multiple futures (thenCombine, allOf).
  • ✅ Exception handling (exceptionally, handle).

CompletableFuture<String> completableFuture = CompletableFuture.supplyAsync(() -> {
    try {
        Thread.sleep(2000);
    } catch (InterruptedException e) {}
    return "Hello from CompletableFuture!";
});

completableFuture
    .thenApply(result -> result + " - processed")
    .thenAccept(System.out::println)  // Non-blocking callback
    .exceptionally(ex -> {
        System.out.println("Error: " + ex.getMessage());
        return null;
    });

System.out.println("Doing other work while async task runs...");
Thread.sleep(3000); // wait so async can finish

👉 Unlike Future, here we use callback chaining instead of blocking.

📌 3. Key Differences
Aspect Future CompletableFuture
Completion Only async task sets result Can be completed manually
Blocking get() blocks Non-blocking callbacks available
Chaining Not supported Supports chaining (thenApply, thenRun)
Combining tasks Not supported allOf(), anyOf(), thenCombine()
Error handling No built-in support exceptionally(), handle()
📌 4. Real-Time Use Case

Future: Good for simple background jobs like sending one email. CompletableFuture: Ideal for microservices calls, chaining async DB/API operations, running multiple calls in parallel and combining results.

📌 Conclusion

Future is basic and blocking. CompletableFuture is advanced, non-blocking, and supports chaining, error handling, and parallel task composition → making it the standard choice in modern Java apps.

📌 Scenario

Suppose you have a microservice that needs to fetch data from 3 different services:

  • 👤 User Service → User details
  • 🛒 Order Service → Orders list
  • 💳 Payment Service → Payment info

Instead of calling them sequentially (slow), you can fetch all in parallel with CompletableFuture.

📌 Code Example

@Service
public class AggregatorService {

    private final UserService userService;
    private final OrderService orderService;
    private final PaymentService paymentService;

    public AggregatorService(UserService userService, 
                             OrderService orderService, 
                             PaymentService paymentService) {
        this.userService = userService;
        this.orderService = orderService;
        this.paymentService = paymentService;
    }

    public CompletableFuture<UserProfile> getUserProfile(Long userId) {

        CompletableFuture<User> userFuture =
            CompletableFuture.supplyAsync(() -> userService.getUser(userId));

        CompletableFuture<List<Order>> ordersFuture =
            CompletableFuture.supplyAsync(() -> orderService.getOrders(userId));

        CompletableFuture<Payment> paymentFuture =
            CompletableFuture.supplyAsync(() -> paymentService.getPayment(userId));

        // Combine all futures
        return CompletableFuture.allOf(userFuture, ordersFuture, paymentFuture)
            .thenApply(v -> new UserProfile(
                    userFuture.join(),
                    ordersFuture.join(),
                    paymentFuture.join()
            ));
    }
}

// --- DTO ---
public record UserProfile(User user, List<Order> orders, Payment payment) { }
📌 Explanation
  • supplyAsync() → Runs API calls in parallel threads.
  • allOf() → Waits for all futures to finish.
  • join() → Retrieves the result (safe here since tasks are completed).
  • Total time = Max of all calls, not sum → Big performance boost 🚀.
📌 Output

Instead of 3 API calls taking 2s + 3s + 1s = 6s sequentially, parallel execution will take only ~3s (the longest call).

📌 Real-Time Use Cases
  • Aggregating data from multiple microservices (User, Orders, Payments, Notifications).
  • Calling external APIs in parallel for faster response.
  • Running independent DB queries simultaneously.
📌 Conclusion

CompletableFuture with allOf() is perfect for parallel API calls. It improves performance and responsiveness in microservices and backend aggregation patterns.

📌 1) MVC (Servlet) Apps — Use a HandlerInterceptor

Works for Spring MVC controllers. Captures start, end, duration, method, URI, status, client IP, and puts a traceId into MDC for every log line. 


package com.example.logging;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.lang.Nullable;
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.time.Instant;
import java.util.UUID;

@Component
public class ApiTimingInterceptor implements HandlerInterceptor {
  private static final Logger log = LoggerFactory.getLogger(ApiTimingInterceptor.class);
  private static final String START_TIME = "startTime";

  @Override
  public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    long now = System.currentTimeMillis();
    request.setAttribute(START_TIME, now);

    String traceId = UUID.randomUUID().toString();
    MDC.put("traceId", traceId);

    // optional: request-scoped MDC fields
    MDC.put("method", request.getMethod());
    MDC.put("path", request.getRequestURI());

    log.debug("➡️ START {} {} at {}", request.getMethod(), request.getRequestURI(), Instant.ofEpochMilli(now));
    return true;
  }

  @Override
  public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, @Nullable Exception ex) {
    long start = (long) request.getAttribute(START_TIME);
    long end = System.currentTimeMillis();
    long durationMs = end - start;

    String method = request.getMethod();
    String uri = request.getRequestURI();
    int status = response.getStatus();

    // better client IP if behind proxy
    String clientIp = getClientIp(request);
    String ua = request.getHeader("User-Agent");

    log.info("✅ END {} {} status={} duration={}ms start={} end={} ip={} ua={}",
        method, uri, status, durationMs, Instant.ofEpochMilli(start), Instant.ofEpochMilli(end), clientIp, ua);

    if (ex != null) {
      log.warn("❗ Exception on {} {}: {}", method, uri, ex.toString());
    }
    // Clean up MDC
    MDC.clear();
  }

  private String getClientIp(HttpServletRequest request) {
    String xff = request.getHeader("X-Forwarded-For");

package com.example.logging;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.time.Instant;
import java.util.UUID;

@Component
public class ApiTimingFilter extends OncePerRequestFilter {
  private static final Logger log = LoggerFactory.getLogger(ApiTimingFilter.class);

  @Override
  protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
      throws ServletException, IOException {
    long start = System.currentTimeMillis();
    MDC.put("traceId", UUID.randomUUID().toString());
    MDC.put("method", req.getMethod());
    MDC.put("path", req.getRequestURI());
    try {
      chain.doFilter(req, res);
    } finally {
      long end = System.currentTimeMillis();
      long duration = end - start;
      log.info("HTTP {} {} status={} duration={}ms start={} end={}",
          req.getMethod(), req.getRequestURI(), res.getStatus(), duration,
          Instant.ofEpochMilli(start), Instant.ofEpochMilli(end));
      MDC.clear();
    }
  }

  @Override
  protected boolean shouldNotFilter(HttpServletRequest request) {
    String p = request.getRequestURI();
    return p.startsWith("/actuator/health") || p.startsWith("/css/") || p.startsWith("/js/") || p.startsWith("/images/");
  }
}

In microservices, a single user request can hop across many services (A → B → C). When something is slow or fails, it's hard to know where and why. Distributed tracing solves this by attaching a traceId to the request and creating spans for each hop. Zipkin collects & visualizes these traces so you can follow the request end-to-end.

  • traceId = unique id for the entire request path.
  • spanId = id of a single operation (e.g., an HTTP call, DB call).
  • Context propagates via headers (B3/W3C) so every service knows the same trace.

📌 Why?

In a Spring Boot 3 app with JWT authentication, every request has an Authentication object inside the SecurityContextHolder. If you’re using Spring Security OAuth2 Resource Server, the principal is usually a Jwt. From here, you can extract claims like user_id, sub, or username and populate createdBy/updatedBy in entities.

📌 Example Utility

package com.example.security;

import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.security.oauth2.server.resource.authentication.JwtAuthenticationToken;
import org.springframework.security.core.userdetails.UserDetails;

import java.util.Optional;

public final class CurrentUser {
  private CurrentUser() {}

  public static Optional<String> userId() {
    Authentication auth = SecurityContextHolder.getContext().getAuthentication();
    if (auth == null || !auth.isAuthenticated()) return Optional.empty();

    // Case 1: OAuth2 JWT
    if (auth instanceof JwtAuthenticationToken jwtAuth) {
      Jwt jwt = jwtAuth.getToken();
      // try different claim names
      String userId = claim(jwt, "user_id")
          .orElseGet(() -> claim(jwt, "uid").orElse(jwt.getSubject())); // fallback "sub"
      return Optional.ofNullable(userId);
    }

    // Case 2: Classic UserDetails (form login)
    Object principal = auth.getPrincipal();
    if (principal instanceof UserDetails ud) {
      return Optional.ofNullable(ud.getUsername());
    }
    if (principal instanceof String s) {
      return Optional.of(s); // sometimes "anonymousUser"
    }

    return Optional.empty();
  }

  private static Optional<String> claim(Jwt jwt, String name) {
    Object v = jwt.getClaims().get(name);
    return v != null ? Optional.of(String.valueOf(v)) : Optional.empty();
  }
}

Put the authenticated userId (from JWT / SecurityContext) into MDC at the start of every request and remove it at the end. Then configure Log4j2 pattern to print it automatically on every log line.

🧩 1) Filter to populate MDC

package com.example.logging;

import com.example.security.CurrentUser; // the utility you created earlier
import org.slf4j.MDC;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.util.UUID;

@Component
public class MdcUserFilter extends OncePerRequestFilter {

  @Override
  protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
      throws ServletException, IOException {

    // Optional trace/request ids (use your gateway's header if present)
    String traceId = headerOrDefault(req, "X-Request-Id", UUID.randomUUID().toString());
    MDC.put("traceId", traceId);

    // Extract userId from SecurityContext/JWT
    String userId = CurrentUser.userId().orElse("anonymous");
    MDC.put("userId", userId);

    // Add HTTP metadata if you like
    MDC.put("method", req.getMethod());
    MDC.put("path", req.getRequestURI());

    try {
      chain.doFilter(req, res);
    } finally {
      MDC.clear(); // IMPORTANT: avoid leakage across threads
    }
  }

  private String headerOrDefault(HttpServletRequest req, String name, String def) {
    String v = req.getHeader(name);
    return (v == null || v.isBlank()) ? def : v;
  }
}

📌 Why version your API?

To evolve contracts without breaking clients. Typical changes: add fields (non-breaking), rename/remove fields (breaking), change semantics. Keep old clients working while you ship new shapes.

  • Header: X-API-Version: 1

🧠 Choosing a strategy
  • Path: simplest, cache/CDN friendly, easy to route in gateways (recommended default).
  • Header: keeps URLs clean; needs client/header control and proxy awareness.
  • Media type: very RESTful; more tooling/config; great when multiple representations exist.
  • Query param: easy to test, but less canonical; be careful with caches.
🧱 Structure & maintenance tips
  • Package by version: api.v1, api.v2 controllers & DTOs; reuse domain/services.
  • Keep v1 backward-compatible (additive) when possible; reserve v2 for breaking changes.
  • Deprecate with Deprecation/Sunset headers and docs; set EOL date.
  • Document with OpenAPI (springdoc): create groups per path /v1/**, /v2/**.
📝 Spring Boot “versioning” (project releases)

Spring Boot itself follows MAJOR.MINOR.PATCH (e.g., 3.3.4). Breaking changes only on MAJOR, features on MINOR, fixes on PATCH. Match Boot 3.x with Java 17+ and Spring Framework 6.x (Jakarta).

✅ TL;DR

Use path versioning for clarity and gateway/CDN friendliness; keep DTOs per version; reuse services; add deprecation headers & docs. Switch to header or media-type versioning if your org prefers contract-in-headers.

📌 What is CQRS?

Command Query Responsibility Segregation splits the model into:
• Write/Command side: handles state changes (create/update/delete), validates invariants.
• Read/Query side: serves queries using denormalized, query-optimized views.
Data sync is via events (e.g., Kafka) or an Outbox pattern. Reads are eventually consistent.

🧱 Architecture (Order domain)

[Client/UI]
   |            Commands (POST/PUT)               Queries (GET)
   v                                              ^
[Write API]  --OrderPlaced/ItemAdded-->  [Broker]  --events-->  [Read API Projector]
   |                                                        |
 [Write DB - normalized]                           [Read DB - denormalized views]

@Entity
@Table(name = "orders")

  private String customerId;
  private String status; // NEW, PAID, CANCELLED
  private BigDecimal total = BigDecimal.ZERO;

  public void addItem(String sku, int qty, BigDecimal price) {

    this.total = this.total.add(price.multiply(BigDecimal.valueOf(qty)));
  }
}

    events.publish(new OrderCreatedEvent(o.getId(), o.getCustomerId()));
    return o;
  }

  @Transactional
  public Order addItem(AddItemCmd cmd) {
    Order o = repo.findById(cmd.orderId()).orElseThrow();
    o.addItem(cmd.sku(), cmd.qty(), cmd.price());
    events.publish(new ItemAddedEvent(o.getId(), cmd.sku(), cmd.qty(), cmd.price()));
    return o;

  @Transactional
  public Order pay(PayOrderCmd cmd) {
    Order o = repo.findById(cmd.orderId()).orElseThrow();
    if (!"NEW".equals(o.getStatus())) throw new IllegalStateException("Only NEW can be paid");
    o.setStatus("PAID");
    events.publish(new OrderPaidEvent(o.getId(), o.getTotal()));
    return o;
  }
}

// projector/OrderEventsListener.java
@Component
public class OrderEventsListener {
  private final OrderViewRepository repo;
  private final ObjectMapper om = new ObjectMapper();

  public OrderEventsListener(OrderViewRepository repo) { this.repo = repo; }

  @KafkaListener(topics = "order-events", groupId = "read-side")
  @Transactional
  public void onMessage(String msg) throws Exception {
    JsonNode node = om.readTree(msg);
    String type = node.get("type").asText(); // if you include "type" in payload
    switch (type) {
      case "OrderCreated" -> {
        String id = node.get("orderId").asText();
        String cust = node.get("customerId").asText();
        repo.save(new OrderView(id, cust, "NEW", BigDecimal.ZERO, Instant.now()));
      }
      case "ItemAdded" -> {
        String id = node.get("orderId").asText();
        BigDecimal price = new BigDecimal(node.get("price").asText());
        int qty = node.get("qty").asInt();
        OrderView v = repo.findById(id).orElseThrow();
        v.setTotal(v.getTotal().add(price.multiply(BigDecimal.valueOf(qty))));
        v.setLastEventAt(Instant.now());
      }
      case "OrderPaid" -> {
        String id = node.get("orderId").asText();
        OrderView v = repo.findById(id).orElseThrow();
        v.setStatus("PAID");
        v.setLastEventAt(Instant.now());
      }
    }
  }
}

✅ Key Points for Interviews
  • Separation: Different models for commands vs queries; can scale independently.
  • Eventual Consistency: Reads may lag; design UI with “syncing…” states.
  • Atomicity: Use Outbox or transactional messaging to avoid lost events (write + event as one unit).
  • Idempotency: Projectors should tolerate duplicate events (check version/eventId).
  • Schema Freedom: Read DB can be multiple views (SQL/NoSQL) optimized per query.
  • When to use: Complex domains, heavy read load, multiple query shapes, microservices.
  • When not: Simple CRUD, strict read-after-write requirements without eventual consistency tolerance.
🧩 Variations
  • In-process CQRS: same codebase/DB, separate services/layers.
  • Event Sourcing: persist events as source of truth; rebuild state from events + snapshots.
  • Transport: Kafka/PubSub/RabbitMQ; or Postgres logical decoding; or Debezium CDC.

🎯 Goal

Design a Notification feature that supports Email, SMS, and Push without violating the Liskov Substitution Principle (LSP). Subtypes must be safely substitutable wherever their base type is expected—no surprise exceptions or broken pre/post-conditions.

❌ Anti-pattern (LSP Violation)

// Single concrete class with "type" switches & UnsupportedOperationException
@Service
public class NotificationService {
  public void send(String type, String to, String subject, String message) {
    switch (type) {
      case "EMAIL" -> sendEmail(to, subject, message);
      case "SMS"   -> sendSms(to, message);
      case "PUSH"  -> sendPush(to, message);
      default -> throw new UnsupportedOperationException("Unknown type");
    }
  }
  // ... sendEmail/sendSms/sendPush impls
}
// ❌ Problems:
// - Callers can pass any 'type' and get runtime errors.
// - Behavior depends on string flags; can't substitute a subtype safely.
// - Violates Open/Closed & LSP (adding new types edits existing logic).
✅ LSP-Compliant Design (Strategy + Polymorphism)

// Contract: any NotificationChannel can be used wherever a channel is expected
public interface NotificationChannel {
  void send(NotificationRequest req);
}

// Immutable input DTO (preconditions validated at construction)
public record NotificationRequest(
    String to,        // email/phone/device token
    String subject,   // optional for SMS/Push
    String message
) {
  public NotificationRequest {
    if (to == null || to.isBlank()) throw new IllegalArgumentException("to is required");
    if (message == null || message.isBlank()) throw new IllegalArgumentException("message is required");
  }
}

// Concrete channels keep invariants consistent with the interface contract

@Component("EMAIL")
class EmailChannel implements NotificationChannel {
  @Override public void send(NotificationRequest req) {
    // send via SMTP/provider; subject is used
    System.out.printf("EMAIL -> %s | %s: %s%n", req.to(), req.subject(), req.message());
  }
}

@Component("SMS")
class SmsChannel implements NotificationChannel {
  @Override public void send(NotificationRequest req) {
    // subject ignored but never breaks contract
    System.out.printf("SMS   -> %s | %s%n", req.to(), req.message());
  }
}

@Component("PUSH")
class PushChannel implements NotificationChannel {
  @Override public void send(NotificationRequest req) {
    System.out.printf("PUSH  -> %s | %s%n", req.to(), req.message());
  }
}
🧰 Channel Registry (No if/else chains)

// Spring will inject all beans implementing NotificationChannel as a Map by @Component name
@Service
public class ChannelRegistry {
  private final Map<String, NotificationChannel> channels;
  public ChannelRegistry(Map<String, NotificationChannel> channels) { this.channels = channels; }

  public NotificationChannel get(String type) {
    var ch = channels.get(type);
    if (ch == null) throw new IllegalArgumentException("Unsupported channel: " + type);
    return ch;
  }
}
🚀 Application Facade (uses base type)

@Service
public class NotificationFacade {
  private final ChannelRegistry registry;
  public NotificationFacade(ChannelRegistry registry) { this.registry = registry; }

  public void notify(String type, NotificationRequest req) {
    // LSP: Any NotificationChannel can be substituted here safely
    NotificationChannel channel = registry.get(type);
    channel.send(req);
  }
}
🌐 REST Controller

@RestController
@RequestMapping("/api/notifications")
public class NotificationController {
  private record SendDto(String type, String to, String subject, String message) {}
  private final NotificationFacade facade;
  public NotificationController(NotificationFacade facade) { this.facade = facade; }

  @PostMapping("/send")
  public ResponseEntity<Void> send(@RequestBody SendDto dto) {
    facade.notify(dto.type(), new NotificationRequest(dto.to(), dto.subject(), dto.message()));
    return ResponseEntity.accepted().build();
  }
}
🔎 Why this honors LSP?
  • Uniform contract: NotificationChannel#send() is honored by every subtype. None throws “not supported”.
  • Stable preconditions: NotificationRequest validates required fields; subtypes do not strengthen requirements.
  • Stable postconditions: Each channel “sends” without weakening the expected outcome.
  • Substitutability: The NotificationFacade uses only the base type; any channel bean can be swapped in.

💡 Extensions (still LSP-safe)
  • New Channel (e.g., WhatsApp) → just add a new @Component("WHATSAPP") class; no changes elsewhere.
  • Retry/Idempotency → wrap channels with a decorator (e.g., RetryingChannel) that also implements NotificationChannel.

🧠 Interview Takeaways
  • Avoid flag-based behavior and UnsupportedOperationException in subtypes.
  • Program to an interface; keep base contracts stable and minimal.
  • Use Strategy + Spring’s bean map injection to stay LSP- and OCP-compliant.

📌 What is a SQL View?

A SQL View is a stored query in the database that behaves like a read-only table. In Spring Boot, we can map it like a normal entity or query it directly using native SQL.

🛠️ Step 1: Create SQL View

-- Example: Create a view for "active users"
CREATE VIEW active_users AS
SELECT id, name, email
FROM users
WHERE status = 'ACTIVE';
🛠️ Step 2: Create Entity for the View

@Entity
// ⚠️ Views are read-only, so no @GeneratedValue or insert/update
@Table(name = "active_users") 
public class ActiveUser {
    @Id
    private Long id;   // must match the view's PK (or unique column)
    private String name;
    private String email;

    // getters/setters
}
🛠️ Step 3: Repository for the View

public interface ActiveUserRepository extends JpaRepository<ActiveUser, Long> {
    // Derived query
    List<ActiveUser> findByNameContainingIgnoreCase(String name);

    // Or native query
    @Query(value = "SELECT * FROM active_users WHERE email LIKE %:email%", nativeQuery = true)
    List<ActiveUser> searchByEmail(@Param("email") String email);
}
🛠️ Step 4: Service Layer

@Service
public class UserService {
    private final ActiveUserRepository repo;
    public UserService(ActiveUserRepository repo) { this.repo = repo; }

    public List<ActiveUser> getActiveUsers() {
        return repo.findAll();
    }
}
🛠️ Step 5: Controller

@RestController
@RequestMapping("/api/active-users")
public class ActiveUserController {
    private final UserService service;
    public ActiveUserController(UserService service) { this.service = service; }

    @GetMapping
    public List<ActiveUser> list() {
        return service.getActiveUsers();
    }
}
✅ Key Notes
  • Map the SQL view like a normal entity, but keep it read-only.
  • Ensure the view has a unique column to use as @Id.
  • For complex views, prefer native queries with DTO projections.
  • Don’t use save() on view entities → they’re not writable.
🚀 Alternative: DTO Projection (no entity)

public interface ActiveUserProjection {
    Long getId();
    String getName();
    String getEmail();

public interface UserRepository extends JpaRepository<User, Long> {
    @Query(value = "SELECT id, name, email FROM active_users", nativeQuery = true)

Here, no entity is mapped. Spring directly maps the view result to a projection (DTO interface).

📌 1. Always use a Named, Tuned Thread Pool

Prefer ThreadPoolTaskExecutor over raw threads. Tune core/max/queue and use a clear prefix for logs.


@Configuration
@EnableAsync
public class AsyncConfig {
  @Bean("appExecutor")
  public ThreadPoolTaskExecutor appExecutor() {
    ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(Runtime.getRuntime().availableProcessors() * 2);
    ex.setMaxPoolSize(ex.getCorePoolSize() * 2);
    ex.setQueueCapacity(1000); // keep large enough for bursts; set to 0 for direct handoff
    ex.setKeepAliveSeconds(60);
    ex.setThreadNamePrefix("app-async-");
    ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    ex.setWaitForTasksToCompleteOnShutdown(true);
    ex.setAwaitTerminationSeconds(30);
    ex.initialize();
    return ex;
  }
}

Tip: For CPU-bound work: small pools (≈ 2×CPU). For I/O-bound: larger pools, but monitor!

📌 3. Beware of Self-Invocation (Proxy Gotcha)

@Async works via proxies. Calling an @Async method from the same class won’t go async.


@Service
public class A {
  @Async public CompletableFuture<Void> task(){ /*...*/ return CompletableFuture.completedFuture(null); }

  public void wrong() { this.task(); }        // ❌ won't be async
}

@Service
@RequiredArgsConstructor
public class B {
  private final A a;
  public void right() { a.task(); }           // ✅ goes through proxy
}

If you return an entity class directly from a Spring Boot controller, it will be serialized into JSON or XML by default, depending on the configured message converters.

📌 What Happens Internally?
  • Jackson (JSON Serialization): Spring Boot automatically converts the entity object to JSON using Jackson.
  • Circular Reference Issue: If there are bidirectional relationships, it can lead to infinite recursion.
  • Lazy Loading Problem: If a field is lazily loaded and not initialized, it may cause LazyInitializationException.
  • Unintended Data Exposure: Returning the entity directly might expose sensitive fields.
📝 Example: Returning an Entity

🚀 Sample Controller


@RestController
@RequestMapping("/users")
public class UserController {
    @Autowired
    private UserRepository userRepository;

    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id) {
        return userRepository.findById(id).orElse(null); // Returns entity directly
    }
}
⚠️ Issues You Might Face
  • Circular References: If User has a relation with another entity, it may cause infinite loops.
  • Lazy Initialization: If @OneToMany(fetch = FetchType.LAZY) is used, uninitialized data might cause errors.
  • Security Risks: Exposing the entire entity might leak sensitive data.
✅ Best Practice: Use DTO Instead

🔥 Using a DTO to Avoid Issues


public class UserDTO {
    private Long id;
    private String name;
    private String email;
    
    public UserDTO(User user) {
        this.id = user.getId();
        this.name = user.getName();
        this.email = user.getEmail();
    }
}
      

@RestController
@RequestMapping("/users")
public class UserController {
    @Autowired
    private UserRepository userRepository;

    @GetMapping("/{id}")
    public UserDTO getUser(@PathVariable Long id) {
        User user = userRepository.findById(id).orElse(null);
        return user != null ? new UserDTO(user) : null;
    }
}
✅ Conclusion

Returning an entity directly can cause serialization issues, circular references, and security risks. The recommended approach is to use a DTO (Data Transfer Object) to return only the necessary fields.

Circular dependency occurs when two or more beans depend on each other, creating a loop that prevents Spring from properly instantiating them.

📌 Example of Circular Dependency

Consider two services that depend on each other:


@Service
public class ServiceA {
    private final ServiceB serviceB;

    @Autowired
    public ServiceA(ServiceB serviceB) {
        this.serviceB = serviceB;
    }

    public void execute() {
        System.out.println("Executing ServiceA");
    }
}
      

@Service
public class ServiceB {
    private final ServiceA serviceA;

    @Autowired
    public ServiceB(ServiceA serviceA) {
        this.serviceA = serviceA;
    }

    public void execute() {
        System.out.println("Executing ServiceB");
    }
}

When Spring tries to instantiate ServiceA, it requires ServiceB, which in turn requires ServiceA, leading to a circular dependency.

🛠️ How to Fix Circular Dependency?
✔ 1. Use @Lazy Annotation

Inject one of the dependencies lazily:


@Service
public class ServiceA {
    private final ServiceB serviceB;

    @Autowired
    public ServiceA(@Lazy ServiceB serviceB) {
        this.serviceB = serviceB;
    }
}
✔ 2. Use Setter Injection

Instead of constructor injection, use setter injection:


@Service
public class ServiceA {
    private ServiceB serviceB;

    @Autowired
    public void setServiceB(ServiceB serviceB) {
        this.serviceB = serviceB;
    }
}
✔ 3. Use @Bean with Provider

Use ObjectProvider to delay dependency resolution:


@Service
public class ServiceA {
    private final ObjectProvider serviceBProvider;

    @Autowired
    public ServiceA(ObjectProvider serviceBProvider) {
        this.serviceBProvider = serviceBProvider;
    }

    public void execute() {
        ServiceB serviceB = serviceBProvider.getIfAvailable();
        serviceB.execute();
    }
}
✔ 4. Refactor Application Design

If circular dependency exists, rethink the design. Extract common logic into a third service.


@Service
public class CommonService {
    public void execute() {
        System.out.println("Executing Common Service");
    }
}

Now, both ServiceA and ServiceB depend on CommonService instead.

✅ Conclusion

Circular dependencies can cause application startup failures. To fix them:

  • Use @Lazy for delayed initialization.
  • Prefer setter injection over constructor injection.
  • Use ObjectProvider for flexible dependency resolution.
  • Refactor the design by introducing a common dependency.

The behavior of prototype beans and singleton beans in Spring depends on their lifecycle. Let's analyze both scenarios:

📌 1. Injecting a Prototype Bean into a Singleton Bean

🔹 What happens? When a prototype bean is injected into a singleton bean, the **same instance of the prototype bean is used every time** because Spring injects it once when the singleton bean is created.

📝 Example: Injecting a Prototype Bean into a Singleton Bean

@Component
@Scope("prototype")
class PrototypeBean {
    public PrototypeBean() {
        System.out.println("Prototype Bean Created");
    }

    public void showMessage() {
        System.out.println("Hello from Prototype Bean!");
    }
}

@Component
@Scope("singleton")
class SingletonBean {
    private final PrototypeBean prototypeBean;

    @Autowired
    public SingletonBean(PrototypeBean prototypeBean) {
        this.prototypeBean = prototypeBean;
    }

    public void usePrototype() {
        prototypeBean.showMessage();
    }
}

🚨 Problem: Since the SingletonBean is created only **once**, the PrototypeBean instance is also injected **only once**, meaning every call to usePrototype() will use the **same prototype instance** instead of a new one.

✅ Solution: Use ObjectFactory or Provider

@Component
@Scope("singleton")
class SingletonBean {
    private final ObjectFactory<PrototypeBean> prototypeFactory;

    @Autowired
    public SingletonBean(ObjectFactory<PrototypeBean> prototypeFactory) {
        this.prototypeFactory = prototypeFactory;
    }

    public void usePrototype() {
        PrototypeBean prototypeBean = prototypeFactory.getObject();
        prototypeBean.showMessage();
    }
}

This ensures that a **new instance** of the PrototypeBean is created **each time** usePrototype() is called.

📌 2. Injecting a Singleton Bean into a Prototype Bean

🔹 What happens? When a **singleton** bean is injected into a **prototype** bean, it works as expected because the singleton instance remains the same across all prototype instances.

@Scope("singleton")

In Java, you can prevent a subclass from being serialized even if its superclass implements Serializable. This ensures that sensitive or unnecessary data isn't accidentally serialized.

        }

PlatformTransactionManager is the central interface in Spring for managing transactions across different data sources. It abstracts transaction management, allowing developers to use a consistent API regardless of the underlying transaction system (JDBC, JPA, Hibernate, etc.).

📌 1. Why Use PlatformTransactionManager?
  • ✔️ Works across multiple data sources like JDBC, JPA, Hibernate.
  • ✔️ Supports declarative and programmatic transaction management.
  • ✔️ Provides a consistent way to manage transactions.
📌 2. Common Implementations
  • 🔹 DataSourceTransactionManager → For JDBC
  • 🔹 JpaTransactionManager → For JPA/Hibernate
  • 🔹 HibernateTransactionManager → For Hibernate
📌 3. Declarative Transaction Management using @Transactional

Spring allows you to manage transactions using the @Transactional annotation.


import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class BankService {

    @Transactional
    public void transferMoney(Long fromAccount, Long toAccount, Double amount) {
        debit(fromAccount, amount);
        credit(toAccount, amount);
    }
}
📌 4. Programmatic Transaction Management

If you need more control, you can use the TransactionTemplate:


import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.TransactionDefinition;
import org.springframework.transaction.TransactionStatus;
import org.springframework.transaction.support.DefaultTransactionDefinition;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

@Service
public class BankService {

    @Autowired
    private PlatformTransactionManager transactionManager;

    public void transferMoney(Long fromAccount, Long toAccount, Double amount) {
        TransactionDefinition def = new DefaultTransactionDefinition();
        TransactionStatus status = transactionManager.getTransaction(def);
        try {
            debit(fromAccount, amount);
            credit(toAccount, amount);
            transactionManager.commit(status);
        } catch (Exception e) {
            transactionManager.rollback(status);
            throw e;
        }
    }
}
📌 5. Configuring PlatformTransactionManager

You can define a transaction manager in a Spring Boot application:


import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jdbc.datasource.DataSourceTransactionManager;

import javax.sql.DataSource;

@Configuration
public class TransactionConfig {

    @Bean
    public PlatformTransactionManager transactionManager(DataSource dataSource) {
        return new DataSourceTransactionManager(dataSource);
    }
}
✅ Conclusion
  • ✔️ PlatformTransactionManager provides a unified way to handle transactions.
  • ✔️ Use @Transactional for declarative transaction management.
  • ✔️ Use TransactionTemplate or PlatformTransactionManager for programmatic transactions.
  • ✔️ Different implementations exist for JDBC, JPA, and Hibernate.

The @Transactional annotation in Spring provides various parameters to customize transaction behavior.

📌 1. propagation (Transaction Propagation Behavior)

Defines how the method behaves within an existing transaction.


@Transactional(propagation = Propagation.REQUIRES_NEW)
public void saveData() { ... }
  • REQUIRED (Default) - Uses an existing transaction or creates a new one.
  • REQUIRES_NEW - Always creates a new transaction.
  • SUPPORTS - Uses a transaction if available.
  • NOT_SUPPORTED - Always runs without a transaction.
  • NEVER - Throws an error if a transaction exists.
  • MANDATORY - Requires an existing transaction.
  • NESTED - Runs inside an existing transaction as a nested one.
📌 2. isolation (Transaction Isolation Level)

Controls data visibility for concurrent transactions.


@Transactional(isolation = Isolation.READ_COMMITTED)
public void processTransaction() { ... }
  • DEFAULT - Uses the database's default isolation.
  • READ_COMMITTED - Prevents dirty reads.
  • READ_UNCOMMITTED - Allows dirty reads.
  • REPEATABLE_READ - Prevents dirty & non-repeatable reads.
  • SERIALIZABLE - Fully isolated (slowest).
📌 3. rollbackFor & noRollbackFor

Controls which exceptions trigger a rollback.


@Transactional(rollbackFor = {SQLException.class, RuntimeException.class})
public void updateRecord() { ... }
  • rollbackFor - Specifies which exceptions trigger rollback.
  • noRollbackFor - Specifies exceptions that should not trigger rollback.
📌 4. timeout (Transaction Timeout)

@MapsId is used in JPA when you want to share the primary key of one entity with another entity in a one-to-one relationship.

📌 Use Case

You have two entities: one is a parent (e.g., User), and the other is a child (e.g., UserProfile), and you want them to share the same primary key.

🧩 Example: User & UserProfile

@Entity
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String username;
}
      

@Entity
public class UserProfile {
    @Id
    private Long id;

    private String address;

    @OneToOne
    @MapsId // 👈 Maps this entity's ID to the user's ID
    @JoinColumn(name = "id")
    private User user;
}
🧠 What Happens Internally?
  • @MapsId tells Hibernate to use the foreign key (User's ID) as the primary key for UserProfile.
  • No separate primary key generation for UserProfile.
  • Ensures tight coupling between both entities.
✅ Benefits
  • Ensures data integrity with shared identity.
  • Great for one-to-one relationships where both entities must have same ID.
⚠️ Caution
  • You must persist the parent entity before the child.
  • @MapsId doesn't work well with composite keys unless carefully modeled.

@MapsId is most commonly used with @OneToOne, but it can also work with @ManyToOne associations — with some limitations.

✅ Works With:
  • OneToOne — Common and clean for shared primary key mapping.
  • ManyToOne — When used with composite primary keys.
🧩 Example with @ManyToOne

Used when your entity has a composite primary key and one of the fields is a foreign key.


@Embeddable
public class OrderItemId implements Serializable {
    private Long orderId;
    private Long productId;
}
      

@Entity
public class OrderItem {

    @EmbeddedId
    private OrderItemId id;

    @ManyToOne
    @MapsId("orderId") // 👈 Maps this part of composite key
    @JoinColumn(name = "order_id")
    private Order order;

    @ManyToOne
    @MapsId("productId") // 👈 Maps this part of composite key
    @JoinColumn(name = "product_id")
    private Product product;

    private int quantity;
}
💡 Why Use @MapsId?
  • It tightly couples foreign keys as part of the primary key (especially in composite keys).
  • It improves referential integrity.
⚠️ Caveats
  • For @ManyToOne, it only makes sense if you're working with an embedded/composite ID.
  • Not useful in typical single ID scenarios — stick with @OneToOne there.

@Component
@Slf4j
public class AuditLoggingInterceptor implements Interceptor, Serializable {

    private static final String UPDATED_ON = "updatedOn";

    @Override
    public boolean onSave(Object entity, Object id, Object[] state, String[] propertyNames, Type[] types) throws CallbackException {

        boolean found = false;
        for (int i = 0; i < propertyNames.length; i++) {
            if(CREATED_ON.equalsIgnoreCase(propertyNames[i]) && state[i]==null){
                state[i] = getDate();
                found = true;

            }else if(UPDATED_ON.equalsIgnoreCase(propertyNames[i]) && state[i]==null){
                state[i] = getDate();
                found = true;

            }
        }
        return found;
    }

    @Override
    public boolean onFlushDirty(Object entity, Object id, Object[] currentState, Object[] previousState, String[] propertyNames, Type[] types) throws CallbackException {
        boolean isUpdated = false;

        for (int i = 0; i < propertyNames.length; i++) {

                isUpdated = true;
                break; // Exit the loop as soon as the field is found and updated
            }
        }
        return isUpdated;
    }

    }

🔹 Are Spring Beans Thread-Safe?
  • By default, Spring beans are singleton-scoped, meaning only one instance is created per container.
  • Singleton beans are NOT thread-safe unless you make them so manually.
  • Spring doesn't add any synchronization or thread-safety logic by itself.
✅ How to Make a Spring Bean Thread-Safe?
  • 1️⃣ Use Stateless Design: Don't store mutable data in class-level variables.
  • 2️⃣ Use Thread-Safe Data Structures: E.g., ConcurrentHashMap, AtomicInteger.
  • 3️⃣ Synchronize Critical Sections: Use synchronized blocks or locks.
  • 4️⃣ Use @Scope("prototype") if each thread should get a new instance (not recommended unless needed).
  • 5️⃣ Use ThreadLocal: To give each thread its own variable copy.
💡 Example of Thread Safety using ThreadLocal
@Component
public class ThreadSafeBean {

    private ThreadLocal<SimpleDateFormat> dateFormat = 
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

    public String formatDate(Date date) {
        return dateFormat.get().format(date);
    }
}
💡 Example of Non-Thread-Safe Code
@Component
public class NotThreadSafeBean {
    private SimpleDateFormat sdf = new SimpleDateFormat("yyyy-MM-dd");

    public String formatDate(Date date) {
        return sdf.format(date); // Not thread-safe
    }
}
⚠️ Conclusion
  • Spring doesn’t guarantee thread safety — it’s up to the developer to design thread-safe beans.
  • Prefer stateless and immutable bean design for multi-threaded environments.

📌 Enable Asynchronous Support

First, enable asynchronous processing in your Spring Boot application by using the `@EnableAsync` annotation in a configuration class:


@Configuration
@EnableAsync
public class AsyncConfig {
}
📌 Use `@Async` Annotation

The `@Async` annotation is used to mark methods that should run asynchronously. These methods will execute in a separate thread, allowing the main thread to continue processing.


@Service
public class AsyncService {

    @Async
    public CompletableFuture processAsyncTask() {
        try {
            Thread.sleep(5000); // Simulate a long-running task
        } catch (InterruptedException e) {
            e.printStackTrace();
        }
        return CompletableFuture.completedFuture("Task Completed");
    }
}
📌 Calling Asynchronous Methods

Once you define an asynchronous method, you can call it just like any regular method. The main thread won't wait for the asynchronous task to finish.


@RestController
public class AsyncController {

    @Autowired
    private AsyncService asyncService;

    @GetMapping("/asyncTask")
    public String callAsyncTask() throws InterruptedException {
        CompletableFuture result = asyncService.processAsyncTask();
        return "Async task initiated!";
    }
}
📌 Configuring Thread Pool

By default, Spring Boot uses a simple executor to run async methods. You can customize the executor by defining a `TaskExecutor` bean in your configuration:


@Configuration
public class AsyncConfig {

    @Bean
    public Executor taskExecutor() {
        return new ThreadPoolTaskExecutor();
    }
}
📌 Benefits of Asynchronous Execution
  • Improved performance: By running time-consuming tasks asynchronously, your application can process other requests in parallel.
  • Non-blocking: The main thread is not blocked while waiting for the task to complete.

📌 Enable Scheduling Support

First, you need to enable scheduling in your Spring Boot application by using the `@EnableScheduling` annotation:


@Configuration
@EnableScheduling
public class SchedulerConfig {
}
📌 Create Scheduled Tasks

You can schedule tasks using the `@Scheduled` annotation. The scheduled task will execute at a fixed rate or with a fixed delay, or even based on a cron expression.


@Service
public class MyScheduledService {

    // Executes every 5 seconds
    @Scheduled(fixedRate = 5000)
    public void scheduledTask() {
        System.out.println("Task executed at: " + LocalDateTime.now());
    }

    // Executes after 3 seconds with a fixed delay of 5 seconds
    @Scheduled(initialDelay = 3000, fixedDelay = 5000)
    public void delayedTask() {
        System.out.println("Delayed task executed at: " + LocalDateTime.now());
    }

    // Executes at a specific time based on cron expression
    @Scheduled(cron = "0 0/1 * * * ?")
    public void cronTask() {
        System.out.println("Cron task executed at: " + LocalDateTime.now());
    }
}
📌 Scheduled Task Example

The task in the example runs at a fixed rate every 5 seconds. The `@Scheduled` annotation can take multiple parameters:

  • fixedRate: Task executes at a fixed interval (in milliseconds).
  • fixedDelay: Task executes after a fixed delay from the previous execution.
  • initialDelay: Delay before the first execution.
  • cron: Task executes at a specific time defined by a cron expression.
📌 Cron Expression Example

Here’s an example of a cron expression to execute a task every minute:


@Scheduled(cron = "0 0/1 * * * ?")
public void cronTask() {
    System.out.println("This task runs every minute at the beginning of the minute.");
}
📌 Thread Pool Configuration

If you want to control the number of threads for scheduled tasks, you can define a `TaskScheduler` bean to customize the thread pool:


@Configuration
public class SchedulerConfig {

    @Bean
    public TaskScheduler taskScheduler() {
        ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
        scheduler.setPoolSize(5);  // Set the number of threads
        scheduler.setThreadNamePrefix("scheduled-task-");
        return scheduler;
    }
}

📌 What is GraalVM Native Image?

GraalVM Native Image is a technology that compiles your Spring Boot application ahead-of-time (AOT) into a standalone, native binary (like a Linux executable) instead of running on the traditional JVM.

📌 How It Boosts Startup Time

  • 💡 Lower memory usage: It strips unused classes and loads only what’s required.
  • 🧊 Perfect for cloud & serverless: Especially in containers and short-lived services.

Example: A regular Spring Boot app may take 2–5 seconds to start, whereas a native image version can start in 50–100ms ⚡

    • Classpath scanning
    • Dynamic proxies
    • Reflection-based bean initialization

📌 What is the N+1 Problem?

The N+1 problem in JPA happens when you load an entity and then lazily fetch a collection or reference which causes one extra query per item. So, for N entities, it results in N + 1 SQL queries.

Example:


// Fetch all authors and print their books
List<Author> authors = authorRepository.findAll();
for (Author author : authors) {
    System.out.println(author.getBooks()); // Triggers 1 query per author
}

This causes:

  • 1 query for all authors
  • + 1 query per author to fetch books = N + 1 total
📌 Why is this Bad?
  • ⏱️ Performance hit due to multiple DB calls
  • 🔄 More network round-trips
  • 📉 Doesn’t scale well with larger datasets
📌 How to Fix It (4 Common Ways)
  1. Use @EntityGraph (Recommended)

    This tells JPA to eagerly load the relationship in one query:

    
@EntityGraph(attributePaths = "books")
List<Author> findAll();
  2. Use JOIN FETCH in JPQL

    Custom query to fetch related entities in the same query:

    
@Query("SELECT a FROM Author a JOIN FETCH a.books")
List<Author> findAllWithBooks();
  3. DTO Projections

    Load only what you need using DTOs instead of full entities:

    
@Query("SELECT new com.example.dto.AuthorBookDto(a.name, b.title) 
       FROM Author a JOIN a.books b")
List<AuthorBookDto> fetchAuthorBooks();
  4. Batch Fetching (Hibernate specific)

    Use when lazy loading is still needed but you want fewer queries:

    
hibernate.default_batch_fetch_size=10

    JPA will group lazy fetches into batches instead of one-by-one.

📌 Summary
  • N+1 is caused by lazy loading of relationships in a loop
  • Use @EntityGraph or JOIN FETCH to load related data upfront
  • Use DTOs or batch fetching based on your use case

📌 How does @Inject work?

The @Inject annotation comes from JSR-330 (Java Dependency Injection standard). When used in a Spring application, Spring's container recognizes it and injects the required dependency automatically. 


import javax.inject.Inject;

public class MyService {
    @Inject
    private UserRepository userRepository;
}
  • ⛽ It tells the container to inject a dependency at the field, constructor, or method.
  • ✅ It is framework-agnostic (can work with Spring, Jakarta EE, etc.)
📌 Difference between @Autowired and @Inject
Aspect @Autowired (Spring) @Inject (JSR-330)
Package org.springframework.beans.factory.annotation javax.inject
Null Handling Use required=false to make it optional Use @Nullable or Optional for optional injection
Scope Spring-specific Java-standard (vendor-neutral)
Required Spring Context Yes Yes (Spring must still process it)
Support for Qualifier @Qualifier supported @Named supported
📌 Which One Should You Use?
  • 👍 Use @Autowired if you want full Spring-specific features.
  • 🌐 Use @Inject if you prefer standard Java annotations (more portable).
  • 📦 Both annotations work the same way in Spring, but @Autowired gives you more control.
📌 Example with Qualifier

// Using @Autowired
@Autowired
@Qualifier("myBean")
private MyService service;

// Using @Inject
@Inject
@Named("myBean")
private MyService service;
📌 Summary
  • @Inject is a standard Java DI annotation.
  • @Autowired is Spring-specific and has more flexibility.
  • Both are recognized and supported by the Spring container.
