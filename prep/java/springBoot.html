Spring Boot is preferred over the traditional Spring Framework because it simplifies development, reduces boilerplate code, and provides built-in production-ready features.

📌 Key Differences
Feature Spring Framework Spring Boot
Configuration Requires extensive XML or Java-based configuration. Auto-configuration reduces manual setup.
Embedded Server Needs an external Tomcat, Jetty, or Undertow. Has built-in Tomcat, Jetty, and Undertow.
Standalone Applications Manual setup for creating an executable JAR. Directly creates self-contained JARs.
Dependency Management Requires manual dependency resolution. Spring Boot Starters simplify dependencies.
Monitoring & Metrics Needs third-party integration for monitoring. Spring Boot Actuator provides built-in monitoring.
📝 Why Choose Spring Boot?
  • Faster Development: No need to write boilerplate configuration.
  • Embedded Server: Comes with built-in Tomcat, making deployment easy.
  • Microservices Friendly: Ideal for developing microservices architectures.
  • Auto-configuration: Spring Boot intelligently configures beans.
  • Production-Ready Features: Includes monitoring, logging, and metrics.

✅ Conclusion

Spring Boot is preferred over Spring Framework due to its simplicity, reduced configuration, built-in embedded servers, and production-ready features. It is the best choice for modern application development.

Dependency Injection (DI) is a design pattern used in Spring to manage dependencies between classes, making applications more flexible and easier to test.

📌 What is Dependency Injection?

Instead of creating objects manually inside a class, Spring injects the required dependencies automatically, reducing tight coupling.

📝 Types of Dependency Injection
  • 1. Constructor Injection
  • 2. Setter Injection
  • 3. Field Injection
🏆 1. Constructor Injection

The dependency is provided through a constructor. 


      import org.springframework.stereotype.Component;

      @Component
      public class Engine {
          public String start() {
              return "Engine started!";
          }
      }

      import org.springframework.stereotype.Component;
      import org.springframework.beans.factory.annotation.Autowired;

      @Component
      public class Car {
          private final Engine engine;

          @Autowired
          public Car(Engine engine) {
              this.engine = engine;
          }

          public void drive() {
              System.out.println(engine.start() + " Car is running...");
          }
      }

✔️ Recommended because: It ensures immutability and makes unit testing easier.

🏆 2. Setter Injection

The dependency is provided using a setter method. 


      import org.springframework.beans.factory.annotation.Autowired;
      import org.springframework.stereotype.Component;

      @Component
      public class Car {
          private Engine engine;

          @Autowired
          public void setEngine(Engine engine) {
              this.engine = engine;
          }

          public void drive() {
              System.out.println(engine.start() + " Car is running...");
          }
      }

✔️ Used when: The dependency is optional or needs to be changed later.

🏆 3. Field Injection

The dependency is injected directly into a field. 


      import org.springframework.beans.factory.annotation.Autowired;
      import org.springframework.stereotype.Component;

      @Component
      public class Car {
          @Autowired
          private Engine engine;

          public void drive() {
              System.out.println(engine.start() + " Car is running...");
          }
      }

❌ Not recommended: Makes unit testing difficult and introduces hidden dependencies.

✅ Conclusion

Dependency Injection makes applications modular and easy to test. Constructor Injection is the most recommended approach.

In Spring Boot, you can configure and read messages from a messages.yml file to send error and success responses to users.

📌 Steps to Load and Read messages.yml
1️⃣ Create messages.yml in src/main/resources

errors:
  userNotFound: "User not found"
  invalidRequest: "Invalid request"

success:
  userCreated: "User successfully created"
  passwordUpdated: "Password updated successfully"
2️⃣ Configure Spring Boot to Load messages.yml

Spring Boot loads messages.properties by default. To load a YAML file, define a @Bean in a configuration class: 


import org.springframework.context.MessageSource;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.support.ResourceBundleMessageSource;

@Configuration
public class MessageConfig {
    @Bean
    public MessageSource messageSource() {
        ResourceBundleMessageSource messageSource = new ResourceBundleMessageSource();
        messageSource.setBasename("messages"); // No extension needed
        messageSource.setDefaultEncoding("UTF-8");
        return messageSource;
    }
}
3️⃣ Read Messages in Java Code

Inject MessageSource and use it to retrieve messages:


import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.context.MessageSource;
import org.springframework.stereotype.Service;
import java.util.Locale;

@Service
public class MessageService {
    @Autowired
    private MessageSource messageSource;

    public String getMessage(String key) {
        return messageSource.getMessage(key, null, Locale.getDefault());
    }
}
4️⃣ Usage Example

String errorMessage = messageService.getMessage("errors.userNotFound");
String successMessage = messageService.getMessage("success.userCreated");

System.out.println(errorMessage);  // Output: User not found
System.out.println(successMessage); // Output: User successfully created
🏆 Why Does This Work?
  • Spring loads messages.yml as a resource bundle.
  • The MessageSource retrieves messages by key.
  • Locale support is built-in for internationalization.
✅ Conclusion

1. Place messages.yml in src/main/resources.
2. Configure MessageSource in a @Configuration class.
3. Inject MessageSource and fetch messages in your service.
Now your application can dynamically read error/success messages! 🚀

If you have an external configuration file (e.g., babu.yml), you can load it in Spring Boot using @PropertySource or by specifying it in the application.yml file.

📌 Steps to Load an External YAML/Properties File
1️⃣ Create babu.yml in an External Location

For example, store the file in /config/babu.yml:


app:
  name: "Babu Application"
  version: "1.0.0"

database:
  url: "jdbc:mysql://localhost:3306/babu_db"
  username: "babu_user"
  password: "secret"
2️⃣ Tell Spring Boot to Load the External File

You can specify the external file location in the application.yml:


spring:
  config:
    import: "file:/config/babu.yml"

Or set it as a command-line argument when running the application:


java -Dspring.config.location=file:/config/babu.yml -jar myapp.jar
3️⃣ Read Values from babu.yml

Create a configuration class to read the values:


import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.context.annotation.Configuration;
import lombok.Getter;
import lombok.Setter;

@Getter
@Setter
@Configuration
@ConfigurationProperties(prefix = "app")
public class BabuConfig {
    private String name;
    private String version;
}
4️⃣ Inject and Use the Configuration

In your service or controller, use:


import org.springframework.stereotype.Service;
import org.springframework.beans.factory.annotation.Autowired;

@Service
public class BabuService {
    @Autowired
    private BabuConfig babuConfig;

    public void printConfig() {
        System.out.println("App Name: " + babuConfig.getName());
        System.out.println("App Version: " + babuConfig.getVersion());
    }
}
🏆 Why Does This Work?
  • Spring Boot supports external config files via spring.config.import.
  • Command-line arguments allow overriding configuration locations.
  • Using @ConfigurationProperties, we can map YAML values into Java objects.
✅ Conclusion

1. Store your YAML file externally (e.g., /config/babu.yml).
2. Configure Spring Boot to load it via spring.config.import or command-line args.
3. Use @ConfigurationProperties to map YAML values to Java objects.
Now, your app can dynamically load and use configurations from an external file! 🚀

If you return an entity class directly from a Spring Boot controller, it will be serialized into JSON or XML by default, depending on the configured message converters.

📌 What Happens Internally?
  • Jackson (JSON Serialization): Spring Boot automatically converts the entity object to JSON using Jackson.
  • Circular Reference Issue: If there are bidirectional relationships, it can lead to infinite recursion.
  • Lazy Loading Problem: If a field is lazily loaded and not initialized, it may cause LazyInitializationException.
  • Unintended Data Exposure: Returning the entity directly might expose sensitive fields.
📝 Example: Returning an Entity

🚀 Sample Controller


@RestController
@RequestMapping("/users")
public class UserController {
    @Autowired
    private UserRepository userRepository;

    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id) {
        return userRepository.findById(id).orElse(null); // Returns entity directly
    }
}
⚠️ Issues You Might Face
  • Circular References: If User has a relation with another entity, it may cause infinite loops.
  • Lazy Initialization: If @OneToMany(fetch = FetchType.LAZY) is used, uninitialized data might cause errors.
  • Security Risks: Exposing the entire entity might leak sensitive data.
✅ Best Practice: Use DTO Instead

🔥 Using a DTO to Avoid Issues


public class UserDTO {
    private Long id;
    private String name;
    private String email;
    
    public UserDTO(User user) {
        this.id = user.getId();
        this.name = user.getName();
        this.email = user.getEmail();
    }
}
      

@RestController
@RequestMapping("/users")
public class UserController {
    @Autowired
    private UserRepository userRepository;

    @GetMapping("/{id}")
    public UserDTO getUser(@PathVariable Long id) {
        User user = userRepository.findById(id).orElse(null);
        return user != null ? new UserDTO(user) : null;
    }
}
✅ Conclusion

Returning an entity directly can cause serialization issues, circular references, and security risks. The recommended approach is to use a DTO (Data Transfer Object) to return only the necessary fields.

When you return an entity class directly as a response in Spring Boot, it can lead to **data exposure** because Spring Boot serializes the Java field names, not the database column names mapped using @Column.

📌 How Data Exposure Happens
  • Spring Uses Field Names, Not Column Names: The response JSON will have field names from the Java class, not database column names.
  • Sensitive Data Might Get Exposed: If your entity has fields like password or isAdmin, they might be included in the response.
  • Lazy Loading Issues: If an entity has relationships like @OneToMany, it may cause serialization problems or performance issues.
📝 Example

🚀 Entity Class 


      @Entity
      public class User {
          @Id
          private Long id;

          @Column(name = "user_full_name")
          private String fullName;

          @Column(name = "user_password")
          private String password;
      }

🔥 JSON Response (Data Exposure) 


      {
          "id": 1,
          "fullName": "John Doe",
          "password": "secret123"
      }
✅ How to Prevent Data Exposure?
  • Use @JsonIgnore on sensitive fields: 
    
          @JsonIgnore
          private String password;
  • Use DTOs Instead of Returning Entities Directly: 
    
          public class UserDTO {
              private Long id;
              private String fullName;

              public UserDTO(User user) {
                  this.id = user.getId();
                  this.fullName = user.getFullName();
              }
          }
✅ Conclusion

Even though @Column(name="xyz") maps the entity field to a database column, serialization does not respect that. The field names in your Java class get exposed in the API response. To prevent data leaks, always use DTOs or @JsonIgnore.

  • Loads Configuration Classes: It allows importing other @Configuration classes.

In Spring Boot, we can configure multiple data sources using @Configuration and @Primary annotations. We can choose which data source to use by autowiring the corresponding DataSource or JdbcTemplate.

📌 1. Define Properties in application.yml

      spring:
        datasource:
          primary:
            url: jdbc:mysql://localhost:3306/primary_db
            username: root
            password: root
            driver-class-name: com.mysql.cj.jdbc.Driver
          secondary:
            url: jdbc:postgresql://localhost:5432/secondary_db
            username: postgres
            password: admin
            driver-class-name: org.postgresql.Driver
📝 2. Configure Primary Data Source

      @Configuration
      @EnableTransactionManagement
      @EnableJpaRepositories(
          basePackages = "com.example.repo.primary",
          entityManagerFactoryRef = "primaryEntityManagerFactory",
          transactionManagerRef = "primaryTransactionManager"
      )
      public class PrimaryDataSourceConfig {
          
          @Primary
          @Bean(name = "primaryDataSource")
          @ConfigurationProperties(prefix = "spring.datasource.primary")
          public DataSource dataSource() {
              return DataSourceBuilder.create().build();
          }

          @Primary
          @Bean(name = "primaryEntityManagerFactory")
          public LocalContainerEntityManagerFactoryBean entityManagerFactory(
                  EntityManagerFactoryBuilder builder,
                  @Qualifier("primaryDataSource") DataSource dataSource) {
              return builder
                  .dataSource(dataSource)
                  .packages("com.example.entity.primary")
                  .persistenceUnit("primaryDb")
                  .build();
          }

          @Primary
          @Bean(name = "primaryTransactionManager")
          public PlatformTransactionManager transactionManager(
                  @Qualifier("primaryEntityManagerFactory") EntityManagerFactory entityManagerFactory) {
              return new JpaTransactionManager(entityManagerFactory);
          }
      }

Circular dependency occurs when two or more beans depend on each other, creating a loop that prevents Spring from properly instantiating them.

📌 Example of Circular Dependency

Consider two services that depend on each other:


@Service
public class ServiceA {
    private final ServiceB serviceB;

    @Autowired
    public ServiceA(ServiceB serviceB) {
        this.serviceB = serviceB;
    }

    public void execute() {
        System.out.println("Executing ServiceA");
    }
}
      

@Service
public class ServiceB {
    private final ServiceA serviceA;

    @Autowired
    public ServiceB(ServiceA serviceA) {
        this.serviceA = serviceA;
    }

    public void execute() {
        System.out.println("Executing ServiceB");
    }
}

When Spring tries to instantiate ServiceA, it requires ServiceB, which in turn requires ServiceA, leading to a circular dependency.

🛠️ How to Fix Circular Dependency?
✔ 1. Use @Lazy Annotation

Inject one of the dependencies lazily:


@Service
public class ServiceA {
    private final ServiceB serviceB;

    @Autowired
    public ServiceA(@Lazy ServiceB serviceB) {
        this.serviceB = serviceB;
    }
}
✔ 2. Use Setter Injection

Instead of constructor injection, use setter injection:


@Service
public class ServiceA {
    private ServiceB serviceB;

    @Autowired
    public void setServiceB(ServiceB serviceB) {
        this.serviceB = serviceB;
    }
}
✔ 3. Use @Bean with Provider

Use ObjectProvider to delay dependency resolution:


@Service
public class ServiceA {
    private final ObjectProvider serviceBProvider;

    @Autowired
    public ServiceA(ObjectProvider serviceBProvider) {
        this.serviceBProvider = serviceBProvider;
    }

    public void execute() {
        ServiceB serviceB = serviceBProvider.getIfAvailable();
        serviceB.execute();
    }
}
✔ 4. Refactor Application Design

If circular dependency exists, rethink the design. Extract common logic into a third service.


@Service
public class CommonService {
    public void execute() {
        System.out.println("Executing Common Service");
    }
}

Now, both ServiceA and ServiceB depend on CommonService instead.

✅ Conclusion

Circular dependencies can cause application startup failures. To fix them:

  • Use @Lazy for delayed initialization.
  • Prefer setter injection over constructor injection.
  • Use ObjectProvider for flexible dependency resolution.
  • Refactor the design by introducing a common dependency.

The behavior of prototype beans and singleton beans in Spring depends on their lifecycle. Let's analyze both scenarios:

📌 1. Injecting a Prototype Bean into a Singleton Bean

🔹 What happens? When a prototype bean is injected into a singleton bean, the **same instance of the prototype bean is used every time** because Spring injects it once when the singleton bean is created.

📝 Example: Injecting a Prototype Bean into a Singleton Bean

@Component
@Scope("prototype")
class PrototypeBean {
    public PrototypeBean() {
        System.out.println("Prototype Bean Created");
    }

    public void showMessage() {
        System.out.println("Hello from Prototype Bean!");
    }
}

@Component
@Scope("singleton")
class SingletonBean {
    private final PrototypeBean prototypeBean;

    @Autowired
    public SingletonBean(PrototypeBean prototypeBean) {
        this.prototypeBean = prototypeBean;
    }

    public void usePrototype() {
        prototypeBean.showMessage();
    }
}

🚨 Problem: Since the SingletonBean is created only **once**, the PrototypeBean instance is also injected **only once**, meaning every call to usePrototype() will use the **same prototype instance** instead of a new one.

✅ Solution: Use ObjectFactory or Provider

@Component
@Scope("singleton")
class SingletonBean {
    private final ObjectFactory<PrototypeBean> prototypeFactory;

    @Autowired
    public SingletonBean(ObjectFactory<PrototypeBean> prototypeFactory) {
        this.prototypeFactory = prototypeFactory;
    }

    public void usePrototype() {
        PrototypeBean prototypeBean = prototypeFactory.getObject();
        prototypeBean.showMessage();
    }
}

This ensures that a **new instance** of the PrototypeBean is created **each time** usePrototype() is called.

📌 2. Injecting a Singleton Bean into a Prototype Bean

🔹 What happens? When a **singleton** bean is injected into a **prototype** bean, it works as expected because the singleton instance remains the same across all prototype instances.

📝 Example: Injecting a Singleton Bean into a Prototype Bean

@Component
@Scope("singleton")

    public SingletonBean() {
        System.out.println("Singleton Bean Created");

        singletonBean.showMessage();
    }
}

✅ No issues here! Since the singleton bean is created only once, each new prototype instance correctly receives the **same singleton instance**.

✅ Conclusion
  • Injecting a prototype bean into a singleton: Creates a **single prototype instance**, not a new one each time. ✅ Use ObjectFactory or Provider to solve it.
  • Injecting a singleton bean into a prototype: Works fine because the singleton instance is shared across all prototypes.

@PostConstruct and @PreDestroy are lifecycle annotations in Spring used for defining **initialization and cleanup logic** in a Spring bean.

The @PostConstruct annotation is used on a method that should be executed **after the bean is initialized** (i.e., after dependency injection is done).

In Java, you can prevent a subclass from being serialized even if its superclass implements Serializable. This ensures that sensitive or unnecessary data isn't accidentally serialized.

@Service
public class BankService {

    @Autowired
    private PlatformTransactionManager transactionManager;

    public void transferMoney(Long fromAccount, Long toAccount, Double amount) {
        TransactionDefinition def = new DefaultTransactionDefinition();
        TransactionStatus status = transactionManager.getTransaction(def);
        try {
            debit(fromAccount, amount);
            credit(toAccount, amount);
            transactionManager.commit(status);
        } catch (Exception e) {
            transactionManager.rollback(status);
            throw e;
        }
    }
}

The @Transactional annotation in Spring provides various parameters to customize transaction behavior.

📌 1. propagation (Transaction Propagation Behavior)

Defines how the method behaves within an existing transaction.


@Transactional(propagation = Propagation.REQUIRES_NEW)
public void saveData() { ... }
  • REQUIRED (Default) - Uses an existing transaction or creates a new one.
  • REQUIRES_NEW - Always creates a new transaction.
  • SUPPORTS - Uses a transaction if available.
  • NOT_SUPPORTED - Always runs without a transaction.
  • NEVER - Throws an error if a transaction exists.
  • MANDATORY - Requires an existing transaction.
  • NESTED - Runs inside an existing transaction as a nested one.
📌 2. isolation (Transaction Isolation Level)

Controls data visibility for concurrent transactions.


@Transactional(isolation = Isolation.READ_COMMITTED)
public void processTransaction() { ... }
  • DEFAULT - Uses the database's default isolation.
  • READ_COMMITTED - Prevents dirty reads.
  • READ_UNCOMMITTED - Allows dirty reads.
  • REPEATABLE_READ - Prevents dirty & non-repeatable reads.
  • SERIALIZABLE - Fully isolated (slowest).
📌 3. rollbackFor & noRollbackFor

Controls which exceptions trigger a rollback.


@Transactional(rollbackFor = {SQLException.class, RuntimeException.class})
public void updateRecord() { ... }
  • rollbackFor - Specifies which exceptions trigger rollback.
  • noRollbackFor - Specifies exceptions that should not trigger rollback.
📌 4. timeout (Transaction Timeout)

Defines how long (in seconds) the transaction can run before rollback.


@Transactional(timeout = 5) // Rolls back if it exceeds 5 seconds
public void longRunningTask() { ... }
📌 5. readOnly (Optimize Read Operations)

Marks a transaction as read-only to improve performance.


@Transactional(readOnly = true)
public List getAllUsers() { ... }
📌 6. transactionManager (Specify Transaction Manager)

Defines which transaction manager to use.


@Transactional(transactionManager = "myTransactionManager")
public void processPayment() { ... }
✅ Full Example Using Multiple Parameters

@Transactional(
    propagation = Propagation.REQUIRES_NEW, 
    isolation = Isolation.READ_COMMITTED, 
    rollbackFor = Exception.class, 
    timeout = 10, 
    readOnly = false)
public void executeTransaction() { ... }
