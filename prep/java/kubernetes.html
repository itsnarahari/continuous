1️⃣ What is Kubernetes?

Kubernetes (K8s) is an open-source container orchestration platform that automates:
✔ Deployment
✔ Scaling
✔ Load Balancing
✔ Self-healing of containers

It manages containerized applications across clusters of servers.
2️⃣ Why do we need Kubernetes?

Without Kubernetes:
- You need to start containers manually
- Restart them on failure
- Scale up/down yourself
- Manage load balancing
- Handle deployments manually

Kubernetes automates all these tasks!
3️⃣ Kubernetes – Core Concepts (Very Important)

Pod → Smallest deployable unit (contains one or more containers)
Node → Machine (worker) where pods run
Cluster → Group of nodes
Deployment → Manages replica pods (rolling updates)
Service → Exposes pods as network service (ClusterIP, NodePort, LoadBalancer)
Ingress → Routes external HTTP/HTTPS traffic to services
ConfigMap → Stores non-secret config
Secret → Stores sensitive data (Base64 encoded)
Namespace → Logical separation inside cluster
4️⃣ Getting Started – Create Deployment & Service

# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: my-app
          image: nginx:latest
          ports:
            - containerPort: 80
      

# service.yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  type: NodePort
  selector:
    app: my-app
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080
      

# Apply YAML files
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml

# Get resources
kubectl get pods
kubectl get svc
kubectl get deployments

1️⃣ Kubernetes Architecture Overview

Kubernetes cluster has two types of nodes:
👉 Control Plane (Master Node)
👉 Worker Nodes

Control Plane = Brain of the cluster  
Worker Nodes = Where your applications (pods) run
2️⃣ Control Plane (Master Node) Components

📌 API Server (kube-apiserver)
- The entry point to the cluster
- All kubectl commands talk to API server
- Validation + Authentication + Authorization

📌 etcd
- Distributed key-value database
- Stores complete cluster state
- Example: pods, deployments, configs

📌 Controller Manager (kube-controller-manager)
- Runs controllers that watch cluster state:
  ✔ Node Controller
  ✔ Deployment Controller
  ✔ReplicaSet Controller
  ✔ Endpoints Controller
- Ensures desired state is maintained

📌 Scheduler (kube-scheduler)
- Decides which node will run the pod
- Based on:
  ✔ CPU/Memory availability
  ✔ NodeSelector / Taints / Tolerations
  ✔ Affinity rules

📌 Cloud Controller Manager
- Integrates K8s with cloud providers (AWS/Azure/GCP)
- Manages:
  ✔ Load balancers
  ✔ Volumes
  ✔ Route tables
3️⃣ Worker Node Components

📌 Kubelet
- Agent running on each worker node
- Makes sure containers are running
- Talks to API server
- Reports node health

📌 Kube-Proxy
- Handles networking rules
- Maintains cluster networking communication
- Implements Service → Pod routing

📌 Container Runtime
- Software that runs containers
- Examples:
  ✔ containerd (default)
  ✔ Docker
  ✔ CRI-O
- Pulls images & starts containers

🔹 **What is ETCD?**
- ETCD is a distributed, consistent key-value store.
- Kubernetes uses it as the "single source of truth".
- Stores cluster state: Pods, Nodes, ConfigMaps, Secrets, etc.

🔹 **How ETCD Works Internally**
1️⃣ **Key–Value Store**
   - Stores everything in simple **key-value** pairs.
   - Example:
     /registry/pods/default/myapp
     /registry/services/kube-system/kube-dns

2️⃣ **Uses Raft Consensus Algorithm**
   - ETCD uses the **Raft** protocol to maintain consistency.
   - Components:
     - **Leader** → handles all writes.
     - **Followers** → replicate leader’s data.
   - Ensures:
     ✔ No data loss  
     ✔ All nodes have same data  
     ✔ High availability  

3️⃣ **Writes**
   - All write requests go to the **leader**.
   - Leader replicates changes to followers.
   - Once majority (quorum) acknowledges → write is committed.

4️⃣ **Reads**
   - By default, reads can come from leader or followers (depending on consistency mode).

5️⃣ **Watch**
   - ETCD supports watching keys for real-time updates.
   - Kubernetes controllers use this heavily.
   - Example:
     - Scheduler watches for “pending pods”
     - Controller manager watches for "replicas count changes"

6️⃣ **Snapshot & Backup**
   - ETCD regularly stores snapshots.
   - Helps in disaster recovery.

🔹 **Why ETCD is Important for Kubernetes**
- Stores entire cluster state.
- If ETCD is down:
  ❌ No scheduling  
  ❌ No new pods  
  ❌ No updates  
  ❌ Cluster becomes read-only  

🔹 **ETCD Cluster Setup**
- Best practice:
  - 3 or 5 node ETCD cluster
  - Odd number ensures quorum
  - Located on dedicated nodes

1️⃣ What Is a Selector?

Kubernetes selector = A filtering mechanism used to match objects using labels.

It allows one resource (Service, Deployment, ReplicaSet, NetworkPolicy, HPA, etc.)
to automatically target/find Pods based on labels.
2️⃣ Why Do We Need Selectors? (Real Benefits)

✔ Helps Services find the correct Pods  
✔ Helps ReplicaSets manage only specific Pods  
✔ Helps Deployments control the correct ReplicaSets  
✔ Helps NetworkPolicies apply only to selected Pods  
✔ Helps Jobs, CronJobs associate with Pods  
✔ Decouples configuration → You can update Pods without changing Service  
✔ Enables rolling updates cleanly  
✔ Allows multiple versions (blue/green, canary) to run
3️⃣ Types of Selectors

1️⃣ Equality-based selectors  
   Example:
       app = myapp  
       tier != db  

2️⃣ Set-based selectors  
   Example:
       env in (dev, prod)  
       version notin (v1, v2)
4️⃣ Example: Service Selecting Pods

# Service.yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app: web        # Service targets pods with this label
  ports:
    - port: 80
      targetPort: 8080
---
# Pod.yaml
apiVersion: v1
kind: Pod
metadata:
  labels:
    app: web        # This pod will be picked by service
spec:
  containers:
    - name: app
      image: nginx
      

➡ Service finds Pods automatically  
➡ If new Pods with label app=web are created, service routes traffic to them  
➡ If Pods are deleted, service updates endpoints automatically
5️⃣ Example: Deployment → ReplicaSet → Pods

selector:
  matchLabels:
    app: backend
template:
  metadata:
    labels:
      app: backend
      

✔ Deployment uses selector to manage ReplicaSets  
✔ ReplicaSet uses same selector to manage Pods  
✔ Ensures rolling updates work with ZERO conflict
6️⃣ Why Selectors Are Mandatory?

Mandatory because without selectors:

❌ Services won’t know which Pods to route traffic to  
❌ ReplicaSets won’t know which Pods to manage  
❌ Deployments can accidentally adopt the wrong Pods  
❌ NetworkPolicies won’t know where to apply rules  

➡ Selectors maintain boundaries and grouping in Kubernetes.
7️⃣ Interview Answers

Q: What is the use of selectors in Kubernetes?  
A: Selectors allow Kubernetes components like Services, ReplicaSets, and Deployments 
   to identify and manage Pods based on labels.

Q: What if you don't specify selectors?  
A: Kubernetes cannot link resources → Services won't route traffic, Deployments won't control Pods.

Q: What is the difference between equality and set-based selectors?  
A: Equality matches exact key-value pairs; set-based matches against multiple values.

Q: How do selectors support rolling updates?  
A: Deployment creates new ReplicaSet with same selectors → Kubernetes migrates traffic automatically.

1️⃣ What is Ingress?

Ingress controls INCOMING traffic from the Internet or external clients into Kubernetes cluster.
It routes requests to different services based on:

  • 🔹 Hostname (e.g., api.myapp.com)
  • 🔹 URL path (e.g., /api, /admin)
  • 🔹 SSL/TLS termination (HTTPS)
  • 🔹 One Load Balancer → Many services

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: "myapp.com"
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: ui-service
                port:
                  number: 80

          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 8080

          - path: /admin
            pathType: Prefix
            backend:
              service:
                name: admin-service
                port:
                  number: 8090

Ingress Traffic Flow:


Internet → Ingress Controller → UI / API / Admin Services
2️⃣ What is Egress?

Egress controls OUTGOING traffic from pods to the Internet or external networks.
Used when your pod needs to call:

  • 🔹 Third-party APIs (payment, OTP, SMS, email)
  • 🔹 External database
  • 🔹 Any external website

By default Kubernetes allows all egress.
To restrict, we use Egress NetworkPolicies.


apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-external-api
spec:
  podSelector:
    matchLabels:
      app: payment-service
  policyTypes:
    - Egress
  egress:
    - to:
        - ipBlock:
            cidr: 172.217.0.0/16  # example: google APIs
      ports:
        - protocol: TCP
          port: 443

Egress Flow:


Pod → Egress Rule → Internet / External API
3️⃣ Simple Difference
Ingress Egress
Incoming traffic to cluster Outgoing traffic from cluster
Internet → Pod Pod → Internet
Uses Ingress Controller + Rules Uses NetworkPolicy
Routes multiple services with 1 IP Restricts/controls pod outbound calls
Supports Host/Path routing Supports IP/Port outbound filtering

Client → Service → kube-proxy → Available Pod

No need to expose a Service externally.

1️⃣ What Are Kubernetes Tasks?

Kubernetes Tasks are operations that run for a short time and exit after completing their work.
They are NOT long-running services like Deployments.

Two main task types:

  • ✔ Job → Run once until success
  • ✔ CronJob → Run on a schedule (every day, hour, minute)

Service (Deployment) → Runs forever  
Jobs / CronJobs     → Run once or on schedule and exit
2️⃣ Kubernetes Job – One-Time Task

A Job runs a task one time and makes sure it completes successfully.

  • ✔ Retries automatically if pod fails
  • ✔ Useful for batch jobs
  • ✔ Runs multiple pods in parallel if needed
📌 Example: Database Migration Job

apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration-job
spec:
  template:
    spec:
      containers:
        - name: migration
          image: myapp-migration:latest
      restartPolicy: Never

Use cases:

  • 🟢 Send one-time email
  • 🟢 Database migration script
  • 🟢 Clean logs once
  • 🟢 One-time data processing
3️⃣ Kubernetes CronJob – Scheduled Tasks

A CronJob runs tasks at specific times using a cron schedule.

  • ✔ Every minute
  • ✔ Every hour
  • ✔ Every midnight
  • ✔ Weekly, Monthly
📌 Example: Daily Backup Job

apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup-cron
spec:
  schedule: "0 0 * * *"   # every midnight
  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - name: backup
              image: backup-script:latest
          restartPolicy: OnFailure

Use cases:

  • 🔵 Daily database backup
  • 🔵 Delete expired tokens
  • 🔵 Generate monthly reports
  • 🔵 Sync data with external APIs
  • 🔵 Automatic email reminders

Most common service type. Accessible only inside the cluster. 


spec:
  type: ClusterIP

    app: order
  ports:
    - port: 8080
      

Service → Pod routing
Internal-only communication

Use When:

  • ✔ Microservice-to-microservice communication
  • ✔ Spring Boot internal APIs
  • ✔ Backend services, Redis, DB adapters
2️⃣ NodePort (Exposes on Node's IP)

Opens port on every node at range 30000–32767. 


spec:
  type: NodePort
  ports:
    - port: 8080
      nodePort: 30080
      

Access: http://NodeIP:30080

Use When:

  • ✔ Minikube / Kind / Local Kubernetes
  • ✔ Debugging services without Ingress
  • ✔ Quick POC testing

Not recommended for production.

3️⃣ LoadBalancer (Cloud Load Balancer)

Creates a public cloud Load Balancer (AWS ELB, GCP LB, Azure LB). 


spec:
  type: LoadBalancer
  ports:
    - port: 80
      targetPort: 8080
      

Internet → Cloud LB → NodePort → ClusterIP → Pod

Use When:

  • ✔ Production applications
  • ✔ Exposing APIs to public
  • ✔ Without using Ingress (simple setup)
4️⃣ ExternalName Service (DNS Alias)

Maps a Kubernetes service to an external DNS name. 


spec:
  type: ExternalName
  externalName: api.external.com
      

Inside cluster: my-external-service → api.external.com

Use When:

  • ✔ Call external APIs using internal DNS
  • ✔ Database hosted outside Kubernetes
  • ✔ Migrate legacy systems gradually
5️⃣ Headless Service (No ClusterIP)

No load balancer, no ClusterIP. Returns **pod IPs directly** → used for databases. 


spec:
  clusterIP: None
  selector:
    app: mysql
      

DNS → returns pod IP list (mysql-0, mysql-1, mysql-2)

Use When:

  • ✔ StatefulSets
  • ✔ Databases: MySQL, Cassandra, Kafka
  • ✔ Apps needing direct pod discovery

You give YAML → Kubernetes takes care of everything

2️⃣ Kubernetes Full Lifecycle (Step-by-Step)
📌 Step 1: Write YAML (Desired State)

apiVersion: apps/v1
kind: Deployment
metadata:
  name: spring-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: spring-app
  template:
    metadata:
      labels:
        app: spring-app
    spec:
      containers:
        - name: app
          image: springio/spring-app

You define:

  • ✔ How many replicas
  • ✔ What image
  • ✔ What ports
📌 Step 2: Apply YAML

kubectl apply -f deployment.yaml

Kubectl sends it to the Kubernetes API Server.

📌 Step 3: API Server Reads & Stores in ETCD

API Server → Stores desired state → ETCD

ETCD = database of your entire cluster.

📌 Step 4: Scheduler Chooses the Best Node

Scheduler checks:
✔ CPU available?
✔ Memory available?
✔ Node affinity?
✔ Taints/Tolerations?

Then places pods on selected worker nodes.

📌 Step 5: Kubelet Creates the Containers

kubelet → pulls image → starts container → checks health

Container runtime (Docker/containerd) actually runs the container.

📌 Step 6: kube-proxy Creates Networking Rules

Service → kube-proxy → Routes traffic to pods

Load balances across replica pods.

📌 Step 7: Probes Check Health (Liveness/Readiness)

If pod unhealthy → restart  
If pod not ready → remove from Service endpoint
📌 Step 8: HPA Autoscaling (If Enabled)

CPU > threshold → Add more pods  
CPU < threshold → Reduce pods
📌 Step 9: Self-Healing

Pod crashes → new pod created automatically  
Node goes down → pods recreated on new nodes

  • ✔ Zero-downtime deployments

Fewer failures → More stability → Lower maintenance cost

1️⃣ Why Schedule Tasks in Kubernetes?

Spring Boot has @Scheduled, but it runs inside your microservice pod. In Kubernetes, using CronJobs is better because:

  • ✔ Tasks run independently from your main Spring Boot API
  • ✔ Automatic retries
  • ✔ Logs stored separately
  • ✔ Controlled concurrency (Forbid / Replace)
  • ✔ If a node crashes → Kubernetes re-runs the task

Spring Boot API (stateless)  
⟶ CronJob handles scheduled tasks  
⟶ Better scalability / separation of concerns
2️⃣ Spring Boot Scheduled Task Example (@Scheduled)

@Component
@EnableScheduling
public class ReportScheduler {

    @Scheduled(cron = "0 0 2 * * *") // every day at 2 AM
    public void generateReport() {
        System.out.println("📁 Generating daily report...");
    }
}

Problem: If this instance scales to 5 pods → the job runs 5 times ❌ That’s why Kubernetes CronJob is preferred.

3️⃣ Kubernetes CronJob – Best Way to Run Scheduled Tasks

Here we create a **Docker image** that runs only the Spring Boot task, not the API.

📌 Step 1 – Create Separate Spring Boot Job Class

@SpringBootApplication
public class CronApp {

    public static void main(String[] args) {
        SpringApplication.run(CronApp.class, args);
    }
}

@Component
public class DailyReportJob {

    @PostConstruct
    public void runJob() {
        System.out.println("Starting daily report job...");
        // business logic here
        System.out.println("Done!");
        System.exit(0);
    }
}

This will:

  • ✔ Start job
  • ✔ Run business logic
  • ✔ Exit immediately
📌 Step 2 – Build Docker Image

FROM eclipse-temurin:17-jdk
COPY target/cron-job.jar app.jar
ENTRYPOINT ["java","-jar","/app.jar"]
📌 Step 3 – Kubernetes CronJob YAML

apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-report-cron
spec:
  schedule: "0 2 * * *"   # Run at 2 AM daily
  jobTemplate:
    spec:
      backoffLimit: 3
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: report-job
              image: myrepo/report-job:1.0
              env:
                - name: DB_HOST
                  valueFrom:
                    configMapKeyRef:
                      name: app-config
                      key: db-host
                - name: DB_PASS
                  valueFrom:
                    secretKeyRef:
                      name: db-secret
                      key: db-password

Kubernetes ensures:

  • ✔ Job runs exactly once
  • ✔ Automatically retries on failure
  • ✔ No duplicate execution
  • ✔ Logs can be checked via kubectl logs

5️⃣ Avoid Duplicate Job Runs (IMPORTANT)

spec:
  concurrencyPolicy: Forbid

Options:

  • ✔ Forbid → skip new run if previous not finished
  • ✔ Replace → kill old one, run new one
  • ✔ Allow → allow parallel jobs
