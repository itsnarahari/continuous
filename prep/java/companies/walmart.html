⚠️ Scalability challenges under high contention
  • Hot buckets: Too many threads hit same bin → CAS retries & locking slow everyone.
  • Remapping bottlenecks: compute/merge lock a bin while function runs; heavy work inside serializes threads.
  • Resizing overhead: Small initial capacity → frequent resizes, all threads “help transfer” causing CPU/cache churn.
  • Counter cells contention: Calls like size() sum striped counters; high writes → retries.
  • Poor hash codes: Collisions even with tree bins → per-bin serialization.
🔎 Red flags in production
  • High CPU but low throughput.
  • Profiles show time in ConcurrentHashMap$Node or transfer.
  • Endpoints with size() or heavy compute have long tail latency.
✅ Optimizations
  1. Pre-size correctly: 
    int expected = 1_000_000;
ConcurrentHashMap<K,V> map = new ConcurrentHashMap<>(expected, 0.75f);
    Avoid resizes in hot paths.
  2. Use good hashCodes: Ensure keys distribute well; add shard-id if few keys dominate.
  3. Avoid size() / isEmpty(): Track counts separately for hot paths.
  4. Keep remap functions tiny: Don’t do I/O or CPU-heavy work inside computeIfAbsent.
⚡ Patterns to reduce contention

1. LongAdder per key (better counters):

ConcurrentHashMap<String, LongAdder> counts = new ConcurrentHashMap<>();

void incr(String k) {
  counts.computeIfAbsent(k, kk -> new LongAdder()).increment();
}

2. Sharding (striped maps):

final int SHARDS = 64;
final ConcurrentHashMap<K,V>[] shards =
  IntStream.range(0, SHARDS)
           .mapToObj(i -> new ConcurrentHashMap<K,V>())
           .toArray(ConcurrentHashMap[]::new);

private ConcurrentHashMap<K,V> shard(K key) {
  int h = key.hashCode();
  int idx = (h ^ (h >>> 16)) & (SHARDS - 1);
  return shards[idx];
}

3. Read-mostly workloads → immutable snapshot:

volatile Map<K,V> snapshot = Map.of();

void update(Map<K,V> newData) {
  snapshot = Map.copyOf(newData);
}

V get(K k) { return snapshot.get(k); }
📝 Quick checklist (TL;DR)
  • Pre-size the map
  • Ensure good hashCode()
  • Avoid size() on hot paths
  • Use LongAdder for counters
  • Shard the map if few keys are super hot
  • Keep compute/merge lambdas minimal
  • Switch to immutable snapshots for read-mostly cases

Goal of JMM: Provide rules that guarantee predictable behavior of multithreaded programs across CPUs, caches, and compiler optimizations. It defines when writes by one thread become visible to others and what order of operations is guaranteed.

⚠️ Challenges in multi-core systems
  • Caching: Each CPU core may cache variables; without rules, threads may see stale values.
  • Reordering: Compilers and CPUs reorder instructions for performance. Without constraints, this breaks predictable multithreading.
  • Store/load buffers: Writes may be delayed in per-core buffers, not visible immediately to other cores.
🔑 JMM Guarantees
  • Atomicity: Reads/writes to volatile variables, references, and primitives (except long/double before Java 5) are atomic.
  • Visibility: A write to a volatile variable is flushed to main memory immediately; subsequent reads see the updated value.
  • Ordering: The happens-before relationship ensures a logical order of operations between threads.

Happens-before rules:

  • Program order rule: Within a single thread, operations appear in program order.
  • Monitor lock rule: Unlock on a monitor happens-before subsequent lock on the same monitor.
  • Volatile rule: Write to a volatile happens-before every subsequent read of that variable.
  • Thread start rule: A call to Thread.start() happens-before actions in the started thread.
  • Thread termination rule: Actions in a thread happen-before Thread.join() returns.
  • Transitivity: If A happens-before B and B happens-before C, then A happens-before C.
✅ Tools provided by JMM
  • Volatile variables: Ensure visibility + establish ordering (a lightweight synchronization).
  • Synchronized blocks/locks: Imply memory barriers on entry/exit, ensuring visibility and ordering of shared state.
  • Final fields safety: Immutable objects (properly constructed) guarantee that final fields are visible correctly after construction.
  • Explicit fences: Unsafe and VarHandles provide fine-grained memory fences in Java 9+.

Example with volatile:

class FlagExample {
  private volatile boolean flag = false;

  public void writer() {
    flag = true; // write is immediately visible
  }

  public void reader() {
    if (flag) {
      // guaranteed to see true once writer() executes
      System.out.println("Flag updated!");
    }
  }
}

Without volatile: Another thread may never observe the update because the CPU could cache flag locally or reorder instructions.

📝 Quick Summary
  • JMM shields us from CPU/cache/compiler reordering by defining happens-before rules.
  • volatile gives visibility + ordering, but no atomic compound actions.
  • synchronized adds visibility, ordering, and mutual exclusion.
  • Immutable objects with final fields are inherently safe for sharing.
  • Correct use of these tools ensures threads on different cores see consistent, ordered data.

Rule of thumb: Use volatile for simple flags, synchronized/locks for compound actions, and design around happens-before to ensure correctness on multi-core systems.

Context: Java offers multiple concurrency primitives. synchronized is the oldest, StampedLock (Java 8) offers advanced locking, and VarHandle (Java 9) provides low-level atomic/volatile-style operations.

🔒 1. synchronized blocks
  • Type: Intrinsic monitor lock (per object).
  • Features: Mutual exclusion; reentrant; enforces visibility & ordering via memory barriers.
  • Pros: Simple, automatic release on exceptions, well-integrated with JMM (happens-before rules).
  • Cons: Blocking only; no read/write distinction; can cause contention under high concurrency.

Example:

class Counter {
  private int count = 0;
  public synchronized void increment() { count++; }
  public synchronized int get() { return count; }
}
📝 2. StampedLock (Java 8)
  • Type: Explicit lock with modes (write, read, optimistic read).
  • Features:
    • Write lock → exclusive, like synchronized.
    • Read lock → shared (multiple readers).
    • Optimistic read → non-blocking, validated if no write occurred.
  • Pros: Improves scalability for read-heavy workloads; supports optimistic concurrency.
  • Cons: Non-reentrant; manual unlock required; more error-prone.

Example:

class Point {
  private double x, y;
  private final StampedLock lock = new StampedLock();

  void move(double dx, double dy) {
    long stamp = lock.writeLock();
    try { x += dx; y += dy; }
    finally { lock.unlockWrite(stamp); }
  }

  double distanceFromOrigin() {
    long stamp = lock.tryOptimisticRead();
    double cx = x, cy = y;
    if (!lock.validate(stamp)) {
      stamp = lock.readLock();
      try { cx = x; cy = y; }
      finally { lock.unlockRead(stamp); }
    }
    return Math.hypot(cx, cy);
  }
}
⚡ 3. VarHandle (Java 9)
  • Type: Low-level mechanism to access and update variables with memory-order semantics.
  • Features: Supports volatile reads/writes, atomic CAS, getAndSet, and explicit memory ordering (plain, opaque, acquire, release, volatile).
  • Pros: Fine-grained, non-blocking concurrency; replaces sun.misc.Unsafe; high-performance data structures.
  • Cons: Very low-level; requires careful design; no mutual exclusion (must build protocols around it).

Example:

import java.lang.invoke.MethodHandles;
import java.lang.invoke.VarHandle;

class AtomicInt {
  private volatile int value = 0;
  private static final VarHandle VALUE;
  static {
    try {
      VALUE = MethodHandles.lookup()
        .findVarHandle(AtomicInt.class, "value", int.class);
    } catch (Exception e) { throw new Error(e); }
  }

  void increment() { VALUE.getAndAdd(this, 1); }
  int get() { return (int) VALUE.getVolatile(this); }
}
📊 Head-to-Head
  • Ease of use: synchronized ✅ easiest → StampedLock ⚠️ advanced → VarHandle ⚡ very low-level.
  • Read scalability: synchronized ❌ single lock → StampedLock ✅ many readers + optimistic → VarHandle ✅ non-blocking if carefully built.
  • Atomic ops: synchronized ✅ via lock → StampedLock ✅ with write lock → VarHandle ✅ CAS & fences, no blocking.
  • Safety: synchronized ✅ automatic → StampedLock ⚠️ manual unlock → VarHandle ⚠️ very error-prone.
📝 Quick Summary
  • Use synchronized for simplicity & correctness when contention is moderate.
  • Use StampedLock for read-heavy workloads needing optimistic reads & better scalability.
  • Use VarHandle when building lock-free or high-performance concurrent data structures.

Rule of thumb: Start with synchronized (easy & safe), move to StampedLock for specialized read-heavy needs, and only drop to VarHandle when you really need fine-grained, lock-free atomic operations.

What is a JVM memory leak? Objects remain reachable from GC roots even though the application no longer needs them (e.g., stuck in static caches, collections, ThreadLocals, listeners, class loaders). GC can’t reclaim them → heap (or metaspace/native) grows and never returns after Full GC.

🚦 First, stabilize production (no restart if possible)
  • Reduce pressure: temporarily rate-limit, drain traffic to other replicas, or lower concurrency.
  • Guard rails: ensure -XX:+ExitOnOutOfMemoryError (fail fast), sufficient replicas, and alerts on heap/GC/pause time.
🔍 Detecting a leak vs. a spike
  • Leak signal: Old Gen rises across time and does not return to baseline after Full GC.
  • Not a leak: Eden churn is high but Old Gen plateaus; post-GC baselines are stable.
  • Metaspace/native leak: Heap looks fine but process RSS grows; watch Metaspace, Direct, and Threads.

Quick live checks (no restart):

# GC & heap info snapshots
jcmd <pid> GC.heap_info
jstat -gc -t <pid> 1s 60            # watch promotion, old-gen, FGC count

# Class histogram (what types are growing)
jcmd <pid> GC.class_histogram

# Force a Full GC once (if safe) to see if old gen returns
jcmd <pid> GC.run

# Heap dump (big file; do when near OOM or in off-peak)
jcmd <pid> GC.heap_dump filename=/tmp/heap_$(date +%s).hprof
🎥 Low-impact continuous profiling (JDK 11+)
  • Prefer Java Flight Recorder (JFR) for live leak hunting (low overhead).
# Start a short JFR capture (2–5 min) with GC/allocation events
jcmd <pid> JFR.start name=leak settings=profile duration=5m filename=/tmp/leak.jfr
# Or dump early if you see the issue
jcmd <pid> JFR.dump  name=leak filename=/tmp/leak_now.jfr
🧪 If restart is allowed (next deploy)
  • Enable GC logs: -Xlog:gc*:file=/var/log/gc.log:time,uptime,level,tags
  • Enable Native Memory Tracking (NMT): -XX:NativeMemoryTracking=summary
  • Then you can inspect native growth: jcmd <pid> VM.native_memory summary
  • Always set: -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/oom.hprof
🧩 Analyzing evidence
  • Heap dump with MAT/JMC/YourKit:
    • Open Dominator Tree → find largest retainers.
    • Use Path to GC Roots (exclude weak/soft) to see why they’re kept.
    • Compare two dumps over time → classes/collections that monotonically grow are suspects.
  • JFR: Allocation flame graphs, object statistics, GC pauses, thread counts, class load/unload.
  • GC logs: rising old-gen occupancy after Full GC, frequent promotion failure, long concurrent cycles.
  • NMT: “Internal,” “Class,” “Thread,” “Arena,” “Direct” categories to spot native leaks.
🕵️ Common leak patterns & fixes
  • Unbounded caches/collections:
    • Fix: use bounded caches (e.g., Caffeine maximumSize/expireAfter*), remove ad-hoc Map caches.
    • For ConcurrentHashMap counters, prefer LongAdder and remove stale keys.
  • Listener / callback leaks: event buses, observers, WebSocket sessions not deregistered.
    Fix: always unregister in finally; use try-with-resources style lifecycles.
  • ThreadLocal leaks (esp. with pools): values live as long as the thread.
    Fix: try { … } finally { threadLocal.remove(); }; minimize ThreadLocal scope.
  • ClassLoader/Metaspace leaks: custom loaders, reloading frameworks keep strong refs (static singletons, caches).
    Fix: clear static refs in unload hooks; avoid caching Class/reflection artifacts across loaders; verify classes are unloadable in dumps.
  • Direct/Native memory leaks: Netty ByteBuf not released, huge MappedByteBuffer, JNI.
    Fix: ensure release() on buffers; cap with -XX:MaxDirectMemorySize; use NMT to pinpoint.
  • I/O/resource leaks: streams/result sets not closed; image/zip loaders caching.
    Fix: always close via try-with-resources; consider connection pool caps & leaks detection.
  • Queues/futures accumulation: executor queues with no back-pressure; never consumed CompletableFuture chains.
    Fix: bound queues; timeouts; cancel stale tasks; monitor queue sizes.
🛠️ Concrete remediation playbook
  1. Confirm leak: Use jstat/JFR to see rising Old Gen post-GC.
  2. Capture data: GC.class_histogram, short JFR, then one heap dump (off-peak if large).
  3. Identify retainer: MAT Dominator Tree → “Path to GC Roots” for the top suspect.
  4. Patch quickly:
    • Add bounds/TTL to caches; purge oversized maps.
    • Add finally { threadLocal.remove(); } & deregister listeners.
    • Cap direct memory; fix buffer releases; close I/O.
  5. Deploy & verify: watch post-GC baseline, allocation/promotion rate, and RSS.
  6. Backstop: configure -XX:+HeapDumpOnOutOfMemoryError, GC logs, NMT for the next incident.

📝 Quick Summary
  • Use live tools first (jstat, jcmd, JFR) to confirm a leak without restarting.
  • Take a heap dump only when necessary and analyze Dominators + GC Roots to find the retainer.
  • Most leaks come from unbounded caches, ThreadLocal misuse, listeners, class loaders, or direct/native memory.
  • Fix by bounding, removing strong refs, closing resources, and capping native/direct memory.
  • Verify with post-deploy baselines; keep GC logs/NMT/JFR enabled in your SRE toolbox.

Rule of thumb: Prove the leak with data → find the retainer (dominator) → remove the strong reference or bound it → verify post-GC baseline and RSS. Avoid “just increase heap” unless accompanied by a real fix.

Goal of JVM GC: Reclaim heap memory automatically while balancing throughput (do more work per unit time), latency (shorter GC pauses), and footprint (memory efficiency). CMS, G1, and ZGC represent different generations of low-latency collectors.

🕰️ 1. CMS — Concurrent Mark Sweep (Legacy, JDK 8)
  • Phases: Initial Mark (STW) → Concurrent Mark → Remark (STW) → Concurrent Sweep.
  • Pause profile: Shorter pauses during marking; no compaction → risk of fragmentation.
  • Pros: Low-pause collector in Java 6–8 era; good for latency-sensitive apps before G1/ZGC.
  • Cons: Fragmentation, Full GC fallback (stop-the-world, expensive), heavy tuning needed.
  • Status: Deprecated JDK 9, removed JDK 14.

Typical CMS flags (Java 8 only):

-XX:+UseConcMarkSweepGC -XX:+CMSClassUnloadingEnabled 
-XX:CMSInitiatingOccupancyFraction=70 -XX:+UseCMSInitiatingOccupancyOnly
🧩 2. G1GC — Garbage-First (Default since JDK 9)
  • Heap model: Region-based heap (1–32 MB regions); young/old are logical sets of regions.
  • Collection: Evacuation compacts memory incrementally → less fragmentation.
  • Pause targeting: Tries to meet -XX:MaxGCPauseMillis (~200ms default) by selecting regions.
  • Pros: Predictable pauses, incremental compaction, fewer tuning knobs, good balance of throughput & latency.
  • Cons: More CPU/memory overhead than ParallelGC; not true sub-10ms latency.
  • Status: Default GC in JDK 11+, well-supported, production safe.

Typical G1 setup:

-XX:+UseG1GC -Xms4g -Xmx4g 
-XX:MaxGCPauseMillis=100 
-XX:InitiatingHeapOccupancyPercent=30 
-Xlog:gc*:file=gc.log:time,uptime,tid,level
⚡ 3. ZGC — Z Garbage Collector (JDK 11+, stable in 15+)
  • Heap model: Region-based + colored pointers; concurrent relocation with load barriers.
  • Pause profile: Ultra-low pauses, typically < 10ms, independent of heap size (up to multiple TB).
  • Pros: True low-latency GC, scales to very large heaps, minimal tuning needed.
  • Cons: Slightly lower throughput vs. G1, higher CPU overhead due to barriers.
  • Status: Production-ready in JDK 15+, recommended for latency-critical systems.

Enable ZGC:

java -XX:+UseZGC -Xms8g -Xmx8g -XX:MaxGCPauseMillis=5 -Xlog:gc*
📊 Head-to-Head Comparison
Collector Pause Time Compaction Heap Size Status Use Case
CMS Low (but unpredictable) No (risk of fragmentation) GBs Removed in JDK 14 Legacy Java 8 apps needing low latency
G1GC Targeted (50–200ms) Incremental compaction 10s–100s GB Default since JDK 9 General-purpose, balanced throughput/latency
ZGC < 10ms (predictable) Concurrent relocation (no long STW) Multi-TB Stable JDK 15+ Latency-critical, huge heap apps (fintech, trading, SaaS)
📝 When to choose what?
  • CMS: Only if stuck on Java 8 legacy systems that can’t migrate. Plan migration soon.
  • G1GC: Default choice for most server-side apps. Great balance for web services, batch jobs, microservices.
  • ZGC: Choose when ultra-low latency (<10ms) and/or huge heaps (100s GB–TB) are requirements. Ideal for trading, gaming, real-time analytics.

Rule of thumb: Start with G1GC (default, well-tuned for general workloads). Stick with CMS only on Java 8 if migration isn’t possible. Move to ZGC when you hit latency SLAs that G1 cannot meet or need massive heaps with predictable pauses.

Context: You’re building a high-throughput service. You must decide between ForkJoinPool (FJP) (work-stealing, great for CPU-bound parallelism) and Virtual Threads (Loom) (millions of cheap threads, ideal for I/O-bound concurrency). Often the best design combines both: Loom for request-level concurrency + FJP for CPU hotspots.

🔎 Mental model
  • ForkJoinPool: Few OS threads (~#cores). Tasks split/steal. Do not block them on I/O; keep them busy with CPU work. If you must block → use ManagedBlocker.
  • Virtual Threads: Thread-per-task style without the classic thread cost. Blocking I/O parks the virtual thread and releases the carrier → scalable I/O concurrency.
  • Throughput strategy: Bound the few scarce resources (CPU, DB connections, rate limits), let everything else be cheap & concurrent.
🧱 Architecture patterns
  • I/O-heavy microservice (HTTP/DB/cache calls): Use virtual thread per request. For fan-out calls, use Structured Concurrency.
  • CPU-bound compute (analytics, scoring, transforms): Use a dedicated FJP sized ≈ cores (or a fixed pool) and run pure CPU tasks there; avoid blocking.
  • Mixed workload: Accept on a virtual thread → split CPU chunk to an FJP task → await result → continue on the same virtual thread.

Loom (virtual threads) — request-per-thread with fan-out using StructuredTaskScope:

import java.net.http.*;
import java.time.Duration;
import java.util.concurrent.*;
import java.util.concurrent.StructuredTaskScope;

class Aggregator {
  private final HttpClient http = HttpClient.newHttpClient(); // blocking send() is fine on virtual threads

  Response handle(Request req) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
      Future<HttpResponse<String>> a = scope.fork(() -> http.send(req.a(), HttpResponse.BodyHandlers.ofString()));
      Future<HttpResponse<String>> b = scope.fork(() -> http.send(req.b(), HttpResponse.BodyHandlers.ofString()));

      scope.joinUntil(Instant.now().plus(Duration.ofMillis(300))); // deadline / timeout
      scope.throwIfFailed();

      return combine(a.resultNow().body(), b.resultNow().body());
    }
  }
}

public class Server {
  public static void main(String[] args) throws Exception {
    try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
      // Submit each inbound request as its own virtual thread task:
      acceptLoop(req -> exec.submit(() -> new Aggregator().handle(req)));
    }
  }
}
  • Simple synchronous code; no reactive complexity. Millions of concurrent tasks possible (memory permitting).
  • Bound scarce resources: semaphore around DB pool, rate limiter for downstreams; threads are not the limit anymore.

FJP — CPU hot path with work-stealing (divide & conquer):

import java.util.concurrent.*;

class SumTask extends RecursiveTask<Long> {
  private final long[] arr; private final int lo, hi; static final int THRESH = 1_000;
  SumTask(long[] a, int lo, int hi) { this.arr = a; this.lo = lo; this.hi = hi; }

  protected Long compute() {
    if (hi - lo <= THRESH) {
      long s = 0; for (int i = lo; i < hi; i++) s += arr[i]; return s;
    }
    int mid = (lo + hi) >> 1;
    SumTask left = new SumTask(arr, lo, mid);
    SumTask right = new SumTask(arr, mid, hi);
    left.fork();
    long r = right.compute();   // compute one half
    long l = left.join();       // join the other
    return l + r;
  }
}

class CpuService {
  private final ForkJoinPool pool = new ForkJoinPool(Runtime.getRuntime().availableProcessors());
  long sum(long[] a) { return pool.invoke(new SumTask(a, 0, a.length)); }
}
  • Keep tasks pure CPU. If a task may block, use ForkJoinPool.managedBlock(...) to let the pool compensate.
  • Avoid using the common FJP for server logic (parallel streams can interfere). Create a dedicated pool.
🧪 Putting it together (production recipe)
  1. Entry: Accept each request on a virtual thread (simple thread-per-request model).
  2. Fan-out I/O: Call downstreams in parallel via StructuredTaskScope with deadlines, fallbacks, and cancellation.
  3. CPU hotspot: Offload to a dedicated FJP (or fixed pool) sized ≈ cores; return results back to the virtual thread.
  4. Backpressure: Bound DB connections, queue lengths, and per-client QPS. Threads are cheap, resources aren’t.
  5. Observability: Track latency budgets, FJP queue lengths, virtual-thread counts, carrier thread utilization; enable GC logs & JFR.
⚠️ Pitfalls & how to avoid them
  • Virtual thread pinning: A v-thread is pinned (can’t unmount) when blocking while holding a monitor (synchronized) or during certain native calls.
    Avoid long-running/blocking I/O inside synchronized; prefer ReentrantLock or move blocking outside the critical section.
    -Djdk.tracePinnedThreads=full helps diagnose.
  • Unbounded concurrency: Millions of v-threads can overload DBs/downstreams. Use semaphores/bulkheads/rate-limits.
  • Blocking on FJP: If you must block inside FJP, wrap with ForkJoinPool.managedBlock so the pool can compensate.
  • Common FJP interference: parallelStream() uses the common pool; segregate it from request pools.

ManagedBlocker pattern (if a CPU task must occasionally block):

ForkJoinPool.managedBlock(new ForkJoinPool.ManagedBlocker() {
  volatile boolean done = false;
  public boolean block() throws InterruptedException {
    try { someBlockingCall(); } finally { done = true; }
    return true;
  }
  public boolean isReleasable() { return done; }
});
🧰 Tuning & ops tips
  • Virtual thread scheduler size: defaults ≈ #cores. Can tweak with -Djdk.virtualThreadScheduler.parallelism=N (rarely needed).
  • Thread dumps: V-threads show up normally; use JFR events for blocking, pinning, and allocation profiles.
  • FJP sizing: new ForkJoinPool(cores) for CPU; measure steal count and queued submissions.
  • Time budgets: Prefer joinUntil(deadline) / orTimeout over infinite waits; propagate cancellations.

  • Use a dedicated ForkJoinPool (or fixed pool) for pure CPU tasks (divide & conquer, SIMD/vectorized ops, parsing).

Definition: False sharing occurs when multiple threads update different variables that happen to lie on the same CPU cache line (typically 64 bytes). Even though the variables are independent, hardware cache coherence invalidates the entire line on each write → forcing other cores to reload, leading to massive performance degradation.

⚠️ Why it hurts
  • Cache-line thrashing: Each update invalidates other cores’ caches, creating unnecessary coherence traffic.
  • Symptoms: Throughput collapses under contention, high CPU usage, but no locks/visible contention in code.
  • Hard to spot: Variables are logically independent, so leaks only appear under performance profiling (perf, JFR, async-profiler).

Example of false sharing:

class Counter {
  volatile long a = 0; // Thread 1 updates
  volatile long b = 0; // Thread 2 updates
}
// If 'a' and 'b' sit in the same 64-byte cache line → false sharing
✅ How to avoid it
  • Padding / spacing: Separate frequently-updated fields so they don’t share a cache line.
  • @Contended annotation (JDK 8+): Place on fields or classes to instruct the JVM to pad them. Requires -XX:-RestrictContended JVM flag.
  • Manual padding: Add dummy long fields around hot variables (old-school technique).
  • Separate objects: Put hot variables into different objects (heap layout usually prevents cache-line overlap).
  • Concurrency libraries: Use LongAdder, LongAccumulator, or Striped64-based structures that are already designed to avoid false sharing.

Solution with @Contended:

import jdk.internal.vm.annotation.Contended;

class PaddedCounter {
  @Contended volatile long value = 0;
}
// run with: java -XX:-RestrictContended ...

Solution with manual padding:

class PaddedCounter {
  volatile long value = 0;
  // Padding to avoid sharing cache line with other fields
  long p1, p2, p3, p4, p5, p6, p7;
}

Better approach — LongAdder:

LongAdder counter = new LongAdder();
counter.increment();       // low-contention update
long sum = counter.sum();  // aggregate result
📝 Quick Summary
  • False sharing = independent variables on the same cache line → needless coherence traffic.
  • Avoid by padding, @Contended, separating objects, or using LongAdder/Accumulators.
  • Always measure before optimizing: use JFR/async-profiler to confirm the issue.

Rule of thumb: For counters/metrics → use LongAdder. For custom data structures → use @Contended (if available) or manual padding. Don’t micro-optimize unless you prove false sharing with profiling.

Context: In concurrent programming we often need producer-consumer or inter-thread handoff. Java provides both blocking queues (with built-in locking/conditions) and non-blocking (lock-free) queues based on CAS (compare-and-swap).

⏸️ Blocking Queues (lock-based)
  • Examples: ArrayBlockingQueue, LinkedBlockingQueue, PriorityBlockingQueue, SynchronousQueue.
  • Characteristics:
    • Internally use locks (ReentrantLock) + conditions (notEmpty, notFull).
    • put() and take() block threads until space/data is available.
    • Fairness options supported (e.g., ArrayBlockingQueue with fair lock).
  • Pros:
    • Straightforward for producer-consumer pipelines.
    • Built-in blocking/backpressure; easy to use in thread pools.
  • Cons:
    • Lock contention under high concurrency → context switches.
    • Blocking threads consume stack and scheduling overhead.

Example (blocking queue):

BlockingQueue<String> queue = new ArrayBlockingQueue<>(100);

Thread producer = new Thread(() -> {
  try {
    queue.put("task"); // blocks if full
  } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
});

Thread consumer = new Thread(() -> {
  try {
    String t = queue.take(); // blocks if empty
    process(t);
  } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
});
⚡ Non-blocking (lock-free) data structures
  • Examples: ConcurrentLinkedQueue, ConcurrentLinkedDeque, AtomicStampedReference-based stacks, LongAdder counters.
  • Characteristics:
    • Use CAS (compare-and-swap) instead of locks.
    • offer()/poll() are non-blocking; they return immediately (null if empty, false if full).
    • Progress guarantee = lock-free (system as a whole makes progress, even if individual threads starve).
  • Pros:
    • Scale better under high concurrency (no lock convoying).
    • Low-latency operations; threads not parked.
  • Cons:
    • No built-in blocking/backpressure → need while spin loops or custom conditions.
    • Starvation possible if a thread repeatedly loses CAS race.

Example (lock-free queue):

Queue<String> queue = new ConcurrentLinkedQueue<>();

// Producer
queue.offer("task"); // returns false if it fails (rare)

// Consumer
String task = queue.poll(); // null if empty
if (task != null) process(task);

Aspect Blocking Queue Lock-free Queue
Implementation Locks + Conditions CAS + atomic ops
Thread behavior Blocks on empty/full Returns immediately (null/false)
Throughput Good but may degrade with contention Higher under heavy concurrency
Fairness Can be configured No fairness guarantee
Use cases Producer-consumer pipelines, thread pools High-throughput message passing, counters, async queues
📝 Summary
  • Blocking queues → easy-to-use, backpressure, great for classic producer-consumer with bounded buffers.
  • Lock-free queues → non-blocking, high-throughput, but caller must handle retries/timeouts.
  • In practice: Use blocking queues for thread pools (ExecutorService), lock-free queues for low-latency, high-concurrency algorithms (e.g., telemetry, logging, messaging).

Rule of thumb: If you need coordination + backpressure, choose blocking queues. If you need max concurrency + low latency, use lock-free data structures.

Idea: Load re-loadable code with a throwaway child ClassLoader. On change, create a new loader, load fresh classes, swap the instance, and drop all strong references to the old loader so the JVM can unload its classes.

🧠 Design principles
  • Parent (stable ABI): Define shared APIs (interfaces, DTOs) in the parent loader (app classpath).
  • Child (reloadable impl): Each version is loaded by its own fresh ClassLoader instance.
  • Swap atomically: Keep a single AtomicReference to the current {loader, instance}. Replace on reload.
  • No leaks: Never store plugin classes/objects in parent singletons; close old URLClassLoader; stop threads/resources the plugin started.
  • Parent vs child-first: Parent-first is safer; use child-first only if the plugin must override libs also on the parent path.

🧰 Hot reloader with URLClassLoader (parent-first)
import java.net.*; import java.nio.file.*; import java.util.concurrent.atomic.AtomicReference;

public final class HotReloader implements AutoCloseable {
  public record State(URLClassLoader loader, Plugin instance) {}
  private final Path jarPath; private final String implClass; private final Class<Plugin> api;
  private final AtomicReference<State> state = new AtomicReference<>();

  public HotReloader(Path jar, String implClass, Class<Plugin> api) throws Exception {
    this.jarPath = jar; this.implClass = implClass; this.api = api;
    reload(); // initial load
  }

  public Plugin current() { return state.get().instance(); }

  public synchronized void reload() throws Exception {
    State old = state.get();
    URLClassLoader cl = new URLClassLoader(new URL[]{ jarPath.toUri().toURL() }, api.getClassLoader());
    Class<?> clazz = Class.forName(implClass, true, cl);
    Plugin fresh = api.cast(clazz.getDeclaredConstructor().newInstance());
    state.set(new State(cl, fresh));
    if (old != null) old.loader().close(); // releases JAR file handles
  }

  @Override public void close() throws Exception {
    State s = state.getAndSet(null);
    if (s != null) s.loader().close();
  }
}

🧭 Child-first loader (when plugin must override parent libs)
public class ChildFirstURLClassLoader extends URLClassLoader {
  public ChildFirstURLClassLoader(URL[] urls, ClassLoader parent) { super(urls, parent); }

  @Override protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    if (name.startsWith("java.") || name.startsWith("javax.") || name.startsWith("jakarta.")) {
      return super.loadClass(name, resolve); // always delegate core
    }
    synchronized (getClassLoadingLock(name)) {
      Class<?> c = findLoadedClass(name);
      if (c == null) {
        try { c = findClass(name); }                   // try child first
        catch (ClassNotFoundException ex) { c = super.loadClass(name, resolve); }
      }
      if (resolve) resolveClass(c);
      return c;
    }
  }
}

Note: Prefer parent-first unless you truly need to shadow parent deps; child-first increases risk of class cast or linkage errors if types get loaded by different loaders.

Objective: Minimize tail latency (p99/p999) jitter during market hours. Strategy: pick a low-pause GC, avoid allocation spikes, warm up JIT & memory, and bound every external resource.

1) Choose the collector & set realistic pause budgets
  • ZGC (JDK 17+): sub-10ms pauses independent of heap size; best for strict latency SLOs.
    java \
 -XX:+UseZGC -Xms8g -Xmx8g \
 -XX:MaxGCPauseMillis=5 \
 -XX:+AlwaysPreTouch \
 -Xlog:gc*:file=/var/log/gc.log:time,uptime,level,tags
  • G1 (default): good balance; don’t expect <10ms under load, aim ~20–50ms.
    java \
 -XX:+UseG1GC -Xms8g -Xmx8g \
 -XX:MaxGCPauseMillis=30 \
 -XX:InitiatingHeapOccupancyPercent=25 \
 -XX:+AlwaysPreTouch \
 -Xlog:gc*:file=/var/log/gc.log:time,uptime,level,tags
  • Heap policy: set -Xms = -Xmx to avoid in-flight expansions; +AlwaysPreTouch to fault pages at start, not during trading.
  • Disable explicit Full GC: -XX:+DisableExplicitGC so rogue code can’t force STW.
2) Allocation, object lifetime & GC pressure
  • Minimize allocations on hot paths: avoid boxing, String concatenation, temporary collections; prefer reuse/simple structs.
  • Prefer direct I/O buffers with pooling: especially with Netty/Aeron; cap off-heap: -XX:MaxDirectMemorySize=1g.
  • Counters/metrics: use LongAdder to avoid contention and false sharing.
  • Caches: always bounded (Caffeine maximumSize/expireAfter*) to prevent leak-like growth.
3) JIT warm-up & code cache
  • Warm up before market open: replay representative traffic so C2 compiles hot methods and profiles stabilize.
  • Code cache headroom: avoid “CodeCache full” deopts mid-session: -XX:ReservedCodeCacheSize=512m (or larger after measuring).
  • Tiered compilation: keep defaults (Tiered + C1/C2). Only tweak with evidence; heavy hand-tuning often hurts p99.
4) Threading, scheduling & safepoint hygiene
  • Dedicated pools: separate I/O vs compute pools; avoid using the common ForkJoinPool for latency-critical work.
  • Avoid long synchronized blocks on hot paths: prefer fine-grained locks or lock-free algorithms; watch for false sharing.
  • Safepoint noise: avoid frequent System.gc(), Thread.stop(), or biased-locking era flags (modern JDKs removed it).
  • Core pinning (ops level): pin critical processes/threads with cgroups/CPU sets; set -XX:ActiveProcessorCount if container CPU limits mislead the JVM.
5) OS/JVM I/O stack for predictable latency
  • Linux settings (ops): disable Transparent Huge Pages (THP) for jitter; prefer noop/deadline I/O scheduler; isolate CPUs for the engine.
  • Network: use epoll/kqueue NIO; batch syscalls; tune socket buffers; avoid DNS blocking on hot paths.
  • Clock & timers: use monotonic time (Java’s System.nanoTime()) for latency budgets, not currentTimeMillis().
6) Observability for tail latency
  • JFR always-on, low overhead: 
    -XX:StartFlightRecording=name=prod,filename=/var/log/app.jfr,dumponexit=true,settings=profile,maxsize=512m,maxage=12h
    Watch “Garbage Collections”, “Allocation in new TLAB/Outside TLAB”, “Thread Park”, “Socket Read/Write”.
  • Metrics: export p50/p95/p99/p999, allocation rate (MB/s), GC pause time %, Old-gen occupancy, code cache usage, queue depths.
  • GC logs: keep rolling logs, parse for concurrent cycle scheduling vs. business spikes.
7) Failure-proofing & noise reduction
  • Noisy neighbors: isolate the JVM (dedicated cores/memory); avoid co-locating cron/batch on the same host.
  • OOM behavior: -XX:+ExitOnOutOfMemoryError + fast restart automation; also -XX:+HeapDumpOnOutOfMemoryError off-hours.
  • Load shedding: rate limits and timeouts so downstream stalls don’t propagate jitter.
8) Quick decision guide
ConstraintRecommendationWhy
Strict p99 < 10ms, large heap ZGC, -Xms=-Xmx, +AlwaysPreTouch Concurrent relocation, tiny STW, stable pauses.
Balanced latency/throughput G1 with MaxGCPauseMillis=20–50 Predictable, fewer knobs; good with moderate heaps.
Extreme allocation bursts Reduce allocations, pool buffers, cap direct mem GC pressure is the #1 jitter source.

📝 Summary
  • Pick ZGC for hard low-latency SLOs; otherwise start with G1.
  • Fix allocation hotspots, bound caches, pool direct buffers, and pre-touch memory.
  • Warm up JIT and provision ample code cache; keep JFR on to watch tail latency.
  • Isolate CPU/memory, disable THP, and shield the engine from noisy neighbors.

Rule of thumb: Get the GC right, keep allocation predictable, warm everything up, and measure p99/p999 continuously—optimize only what moves those tails.

Context: Spring Boot’s auto-configuration creates default beans based on what is present on the classpath and what you haven’t defined yourself. It relies heavily on @ConditionalOnClass and @ConditionalOnMissingBean to activate configuration only when appropriate.

⚙️ @ConditionalOnClass
  • Purpose: Activates a configuration class only if a certain class is on the classpath.
  • Why: Prevents ClassNotFoundException and loads beans only when required dependencies exist.
  • Example: Only configure a JdbcTemplate if JDBC is available.

Example snippet:

@Configuration
@ConditionalOnClass(DataSource.class) // applies only if DataSource is on classpath
public class JdbcTemplateAutoConfiguration {

  @Bean
  @ConditionalOnMissingBean // only create if user hasn’t defined one
  public JdbcTemplate jdbcTemplate(DataSource dataSource) {
    return new JdbcTemplate(dataSource);
  }
}
⚙️ @ConditionalOnMissingBean
  • Purpose: Prevents overriding user-defined beans. Auto-config only contributes a default if you haven’t provided one.
  • Why: Respect user customization. Spring Boot’s philosophy: “convention over configuration, but don’t fight explicit user config.”
  • Example: If the app already declares a RestTemplate, Boot skips its own default bean.

Example snippet:

@Configuration
@ConditionalOnClass(RestTemplate.class)
public class RestTemplateAutoConfiguration {

  @Bean
  @ConditionalOnMissingBean(RestTemplate.class)
  public RestTemplate restTemplate(ObjectProvider<RestTemplateBuilder> builder) {
    return builder.getIfAvailable(RestTemplateBuilder::new).build();
  }
}
📊 Internal flow during startup
  1. Spring Boot scans META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (formerly spring.factories) for candidate auto-configurations.
  2. Each candidate is annotated with @ConditionalOnClass, @ConditionalOnMissingBean, or others.
  3. Spring’s ConditionEvaluator checks classpath & bean factory before loading the configuration.
  4. If @ConditionalOnClass fails → configuration is skipped (not loaded at all).
  5. If @ConditionalOnClass passes but user has defined a bean → @ConditionalOnMissingBean suppresses Boot’s default bean.
  6. Otherwise → Boot registers the default bean, making it available in the application context.
📝 Summary
  • @ConditionalOnClass → guard auto-config against missing dependencies.
  • @ConditionalOnMissingBean → respect user-defined beans; only register defaults when necessary.
  • Together they make Boot’s auto-configuration safe, non-invasive, and extensible.

Rule of thumb: Spring Boot uses @ConditionalOnClass to detect capability and @ConditionalOnMissingBean to back off gracefully. This combination ensures auto-config works out of the box without overriding explicit user choices.

Problem: Two or more beans require each other during creation (A → B → … → A), causing startup failure (e.g., BeanCurrentlyInCreationException, UnsatisfiedDependencyException). Since Spring 5.3 / Boot 2.6+, circular references are disabled by default; you should fix the design, not rely on auto-resolution.

🧭 Quick triage (what to look for in the error)
  • Read the injection chain: the stack/causes list bean names in order. Note the first bean and the last bean before the cycle.
  • Spot the pattern: field/constructor injection between services, @Bean methods calling each other, or configuration class cross-calls.
  • Temporary toggle (last resort to get more logs): if your Boot version supports it, set spring.main.allow-circular-references=true only in a debug profile to let the app start and inspect beans (then revert).
🔎 Instrumentation & visibility
  • Enable debug report: run with --debug to see auto-config and bean conditions.
  • Actuator beans view: expose /actuator/beans in a debug profile to inspect dependencies.
  • Dump dependency graph (test-time): print who-depends-on-whom to locate the loop.

    DefaultListableBeanFactory f = (DefaultListableBeanFactory) ctx.getAutowireCapableBeanFactory();
    for (String b : f.getBeanDefinitionNames()) {

🧩 Common circular patterns & fixes
  • Service ↔ Service cycles via constructor injection
    • Fix: break the hard edge with Provider<T>/ObjectProvider<T> or @Lazy on one side, then refactor design.
    @Service
class A {
  private final Provider<B> b; // lazy edge
  A(Provider<B> b) { this.b = b; }
  void use() { b.get().doWork(); } // resolved after A is constructed
}
  • @Bean methods calling each other in @Configuration classes
    • Why: with proxy-bean-methods (CGLIB), method calls return managed singletons; inter-calls during creation can loop.
    • Fix: extract shared factory logic; wire dependencies via method parameters; or set @Configuration(proxyBeanMethods = false) and avoid cross-calls.
    @Configuration(proxyBeanMethods = false)
class MyConfig {
  @Bean Foo foo(Bar bar) { return new Foo(bar); }
  @Bean Bar bar() { return new Bar(); } // no cross-method call
}
  • Layering violation (Controller → Service → Repository → Service)
    • Fix: split responsibilities; introduce a small port interface in the lower layer and inject that instead of the concrete upper service.
  • Event/listener or AOP advice cycles
    • Fix: decouple with application events, message queues, or split the bean providing cross-cutting logic into a separate module.
  • ConfigurationProperties + service usage in config
    • Fix: keep @ConfigurationProperties classes POJO-only; don’t inject services into them.
🛠️ Techniques to break cycles (tactical)
  • @Lazy on one side: defers resolution until first use (good for large refactors).
  • Provider/ObjectProvider: inject a handle you can get() later; expresses optional/lazy dependency explicitly.
  • Setter injection for secondary dependency: keep the primary constructor acyclic; set the optional edge afterward.
  • Factory/Facade extraction: move shared creation logic into a new bean to re-route the dependency direction.
  • Events / queues: replace direct call with an event; subscriber processes asynchronously (no direct bean reference).

Example using @Lazy to break A ↔ B:

@Service class A { A(@Lazy B b) { this.b = b; } private final B b; }
@Service class B { B(A a) { this.a = a; } private final A a; }

Example using ObjectProvider:

@Service
class BillingService {
  private final ObjectProvider<FraudService> fraud;
  BillingService(ObjectProvider<FraudService> fraud) { this.fraud = fraud; }
  void bill() { fraud.getIfAvailable(() -> FraudService.noop()).check(); }
}
🏗️ Strategic prevention (large codebases)
  • Constructor injection everywhere: fails fast on cycles; makes dependencies explicit.
  • Modular boundaries: define clear ports & adapters per module; depend inward on interfaces, not outward on concrete services.
  • Restrict package visibility: keep service impls package-private, expose only APIs.
  • Smell tests: lightweight context tests per slice (web/service/repo) using @SpringBootTest or @ContextConfiguration to catch cycles early.
  • Config hygiene: minimize logic inside @Configuration; avoid cross-calling @Bean methods.
🧪 Minimal reproduction for debugging
  • Extract just the implicated beans into a tiny test app; reproduce the cycle in isolation.
  • From the error’s chain (A → B → C → A), write a focused @SpringBootTest or @ContextConfiguration(classes = {A.class,B.class,C.class}) to iterate quickly.
📝 Summary
  • Read the bean chain in the exception; use Actuator and debug logs to visualize dependencies.
  • Break the cycle tactically with @Lazy, Provider/ObjectProvider, setter injection, or a small factory/facade.
  • Fix the design strategically: enforce constructor injection, modularize with ports/adapters, and keep configuration classes simple.
  • Avoid relying on allow-circular-references; use it only briefly to inspect the graph, then remove.

Rule of thumb: Cycles indicate a design boundary leak. Break the immediate loop to restore startup, then refactor the dependency direction so each layer only depends downward or on stable interfaces.

Goal: Use an Authorization Server (AS) to issue signed JWT access tokens and a Resource Server (RS) (your Spring Boot APIs) to validate them. Add key rotation so signing keys change periodically without breaking live tokens.

🔎 Architecture (high level)
  • AS (e.g., Spring Authorization Server/Keycloak/Okta): issues JWTs signed with a private key (RS256/ES256). Publishes /.well-known/jwks.json with the current + previous public keys.
  • RS (your Boot app): validates incoming JWTs using the AS JWKS URI (kid-based key selection), enforces scopes/authorities.
  • Rotation: AS periodically generates a new keypair (new kid), starts signing new tokens with it, but keeps the old public key in JWKS until all old tokens expire.
🧰 Resource Server (Spring Boot 3 / Spring Security 6)

Point your API to the AS JWKS endpoint. Validate issuer/audience/scopes.

import org.springframework.security.config.annotation.web.builders.HttpSecurity;

import com.nimbusds.jose.jwk.*;
import com.nimbusds.jose.jwk.source.*;
import com.nimbusds.jose.proc.SecurityContext;
import org.springframework.context.annotation.*;
import org.springframework.scheduling.annotation.Scheduled;

import java.time.Instant;
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;

@Configuration
@EnableScheduling
public class JwkRotationConfig {

  // Keep multiple active keys: current signer + previous (until tokens expire)
  private final Map<String, RSAKey> activeKeys = new ConcurrentHashMap<>();
  private volatile String currentKid;

  public JwkRotationConfig() {
    rotateNow(); // initial key at startup
  }

  @Bean
  JWKSource<SecurityContext> jwkSource() {
    return new ImmutableJWKSet<>(new JWKSet(() -> new ArrayList<>(activeKeys.values())));
  }

  /** Called by SAS to publish JWKS at /.well-known/jwks.json */
  @Bean
  public com.nimbusds.jose.jwk.JWKSet jsonWebKeySet() {
    return new JWKSet(() -> new ArrayList<>(activeKeys.values()));
  }

  /** Rotate key periodically (e.g., every 30 days). Keep old keys for token TTL + grace. */
  @Scheduled(cron = "0 0 0 1 * ?") // monthly at 00:00
  public void scheduledRotate() { rotateNow(); pruneExpired(); }

  private synchronized void rotateNow() {
    try {
      RSAKey newKey = newKey("kid-" + Instant.now().toEpochMilli());
      activeKeys.put(newKey.getKeyID(), newKey.toPublicJWK().toRSAKey().toPrivateKey() == null ? newKey : newKey);
      currentKid = newKey.getKeyID();
    } catch (Exception e) {
      throw new IllegalStateException("Key rotation failed", e);
    }
  }

  private RSAKey newKey(String kid) throws Exception {
    return new RSAKeyGenerator(2048).keyUse(KeyUse.SIGNATURE).keyID(kid).algorithm(JWSAlgorithm.RS256).generate();
  }

  /** Implement your own retention policy based on token lifetime (e.g., keep for 8h after last issue). */
  private void pruneExpired() {
    // no-op example: in prod, remove keys older than (rotationTime + accessTokenTTL + buffer)
  }

  /** Helper exposed to your token generator to set 'kid' when signing (SAS does this automatically if wired). */
  public String currentKid() { return currentKid; }
}

  • JWKS caching: Set Cache-Control/max-age on JWKS responses; keep it low (e.g., 5–10 min). The RS decoder caches keys automatically.
  • Issuer/Audience checks: Always validate iss and aud. Reject tokens without expected audience.
  • Clock skew: Allow small skew (e.g., 60s) to avoid nbf/exp edge failures across nodes.
  • Deprecate keys safely: Only remove an old key from JWKS after the longest access-token TTL + grace (and after you’ve stopped issuing with it).
🧯 Troubleshooting rotation
  • Sudden 401s after rotate: RS cache may hold stale JWKS. Ensure JWKS has correct Cache-Control; bump kid and verify both keys present during overlap.
  • “No key found for kid”: Token header has unknown kid → AS didn’t publish new JWKS or RS points to wrong URL.
  • Signature invalid: Check alg mismatch (e.g., RS256 vs ES256). Ensure no proxy rewrites JWKS JSON.

📝 Summary
  • RS validates JWTs via JWKS URI; no DB call needed on each request.
  • AS rotates signing keys: new kid for new tokens, keep old public keys in JWKS until old tokens expire.
  • Use short access-token TTL, rotate refresh tokens, validate iss/aud, and secure private keys in KMS/Vault.
  • Set JWKS caching headers and design an overlap period to make rotation invisible to clients.

Rule of thumb: Rotate keys regularly, overlap JWKS entries, and keep tokens short-lived. With proper issuer/audience checks and JWKS caching, rotation is a no-downtime, no-surprise operation.
