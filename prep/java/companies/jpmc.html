JPMC

Goal of GC: reclaim heap memory automatically while balancing throughput (doing more work) vs latency (shorter pauses). CMS and G1 both target lower pause times than throughput-oriented collectors.

CMS — Concurrent Mark Sweep (Legacy)
  • Where it works: Primarily old generation (young gen usually handled by ParNew).
  • Phases: Initial Mark (STW) → Concurrent Mark (app runs) → Remark (STW) → Concurrent Sweep (no compaction).
  • Pros: Short STW pauses during most cycles; good for low-latency on Java 6/7/8 era.
  • Cons: No compaction → fragmentation; may trigger long Full GC (Serial Old) on promotion failure; more tuning needed; deprecated in JDK 9, removed in JDK 14.
  • Key knobs: -XX:CMSInitiatingOccupancyFraction, -XX:+UseCMSInitiatingOccupancyOnly, -XX:+CMSClassUnloadingEnabled, -XX:ConcGCThreads.

Example CMS flags (Java 8 only):

-XX:+UseConcMarkSweepGC -XX:+CMSClassUnloadingEnabled -XX:CMSInitiatingOccupancyFraction=70 -XX:+UseCMSInitiatingOccupancyOnly
G1 — Garbage-First (Default since JDK 9)
  • Region-based heap: Heap split into equal-sized regions (1–32MB). Young/Old are logical sets of regions.
  • Evacuating & compaction: Copies live objects out of selected regions → compacts continually → little fragmentation.
  • Concurrent global marking: Finds live data across heap; after marking, performs mixed collections (young + some old regions).
  • Pause-time targeting: Tries to meet -XX:MaxGCPauseMillis (default ~200ms) by choosing just enough regions each cycle.
  • Remembered Sets (RSet): Track cross-region references; enable partial collection at the cost of extra memory/CPU.
  • Humongous objects: ≥ 50% of region size go into contiguous “humongous” regions; avoid many huge arrays if possible.
  • Key knobs: -XX:MaxGCPauseMillis, -XX:InitiatingHeapOccupancyPercent, -XX:ConcGCThreads, -XX:ParallelGCThreads, (rarely) -XX:G1HeapRegionSize.

Typical G1 setup (JDK 11+):

-XX:+UseG1GC -Xms4g -Xmx4g -XX:MaxGCPauseMillis=100 -XX:InitiatingHeapOccupancyPercent=30 -Xlog:gc*:file=gc.log:time,uptime,tid,level
Head-to-Head: CMS vs G1
  • Status: CMS is deprecated/removed; G1 is the general-purpose default from JDK 9 onward.
  • Compaction: CMS = none (fragmentation risk); G1 = incremental compaction via evacuation (stable allocation latency).
  • Pause control: CMS pauses depend on old-gen shape and remark; G1 actively sizes work to meet MaxGCPauseMillis.
  • Throughput: Parallel GC may still win raw throughput; G1 balances throughput with predictable pauses better than CMS.
  • Tuning effort: CMS often needs more manual tuning; G1 usually works well with few flags (adjust pause target + heap size).
  • Footprint & overhead: G1’s RSets add memory/CPU overhead; CMS risks costly Full GC on promotion failure.
When to choose what?
  • Modern JDK (11+): Prefer G1 by default for server apps needing predictable pauses.
  • Ultra-low latency: Consider newer collectors (Shenandoah/ZGC) if you need sub-10ms pauses at large heaps.
  • Legacy Java 8 apps: If you still run CMS, plan migration to G1 (or Parallel/ Shenandoah backports) to avoid CMS removal.

1) synchronized — simplest & safest for most cases
class Counter {
  private int value;

  public synchronized void inc() { value++; }  // method-level monitor
  public int get() {
    synchronized (this) { return value; }     // block-level monitor
  }
}
  • Pros: Minimal boilerplate, automatic release, JVM-optimized.
  • Cons: No timeout/tryLock, no interruptible acquire, single condition only.
2) ReentrantLock — more control (timeouts, interruptible waits, multiple conditions)
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.*;

class BoundedQueue<E> {
  private final ReentrantLock lock = new ReentrantLock(true); // fair
  private final Condition notFull  = lock.newCondition();
  private final Condition notEmpty = lock.newCondition();
  private final Object[] items = new Object[100];
  private int put, take, count;

  public void put(E e) throws InterruptedException {
    lock.lockInterruptibly();
    try {
      while (count == items.length) notFull.await();
      items[put] = e;
      if (++put == items.length) put = 0;
      count++;
      notEmpty.signal();
    } finally { lock.unlock(); }
  }

  public E poll(long timeoutMs) throws InterruptedException {
    long nanos = TimeUnit.MILLISECONDS.toNanos(timeoutMs);
    lock.lock();
    try {
      while (count == 0) {
        if ((nanos = notEmpty.awaitNanos(nanos)) <= 0) return null; // timeout
      }
      @SuppressWarnings("unchecked")
      E e = (E) items[take];
      items[take] = null;
      if (++take == items.length) take = 0;
      count--;
      notFull.signal();
      return e;
    } finally { lock.unlock(); }
  }
}
  • Pros: tryLock(), timed/interruptible locking, multiple Conditions, optional fairness.
  • Cons: Must unlock() in finally; misuse leads to deadlocks/leaks.
3) ReadWriteLock — boost read-heavy workloads
import java.util.*;
import java.util.concurrent.locks.*;

class RWCache<K,V> {
  private final Map<K,V> map = new HashMap<>();
  private final ReadWriteLock rw = new ReentrantReadWriteLock();
  private final Lock r = rw.readLock(), w = rw.writeLock();

  public V get(K k) {
    r.lock();
    try { return map.get(k); }
    finally { r.unlock(); }
  }

  public void put(K k, V v) {
    w.lock();
    try { map.put(k, v); }
    finally { w.unlock(); }
  }

  // Downgrade pattern: write -> read (safe), avoid read -> write (upgrade)
  public V computeIfAbsent(K k, java.util.function.Supplier<V> sup) {
    V v;
    r.lock();
    try {
      v = map.get(k);
      if (v != null) return v;
    } finally { r.unlock(); }

    w.lock();
    try {
      v = map.get(k);
      if (v == null) {
        v = sup.get();
        map.put(k, v);
      }
      // Downgrade: acquire read before releasing write
      r.lock();
    } finally { w.unlock(); }
    try { return v; }
    finally { r.unlock(); }
  }
}
  • Pros: Many readers concurrently; single writer; supports lock downgrading.
  • Cons: Reader/writer starvation possible without fairness; poor fit if writes are frequent or readers are short-lived.
Choosing guide
  • Start simple: Use synchronized for most critical sections.
  • Need timeouts/interruptibility/multiple conditions? Use ReentrantLock.
  • Read-heavy & long reads? Use ReadWriteLock (with fairness if needed).
Gotchas & tips
  • Always release explicit locks in finally.
  • Avoid lock upgrade (read → write) with ReadWriteLock; use compute patterns or release/reacquire.
  • Prefer composition over nesting locks; beware deadlocks with multiple locks—define a strict acquisition order.
  • Measure: lock contention may vanish with better data partitioning (sharding/striped locks) or non-blocking structures.

What it guarantees: A volatile write by one thread is immediately visible to other threads, and it prevents certain instruction reorderings. It does not make compound operations (read-modify-write) atomic.

Java Memory Model (JMM) semantics
  • Happens-Before: A write to a volatile variable happens-before every subsequent read of that variable.
  • Visibility: Reading a volatile forces the thread to see the most recent write (flush/refresh around that variable).
  • Ordering: The JMM treats a volatile write as a release and a volatile read as an acquire barrier:
    • Operations before a volatile write cannot move after it.
    • Operations after a volatile read cannot move before it.
  • Atomicity scope: Single read/write of a volatile is atomic (incl. 64-bit long/double since Java 5).
How the JVM enforces it under the hood
  • Compiler barriers: JIT inserts fences so the optimizer doesn’t reorder memory ops across volatile accesses.
  • CPU fences & cache-coherence: On common CPUs:
    • x86_64: TSO already prevents many reorderings; volatile writes often compile to mov with a store-store/store-load effect via cache-coherence; reads use acquire semantics. A full fence may appear around some patterns.
    • ARM/AArch64/Power: explicit dmb/ish (memory barriers) are inserted for acquire/release.
    Coherence protocols (e.g., MESI) ensure other cores invalidate/update their cached lines for that address.
  • No pinning in registers: The JVM won’t cache a volatile field in a register across loops; each access hits memory (or at least the coherent cache view).
Correct uses
  • Publish/visibility flag: Stop signals, configuration toggles, “ready” flags.
  • Safe publication: Writing a fully constructed object reference to a volatile safely publishes that object to readers.
  • Double-checked locking: Works only if the instance reference is volatile.

Example: stop flag

class Worker {
  private volatile boolean running = true;

  public void run() {
    while (running) {
      // do work
    }
  }
  public void stop() { running = false; } // visible immediately to run()
}

Example: safe publication with DCL

class Singleton {
  private static volatile Singleton INSTANCE;
  private Singleton() { /* initialize fields */ }
  public static Singleton get() {
    Singleton s = INSTANCE;
    if (s == null) {
      synchronized (Singleton.class) {
        s = INSTANCE;
        if (s == null) INSTANCE = s = new Singleton();
      }
    }
    return s;
  }
}
Limitations & pitfalls
  • Not a substitute for atomic RMW: x = x + 1 isn’t atomic even if x is volatile.
  • No mutual exclusion: Volatile doesn’t protect invariants across multiple fields.
  • False sharing: Adjacent volatile fields on the same cache line can cause contention.
  • Construction safety: Don’t publish this from a constructor; use final fields or safe publication.

Wrong: volatile counter still races

class Counter {
  private volatile int x = 0;
  public void inc() { x = x + 1; } // read + add + write: data race remains
}

Right: use atomic or locks for RMW

import java.util.concurrent.atomic.AtomicInteger;
class Counter {
  private final AtomicInteger x = new AtomicInteger();
  public void inc() { x.getAndIncrement(); } // atomic
  public int get() { return x.get(); }
}

Performance notes
  • Each volatile access may add fencing and inhibit certain compiler optimizations.
  • Prefer final for immutable state; use volatile for small, independent flags or references.
  • For high-frequency counters, prefer LongAdder under contention.

Quick defs: Deadlock = threads wait forever on each other. Starvation = a thread never gets CPU/lock/time. Livelock = threads keep changing state but no one makes progress.

ProblemSymptomTypical CauseFix/Strategy

Deadlock — prevent, avoid, detect
  • Coffman conditions: mutual exclusion, hold-&-wait, no preemption, circular wait. Break at least one.
  • Prevention (design-time): Global lock ordering, acquire all-or-none, avoid nested locks, prefer immutable or lock-free structures.
  • Avoidance (run-time): tryLock(timeout) with rollback/backoff; timeouts on I/O/RPC; partition state (striped locks).
  • Detection & recovery: Periodically thread-dump; if found, abort op/restart component; add watchdogs.

Example: fix with global lock ordering

import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

class OrderedLocker {
  static void inOrder(Lock a, Lock b, Runnable critical) {
    // Order by identity to avoid cycles
    Lock first = a.hashCode() < b.hashCode() ? a : b;
    Lock second = (first == a) ? b : a;
    first.lock();
    try {
      second.lock();
      try { critical.run(); }
      finally { second.unlock(); }
    } finally { first.unlock(); }
  }
}

class TransferService {
  private final Lock lockA = new ReentrantLock();
  private final Lock lockB = new ReentrantLock();

  public void transferAB() { OrderedLocker.inOrder(lockA, lockB, () -> {/*...*/}); }
  public void transferBA() { OrderedLocker.inOrder(lockB, lockA, () -> {/*...*/}); }
}

Example: avoidance with tryLock() + backoff

import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.*;

boolean safeDoBoth(Lock l1, Lock l2) throws InterruptedException {
  long deadline = System.nanoTime() + TimeUnit.MILLISECONDS.toNanos(200);
  while (System.nanoTime() < deadline) {
    if (l1.tryLock(10, TimeUnit.MILLISECONDS)) {
      try {
        if (l2.tryLock(10, TimeUnit.MILLISECONDS)) {
          try { /* critical */ return true; }
          finally { l2.unlock(); }
        }
      } finally { l1.unlock(); }
    }
    Thread.sleep((long)(5 + Math.random()*15)); // randomized backoff
  }
  return false; // rollback & retry at higher level
}
Starvation — ensure fairness and bounding
  • Causes: unfair locks, unbounded producer work, thread-priority abuse, monopolizing long critical sections.
  • Fixes: new ReentrantLock(true) or fair Semaphore, use bounded queues (LinkedBlockingQueue(cap)), break long tasks into chunks, yield/park between batches, apply backpressure.

Livelock — add asymmetry/randomness
  • Cause: all parties repeatedly back off in sync (no one gets through).
  • Fixes: randomized backoff, designate a winner (asymmetry), give up after N retries & escalate to stronger lock or queue.

Example: randomized backoff to break livelock

import java.util.concurrent.locks.*;
class LivelockBreaker {
  private final Lock lock = new ReentrantLock();
  void work() throws InterruptedException {
    int tries = 0;
    while (tries++ < 20) {
      if (lock.tryLock()) {
        try { /* do work */ return; }
        finally { lock.unlock(); }
      }
      // random backoff to avoid synchronized retries
      Thread.sleep((long)(1 + Math.random()*10));
    }
    // escalate: schedule task on single-threaded executor / queue
  }
}

  • Keep critical sections tiny; avoid nested locks; define strict lock order.
  • Use high-level utilities: ConcurrentHashMap, StampedLock (optimistic reads), LongAdder.

  • Security filter chain processes requests; AuthenticationManager builds Authentication object on success.
  • Authorization: HttpSecurity.authorizeHttpRequests() and method security @PreAuthorize.
import org.springframework.context.annotation.Bean;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@EnableMethodSecurity
class SecurityConfig {
  @Bean SecurityFilterChain api(HttpSecurity http) throws Exception {
    http.csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(reg -> reg
          .requestMatchers("/public/**").permitAll()
          .requestMatchers("/admin/**").hasRole("ADMIN")
          .anyRequest().authenticated())
        .httpBasic();
    return http.build();
  }
}

  2. Client sends Authorization: Bearer <token>.
  3. JWT filter validates signature/expiry, builds UsernamePasswordAuthenticationToken and sets in context.
// Pseudo: filter
class JwtFilter extends OncePerRequestFilter {
  protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
      throws IOException, ServletException {
    String hdr = req.getHeader("Authorization");
    if (hdr != null && hdr.startsWith("Bearer ")) {
      String jwt = hdr.substring(7);
      Claims c = jwtService.parse(jwt); // verify
      var auth = new UsernamePasswordAuthenticationToken(c.getSubject(), null, toAuthorities(c));
      SecurityContextHolder.getContext().setAuthentication(auth);
    }
    chain.doFilter(req, res);
  }
}
// Security chain registration
@Bean SecurityFilterChain jwtChain(HttpSecurity http, JwtFilter f) throws Exception {
  http.csrf(csrf -> csrf.disable())
      .addFilterBefore(f, UsernamePasswordAuthenticationFilter.class)
      .authorizeHttpRequests(reg -> reg.anyRequest().authenticated());
  return http.build();
}

What it is: java.util.concurrent.locks.ReadWriteLock exposes two locks: read (shared) and write (exclusive). Many readers may hold the read lock simultaneously iff no writer holds the write lock; a writer requires exclusive access.

1) ReentrantReadWriteLock — essentials
  • Reentrant: the same thread can re-acquire its read or write lock. A thread with the write lock can reenter both write and read.
  • No lock upgrade: holding read then calling writeLock().lock() will block (risking deadlock). Release read first, then acquire write.
  • Lock downgrade: allowed: acquire read while holding write, then release write (keeps read).
  • Fairness: new ReentrantReadWriteLock(true) reduces starvation (esp. writers) but can lower throughput. Default (non-fair) is often faster.
  • Conditions: only from the write lock: writeLock().newCondition(). Read lock does not support conditions.

Basic pattern

import java.util.concurrent.locks.*;

class Counter {
  private final ReadWriteLock rw = new ReentrantReadWriteLock(); // non-fair by default
  private final Lock r = rw.readLock();
  private final Lock w = rw.writeLock();
  private long value;

  long get() {
    r.lock();
    try { return value; }
    finally { r.unlock(); }
  }

  void inc() {
    w.lock();
    try { value++; }
    finally { w.unlock(); }
  }
}
2) Read-mostly cache with RWL
import java.util.*;
import java.util.concurrent.locks.*;

class RWCache<K,V> {
  private final Map<K,V> map = new HashMap<>();
  private final ReadWriteLock rw = new ReentrantReadWriteLock();
  private final Lock r = rw.readLock(), w = rw.writeLock();

  V get(K k) {
    r.lock();
    try { return map.get(k); }
    finally { r.unlock(); }
  }

  V computeIfAbsent(K k, java.util.function.Function<K,V> loader) {
    V v;
    r.lock();
    try {
      v = map.get(k);
      if (v != null) return v;
    } finally { r.unlock(); }

    // Upgrade pattern: release read, acquire write, recheck, populate
    w.lock();
    try {
      v = map.get(k);
      if (v == null) {
        v = loader.apply(k);
        map.put(k, v);
      }
      // Downgrade: acquire read before releasing write if continuing with read operations
      // r.lock(); try { ... } finally { r.unlock(); }
      return v;
    } finally { w.unlock(); }
  }
}
3) Downgrading correctly (write ➜ read)
void writeThenRead() {
  w.lock();
  try {
    // ... modify shared state ...
    r.lock();             // acquire read while still holding write
  } finally {
    w.unlock();           // now only read lock remains (downgraded)
  }
  try {
    // ... perform read-only work safely ...
  } finally {
    r.unlock();
  }
}
4) Interruptible & timed acquisition

5) When to use RWL vs alternatives
  • Use RWL when: reads are frequent/long, writes are infrequent; read critical sections are sizable (not just a few instructions).
  • Prefer simple locks (synchronized / ReentrantLock) when: low contention, very short sections—overhead of RWL may hurt.
  • Prefer data structures: ConcurrentHashMap often beats hand-rolled RWL maps; LongAdder for hot counters; immutable snapshots for copy-on-write scenarios.
6) Writer/reader starvation & fairness
  • Writer starvation (non-fair): constant stream of readers can delay writers. If this matters, use new ReentrantReadWriteLock(true).
  • Fair locks queue strictly (roughly FIFO) → predictable but potentially lower throughput.

  ReentrantReadWriteLock rrw = new ReentrantReadWriteLock();

8) StampedLock vs ReentrantReadWriteLock (advanced)
  • StampedLock (Java 8+): supports optimistic reads and tryConvertToWriteLock for upgrades; can offer higher throughput on highly contended read-mostly workloads.
  • Trade-offs: not reentrant, no Condition, API is lower-level (you manage long stamps), easy to misuse.
import java.util.concurrent.locks.StampedLock;

class StampedPoint {
  private double x, y;
  private final StampedLock sl = new StampedLock();

  double distance() {
    long s = sl.tryOptimisticRead();
    double cx = x, cy = y;
    if (!sl.validate(s)) {           // a write happened; fall back to read lock
      s = sl.readLock();
      try { cx = x; cy = y; }
      finally { sl.unlockRead(s); }
    }
    return Math.hypot(cx, cy);
  }

  void move(double dx, double dy) {
    long s = sl.writeLock();
    try { x += dx; y += dy; }
    finally { sl.unlockWrite(s); }
  }
}
9) Common pitfalls
  • ❌ Upgrading (read ➜ write) by calling writeLock().lock() while still holding read → can deadlock. Release read first, then acquire write; or use StampedLock.tryConvertToWriteLock.
  • ❌ Holding write lock while doing slow I/O/remote calls—keeps readers blocked. Keep write sections short.
  • ❌ Using RWL for tiny getters/setters—overhead may exceed benefit.
  • ❌ Forgetting finally unlock → leaked locks, stalls. Always unlock in finally.
10) Quick choosing guide
  • Mostly reads, occasional writes with non-trivial critical sections → ReentrantReadWriteLock (non-fair; switch to fair if writers starve).
  • Extremely read-heavy and contention is high → consider StampedLock with optimistic reads.
  • Simple/low contention → synchronized or ReentrantLock (simpler, fewer foot-guns).
  • Maps/caches → prefer ConcurrentHashMap / Caffeine over manual RWL.

Definition: Starvation (resource starvation) is when a thread or task is perpetually denied the resources it needs to make progress—CPU time, locks, I/O, or queue slots—while others keep getting them. It’s not stuck forever by a circular wait (that’s deadlock); it’s just consistently outcompeted.

Common causes
  • Unfair scheduling: higher-priority or frequently waking threads monopolize CPU.
  • Unfair locks: readers continuously acquire a lock, preventing writers (“writer starvation”).
  • Contention hot spots: a few hot keys/locks always busy.
  • Thread pool saturation: all workers blocked on I/O or waiting on other tasks → queued tasks never run.
  • Queue bias: always serving head-of-line or certain partitions first.
Starvation vs others
  • Deadlock: threads wait on each other in a cycle; no one can progress.
  • Livelock: threads keep changing state/rescheduling but do no useful work.
  • Starvation: some progress happens, but one thread/task rarely/never progresses.
Java examples

1) Writer starvation with non-fair ReadWriteLock

import java.util.concurrent.locks.*;

class RWStarveDemo {
  private final ReadWriteLock rw = new ReentrantReadWriteLock(); // non-fair (default)
  private final Lock r = rw.readLock(), w = rw.writeLock();
  private int value;

  int read() { r.lock(); try { return value; } finally { r.unlock(); } }
  void write(int x) { w.lock(); try { value = x; } finally { w.unlock(); } }
}
// If readers keep arriving, writer may wait a long time.

Fix: fair lock

ReadWriteLock rw = new ReentrantReadWriteLock(true); // fair = reduce writer starvation

2) Thread priority starvation

// High-priority busy loop may starve a low-priority thread on some OS/JVMs
Thread hi = new Thread(() -> { while(true){ /* compute */ } });
hi.setPriority(Thread.MAX_PRIORITY); hi.start();

Avoid priority games; rely on fair locking and backoff rather than MAX_PRIORITY loops.

3) Thread-pool starvation

// All workers block on an RPC and then submit follow-up work back to the same pool.
// The follow-up tasks cannot start (no free workers) → pipeline stalls.
var pool = java.util.concurrent.Executors.newFixedThreadPool(8);

pool.submit(() -> {
  // blocking call...
  var result = rpc.call();
  pool.submit(() -> process(result)); // may never run if all 8 are blocked similarly
});

Fixes

  • Use separate pools (I/O vs CPU), or a bounded queue + backpressure.
  • Prefer async/non-blocking I/O (CompletableFuture, reactive) to free threads.
Detection & symptoms
  • Very long wait times for a subset of requests/threads; p99/p999 spikes while average is fine.
  • Metrics: growing queue length, thread states WAITING/TIMED_WAITING for one group; others RUNNABLE.
  • Lock diagnostics: threads waiting long on the same monitor/lock; use jstack/jcmd Thread.print.
How to prevent/fix starvation
  • Fairness: prefer fair locks where starvation risk is real (new ReentrantLock(true), new ReentrantReadWriteLock(true)).
  • Bound & shed: bounded queues with rejection strategies; apply rate limiting so the system doesn’t overload.
  • Separate concerns: split thread pools (CPU vs I/O), separate per-dependency pools (bulkheads).
  • Backoff & jitter on retries so “noisy neighbors” don’t monopolize.
  • Prioritize fairness in queues: round-robin or weighted fair queues; avoid strict head-of-line bias.
  • Reduce lock hold time: keep critical sections short; avoid blocking I/O inside locks.
  • Use data structures: e.g., ConcurrentHashMap, LongAdder reduce contention vs coarse locks.
Quick checklist
  • ✅ Measure tail latencies and queue wait times; inspect lock contention.
  • ✅ Use fair locks where needed; keep write sections short; consider RW locks only when read-mostly.
  • ✅ Isolate with bulkheads and separate pools; avoid nested submissions to the same tiny pool.
  • ✅ Apply backpressure and retries with backoff; cap concurrency per endpoint/tenant.

Definition: Livelock is when threads/processes keep changing state in response to each other (so they’re “alive”), but no one makes progress. Unlike deadlock (everyone blocked), livelocked threads are often running hot, repeatedly retrying/backing off and undoing each other.

Livelock vs Deadlock vs Starvation
  • Deadlock: stuck waiting forever (e.g., circular lock wait); CPU mostly idle for those threads.
  • Livelock: threads actively run/retreat/retry but never complete; CPU usage can be high.
  • Starvation: some thread rarely gets service due to unfairness; others do make progress.
Classic causes
  • Mutual politeness: each thread yields/retries when it detects contention, and they keep colliding.
  • Global retry loops without jitter/backoff randomness.
  • Compensating actions that undo each other repeatedly (e.g., rollback-then-retry in lock-free code).
  • Symmetric protocols where both sides react the same way under contention.
Java example: two workers politely backing off forever
import java.util.concurrent.locks.*;

class LivelockDemo {
  private static final Lock A = new ReentrantLock();
  private static final Lock B = new ReentrantLock();

  static void polite(String name, Lock first, Lock second) {
    while (true) {
      boolean gotFirst = first.tryLock();
      if (!gotFirst) { Thread.yield(); continue; }
      try {
        if (second.tryLock()) { // got both: work done
          try {
            System.out.println(name + " doing work");
            break;
          } finally { second.unlock(); }
        } else {
          // politeness: release and let the other try -> both keep doing this = LIVELOCK
          first.unlock();
          try { Thread.sleep(1); } catch (InterruptedException ignored) {}
        }
      } finally { /* if we broke out after success, first is still held and will be unlocked by scope exit */ }
    }
  }

  public static void main(String[] args) {
    new Thread(() -> polite("T1", A, B)).start();
    new Thread(() -> polite("T2", B, A)).start();
  }
}

Both threads keep acquiring one lock, failing on the second, releasing, and retrying in sync—no progress.

How to prevent/fix livelock
  • Break symmetry: enforce a global lock order (A then B for everyone) so retries don’t mirror each other.
  • Randomized backoff: add jitter to retries so threads desynchronize.
  • Bounded retries + escalation: after N failed tries, take a stronger action (block on second lock, enqueue request, or hand off to a coordinator).
  • tryLock with timeout: don’t spin forever; give up and retry the whole operation after a randomized delay.
  • Use higher-level primitives: message queues, single-writer principle, STM-like patterns, or Concurrent collections that avoid manual lock dance.

Applying order & randomized backoff

void safeAcquire(Lock a, Lock b) throws InterruptedException {
  // Enforce order using identity hash to break symmetry
  Lock first = System.identityHashCode(a) < System.identityHashCode(b) ? a : b;
  Lock second = first == a ? b : a;

  java.util.Random rnd = new java.util.Random();
  int attempts = 0;
  while (true) {
    first.lock();
    try {
      if (second.tryLock(5, java.util.concurrent.TimeUnit.MILLISECONDS)) {
        try { /* do work */ return; }
        finally { second.unlock(); }
      }
    } finally { first.unlock(); }
    Thread.sleep(1 + rnd.nextInt(5 + attempts)); // jitter & backoff
    attempts++;
  }
}
Detecting livelock in production
  • Symptoms: high CPU, lots of retries/restarts, throughput ~0 for a specific operation despite active threads.
  • Thread dumps: threads alternate between RUNNABLE and short WAITING/TIMED_WAITING with repeating stack traces in retry loops.
  • Metrics: skyrocketing retry counters, frequent “released-without-progress”, toggling state flags.
  • Tracing/logs: same request spans repeatedly abandoned/restarted without completion.
Checklist
  • ✅ Avoid symmetric retry logic; introduce lock ordering or leader election.
  • ✅ Add exponential backoff + jitter to all contention/retry loops.
  • ✅ Cap retries; escalate to queue/coordination or fail fast with a clear error.
  • ✅ Keep critical sections minimal; avoid doing I/O while holding locks.
