📌 1. Basic Authentication

Sends username:password in every request header (Base64 encoded).


Authorization: Basic dXNlcjpwYXNz
🔐 Not secure unless over HTTPS. Simple to use but rarely used for production APIs.
✅ Use When:
  • Internal tools / admin dashboards
  • Quick testing with Postman / curl
❌ Avoid When:
  • Public APIs
  • Security-critical systems
📌 2. OAuth 1.0

Older standard that requires clients to sign requests using a secret + access token. Used by Twitter API (historically).


Header includes:
oauth_consumer_key, oauth_token, oauth_signature_method, ...
  • Requires cryptographic signing (HMAC-SHA1)
  • Complex implementation & difficult debugging
✅ Use When:
  • You need request integrity without HTTPS (rare)
  • You work with legacy APIs like Twitter v1.1
❌ Avoid When:
  • You're building a new modern app
📌 3. OAuth 2.0 (Modern Standard)

Widely adopted standard used by Google, Facebook, GitHub, AWS. It uses access tokens issued by an authorization server.

  • Supports multiple flows: Authorization Code, Client Credentials, Implicit, Device Code
  • Supports JWT access tokens
  • Separation of resource owner, client, and authorization server

Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6...
✅ Use When:
  • You want third-party login (Google/Facebook)
  • You're building SPAs or mobile apps
  • You want access control with scopes and expiry

MethodSecurityToken SupportRecommended
Basic Auth🔐 Weak❌ No🟡 Internal only
OAuth 1.0✅ Good (signed)✅ Yes🔴 Legacy only
OAuth 2.0✅ Strong (with HTTPS)✅ Yes (JWT/Bearer)🟢 Modern apps
📌 Bonus: JWT (JSON Web Tokens)

JWT = Header + Payload + Signature (all Base64)

  • User ID / roles / expiration
  • Is signed and optionally encrypted
  • Can be verified without DB call
📌 Conclusion
  • 🌐 Use OAuth 2.0 for web/mobile apps
  • 🔐 Use JWT for token-based auth
  • 🔧 Use Basic Auth only for simple internal APIs

📌 What is a Grant Type?

In OAuth 2.0, a Grant Type is a way for a client application to get an access token from the authorization server. Each grant type defines a different flow for authentication, depending on the type of app (web, mobile, backend, etc.).

📌 Common Grant Types
🔐 1. Authorization Code Grant (with PKCE)
  • 🌐 Used by web & mobile apps
  • Redirects user to login at auth server
  • Most secure for public clients

POST /oauth/token
grant_type=authorization_code
code=AUTH_CODE_FROM_REDIRECT
client_id=your_client
redirect_uri=callback_url
🤖 2. Client Credentials Grant
  • Used for machine-to-machine APIs
  • No user interaction

POST /oauth/token
grant_type=client_credentials
client_id=...
client_secret=...
🔁 3. Refresh Token Grant
  • Used to get new access token without re-login
  • Requires a valid refresh_token

POST /oauth/token
grant_type=refresh_token
refresh_token=...
client_id=...
📱 4. Password Grant (Deprecated / Unsafe)
  • Directly sends username & password to auth server
  • ⚠️ Not recommended for public clients

POST /oauth/token
grant_type=password
username=user
password=pass
client_id=...
📺 5. Device Code Grant
  • Used for smart TVs and devices with no browser
  • User logs in from a second device
📊 Summary Table
Grant Type Best For User Interaction Secure?
Authorization Code + PKCEWeb/Mobile Apps✅ Yes✅ High
Client CredentialsMachine-to-Machine❌ No✅ High
Refresh TokenToken Renewal❌ No✅ High
Password GrantLegacy Internal Apps✅ Yes⚠️ Low
Device CodeSmart Devices✅ Yes (other device)✅ Medium
📌 Conclusion

Each grant type is designed for a different use case. Most modern applications use Authorization Code with PKCE for frontend users and Client Credentials for backend services.

📌 Why OAuth with PKCE?

OAuth 2.0 with PKCE (Proof Key for Code Exchange) is the most secure and recommended flow for SPAs (React) and mobile apps (iOS/Android).

📌 How the Flow Works
  1. 🧠 Your app generates a code_verifier and code_challenge
  2. 🔗 User is redirected to the OAuth login (Google, GitHub, etc.)
  3. 🪪 After login, the auth server redirects back with an authorization_code
  4. 🔁 Your app sends the code + code_verifier to exchange for an access_token
🔐 React Integration Example (PKCE)

// Example with Google OAuth (using oidc-client-ts or similar libs)

import { createAuthProvider } from "react-token-auth";

export const { useAuth, authFetch, login, logout } = createAuthProvider({
  getAccessToken: () => localStorage.getItem("access_token"),
  onUpdateToken: (token) => localStorage.setItem("access_token", token),
});

For full PKCE support, use libraries like:

  • oidc-client-ts (React)
  • AppAuth (for React Native)
  • Or use Auth0, Firebase Auth, Azure AD for easy setup
📱 Mobile App Integration (React Native)

Use expo-auth-session or react-native-app-auth for secure login with PKCE:


import * as AuthSession from 'expo-auth-session';

const redirectUri = AuthSession.makeRedirectUri({ useProxy: true });

const authUrl = `https://accounts.google.com/o/oauth2/v2/auth?client_id=...&response_type=code&redirect_uri=${redirectUri}&scope=email`;

const result = await AuthSession.startAsync({ authUrl });
📦 Token Storage
  • React: store token in httpOnly cookies (recommended) or localStorage
  • Mobile: store securely in SecureStore or Keychain
🔐 Security Notes
  • Always use HTTPS
  • Use PKCE for public clients (SPA/mobile)
  • Don't store tokens in plain AsyncStorage or JS variables
✅ Conclusion

React and Mobile apps use OAuth 2.0 Authorization Code Flow with PKCE to securely authenticate users. Libraries handle most of the heavy lifting, and the server issues access and refresh tokens for API calls.

📦 1. Decomposition Patterns
  • Decompose by Business Capability – Split services based on business domains
  • Decompose by Subdomain – Inspired by DDD (Domain-Driven Design)
  • Self-Contained System – Each service with its own UI/backend/database

  • API Gateway – A single entry point for all services (e.g., Zuul, Spring Cloud Gateway)
  • Aggregator – Combines responses from multiple services
  • Proxy – Routes request to appropriate microservice
  • Client-Side Service Discovery – Client fetches service location (e.g., Eureka client)
  • Backend for Frontend (BFF) – Separate APIs for each client type (web/mobile)
🧵 3. Database Patterns
  • Database per Service – Each microservice owns its DB schema
  • Shared Database (Anti-pattern) – Multiple services on one DB (avoid)
  • Command Query Responsibility Segregation (CQRS) – Separate read/write models
  • Event Sourcing – Persist events instead of current state
📨 4. Communication Patterns
  • Synchronous REST – Simple, direct HTTP calls
  • Asynchronous Messaging – Use message brokers (Kafka, RabbitMQ)
  • Publish-Subscribe – One-to-many broadcasting (e.g., Kafka topics)
  • Choreography vs Orchestration – Event-driven flow vs centralized logic
🛠️ 5. Reliability Patterns
  • Circuit Breaker – Prevent system failure when service is down (e.g., Resilience4j)
  • Bulkhead – Isolate failures by partitioning resources
  • Retry – Automatically retry failed calls
  • Timeout – Avoid waiting indefinitely on failed services
  • Fail Fast – Quickly return error instead of hanging
🕵️‍♂️ 6. Observability Patterns
  • Log Aggregation – Centralized log storage and querying (e.g., ELK, Loki)
  • Distributed Tracing – Track requests across services (e.g., Zipkin, Jaeger)
  • Health Check – Endpoint to check service status
  • Metrics Collection – Collect CPU, memory, request time, etc.
🔒 7. Security Patterns
  • Access Token Propagation – Forward user's token across services
  • API Gateway with JWT – Validate token before routing
  • OAuth2 / OpenID Connect – Secure authentication and authorization
  • Service-to-Service Mutual TLS – Secure internal communication
📦 8. Deployment Patterns
  • Service Registry and Discovery – Auto-register and discover services (e.g., Eureka, Consul)
  • Sidecar Pattern – Attach helper container (e.g., logging, proxy)
  • Service Mesh – Dedicated infrastructure for communication (e.g., Istio, Linkerd)
  • Blue-Green / Canary Deployments – Safe rollout with rollback ability
📌 Conclusion

Microservices architecture relies on a combination of these design patterns to handle scalability, communication, data management, fault tolerance, and security. Choosing the right pattern depends on your app’s complexity, team size, and business needs.

📌 What is Domain-Driven Design?

Domain-Driven Design (DDD) is a software development approach that focuses on modeling the business domain accurately in the code, and structuring the project based on core domain logic rather than technical concerns.

It's especially powerful for complex applications with evolving business rules.

🔑 Key Concepts in DDD
  • Domain: The real-world problem area the application solves
  • Model: The abstract system of concepts that describes selected aspects of a domain
  • Ubiquitous Language: A common language shared by developers and domain experts
  • Bounded Context: A logical boundary within which a domain model is defined and applicable
  • Entities: Objects with identity that persist over time (e.g., User, Order)
  • Value Objects: Objects with no identity, defined by their values (e.g., Address, Money)
  • Aggregates: A cluster of domain objects treated as a single unit (with a root entity)
  • Repositories: Abstractions to access and persist aggregates
  • Services: Domain operations that don’t naturally fit into an entity/value object
  • Domain Events: Events that signal something important in the domain (e.g., OrderPlaced)

🎯 Benefits of DDD
  • ✅ Clear separation of concerns
  • ✅ Scalable and maintainable architecture
  • ✅ Close alignment with business language and rules
  • ✅ Enables better testing of domain logic
⚠️ When to Use DDD?
  • Complex business logic and evolving requirements
  • Large team with domain experts
  • Need for long-term scalability and clarity
❌ When NOT to Use?
  • Simple CRUD apps
  • Short-term or small-scale projects
  • When there's no clear domain complexity
📌 Conclusion

DDD is not just technical design – it’s a collaborative approach between developers and domain experts to build a model-rich, scalable, and business-aligned application. It shines in complex enterprise systems like banking, insurance, e-commerce, etc.

🌐 What is a Bounded Context?

A Bounded Context is a boundary around a specific business domain where a model applies consistently.

  • Each bounded context owns its data and logic
  • Multiple contexts may share the same term but have different meanings

Example:

  • User in “Billing” → means the customer
  • User in “Admin” → means the system operator

📌 1. Synchronous Communication

In synchronous communication, one service waits for a response from the other service before continuing.

  • 🔗 REST API (HTTP)
    • Most common method
    • Simple JSON over HTTP
    • Example: order-service → payment-service
  • 🧩 gRPC
    • High-performance RPC with Protobuf
    • Supports bi-directional streaming
    • Useful in language-agnostic environments
  • 📞 Feign Clients (Spring Cloud)
    • Declarative REST client
    • Tightly integrated with Eureka and Ribbon
📌 2. Asynchronous Communication

In asynchronous communication, the sender doesn't wait for a response and continues its work.

  • 📨 Message Broker (Kafka, RabbitMQ)
    • Event-driven communication
    • Scalable and decoupled
    • Example: OrderPlaced → triggers inventory, billing
  • 📧 Event Bus / Pub-Sub
    • One-to-many messaging
    • Used when multiple services need to react to a single event
    • Example: Firebase Cloud Messaging, AWS SNS
  • 🪝 Webhooks
    • Notify external systems when an event happens
    • Used in 3rd party integrations
📌 3. Hybrid Communication

Some systems use both types depending on the use case.

  • ✅ REST for real-time actions
  • ✅ Kafka for background event handling
  • ✅ gRPC for low-latency, structured internal service calls
⚠️ Tradeoffs
  • Synchronous: Easier to debug, but introduces tight coupling and latency
  • Asynchronous: More scalable and resilient, but adds complexity and eventual consistency
📌 Conclusion

Microservices can communicate in multiple ways depending on latency, reliability, consistency, and team independence needs. A well-designed system usually combines both synchronous REST/gRPC and asynchronous Kafka/event-based communication.

📌 Kafka vs RabbitMQ – High-Level Comparison
Feature Kafka RabbitMQ
Message Model Log-based (publish-subscribe) Queue-based (push to consumers)
Ordering Guaranteed within partitions No global ordering guarantee
Replay Support ✅ Yes (via offset) ❌ No (unless manually handled)
Performance Very high throughput (good for big data) Lower throughput (but lower latency)
Storage Persistent log (retention based) Transient queues (messages expire or removed)
Ideal For Event streaming, analytics, logs Task queues, short-term messaging
🔁 Retry Strategies in Microservices
  • Immediate Retry: Retry N times instantly (not ideal for transient errors)
  • Exponential Backoff: Retry with increasing delays (1s, 2s, 4s…)
  • Jitter: Add randomness to retry timing to avoid thundering herd
  • Resilience4j: Use in Spring Boot for built-in retry + backoff

@Retry(name = "inventoryService", maxAttempts = 3)
public String callInventory() {
    return restTemplate.getForObject("http://inventory/api", String.class);
}
💀 Dead Letter Queue (DLQ)

If a message repeatedly fails, it can be moved to a DLQ for inspection or manual retry.

  • RabbitMQ: Built-in DLX (Dead Letter Exchange)
  • Kafka: You implement your own DLQ topic (e.g., order-dlq)

Spring Boot Kafka example:


@KafkaListener(topics = "orders", errorHandler = "dlqHandler")
public void listen(String message) {
    // Process message
}
🛡️ Idempotency in Event Processing

Idempotency ensures that even if a message is processed multiple times, the result remains the same.

  • 💡 Use unique IDs for every event/message
  • 🗃️ Store processed IDs in a cache or database
  • ✅ Before processing, check if event ID already handled

if (eventAlreadyProcessed(orderId)) return;
processOrder(orderId);
markAsProcessed(orderId);
📌 When to Choose What?
  • Kafka: You need high throughput, replays, distributed event log
  • RabbitMQ: You need low-latency, routing flexibility, classic queuing
  • ✅ Use both! RabbitMQ for command-style tasks, Kafka for domain events
✅ Best Practice
  • Use asynchronous retry to avoid blocking consumers
  • Always implement DLQ for failed messages
  • Ensure idempotency for safe retries
📌 Conclusion

Choosing between Kafka and RabbitMQ depends on your architecture’s needs. Regardless of what you choose, ensure fault tolerance by handling retries, dead letters, and duplicate messages with care.

📦 Problem: Dual Writes in Microservices

Imagine you save something to a database and also publish an event to Kafka:


saveToDatabase(order);
kafkaTemplate.send("order-topic", event);

Risk: If Kafka send fails, DB is already committed → data inconsistency. This is called the dual-write problem.

📌 What is Kafka Outbox Pattern?

The Outbox Pattern avoids this by saving events in the same database transaction, then publishing them to Kafka later in a safe, retryable way.

✅ Steps:
  1. 1️⃣ Save entity + domain event into DB (e.g., `orders` + `outbox` table)
  2. 2️⃣ Background process reads from `outbox` table and sends to Kafka
  3. 3️⃣ Mark event as processed or delete from `outbox`

-- order table
INSERT INTO orders (id, status) VALUES (101, 'PLACED');

-- outbox table
INSERT INTO outbox (id, topic, payload, published) VALUES (501, 'order-topic', '{orderId: 101}', false);
🛠️ Sample Spring Boot Structure
  • OrderService: saves order + outbox entry in one DB transaction
  • OutboxPublisher: scheduled job or Debezium connector
💡 Benefits
  • ✅ Guarantees consistency (DB + Kafka sync)
  • ✅ Works well with eventual consistency systems
  • ✅ No need for 2PC (which is heavy and complex)
🔄 What is Two-Phase Commit (2PC)?

2PC is a distributed transaction protocol used to ensure atomicity across multiple systems (e.g., DB + Kafka).

✅ Phases:
  1. 1️⃣ Prepare: All participants say “yes, I’m ready”
  2. 2️⃣ Commit: Coordinator tells all to commit
⚠️ Drawbacks of 2PC:
  • ❌ Blocks resources for a long time
  • ❌ Doesn’t scale well (tight coupling)
  • ❌ Not supported natively between Kafka and most databases

That’s why Kafka Outbox Pattern is a better modern alternative to 2PC.

📌 Conclusion

Use the Outbox Pattern when your service must both persist data and reliably send a Kafka event. It avoids the complexity and downsides of 2PC by achieving eventual consistency in a safe and robust way.

📌 Problem

When sending messages to Kafka via `KafkaTemplate`, failures like network issues, broker downtime, or serialization errors can occur. These need to be handled gracefully to avoid data loss.

🔁 Retry Logic for KafkaProducer

There are 3 types of retries to consider:

  • ✅ KafkaTemplate retry (synchronous, manual)
  • ✅ Spring Retry (declarative retries)
  • ✅ Outbox + Scheduled Retry (eventually consistent)
Option 1️⃣: Retry Manually on Failure

kafkaTemplate.send("orders", message)
    .addCallback(
        result -> System.out.println("Sent successfully"),
        ex -> {
            log.error("Send failed: retrying...");
            retrySend("orders", message); // custom retry logic
        });
Option 2️⃣: Retry Using Spring Retry

@Retryable(
    value = { KafkaException.class },
    maxAttempts = 3,
    backoff = @Backoff(delay = 2000))
public void sendMessage(String topic, String message) {
    kafkaTemplate.send(topic, message);
}

Use `@EnableRetry` in your configuration class.

Option 3️⃣: Outbox + Scheduled Retry

Messages are saved to DB. A scheduler reads failed/pending events and retries sending.


@Scheduled(fixedDelay = 5000)
public void retryOutboxEvents() {
    List<OutboxEvent> failedEvents = outboxRepo.findUnsentEvents();
    failedEvents.forEach(event -> {
        try {
            kafkaTemplate.send(event.getTopic(), event.getPayload());
            event.markAsSent();
        } catch (Exception e) {
            log.warn("Retry failed, will try again later");
        }
    });
}
🧪 Testing Kafka Failure Scenarios
  • ✅ Use `@EmbeddedKafka` in integration tests
  • ✅ Mock KafkaTemplate to simulate failures
  • ✅ Assert retry attempts and logging

@Mock
KafkaTemplate<String, String> kafkaTemplate;

@Test
void testKafkaSendRetryOnFailure() {
    doThrow(new KafkaException("fail"))
        .doThrow(new KafkaException("fail again"))
        .doNothing()
        .when(kafkaTemplate).send(anyString(), anyString());

    yourService.sendMessage("topic", "msg");

    verify(kafkaTemplate, times(3)).send("topic", "msg");
}
🧯 Fallback on Persistent Failure

If retries exceed the limit, fallback to DLQ or mark the message for manual recovery:

  • ❌ Do NOT lose the event silently
  • ✅ Mark as `FAILED` in DB for alerting or reprocessing
📌 Conclusion

Reliable Kafka publishing requires a combination of:

  • ✅ Retry on transient failures
  • ✅ Persistent storage (Outbox) to avoid data loss
  • ✅ Scheduled retry and fallback alerts for failures

Test all edge cases using mocks and embedded brokers to ensure your system gracefully handles message delivery issues.
